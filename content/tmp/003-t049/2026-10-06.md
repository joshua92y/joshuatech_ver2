# 003-platform-foundation T049 — E2E는 과제 사이에 쌓인 가정을 검사한다: US2 수용 시험 1일차 (2026-10-06)
> 1일차(테스터 실행 → 판정표 → 실패 · 편차 분류 → 문서 정정 하나). 사용자 결정 셋이 남아 과제는 열려 있다.

## 문제
US2("GitOps로 관리되는 안전한 클러스터")의 수용 시나리오 다섯(AC1–AC5)을 사용자 관점에서 끝까지 확인한다. 클러스터 · 인그레스 · 재부팅 하네스, 매니페스트 저장소의 검사 워크플로, 두 클라우드 스택의 plan 차이 0, 두 저장소의 시크릿 0, 브라우저 로그인을 함께 본다. 테스터 에이전트는 조회 전용 권한만 썼다. 운영자 자격이 필요한 plan과 브라우저 확인은 운영자가 직접 했다.

## 배운 개념
- **E2E는 과제 사이에 쌓인 가정을 검사하는 자리다.** 클러스터 하네스의 한 단언(argo-4)에 대해 문서에는 다섯 과제 동안 "다음 데이터 과제(T056) 전에는 통과할 수 없다"고 적혀 있었다. 테스터가 하네스 코드를 읽어 보니, 그 단언이 보는 것은 데이터베이스 · 메시지 큐 · 캐시의 운영자 CRD와 볼륨이었다. 그 입력을 만드는 과제는 T052 · T053 · T055 · T057이었다. 문서의 "막는 과제"를 코드로 확인하지 않고 옮겨 적어 온 것이 원인이다.
- **"required 체크가 있다"는 셋이 모두 있어야 성립한다.** 기본 브랜치의 보호 규칙, 기본 브랜치에 있는 워크플로 파일, 그리고 실제로 돈 실행이다. 매니페스트 저장소는 검사 워크플로 안의 시크릿 스캔이 사실상 required로 동작한다. 앱 저장소는 셋 다 없었다. 시크릿 스캔 워크플로는 기능 브랜치에만 있고, 보호 규칙이 없고, Actions가 한 번도 돈 적이 없다. 같은 수용 기준이 두 저장소에서 다른 상태였고, 앱 저장소 쪽을 소유한 과제가 없었다.
- **쓰기 전용 비밀의 plan 차이는 "공급자 쪽이 바뀌었다"는 뜻이 아니다.** 클라우드 공급자는 OAuth 클라이언트 비밀을 돌려주지 않는다. 그래서 plan은 운영자가 이번 셸에 입력한 값과 상태 파일에 저장된 값을 비교한다. 차이가 났다면 오늘 입력한 값이 상태 값과 다를 가능성이 먼저다. 값을 화면에 내지 않고 비교하려고 읽기 블록을 하나 만들었다. 이 블록은 두 값의 길이, 입력값 앞뒤 공백 여부, SHA-256 일치 여부만 출력한다. 원인이 풀리기 전에는 apply하지 않는다. 틀린 값을 쓰면 GitHub 로그인이 전부 깨진다.
- **PowerShell에서 날짜를 문자열로 바꾸면 오프셋이 사라진다.** ConvertFrom-Json이 만든 UTC DateTime을 문자열로 바꾸면 시간대 표시가 빠진다. 그 문자열을 RoundtripKind로 다시 읽으면 로컬 시각(+09:00)으로 해석된다. 그래서 인증서 만료 단언이 9시간 보수적으로 계산되고 있었다. 거짓 통과는 없지만 잘못된 계산이다.
- **수용 기준의 문면과 실측은 따로 적는다.** SC-001("root 적용 → 전부 Healthy ≤ 30분")은 한 번에 잰 적이 없다. root는 빈 디렉터리로 먼저 만들었고, 플랫폼 구성요소는 2주에 걸쳐 PR 단위로 들어왔기 때문이다. 대체 근거(측정 재부팅에서 전부 Healthy 78초 · 전부 재조정 6분 9초)를 쓰되, 문면 구간은 재구축 리허설에서 잰다고 남겼다.

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| 클라우드 plan 차이(쓰기 전용 비밀) | 해시로 비교한다. 같으면 plan을 다시 돌리고, 다르면 어느 값이 맞는지 사용자가 정한다 | 곧바로 apply — 오늘 입력값이 틀렸다면 로그인 공급자를 깨뜨린다 · 무시 — plan 차이 0이 수용 기준이다 |
| argo-4 | 결정 대기. 권장안은 US3 자원이 생길 때까지 SKIP하는 게이트와 하네스 결함 수정(예외 · 9시간 · 낡은 SKIP 문구) | 편차로만 기록 — 하네스가 계속 FAIL로 남아 다음 과제의 진짜 회귀를 가린다 |
| 앱 저장소 required 체크 | 결정 대기. 권장안은 편차로 기록하고 저장소 정비 과제(T116)에 배정 | 이 과제에서 바로 규칙 추가 — 저장소 설정은 운영자 몫이고, 소유 과제를 먼저 정해야 한다 |
| argo-4의 막는 과제 표기 | 하네스 코드로 확인한 뒤 런북 다섯 곳을 "US3 데이터 자원(T052 · T053 · T055 · T057)"으로 정정 | 설계 문서도 고침 — 닫힌 과제의 설계 문서는 고치지 않는 규칙이라, 정정 기록은 런북과 이 과제에 남긴다 |

## 결과와 검증
- **AC1 노드 · 네트워크 경계**: PASS. 노드 하네스 통과, 두 노드 Ready, 보안 리스트 ingress 0, 노드 NSG는 443을 Cloudflare 대역에서만 받는다, 운영자 plan 차이 0.
- **AC2 GitOps 구조**: PASS(편차). Application 22개 Synced/Healthy, default 프로젝트 비어 있음, sync-wave가 계약 표와 같다. 21개 중 9개는 아직 리소스가 없는 자리표시다.
- **AC3 접근 경계**: PASS(편차). 인그레스 하네스 12/0. 브라우저로 Access를 거쳐 Argo CD에 로그인했다. OIDC 로그인은 US4로 이월했다.
- **AC4 재부팅 복구**: PASS(T048 측정 재부팅 기록 인용).
- **AC5 시크릿**: 두 저장소 전체 이력의 시크릿 스캔은 누출 0이다. 앱 저장소에는 required 체크가 없어 FAIL이다.
- **하네스 합계**: 인프라 61/0 · 클러스터 37 통과 · 1 실패(argo-4) · 12 SKIP · 인그레스 12/0 · 재부팅 3 통과 · 4 SKIP. 매니페스트 검사 워크플로 PASS 38 · FAIL 0.
- **plan**: OCI 차이 0. Cloudflare는 쓰기 전용 비밀 하나가 in-place로 나와 원인을 확인하는 중이다.
