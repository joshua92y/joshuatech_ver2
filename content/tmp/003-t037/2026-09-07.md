# 003-platform-foundation T037 — 업그레이드 창과 백업 게이트: 선언이 지켜지지 않는 조건 찾기 (2026-09-07)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제
2노드 K3s 클러스터의 패치 업그레이드를 사람이 하면 잊거나 백업 없이 돌린다. 요구는 세 가지였다 — (a) 주 1회 정해진 창에서만, (b) 백업이 성공했을 때만, (c) control-plane 노드를 먼저, agent 노드는 그 뒤에. system-upgrade-controller(SUC)는 `Plan` CRD 하나로 이 셋을 선언하게 해 주는 도구지만, "선언한 대로 되는가"를 문서만 믿을 수는 없었다. 게다가 이 task는 코드만 쓰고 클러스터에 적용하지 않는다(적용은 GitOps 부트스트랩 task의 첫 sync). 라이브 검증이 없는 상태에서 상류 소스만으로 보장을 따져야 하는 조건이었고, 그게 이 task의 실제 난점이었다.

## 배운 개념
- **init 컨테이너 순서가 곧 게이트다.** SUC가 Plan을 Job으로 번역할 때 `prepare`는 initContainers의 첫 항목, `cordon`은 두 번째, `upgrade`는 main 컨테이너다(v0.20.1 `pkg/upgrade/job/job.go` 327–346·420–441·467–476행). 쿠버네티스는 init 컨테이너를 순서대로 실행하고 하나라도 실패하면 다음으로 넘어가지 않는다. 그래서 "백업이 성공한 뒤에만 업그레이드"는 내가 쓴 조건문이 아니라 **파드 라이프사이클이 공짜로 주는 성질**이다. 게이트를 놓을 자리는 플랫폼이 이미 순서를 보장하는 지점이라는 것 — 이게 이 task의 가장 재사용 가능한 교훈이다.
- **채널(channel)과 digest 핀은 구조적으로 양립하지 않는다.** 채널 URL이 302로 최신 패치를 알려주고 SUC가 버전 문자열의 `+`를 `-`로 바꿔 이미지 태그로 붙인다. 이 태그 부착은 이미지 참조가 **이름뿐일 때만** 일어나므로, digest를 박으면 채널이 조용히 무력화된다. "플랫폼의 모든 이미지는 digest를 병기한다"는 일반 규칙과 정면으로 충돌하고, 둘 중 하나를 포기해야 한다.
- **창(window)은 작업 시간이 아니라 Job 생성 허가다.** 창 안에서 시작한 Job은 창이 끝나도 계속 간다. "창 = 2시간 안에 끝난다"가 아니다.
- **Plan의 재실행 단위는 spec 전체가 아니다.** 노드에 `plan.upgrade.cattle.io/<plan>=<해시>` 라벨이 있으면 대상에서 빠지고, 그 해시는 해석된 버전 + ServiceAccount + digest 어노테이션이 가리키는 경로 + secrets만으로 계산된다(`pkg/upgrade/plan.go` DigestStatus 51–77행). 그래서 spec의 다른 필드를 고쳐도 다시 돌지 않는다 — "선언을 바꾸면 반영된다"는 직관이 깨지는 자리다. 의도적 재실행용으로 해시에 포함되는 어노테이션 한 칸(`retrigger`)을 따로 뒀다.

## 선택과 대안
- **cordon만 쓰고 drain은 쓰지 않는다.** 노드가 2대뿐이고 단일 replica 상태 저장 워크로드가 로컬 경로 PV로 노드에 묶여 있어 drain해도 갈 곳이 없고 Pending만 남는다. 더 근본적으로, k3s 업그레이드는 k3s 프로세스만 재시작하고 컨테이너는 containerd가 유지하므로 파드를 내보내서 얻는 이득 자체가 없다(research.md K3S-D10). "노드 업그레이드면 drain"은 멀티 노드·복제 워크로드 전제에서만 맞는 격언이었다. 나중에 다른 문서 몇 곳이 "노드 B drain 중"이라고 적었던 것이 검수에서 잡혔는데, Plan에는 `drain:` 키가 아예 없었다.
- **마이너 채널 고정 vs stable 채널 vs 버전 고정.** stable은 마이너를 자동으로 올려 kubectl/컴포넌트 skew 위반과 번들 차트의 파괴 변경에 노출된다. 버전 고정은 더 GitOps답고 digest 핀까지 되지만 의존성 봇에 K3s 채널용 datasource를 따로 붙여야 한다. 결론은 마이너 채널 고정 = 패치만 자동, 마이너 승격은 채널을 바꾸는 PR로 사람이 판단.
- **릴리스 매니페스트를 원격 참조하지 않고 저장소에 복사한다.** CRD와 컨트롤러 매니페스트는 git 트리에 없는 빌드 산출물이라 커밋 SHA로 핀할 수 없고, 릴리스 다운로드 URL은 태그 기반이라 내용이 바뀔 수 있다. 사본이어야 리뷰어가 커밋에서 내용을 보고 의존성 봇이 이미지 줄을 갱신한다. 대가로 sha256과 원본 대비 diff 절차를 파일 머리 주석에 고정했다.
- **실패 복구는 노드 라벨로(채택) vs Plan 제거·재추가 PR로(기각).** 후자는 status를 초기화해 창을 지키지만 PR 두 번과 수동 confirm이 필요하고 그동안 cordon이 남는다. 라벨은 한 명령이고 노드 라벨은 GitOps 관리 밖이라 즉시 듣는다.
- **Job 상한을 기본 900초가 아니라 1800/3600초로.** 게이트가 백업을 포함하므로 상한이 백업 타임아웃(30분)보다 짧으면 게이트가 자기 이유 없이 실패한다. agent Plan은 server Job 전체를 기다리므로 그 상한을 더한 값이 필요하다.
- **prepare에 privileged를 명시.** SUC는 prepare 컨테이너에 securityContext를 주지 않으므로 Plan이 직접 써야 한다. chroot만으로 충분할 가능성이 있지만 라이브 검증 전이라 upgrade 컨테이너와 같은 수준으로 두고, "첫 창에서 성공하면 뺀다"를 최소 권한 축소 항목으로 남겼다.

## 결과와 검증
라이브 실행은 없었다. 검증은 전부 정적이다 — `kustomize build` exit 0(12문서), `kubeconform` 통과, 저장소 검사 스크립트 신규 FAIL 0, WARN 4는 Plan 이미지 4줄(Plan 2개 × prepare·upgrade)의 의도된 예외이며 그 근거가 파일 주석이다. 26 에이전트 다차원 리뷰에서 17건 중 7건 확정(major 2)·10건 반박, critic Approved. 첫 창은 사실상 리허설로 예상됐다: 클러스터 버전이 채널 최신과 같아 upgrade 컨테이너가 "Binary already been replaced"로 exit 0이 되지만, 백업·cordon·uncordon은 실제로 돌기 때문에 게이트가 동작한다는 첫 증거가 된다. 그 증거의 관측 지점은 백업 성공 지표의 타임스탬프가 창 시각으로 갱신됐는지다.

## 다음 학습
- 첫 창 뒤 실측할 항목: 실패 뒤 변경이 정말 창 밖에서 즉시 도는지, prepare에서 privileged를 빼도 chroot만으로 성공하는지, 비상 정지 순서, 재트리거 어노테이션 동작, 의존성 봇 예외 규칙 dry-run.
- 업그레이드가 번들 ingress 차트 버전을 바꾸면 우리 values 키가 **조용히 무시될** 수 있다. 창 뒤 확인 절차가 배포 인자 4종의 존재를 직접 grep하는 이유다. 자동화하지 못한 부분의 비용은 이런 사후 확인 목록으로 남는다.
- 게이트의 백업이 실제로 복원 가능한지는 이 task도, 이 feature도 증명하지 않는다. 백업 성공 지표는 "업로드 성공"이지 "복원 가능"이 아니다 — 복원 리허설은 별도 task로 남겼다.

## 사고·오류
- **가장 큰 정정: "실패하면 다음 창에 다시 돈다"가 틀렸다.** 처음 문서는 그렇게 적었는데 소스를 읽은 리뷰가 뒤집었다. 실패 처리 경로(`handle_batch.go` 86–101행)는 `status.applying`을 비우지 않고, 창 검사는 `len(applying)==0`일 때만 수행된다(`handle_upgrade.go` 158–167행). 즉 **실패한 Plan은 창을 아예 보지 않는다.** 그 뒤 Plan의 resourceVersion이 바뀌는 어떤 사건이든(재트리거 PR 머지, 채널의 새 패치 해석, 아무 metadata 변경, 컨트롤러 파드 재시작) 창 밖에서 즉시 백업 → cordon → k3s 재시작이 실행된다. 알림 mute 창 밖이므로 아무도 보지 않는 시간에 API 서버가 끊길 수 있다. 일반화하면: **선언적 안전 제약에도 전제 조건이 붙어 있고, 그 조건은 정상 경로에서만 성립할 수 있다.** 실패 상태에서 안전 장치가 남아 있는지 따로 확인해야 한다.
- 그래서 대응 순서가 바뀌었다. 실패를 보면 **먼저** 노드에 `plan.upgrade.cattle.io/<plan>=disabled`를 붙여 선택 노드를 0으로 만든다(applying이 비면서 Plan이 Complete로 돌아가 창 게이트가 복원된다). 원인 수정은 그 다음이고, 창 직전에 라벨을 뗀다.
- **비상 정지 순서도 처음엔 반대였다.** disabled 라벨을 붙이면 SUC가 applying에 없는 노드의 진행 중 Job을 스스로 지운다(`handle_batch.go` 145–149행). 바이너리 복사 중에 끊기면 k3s 바이너리가 깨질 수 있으므로 **라벨보다 upgrade 컨테이너 로그 확인이 먼저**다. "정지 명령"이 곧 "안전한 정지"는 아니다.
- **확인 명령 자체가 틀렸다.** `kubectl get plans -o wide`의 VERSION 열은 `.spec.version`을 읽으므로 채널 Plan에서는 **항상 비어 있다.** 해석된 버전은 `.status.latestVersion`에만 있고 표기도 `-k3s1`(노드 쪽은 `+k3s1`)이라 같은 버전인데 불일치로 오독할 수 있다. 프린터 열이 무엇을 읽는지 확인하지 않으면 "값이 비었으니 고장"이라는 오진을 한다.
- **롤백은 없다.** 업그레이드 이미지는 다운그레이드를 거부하므로 Plan 버전을 낮춰도 되돌아가지 않는다. 유일한 복원점이 prepare가 만든 백업이다 — 게이트는 편의 기능이 아니라 되돌릴 수 없는 작업의 전제였다.
- **계약 문구와의 충돌을 코드가 아니라 문서 쪽에서 해소했다.** "이미지 digest 핀" 보완 통제는 채널 Plan과 양립하지 않아 converge 정정 항목으로 넘기고, 의존성 봇이 태그 없는 Plan 이미지에 digest 핀 PR을 내지 못하도록 예외 규칙을 추가했다. 그 PR이 머지되면 채널이 조용히 죽는 종류의 회귀다.
- **수용한 위험 하나**: 창 안에서 채널이 새 패치를 해석하면 진행 중 Job도 삭제된다(`handle_batch.go` 62–66행). 2시간 창에 릴리스가 겹칠 확률이 낮아 수용하고, 피해야 하면 버전 고정으로 회피한다고 적었다.
