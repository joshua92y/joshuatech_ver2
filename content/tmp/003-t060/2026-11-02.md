# 003-platform-foundation T060 — 구현이 없는 상태에서 "빨간" 테스트를 어떻게 믿을 것인가: 테넌트 격리 테스트와 TLS 전용 Postgres 시험 환경 (2026-11-02)
> 1일차이자 마감(설계 · 빌드 · 리뷰 1라운드 · 수정 · 커밋). 짝 구현(T068)은 다음 과제들에서 이 테스트를 초록으로 만든다.

## 문제
공통 라이브러리의 테넌트 격리 모듈(테넌트 범위 모델 · 전역 모델 · 요청 컨텍스트 미들웨어 · RLS 마이그레이션 헬퍼 · 검사 명령)은 아직 한 줄도 없다. 헌법은 "실패하는 테스트를 먼저 쓰고 실패를 관찰하라"고 하지만, 모듈 자체가 없으면 테스트는 import 단계에서 통째로 죽는다. 그 빨강이 "구현이 없어서"인지 "시험 환경이 틀려서"인지 구분할 방법이 필요했고, 시험 환경 자체(비-superuser 앱 역할 · 우회 권한을 가진 소유자 역할 · TLS 이상의 접속)는 운영 환경을 그대로 흉내 내야 했다.

## 배운 개념
- **빨강을 둘로 나눈다.** 시험 인프라(컨테이너 · TLS · 역할)는 Django 플러그인을 끄고(`-p no:django`) 따로 초록을 확인하고, 계약 테스트는 Django 설정 단계에서 `ModuleNotFoundError`로 멈추는 것을 빨강으로 정의했다. 둘을 섞으면 "환경이 깨져서 빨간" 것을 "구현이 없어서 빨간" 것으로 착각한다.
- **공식 Postgres 이미지의 데이터 디렉터리는 VOLUME이다.** 빌드 중 그 경로에 쓴 파일(인증서)은 classic 빌더가 버린다. testcontainers의 이미지 빌드는 BuildKit이 아닌 classic 경로라 지시문의 경로를 그대로 쓰면 서버가 인증서를 못 찾아 뜨지 않는다. 빌더가 프로브 이미지로 실측해 경로를 바꿨다 — "문서에 그렇게 돼 있다"가 아니라 "돌려 봤다"가 결정의 근거였다.
- **TLS를 요구하는 것과 강제하는 것은 다르다.** 클라이언트가 `sslmode=require`를 쓰는 것만으로는 서버가 평문을 받는지 모른다. 서버의 접속 규칙을 `hostssl` 허용 + `hostnossl` 거부로 바꾸고, 평문 접속이 거부되는 테스트를 두어 "TLS 이상"을 증명한다. 공식 이미지의 초기화 순서(규칙 추가 → 초기화 스크립트 → 본 서버)를 알아야 그 교체가 본 서버에 적용된다.
- **행 수준 보안의 두 플래그는 독립이다.** ENABLE과 FORCE는 서로 다른 카탈로그 비트이고, ENABLE이 꺼지면 정책이 통째로 무시된다. 처음 테스트는 FORCE가 빠진 경우만 다뤄서, 검사 명령이 FORCE 비트만 읽어도 통과했을 것이다. 리뷰가 그 구멍을 잡아 "RLS DISABLE → 검사 실패" 음성 테스트를 추가했다.
- **"RLS 없는 테이블은 전부 허용 목록에"라는 규칙은 프레임워크 테이블에서 깨진다.** 마이그레이션 기록 테이블은 반드시 생기고 RLS가 없다. 면제 없이는 모든 pod가 검사에 실패하므로 면제는 선택이 아니라 필수였고, 어떤 테이블을 면제하는지는 데이터 안전 결정이다. 접두 규칙(`django_*`) 대신 **정확한 이름 10개**를 상수로 고정하고 pod가 넓힐 수 없게 했다. 계약과 규칙을 먼저 고치고 테스트가 그것을 가리키게 했다.
- **요청 컨텍스트는 트랜잭션 지역(local)이어야 한다.** `set_config(…, true)`는 트랜잭션이 끝나면 사라지지만, 같은 세션에서 한 번 설정된 뒤의 값은 NULL이 아니라 빈 문자열이다. 정책이 빈 문자열을 UUID로 캐스트하면 오류가 난다 — 테스트는 "다음 요청에서 0행"을 단언해 그 함정도 함께 잡는다. 누출 검사는 같은 DB 세션(backend pid)에서 해야 뜻이 있다.
- **테스트 프레임워크의 뒷정리도 권한 모델을 따른다.** 트랜잭션 테스트 케이스는 끝날 때 테이블을 비우는데(TRUNCATE), 앱 역할에는 그 권한이 없다. 앱 역할에 권한을 더 주는 대신, 두 DB 별칭이 같은 물리 DB임을 `TEST.MIRROR`로 알려 비우기를 소유자 별칭에서만 하게 했다. 소스로는 확인했지만 실행은 구현이 생긴 뒤에야 가능해서 "검증 후 결정" 항목으로 남겼다.
- **경고 정책은 자기 모듈로 한정한다.** 폐기 경고를 오류로 올리되 의존 라이브러리의 경고로 스위트가 죽지 않게 모듈 범위를 좁힌다. 실제로 테스트 컨테이너 라이브러리의 옛 import 경로가 폐기 경고를 내며 우리 모듈로 귀속됐다 — 새 경로로 바꿨다. 규칙 문서의 "전역 플래그" 문구는 구현 형식으로 고쳤다.
- **임시 컨테이너는 볼륨까지 지워야 끝난다.** 하네스는 익명 볼륨까지 지우지만, 손으로 돌린 프로브 컨테이너는 볼륨을 남겼다. 리뷰가 데몬을 읽어 찾아냈고, 위생 검사 목록에 dangling 볼륨 확인을 더했다.

## 선택과 대안
- **시험 이미지는 Dockerfile로 빌드한다**(볼륨 마운트 대신). Windows 경로 매핑 함정을 피하고, 인증서가 이미지에 들어가지만 1회용 자가 서명이라 비밀이 아니다. 접속은 `require`로 두고 `verify-full`은 CA 반출이 필요해 미채택(계약의 "이상" 조건 충족).
- **역할 둘, 별칭 둘.** Django 기본 연결은 앱 역할(우회 불가), 두 번째 별칭은 소유자 역할(마이그레이션 · 시드 · 토글 전용). 테스트의 기대값은 "소유자가 전부 본다" 한 곳에서만 소유자 결과를 통과로 삼는다.
- **검사 명령은 카탈로그를 스캔해야 한다.** 모델에 없는 테이블(`rogue`)을 만들어 실패를 요구한다 — 모델 기반 검사만으로는 잡히지 않는다.
- **PK 타입 같은 미정 항목은 "가정"으로 표시하고 인계한다.** 추상 모델의 필드를 모르는 채 손으로 쓴 마이그레이션은 구현 과제가 실제 필드에 맞춘다(`makemigrations --check` 변경 없음이 기준).
- **이미지 정리 정책은 유지한다**(세션마다 재풀). 병렬 CI가 데몬을 공유하게 되면 그때 고정 태그 재사용이나 세션 접미 태그로 바꾼다.

## 사고·오류
- 지시문의 인증서 경로가 틀렸다(VOLUME 경로) — 빌더가 실측으로 바로잡았다. 설계 때 이미지의 VOLUME 선언을 확인하지 않았다.
- 설계가 테스트 프레임워크의 뒷정리(TRUNCATE) 권한을 놓쳤다 — 빌더가 소스를 읽어 `TEST.MIRROR`로 메웠다.
- 빌더의 수동 프로브가 익명 볼륨을 남겼다 — 리뷰가 찾아 삭제했고, 프로브는 `--rm`으로만 돌린다는 규칙을 더했다.
