# 003-platform-foundation T076 — 라이브: 음성 대조로 시작해 자격을 쥔 탐침까지, 그리고 사흘 묵은 터널 (2026-11-23)
> 라이브 날의 기록이다. 11-20 · 21에 설계 · 빌드한 블록을 실물에서 처음 돌렸고, 과제를 닫았다(tick).

## 문제
- 설계 · 빌드를 마친 블록 여섯을 실물에서 돌려야 했다. 순서는 다음과 같다.
  - Vault 정책 적용과 자격 시드(운영자)
  - E2E 두 번(tester — 1차는 자격 없이, 2차는 1시간짜리 로그인 자료로)
  - 정리
- 11-20 기록이 「실물만 답한다」고 남긴 질문이 셋 있었다.
  - 터널 경유 port-forward가 제때 서는가.
  - K3s TokenRequest가 audience 하나를 문자열로 내는가, 배열로 내는가.
  - Vault의 거부 응답은 실제로 어떤 꼴인가.

## 배운 개념
- **음성 대조는 응답 코드가 아니라 거부 사유까지 본다.**
  - 블록의 PASS 조건은 「4xx이고 인증 객체가 없다」였다. 그래서 컨트롤러가 오류 첫 줄을 따로 봤다.
  - 실제 응답은 403과 audience 불일치 문구였다.
  - role이 없다거나 형식이 틀렸다는 다른 4xx였다면, audience 분리를 증명한 것이 아니다. 판정을 멈췄어야 한다.
- **K3s TokenRequest의 audience 직렬화**
  - audience를 주지 않으면 기본값 두 개의 배열이 나왔다.
  - 하나만 주면 원소 하나짜리 **배열**이었다. 문자열이 아니었다.
  - 블록을 두 꼴 모두 받게 만들어 둔 것이 맞았다. 「문서상 둘 다 가능」인 것을 한쪽으로 가정하지 않은 덕이다.
- **정책 적용의 실물 판정은 두 겹이다.**
  - 사람(컨트롤러)이 plan diff를 줄 단위로 대조했다. 기존 줄은 그대로이고 더한 줄만 있었다.
  - 자격 블록은 비밀을 읽기 전에 권한 조회(`sys/capabilities-self`)로 다섯 경로의 능력을 물었다. 결과가 설계와 정확히 같을 때만 다음으로 갔다.
  - 컨트롤러는 Vault에 로그인하지 않았다. 판정은 검토된 블록 안에서만 일어났다.
- **「0줄」 판정에는 살아 있다는 근거가 필요하다.**
  - 프록시 404 네 개가 정말 「라우터 없음」인지는 응답만 봐서는 모른다. 그래서 프록시 액세스 로그(오리진 상태 0 · 라우터 없음)와 앱 로그 0줄로 확인했다.
  - 그런데 앱 로그 0줄은 로그가 끊겨도 0줄이다. 같은 실행의 정상 요청 하나가 요청 ID로 앱 로그에 찍혔는지(대조 키)를 함께 본다. 찍혀 있으면 「로그는 살아 있고, 404 요청은 오지 않았다」가 된다.
- **세션 수명이 짧은 자격은 쓰기 직전에 받는다.** 1시간짜리 클라우드 읽기 세션을 쓰는 시험 행이 있었다. 그래서 창 순서를 바꿔 세션 발급을 tester 디스패치 직전으로 미뤘다.
- **정리 확인은 파일만이 아니라 프로세스 · 리스너까지 본다.**
  - 캐시 토큰 파일을 지운 뒤에도 사흘 전 세션의 터널 프로세스가 API 포트를 잡고 있었다.
  - 파일 존재 검사만으로는 보이지 않았다. 리스너 조회와 프로세스 시작 시각으로 찾았다.

## 선택과 대안
- **플랫폼 하네스 러너가 멈췄다.** 앞 단계(운영자 자격이 필요한 인프라 plan 시험)가 기준선 FAIL이라, 라이브 시험 파일까지 가지 못했다.
  - 러너를 고치는 것은 과제 범위 밖이다.
  - 같은 파일을 러너와 같은 꼴로 직접 돌렸다(이전 과제 선례). 런북 문구를 보완하고, 러너 구조 개선은 후보로 남겼다.
- **AC4 「iss 불일치 → 401」 증거가 생성물 시험에 없었다.**
  - 생성물 템플릿에 시험을 더하면 닫힌 과제를 바꾸게 된다.
  - 대신 생성물이 쓰는 공통 라이브러리의 해당 시험을 2차 끝에 돌려 증거를 보충했다. 합격선은 그대로 두고 증거 자리만 정정 노트에 적었다.
- **운영자 화면의 port-forward가 한 줄뿐이었다.**
  - 다시 띄우게 하지 않았다. 같은 PC에서 리스너를 조회해, 두 루프백 주소를 모두 같은 프로세스가 잡고 있음을 확인했다.
  - 기대 출력의 글자보다 상태 조회가 더 확실한 판정이다.
- **tester가 지시보다 넓게 가렸다.** 문서에 정해진 꼴인 루프백 주소 한 줄이다. 지시의 「IP 꼴은 옮기지 않는다」를 문자 그대로 따른 것이라 편차로 보지 않았다. 다음 지시문은 예외(루프백 · 정해진 꼴)를 적을 만하다.

## 결과와 검증
- **창 ①**
  - 음성 대조 PASS(403 · audience 거부).
  - 정책 plan은 두 정책의 in-place 변경뿐이었고, apply는 0 · 2 · 0이었다.
  - 자격 시드는 첫 버전이 생겼고 되읽기 해시가 일치했다.
- **tester 1차**(약 26분)
  - 템플릿 하네스 949 passed(skipped 0) · 생성물 165 passed · arm64 이미지 · 앱 스위트 521 passed
  - 배포 증거 사다리 24/24
  - 플랫폼 라이브 파일 96 PASS · 0 FAIL · 11 SKIP
  - 제품 · 구성 FAIL 0
- **tester 2차**(약 3분): 자격 탐침 10/10 · 로그 대조 10/10 · 재시도 0 · 블록이 받은 Vault 토큰 revoke 204.
- **검증 항목 10개**: PASS 넷 · 설계와 같음 넷 · 기록 하나 · audience 꼴 = 배열. 404 기준값은 실측 꼴 그대로라 정정하지 않았다.
- **마감**: 과제 체크(82/119). 런북 기록 칸 · 설계 정정 노트 · tester 보고(원문 둘 + 컨트롤러 판정 둘)를 남겼다.

## 다음 학습
- 1시간 로그인 자료를 「1회용」으로 더 조일지 정해야 한다(마무리 전 사용자 결정). 사본은 만료까지 유효하므로, 실제 노출 창은 파일 삭제 시각이 아니라 발급 수명이다.
- 다음 과제(Playwright · US4 E2E)가 같은 자격 길을 쓰려면 먼저 규칙 문장을 고쳐야 한다. 지금 문장은 블록 하나만 예외로 지명한다.
- 러너 설계: 운영자 자격이 필요한 단계가 뒤의 에이전트 자격 단계를 막지 않게 나누는 법.

## 사고·오류
- **이전 세션의 터널을 사흘 동안 남겼다.**
  - 이전 과제 마감 때 세션 끝 정리(리스너 종료)를 확인하지 않았고, 오늘 창들도 그 리스너를 그대로 썼다.
  - 세션 끝 블록에 터널 프로세스 확인 줄을 더했다.
- **기대 출력을 화면 글자(「두 줄」)로만 적어 두었다.** 실제 화면이 한 줄이었을 때 확인 비용이 생겼다. 상태 조회로 판정하는 줄을 함께 적어 둘 것.
- **tester 1차의 범위 이탈**: 쓰기 범위 밖 임시 디렉터리에 파일 하나를 만들었다가 바로 지웠다(비밀 0 · 자진 보고).
