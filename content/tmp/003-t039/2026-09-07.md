# 003-platform-foundation T039 — 관리 접근을 터널 하나로 좁히고 22 포트를 닫다 (2026-09-07)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제

부트스트랩 기간 동안 두 노드의 SSH는 NSG에 운영자 공인 IP /32짜리 임시 22 규칙을 열어 두고 썼다. K8s API도 그 SSH 위에 로컬 포워딩(`ssh -L 6443`)을 얹어 접근했다. 사용자 결정으로 이 예외는 "창(window)" 방식이었다 — T035에서 열고 T039 끝에서 반드시 닫는다.

T039의 목표는 인바운드 포트를 **하나도 열지 않은** 관리 경로를 만드는 것이다. 클러스터 안 cloudflared 커넥터가 아웃바운드로만 엣지에 붙고, 인증은 Cloudflare Access가 앞단에서 처리한다. 어려운 점은 기술이 아니라 **순서**였다: 새 경로가 실제로 동작하는 것을 확인하기 전에 22를 닫으면 자기 잠금(self-lockout)이고, 터널 오리진 포트나 IdP 권한처럼 문서만으로는 확정할 수 없는 항목이 경로 중간에 박혀 있었다.

## 배운 개념

- **remote-managed 터널**(`config_src = "cloudflare"`): ingress 설정은 Cloudflare 쪽에 있고 pod는 실행 토큰만 갖는다. 설정 정본이 OpenTofu 한 곳뿐이어서, 공개 GitOps 저장소에는 터널 식별자도 설정도 중복 선언하지 않는다. 커넥터 매니페스트는 "토큰을 들고 엣지에 붙는 프로세스"만 기술한다.
- **`cloudflared access tcp/ssh`** 는 WARP 클라이언트 등록 없이 임의 TCP를 로컬 리스너로 받는 방식이다. SSH는 `ProxyCommand`로, kubectl은 `127.0.0.1:6443` 리스너로 받는다. kubeconfig에 `tls-server-name`이 필요한 이유가 여기서 선명해졌다 — 접속 주소는 로컬 루프백이지만 인증서 검증은 API 서버 인증서의 이름으로 해야 한다. 포트를 6443으로 맞추는 것도 의도다: 기존 admin kubeconfig를 한 글자도 고치지 않기 위해서다.
- **cloudflared의 tcp origin은 주어진 host:port를 그대로 dial한다.** Service의 포트 매핑을 대신 해주지 않는다. `default` 네임스페이스의 `kubernetes` Service는 443으로만 listen하고 targetPort가 6443이므로, 오리진은 6443이 아니라 443이어야 한다. 반대로 NetworkPolicy는 ClusterIP DNAT가 filter 평가보다 먼저 일어나기 때문에 목적지가 이미 노드의 6443이다. **같은 한 경로를 두 층이 서로 다른 숫자로 본다** — 이걸 모르면 둘 중 한쪽을 반드시 틀린다.
- **QUIC은 TCP만으로 안 된다.** 커넥터의 엣지 egress 7844는 TCP와 UDP 둘 다 필요하고, UDP가 막히면 조용히 http2로 폴백한다. 계약 허용 매트릭스에 프로토콜 열이 없다는 사실이 이때 드러났다. 커넥터 하나는 기본 HA 연결 4개를 엣지에 만든다.
- **프로브 대상 고르기**: 메트릭 서버의 `/ready`는 등록된 엣지 연결이 있을 때만 200을 준다. 연결 0인 커넥터는 존재 의미가 없으니 liveness도 같은 엔드포인트를 보되, 짧은 엣지 장애로 재시작이 몰리지 않게 failureThreshold를 넉넉히 뒀다. 메트릭 포트는 프로브 도착지일 뿐이고 Service도 scrape 대상도 만들지 않았다(계약에 그 행이 없다).
- **required anti-affinity + replica 2 + 노드 2대**면 기본 `maxSurge: 1`이 세 번째 pod를 영원히 Pending으로 만들어 롤아웃이 멈춘다. `maxSurge: 0`으로 1개씩 교체해야 하고, 교체 중에도 남은 커넥터가 터널을 유지한다.
- **AOP(오리진 mTLS)는 터널 오리진에 적용되지 않는다** — 인바운드 리스너가 없어 클라이언트 인증서를 제시할 곳이 없다. 그래서 터널은 SSH·kubectl 관리 전용이고, HTTP 앱을 터널로 노출하면 오리진 측 mTLS 통제를 그대로 우회하게 된다. "편리해 보이는 확장"이 곧 보안 구멍인 사례.
- **SSA 인수의 판정 기준은 managedFields다.** 수동 apply한 네임스페이스와 Deployment를 나중에 Argo CD가 넘겨받는데, 라벨 값이 계약과 정확히 같으면 필드 소유권이 충돌 없이 공유로 넘어간다. `last-applied-configuration` 어노테이션은 남아 있을 수 있고 남았다고 실패가 아니다(SSA는 남의 필드를 지우지 않는다).

## 선택과 대안

- **커넥터 배포 형태**: 공식 이미지 + 직접 쓴 Deployment 2 replica. 기각 — community Helm 차트(버전 핀·securityContext 통제가 간접적), hostNetwork DaemonSet, `--protocol http2` 고정(UDP 차단 환경 대비였지만 필요 없었다).
- **클라이언트 버전 핀 — 계획을 실행 중에 뒤집었다.** plan A12는 워크스테이션 클라이언트를 2026.5.1로 핀하라고 적었다(2026.6+에서 `access tcp/ssh`가 Access 서비스 토큰을 무시하는 회귀 보고). 그런데 그 회귀는 **비대화형 서비스 토큰 경로에만** 걸리고 운영자의 브라우저 IdP 대화형 로그인과는 무관하다. 운영자 경로는 설치된 2026.8.3으로 SSH·kubectl 모두 실측 통과했으므로 핀을 적용하지 않고, 서비스 토큰이 2026.8.3에서 동작하는지를 tester 경로로 실측한 뒤(VD) 핀 유지/폐기를 정하기로 미뤘다. 부수 근거 하나가 결정적이었다: 2026.5.1 릴리스 자산에 체크섬 파일이 없다 — 검증할 수 없는 바이너리를 "안전을 위해" 고정하는 것은 안전이 아니다.
- **전환 순서를 문서에 못박았다**: 터널 SSH와 kubectl이 실제로 동작하는 것을 확인한 **뒤에만** 임시 22 규칙을 제거한다. 순서를 뒤집으면 잠금이고, 되돌리기는 예외 규칙 재개방이 break-glass다.
- **토큰 투입 방법**: SecureString 입력 → base64 → 파이프로 `kubectl apply --server-side`. 기각 — `--from-literal`(토큰이 셸 히스토리와 `ps` 출력에 남는다), `--dry-run=client -o yaml > file`(평문 파일이 생겨 커밋 사고). Git Bash에서 `/dev/stdin` 형식은 MSYS 경로 변환 때문에 네이티브 kubectl이 열지 못한다는 것도 확인해 절차에서 뺐다.
- **메모리 limit 256Mi**: QUIC 수신 버퍼가 HA 연결 수에 비례해 커진다. 대안이던 `--ha-connections 2`는 엣지 이중화를 절반으로 줄이므로 기각하고 limit을 올렸다. CPU limit은 두지 않았다 — 핸드셰이크와 대용량 전송의 버스트를 스로틀링하지 않기 위해서다.

## 결과와 검증

- 커넥터 2/2, 노드당 1개, 각각 QUIC 연결 4개 등록, 오류 로그 0. 기동 시 나오는 ICMP 프록시 비활성 경고는 `capabilities.drop: [ALL]` + 비루트의 정상 결과이고 TCP 터널 기능과 무관하다.
- 터널 경유 SSH로 두 노드 로그인(호스트 키 지문이 기존 known_hosts 항목과 일치), 터널 경유 `kubectl get nodes` 2 Ready — 오리진 포트 정정의 첫 end-to-end 실증이다. 6443 리스너를 실제로 잡은 프로세스가 cloudflared인지도 확인했다.
- 임시 22 규칙 제거 후 `nsg rules list ... --query 'length(data)'` = 1(선언된 자기참조 규칙만 남음), 제거 뒤에도 SSH·kubectl 정상. **부트스트랩 SSH 예외 창이 닫혔고 이후 SSH 경로는 터널뿐이다.**
- 터널 ingress 3개에 대한 정적 단언을 인프라 하네스에 신설했고, 변이 3종을 검출하는 것으로 단언의 유효성을 확인했다.
- 검증 태도 하나가 명시적으로 규칙이 됐다: **`tofu plan`이 깨끗한 것은 규칙 제거의 증명이 못 된다.** OpenTofu가 만들지 않은 규칙은 상태에 없기 때문이다. 반드시 실제 목록을 조회해 센다.
- 이후 T041에서 Argo CD가 같은 네임스페이스·Deployment를 SSA로 인수했고, 그 과정에서 파드가 재시작되지 않았다.

- 계약 허용 매트릭스에 커넥터 네임스페이스의 **ingress 행이 없다** → default-deny 적용 후 kubelet 프로브가 막힐 수 있다(T041에서 확인). 매트릭스에 프로토콜 열도 없다(7844 TCP+UDP).
- 메트릭 포트가 scrape 목록에 없다 — 터널 지표 미수집이 의도인지 결정하고, 수집하려면 계약을 먼저 고친다(T098).
- 이 Deployment에는 Reloader 어노테이션이 없다 → ExternalSecret 전환(T045) 후 토큰 회전 때마다 수동 `rollout restart`가 필요하다. 감시 대상에 넣을지는 T046에서.
- 상한 조정용 실측: 정상 상태 RSS와 대용량 전송 중 최대 RSS를 함께 보고 256Mi를 재평가.
- 터널이 유일한 경로가 된 만큼, 예외 규칙 재개방·노드 콘솔로 들어가는 break-glass 절차를 실제로 연습해 둘 필요가 있다.

## 사고·오류

1. **Access 정책의 include 이메일이 코드 기본값으로 회전했다.** 새 셸에 `TF_VAR_*`가 없어 첫 plan이 변수 프롬프트에서 멈춘 것을 "행(hang)"으로 오인했다. 변수를 채우고 apply했더니 **3 changed** — 기대했던 터널 오리진 1건 외에 Access 정책 2개의 include 이메일이 누락된 변수 탓에 코드 기본값으로 바뀌었다. 즉 plan 게이트("1 change가 아니면 멈춘다")를 사람이 넘긴 운영 실수다. 재적용으로 원복했고, 같은 회전이 다시 일어나지 않게 그 변수의 코드 기본값을 제거했다. 교훈 둘: **신원·자격 변수에는 기본값을 두지 않는다**, **plan의 change 수가 기대와 다르면 apply 전에 멈춘다.**
2. **Access GitHub IdP 첫 실사용이 실패했다.** SSH 로그인에서 "Authentication error — Failed to fetch user/group information"; IdP 테스트로 재현하니 `GET /user/emails`가 403이었다. 토큰 교환은 성공했고 이메일 조회만 막혔다는 비대칭이 단서였다 — Client ID 형식으로 이 앱이 OAuth App이 아니라 **GitHub App**임을 판별했다. GitHub App은 요청 스코프를 무시하고 계정 권한(Email addresses: Read-only)을 별도로 요구한다. 권한을 추가해 해결하고, 런북의 "OAuth App" 표기를 정정했다. Cloudflare 문서가 OAuth App을 전제하고 있으므로 계약에도 "OAuth App 또는 Email Read 권한을 가진 GitHub App"으로 적기로 했다.
3. **Secret 적용이 전부 connection refused(적용 0건)였다.** API 접근 경로를 열어 두는 창이 닫혀 있었다. 새 창에서 리스너를 띄우고 연결을 확인한 뒤 재실행했는데, 여기서 또 하나를 배웠다 — **새 창에서는 kubeconfig 경로 변수를 다시 정의해야 한다.** 빈 값으로 실행되면 기본 kubeconfig로 떨어져 엉뚱한 컨텍스트를 보게 된다.
4. **`cloudflared access logout`은 존재하지 않는 명령이다.** 절차에 그렇게 적혀 있었는데 2026.8.3의 하위 명령 목록에는 없었다. 세션 종료는 리스너 프로세스 종료 + 토큰 캐시 파일 삭제다. 규칙·런북·스크립트 헤더는 즉시 고쳤고, 불변 문서(plan·계약)의 같은 문구는 converge 대기 항목으로 넘겼다. "문서에 적혀 있으니 있는 명령"이라는 가정이 얼마나 쉽게 통과하는지 보여주는 예다.
