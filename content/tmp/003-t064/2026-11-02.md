# 003-platform-foundation T064 — 이벤트 스키마 호환성 검사를 테스트로 먼저 못박기: "깨지는 변경"의 정의와 CLI 게이트 (2026-11-02)
> 1일차(설계 · 계약 보정 · 빌드 · 리뷰). 짝 구현(T067)이 이 테스트를 초록으로 만든다. 결과·검증 절은 마감 때 채운다.

## 문제
pod 사이의 유일한 결합 계약은 모노레포에 있는 이벤트 JSON Schema다. CI가 `main`의 스키마와 PR의 스키마를 비교해 소비자를 깨뜨리는 변경을 막아야 한다. 테스트를 먼저 쓰려니 "어떤 변경이 깨지는 변경인가"를 사례 단위로 못박고, 아직 없는 검사 스크립트의 입·출력(위반 목록의 모양 · 경로 표기 · 종료 코드)과 봉투 검증 함수를 정해야 했다.

## 배운 개념
- **호환 규칙은 소비자 관점에서 닫는다.** 계약은 "필드 삭제·이름 변경·타입 변경·required 추가·enum 삭제" 금지만 적었다. 그러나 `required`에서 필드를 **빼는** 것도 존재를 전제한 소비자를 깨뜨리고, `string`을 `["string", "null"]`로 넓히는 것도 소비자에게는 타입 변경이며, 스키마 파일을 지우는 것은 토픽 제거다. 셋을 금지 목록에 더하고, 반대로 제목·설명·예시·버전 메타데이터만 바뀌는 것은 위반이 아님을 명시했다 — 과잉 엄격한 검사는 사람들이 우회하게 만든다.
- **위반은 전부 모아서 보고한다.** 첫 위반에서 멈추는 검사는 PR 작성자가 고칠 때마다 한 건씩 발견하게 만든다. 테스트가 "세 가지 변경 → 위반 세 건"으로 fail-fast를 금지한다.
- **경로는 JSON 포인터로.** 위반 위치를 `#/properties/variants/items/properties/url`처럼 스키마 문서 안의 위치로 적으면 중첩 객체·배열 요소도 한 표기로 가리킬 수 있고 사람이 바로 찾아간다.
- **CLI는 종료 코드가 계약이다.** CI 게이트는 출력 문구가 아니라 종료 코드로 판정한다 — 0 깨끗함 · 1 위반 · 2 사용 오류를 테스트가 자식 프로세스로 실제 실행해 고정한다. 사용 오류와 위반을 같은 코드로 내면 "인자를 잘못 줘서 실패"가 "위반"으로 읽힌다.
- **라이브러리를 고정하지 않고 동작을 고정한다.** 봉투 검증은 JSON Schema 2020-12 검증기가 필요하지만 테스트는 검증 함수의 결과(ok · 오류 경로)만 본다. 어떤 검증기를 쓰는지는 구현의 선택이다.
- **버전은 레지스트리에서 실측한다.** 연구 메모의 버전 대신 npm 레지스트리에서 오늘의 최신(vitest 5 · ajv 8.20)과 Node 24 호환 조건을 확인하고 범위를 정했다. pnpm 10이 의존성의 빌드 스크립트를 기본으로 막는다는 점(플랫폼 바이너리는 선택 의존성으로 온다)도 설계에 적었다 — CI는 스크립트 실행 금지 모드다. 실제로는 vitest 5의 빌드 도구가 esbuild가 아닌 rolldown·lightningcss라 설치 스크립트가 하나도 없었다.
- **닫힌 스키마는 "선택 필드 추가 허용"과 양립하지 않는다.** 빌더가 올린 질문: 토픽 스키마에 `additionalProperties: false`가 있으면 생산자가 허용된 선택 필드를 더해 배포한 순간 옛 스키마를 가진 소비자(pod별 배포)가 모든 이벤트를 DLQ로 보낸다. 계약의 세 문장(선택 필드 추가 허용 · 소비자는 스키마로 검증 · 실패는 DLQ)이 동시에 성립하려면 스키마가 열려 있어야 한다 — 계약에 "닫힌 스키마 금지"를 적고, 테스트가 실제 스키마 파일에서 그 사실을 단언한다. enum 미지 값 무시와 같은 원칙이다.
- **숙성 정책은 설치 경로마다 따로 걸어야 한다.** 저장소의 Renovate는 npm 패키지에 3일 숙성을 요구하지만, 사람이 직접 `pnpm add`를 하면 그 창을 거치지 않는다 — 전이 의존성 하나가 배포 19시간 만에 잠금 파일에 들어왔다(리뷰가 레지스트리 배포 시각을 전수 대조해 발견). pnpm 자체의 최소 배포 경과 설정을 워크스페이스에 두어 로컬 해석에도 같은 창이 걸리게 했고, 그 패키지를 3일 지난 버전으로 재해석했다. CI의 고정 잠금 설치는 해석을 건너뛰므로 영향이 없다.
- **잠금 파일은 비밀 스캐너가 건너뛴다.** gitleaks 기본 설정은 `pnpm-lock.yaml`을 허용 목록으로 지나간다 — 잠금 파일의 안전은 integrity 해시 전수 존재와 레지스트리 대조(`pnpm view … dist.integrity`)로 따로 본다.

## 선택과 대안
- **자체 필드 diff vs 범용 스키마 diff 라이브러리**: 자체. 규칙이 작고 명확하며, "무엇이 깨지는가"를 저장소가 소유해야 한다.
- **메모리 스키마 쌍 + 임시 디렉터리 + CLI 자식 프로세스**: 세 층을 다 테스트한다 — 함수 수준(규칙) · 디렉터리 수준(파일 추가/삭제) · 프로세스 수준(종료 코드).
- **봉투 검증은 실제 스키마 디렉터리로**: 가짜 스키마가 아니라 저장소의 `schemas/`를 읽는다 — 스키마가 없으면 빨강이 그 사실을 드러낸다(지난 과제의 "스키마 없으면 실패" 원칙과 같다).
- **vitest 설정 파일 없음**: 기본 탐색으로 충분하다. 설정 파일은 필요가 생길 때 둔다.

## 결과와 검증
- 신규 파일 1(계약 테스트 — id 16 · `it` 선언 24 · 펼치면 38케이스) + 패키지 매니페스트(ESM · test/check-compat 스크립트 · 의존성 3) + 루트 잠금 파일(패키지 66 · 전부 sha512 · 레지스트리 대조 66/66 일치) + 워크스페이스 설정(숙성 3일).
- 빨강: 테스트 수집 단계에서 검사 스크립트 모듈 부재 → 1 suite 실패 · exit 1(Node 직접 import로 교차 확인). 인프라 초록: vitest 5 기동 · 스모크 1 passed(뒤 삭제) · CI 모드 고정 잠금 설치 exit 0(저장소 + 매니페스트만 복사한 빈 트리 양쪽).
- 판별력: 저장소 밖 참조 구현 + 스키마 7개로 38/38 · 변이 13종 전부 검출 · 스크립트만 있고 스키마가 없는 중간 상태는 21 실패/17 통과(다른 이유로 통과 0) → 참조 구현 삭제.
- 리뷰 2렌즈 approve_with_fixes(medium 2 · low 3) → 결정 8개: 닫힌 스키마 금지(계약 · 규칙 · data-model + 테스트 단언 1 + 표본 수정) · pnpm 숙성 설정 + 전이 의존성 재해석(integrity 재대조 일치) · 설계 문서를 테스트 머리 주석(API 정본)과 동기 · 경로 탈출 단언의 근거(토픽 이름 문법 pattern 또는 경로 경계 확인) 기록 · 빌더 편차 8 수용.
- Docker 무관(컨테이너 0). 비밀 스캔 no leaks(잠금 파일은 별도 구조 검사).
