# 003-platform-foundation T040 — 원격 install.yaml을 커밋 SHA로 핀해 Argo CD를 올리고 root Application으로 조정 루프를 증명 (2026-09-07)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제

클러스터에 GitOps 컨트롤러를 넣는 일은 "앱 하나 배포"가 아니다. 이후 모든 플랫폼 컴포넌트가 이 컨트롤러를 통해 들어오므로 **설치 방식 자체가 계약**이 된다. 요구가 넷이었다. (1) 업스트림 매니페스트를 변형 없이, 재현 가능하게 핀한다. (2) 우리 계약에 없는 컴포넌트(dex·applicationset-controller)와 업스트림이 동봉한 보안 객체는 제거한다. (3) 2노드 소형 클러스터에 맞게 리소스 요청을 줄인다(ADR 0002가 잡아 둔 Argo CD 예산은 상주 RAM 약 0.6 GiB). (4) 사람이 손으로 하는 유일한 설치 단계를 멱등하게 만들고, 그 뒤에는 Argo CD가 자기 자신을 관리하는 상태로 이어질 수 있게 한다.

여기에 더해, 부트스트랩이 자동 생성하는 초기 admin 비밀번호를 운영자 릴레이로 어떻게 넘기느냐가 절차 문제였고 — 이 task에서 실제로 실패했다.

## 배운 개념

**kustomize 원격 base의 두 문법은 대상이 다르다.** 계약 문구였던 `?ref=<sha>`는 git 저장소의 *디렉터리*를 가리키는 문법이라 단일 파일에는 쓸 수 없다. kustomize 5.8.1 실측 오류가 그대로 말해 준다 — `refers to file 'install.yaml'; expecting directory`. 그래서 같은 커밋의 raw 단일 파일 URL(경로에 SHA를 넣는 형태)로 핀했다. 대안인 `manifests/cluster-install?ref=<같은 SHA>`는 렌더 결과가 **바이트 단위로 같지만**(1,918,840 B · 59 문서) git clone이 필요해 12.7 s가 들고 repo-server가 대형 저장소를 받아야 한다. 계약 문구가 도구 문법과 어긋날 수 있다는 것, 그리고 그때 고칠 대상은 구현이 아니라 문구라는 것이 배움이었다.

**태그가 아니라 커밋 SHA로 핀한다.** 태그는 움직일 수 있다. 태그가 가리키는 커밋을 확정하는 방법도 배웠다: `git ls-remote <repo> refs/tags/v3.5.2`에 `^{}` peeled 줄이 **없으면** lightweight 태그이므로 출력된 SHA가 곧 커밋이다(태그 객체라면 peeled 줄을 봐야 한다). API로 `object.type: commit`을 교차 확인했다.

**업스트림에 토글이 없으면 `$patch: delete`가 표준 답이다.** install.yaml에는 dex/applicationset 비활성 키가 없고 `argocd-cmd-params-cm`에도 없다(`server.dex.server`는 주소일 뿐). 삭제 패치는 kustomize 표준 기능이고, 같은 객체에 delete 패치를 둘 두면 오류이므로 대상마다 정확히 하나씩 둔다. CRD는 남겨도 무해해서 유지했다.

**NetworkPolicy는 합집합이라 "나중에 좁히기"가 불가능하다.** 이 task에서 가장 이식성 있는 배움이다. 업스트림이 동봉한 NetworkPolicy 5장은 서버가 `ingress: [{}]`(모든 출발지), 컨트롤러·repo-server·notifications가 `namespaceSelector: {}`(모든 네임스페이스 → metrics)로 우리 계약 매트릭스보다 넓었다. 뒤 task가 default-deny + allow 세트를 깔아도 **합집합 특성상 이 5장이 남아 있으면 절대 좁혀지지 않는다.** 유일한 수정 지점이 설치 시점의 삭제 패치였다. 지우기 전에 계약 매트릭스에서 argocd가 필요로 하는 행(같은 ns 통신·API 서버·인그레스 유입·모니터링 스크레이프·외부 443)이 전부 있는지 한 줄씩 대조했다.

**Server-Side Apply와 Server-Side Diff는 한 쌍이다.** SSA가 선택이 아닌 이유는 client-side apply가 `last-applied` 어노테이션에 전체 객체를 넣는데 ApplicationSet CRD가 그 262144 B 한계를 넘기 때문이다. 그리고 SSA는 선언적이라 재실행이 멱등이다. 짝이 되는 `controller.diff.server.side`는 다른 field manager가 넣은 필드(컨트롤러 기본값 등) 때문에 생기는 **가짜 OutOfSync**를 없앤다. 즉 "적용 방식"과 "비교 방식"을 함께 서버 쪽으로 옮겨야 자기 관리가 조용해진다.

**Go 컨트롤러의 메모리 한계는 두 곳에 적는다.** `GOMEMLIMIT`을 메모리 limit의 80–90%로 두면 Go GC가 OOMKill 전에 회수한다(여기서는 limit 1Gi에 900MiB ≈ 88%). 부수적으로 배운 함정: application-controller는 Deployment가 아니라 **StatefulSet**이라 패치 대상 kind가 다르다. 동시성 파라미터(status/operation processors, kubectl·repo-server parallelism)를 업스트림 기본값보다 낮추면 메모리 스파이크를 시간축으로 분산할 수 있고, 대가는 sync가 느려지는 것이다(약 20–30 Application 규모에서 수용).

**app-of-apps의 헬스 전파는 자동이 아니다.** Application CRD의 내장 헬스 평가는 1.8에서 제거되었다. 그래서 `argocd-cm`에 Application 헬스 Lua를 다시 등록하지 않으면 root의 sync-wave가 child의 Healthy를 기다리지 않고 그냥 넘어간다. "wave를 썼으니 순서가 보장된다"는 가정이 조용히 깨지는 지점이다.

**비밀의 "진짜 저장소"를 구분하라.** 초기 비밀번호 Secret은 평문 사본일 뿐이고, 실제 검증에 쓰이는 값은 서버가 읽는 Secret의 `admin.password`(bcrypt 해시)다. 이 구분을 알고 있었기 때문에 아래의 분실이 복구 가능한 사고로 끝났다.

## 선택과 대안

- **core-install.yaml 기각**: server(UI/API)·notifications·dex가 빠져 UI·알림 요구를 못 채운다. install.yaml + 패치가 공식 권장 형태다.
- **argo-helm 차트 기각**: `dex.enabled=false` 같은 토글은 편하지만 공식 자가관리 예제와 다른 **두 번째 템플릿 계층**이 생긴다. 학습·감사 목적에 불리하다.
- **dex 비활성에 `replicas: 0` 기각**: 객체가 남아 Argo UI에 Degraded 노이즈를 만든다 → 삭제 패치.
- **업스트림 NetworkPolicy를 계약 정책으로 덮기 기각**: 위의 합집합 성질 때문에 성립하지 않는다 → 삭제.
- **root Application의 project를 곧바로 `platform`으로 두는 안 기각**: AppProject는 다음 task 산출물이라 존재하지 않고, 없는 project를 참조하면 `InvalidSpecError`로 sync가 거부되어 이 task의 검증 자체가 불가능해진다. 그래서 임시로 전권 project를 쓰고 위험 범위를 명시적으로 좁혔다 — 대상 경로가 비어 있고, 기본 브랜치는 PR과 검사로만 바뀌며, 창은 다음 task까지로 한정.
- **빈 Secret에 삭제 패치 금지**: 서버가 런타임에 채우는 객체라 지우면 안 된다(문서화된 함정).
- **이미지는 태그 대신 멀티아치 인덱스 digest 2개**: 노드가 arm64라 두 인덱스에 linux/arm64가 있는지 확인했다. 대가는 자동 업데이트다 — 기본 kustomize 매니저는 raw URL 속 SHA를 추적하지 못하고, digest-only 항목은 `latest` 기준으로 갱신 PR을 열 수 있다. 그래서 업그레이드는 "새 태그의 SHA + 같은 릴리스의 digest 2개"를 사람이 한 PR에서 맞추는 방식으로 두고, 추적용 주석만 미리 배치했다.

## 결과와 검증

- 적용 전 렌더 검사: 문서 수 40, dex/applicationset 객체 이름 0건, `kind: NetworkPolicy` 0건. 그 다음 `kubectl apply --server-side --force-conflicts -k` → **40 serverside-applied**(CRD 3·SA 5·Role/ClusterRole 6·Binding 6·ConfigMap 7·Secret 2·Service 6·Deployment 4·StatefulSet 1).
- 롤아웃 5/5 성공(약 70초), 파드 5개 Running, `FailedCreate` 이벤트 0 = PSA restricted 통과, digest가 아닌 이미지 참조 0, 컨트롤러 256Mi/1Gi + GOMEMLIMIT 반영, cmd-params 6키 반영.
- root Application 적용 20초 뒤 `Synced Healthy`, conditions 비어 있음. 대상 경로에 매니페스트가 **0개**인데도 의미 있는 증거인 이유: 저장소 도달과 조정 루프 동작을 다른 변수 없이 분리해 증명한다. "아무 것도 배포하지 않는 상태의 성공"을 일부러 첫 관문으로 둔 셈이다.
- 무해 판정 하나: K8s 1.36이 내는 `metadata.finalizers … prefer a domain-qualified finalizer name` 경고는 Argo 표준 finalizer에 대한 업스트림 경고다.
- 관찰과 인계: nodeSelector를 task 문면이 지시하지 않아 넣지 않았고, 결과적으로 파드 5개가 전부 데이터 역할 노드에 붙었다. 계획상 예산은 플랫폼 역할 노드였으므로 nodeSelector 패치는 뒤 task의 결정 항목으로 넘겼다. 실측이 계획과 다를 때 즉석에서 고치지 않고 결정 지점을 명시해 넘기는 편이 안전하다.
- 되돌리기의 비대칭: `kubectl delete -k`는 **CRD까지** 지운다. 이 시점에는 되돌릴 수 있지만 다음 task 이후에는 절대 쓰면 안 되는 명령이 된다. 또 삭제 승인 어노테이션의 시각은 `deletionTimestamp` 이상이어야 인정되므로 순서가 "delete 먼저, 어노테이션 다음"이다.
- 리뷰: 다차원 리뷰 2회 + critic Approved, 마이너 3건 반영. 위의 업스트림 NetworkPolicy 문제는 리뷰가 찾아낸 지적이다.

## 다음 학습

- 구조적 순환(root가 `apps/`만 비재귀로 읽어 AppProject 디렉터리를 스스로 동기화하지 못함)을 어떤 방식으로 끊을지 — 수동 apply 1회, 부트스트랩 base 포함, apps/ 안의 별도 Application 중 택일.
- default-deny + allow 세트가 argocd의 실제 흐름(인그레스 유입·같은 ns pod↔pod·컨트롤러→API·repo-server→외부 443)을 전부 덮는지 계약 매트릭스로 재확인. Argo의 SSA는 항상 force라 수동 생성분 인수 시 conflict 재실행은 필요 없다.
- notifications-controller의 metrics 포트가 계약 매트릭스에 없다 → 스크레이프 대상이면 모니터링 task에서 행을 추가한다.
- gitops 검사 스크립트의 공백 4건: 삭제 패치 target 부재 검사, 원격 base의 태그 문자열 ref 금지, bootstrap 경로 이미지 digest 요구, `GOMEMLIMIT ≤ memory limit` 검사.
- 소형 리소스 값은 어디까지나 가설이다 — 운영 1주 뒤 `kubectl top`으로 재조정하기로 예약했다.

## 사고·오류

- **초기 admin 비밀번호 분실.** 절차 문면은 "클립보드로만 꺼내 비밀번호 관리자에 저장 → 로그인 확인 → 그 뒤 Secret 삭제"였는데, 실제 실행에서는 **로그인 확인 전에** Secret을 삭제했고 클립보드 값은 비밀번호 관리자에 들어가지 않았다. 다음 날 운영자가 bcrypt 해시를 재생성해 서버가 읽는 Secret의 `admin.password`를 교체하는 방식으로 재설정하고, 로컬 포트포워딩으로 로그인을 확인했다.
- 교훈 (a): "비밀 삭제"는 **비밀번호 관리자 항목 확인**과 **실제 로그인 성공** 둘 다 끝난 뒤에만 한다. 운영자 릴레이 지시에서 확인 단계와 삭제 단계를 같은 블록에 넣지 않는다 — 사람은 한 블록을 한 동작으로 실행한다.
- 교훈 (b): 이 경험이 뒤의 Vault init 절차 설계로 이어졌다. 복구 자료를 사용자 입회로 받아 오프라인에 두고, 폐기·정리는 확인 이후 별도 단계로 떼어 놓는 형태다.
- **병렬 작업 사고**: 공유 클론 하나에서 두 빌더가 브랜치를 바꿔 checkout 경합이 났다. 이후 규칙 = gitops 작업은 빌더마다 전용 worktree, 공유 클론에서는 checkout 금지.
- **리뷰 워크플로 결함**: 검증 에이전트가 한도로 실패했을 때 그 지적이 "반박"으로 분류되는 스크립트 버그를 발견했다. 유효 결과 0건은 "반박"이 아니라 "미검증"으로 분리해야 한다.
