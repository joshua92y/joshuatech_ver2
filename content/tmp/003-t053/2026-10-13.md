# 003-platform-foundation T053 — 첫 상태 있는 데이터베이스: 관문의 거짓 음성과 Argo health의 Degraded 매핑을 설계로 흡수하기 (2026-10-13)
> 1일차(2026-10-13 착수). US3의 두 번째 구현 과제 — PostgreSQL 클러스터 하나(단일 인스턴스), 객체 저장소 백업 설정, 매일 백업 스케줄을 gitops 저장소에 선언했다. 이날 안에 선행 PR(네트워크 정책 한 쌍 + 백업 자격 ExternalSecret)이 머지·라이브 확인됐고, 본 PR이 열렸다. 머지와 라이브 확인은 다음 항목으로 이어진다.

## 문제
오퍼레이터(T052)는 떠 있지만 데이터베이스는 아직 없다. 과제 문면은 클러스터 값(인스턴스 1 · 메모리 2Gi · 파라미터 몇 개), 백업 저장소 값(압축 방식 · 보존 30일), 스케줄(매일 02:00 KST · 생성 즉시 1회)을 정해 두었고, 백업은 오퍼레이터 내장 경로가 아니라 **플러그인 경로**(CNPG-I)로만 쓰기로 되어 있었다. 매니페스트 자체는 세 장이지만, 이 과제가 처음으로 "지우면 데이터가 사라지는 객체"를 만들기 때문에 삭제 보호 · 백업 경로 · 네트워크 · 첫 배포 순서가 전부 사실로 확인돼야 했다.

## 배운 개념
- **검사 관문도 틀릴 수 있다 — 스키마의 출처를 따져야 한다.** CI의 매니페스트 스키마 검사(kubeconform)는 공개 CRD 카탈로그(datreeio)의 사본을 쓰고 있었는데, 그 사본이 1년 넘게 오래돼 라이브 CRD가 받아 주는 압축 값(`lz4`)을 거부했다. 거짓 음성이다. 문면을 고쳐서 관문을 통과시키는 대신, **저장소가 직접 렌더하는 CRD에서 스키마를 파생해 1순위로 쓰고 카탈로그는 폴백**으로 돌렸다. 출처가 "라이브에 적용되는 차트 버전"과 항상 같으니 드리프트가 없고, 다른 오퍼레이터(ESO · cert-manager · Traefik · Argo) CRD 47개가 함께 혜택을 받았다. 정적 사본을 저장소에 vendoring하는 안은 동기 의무가 생겨 버렸다.
- **Argo CD의 health 매핑은 sync의 성패를 바꾼다.** Argo 내장 CNPG 클러스터 health는 `Applying configuration`·in-place 재시작·switchover 같은 **정상 운영 상태**를 Degraded로 분류한다. 리소스 wave가 둘 이상인 sync는 다음 wave로 가기 전 health를 기다리고, Degraded를 보면 그 sync를 Failed로 닫는다. 자동 sync는 기본 재시도 5회(약 2.6분 창)를 소진하면 같은 리비전으로 다시 시작하지 않는다. 그래서 이 Application에만 두 가지 예외를 계약에 적고 넣었다: `ApplyOutOfSyncOnly`(한 장 변경을 단일 step으로 만들어 health 대기 자체를 없앤다)와 창을 약 12.5분으로 넓힌 명시 `retry`. 소스 판독에 근거한 설계라 라이브에서 전이를 실측하는 항목(VD-11)으로 남겼다.
- **파드 QoS는 파드 단위다.** 클러스터 컨테이너의 requests = limits를 맞춰도, 플러그인 사이드카(requests ≠ limits · CPU 상한 없음)가 같은 파드에 들어오면 QoS는 Burstable이다. 연구 단계의 "Guaranteed QoS → OOM 보호" 문장은 사이드카를 빼고 본 것이었다. 사이드카에 CPU 상한을 두면 백업 압축이 느려지고, requests를 올리면 2 OCPU 노드의 예산을 건드리므로, 자원 교정 과제(T097)에서 실측 뒤 결정하기로 하고 문서를 사실에 맞췄다.
- **사이드카가 어디에 있는지 명령이 먼저 알아야 한다.** 플러그인 사이드카는 `spec.containers`가 아니라 `spec.initContainers`의 native sidecar(restartPolicy Always · 고정 이름)다. 컨테이너 목록만 보는 확인 명령은 빈 값을 돌려주고 오판으로 이어진다.
- **포트 하나의 역할은 소스에서 확정한다.** 오퍼레이터 → 인스턴스 8000 포트는 상태 수집과 in-place 갱신 경로이고, 백업 **시작**은 `pods/exec` 스트림이라 네트워크 정책 밖이다. 계약에 "백업 요청"이라 적혀 있던 것을 정정했다.
- **백업 객체의 수명과 삭제 방향을 따로 본다.** 보존 기간이 지나면 사이드카가 카탈로그에 없는 Backup 객체를 지우므로 K8s 객체 수는 약 30개로 수렴한다. 반대로 Backup 객체나 스케줄을 지워도 객체 저장소의 데이터는 지워지지 않는다(삭제 RPC·finalizer가 없다). 다만 저장소 버전 삭제 권한을 가진 키가 유출되면 "60일 복구 창"은 방어가 되지 못한다 — 실수 삭제용이라고 범위를 명시했다.
- **노드 재이미지가 이 시점부터 데이터 소실 경로가 된다.** 데이터는 노드 로컬 디스크(local-path)에만 있고, Argo의 삭제 보호도 오퍼레이터도 노드 재이미지를 막지 못한다. 복원 런북이 생기기 전까지 그 노드의 재이미지를 금지하는 경고를 런북 머리에 올렸다.

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| 관문의 거짓 음성 | 검사가 저장소 렌더 CRD에서 스키마를 파생(1순위) · 카탈로그 폴백 | 문면 변경(`lz4` → 다른 압축) — 동결 문면·연구 근거 위반 · 정적 vendoring — 동기 의무 · kind 검증 끄기 — 검증 소실 |
| Argo Degraded 전이 | 이 Application에만 `ApplyOutOfSyncOnly` + 명시 `retry`(계약 예외) | 전 Application 적용 — 필요 없는 곳에 의미 변화 · 그대로 두기 — 파라미터 변경마다 sync Failed |
| 파드 QoS | 사이드카 resources 유지 · 문서 정정 · 실측 항목 | 사이드카 requests = limits — 백업 압축 throttle · 노드 예산 결정은 자원 교정 과제의 몫 |
| PR 단위 | 선행 PR(정책 + 자격) → 본 PR 하나(관문 수정 + 매니페스트 + Application 예외) | 관문 PR 분리 — 운영자 머지 1회 추가 · 두 브랜치 rebase |
| 백업 자격 위치 | 플랫폼 ns 전용 디렉터리의 ExternalSecret(배달자 Application) | 컴포넌트 디렉터리 — 위치 검사가 조용히 꺼진다 |

## 사고·오류
- **"죽은" 워크플로가 살아 있었다.** 세션 압축 뒤 워크플로 기록에 결과 줄이 없고 에이전트 기록이 짧아 죽었다고 판단해 같은 슬라이스의 빌더를 따로 띄웠다. 실제로는 살아서 다른 설계(정적 vendoring)로 같은 파일을 고치고 있었고, 뒤에 띄운 빌더가 "다른 변경이 섞임"을 보고 멈춘 덕에 충돌을 피했다. 생존 판정은 기록 파일의 갱신 시각으로 한다.
- **하네스 두 개가 겹쳤다.** 조정 메시지가 닿기 전에 수정 에이전트가 검사를 돌려, 전체 자기검사와 임시 디렉터리를 공유했다. 양쪽 결과를 증거로 쓰지 않고 단독으로 다시 돌렸다. 하네스 지시에는 "실행 전 다른 하네스 프로세스 0 확인"을 넣기로 했다.
- **연구 문서의 전제 하나가 틀렸다**(파드 QoS Guaranteed) — 사이드카를 빼고 본 결론이었다. 리뷰가 K8s 규칙으로 바로잡았다.
