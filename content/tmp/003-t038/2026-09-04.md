# 003-platform-foundation T038 — 번들 Traefik을 HelmChartConfig 하나로 길들이기 (2026-09-04)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제
K3s는 Traefik을 번들로 깔아 준다. 편하지만 기본값 그대로는 못 쓴다. 2노드 클러스터에서 어느 노드에 뜰지 통제가 없고(플랫폼 역할 노드에 고정해야 한다), 로그가 기본 포맷이라 수집이 어렵고, 트레이싱도 없고, 80→443 리다이렉션과 `X-Forwarded-*` 신뢰 범위가 정해져 있지 않다. 문제는 "값을 어디에 쓰느냐"였다. 번들 컴포넌트의 패키지 매니페스트(`traefik.yaml`)는 K3s가 시작할 때마다 원본으로 다시 쓰므로 거기에 값을 넣으면 재시작 때 사라진다. 게다가 GitOps 저장소 계약은 `platform/traefik/`에 Middleware·TLSOption·TLSStore만 두기로 이미 정해 두었으므로, 차트 값의 정본은 노드의 별도 파일 하나뿐이어야 했다.

## 배운 개념
- **HelmChartConfig**: K3s의 deploy 컨트롤러가 `server/manifests`에서 읽어 번들 차트에 *추가 values 파일*로 넘기는 CR이다. 적용되면 `helm upgrade`가 values 파일 두 개(차트 원본 + 이 파일)를 받는 형태로 나타난다. 즉 번들 차트를 갈아치우지 않고 "덧쓰기"만 한다.
- **우선순위 함정**: 같은 디렉터리의 HelmChart `spec.set` 값은 HelmChartConfig의 `valuesContent`보다 **우선**한다(K3s가 레지스트리 관련 값을 set으로 넣는다). set으로 잡힌 키는 여기서 못 바꾼다. 그래서 검증은 "파일에 썼다"가 아니라 "Deployment args에 나왔다"로 해야 한다.
- **차트 키 철자는 버전에 묶인다**: 번들 chart 40.1.x는 `logs.general.format`·`logs.access.*`이고 하위 키가 전부 소문자(CLI 플래그 이름 그대로) — `fields.headers.defaultmode`, `filters.statuscodes: "400-599"`(문자열, 리스트 아님). upstream 41.x는 같은 설정이 `log`·`accessLog`·`defaultMode`·`statusCodes: [ … ]`로 옮겨 갔다. 40.1.0 values.yaml의 `filters` 블록은 `additionalProperties: false`라 camelCase를 쓰면 helm이 스키마 오류로 **거부**하고, 스키마가 느슨한 자리는 반대로 **조용히 무시**한다. 최신 공식 문서를 그대로 붙여넣는 것이 이 작업의 가장 흔한 실패 경로다.
- **액세스 로그 설계**: 상태코드 400–599만 기록하면 정상 트래픽의 로그 비용과 개인정보 노출이 함께 줄고, 헤더는 기본 drop으로 두고 필요한 것만 keep 할 수 있다.
- **`forwardedHeaders.trustedIPs`의 의미**: "이 목록에 있는 원격 주소가 보낸 `X-Forwarded-*`만 신뢰한다"는 선언이다. 목록을 넓히면 그 범위 안의 누구나 클라이언트 IP를 위조할 수 있다 — 신뢰 목록은 보안 경계다.
- **매니페스트 롤백의 비대칭**: manifests 디렉터리에서 파일을 지워도 이미 적용된 객체는 지워지지 않는다. 롤백은 "파일 삭제 + `kubectl -n kube-system delete helmchartconfig traefik`" 2단계여야 한다. 같은 함정이 이 디렉터리를 쓰는 다른 산출물에도 적용된다.
- **replica 1이어도 순단이 없을 수 있다**: 차트 기본 updateStrategy가 `maxUnavailable: 0 / maxSurge: 1`이라 새 파드가 Ready가 된 뒤 옛 파드가 빠진다. 신규 연결이 비는 구간은 없고, 종료되는 파드의 진행 중 연결만 끊긴다.

## 선택과 대안
- **번들 Traefik 유지 vs `--disable traefik` 후 upstream 41.x를 Argo CD로 설치**: 후자는 최신 차트를 쓸 수 있지만 K3s 업그레이드와 이중 관리가 되고 CRD 소유권이 충돌한다 → 기각. 대가로 차트 버전이 K3s 패치에 묶이는 것을 수용하고, "업그레이드 뒤 values 스키마 확인" 부담을 업그레이드 task로 넘겼다.
- **`trustedIPs`에 파드 CIDR을 넣자는 조사 단계 결정(K3S-D6)**: 기각했다. 클러스터 안의 아무 파드나 `X-Forwarded-*`를 위조할 수 있기 때문이다. 채택안은 Cloudflare IPv4 대역 15개의 리터럴 사본이다(정본은 OpenTofu의 Cloudflare IP 데이터 소스이고, 같은 목록이 443 인그레스 방화벽 규칙을 만든다). manifests 파일은 템플릿이 아니라 있는 그대로 적용되므로 렌더할 수 없다 → "검증 가능한 리터럴 사본 + 공개 API 대조 명령 + 분기 1회 재검토"로 드리프트 위험을 문서화해 남겼다.
- **헤더를 전부 drop**: 기각. 로그가 완전히 익명이 되어 조사가 불가능하고, 로드밸런서 뒤라 `ClientHost`가 실제 클라이언트가 아닐 수 있어 실질 식별자는 Cloudflare가 붙이는 클라이언트 IP 헤더뿐이다. `CF-Connecting-IP`·`CF-Ray`·`User-Agent` 세 개만 keep 하고 `Authorization`·`Cookie` 등은 drop을 유지했다.
- **리뷰가 뒤집은 가장 큰 결정 — mTLS와 `sniStrict`를 이번에 넣지 않기**: 승인된 task 문면은 `tlsOptions.default`에 clientAuth와 `sniStrict`를 처음부터 넣으라고 했다. 그러나 참조할 CA Secret이 없는 상태로 clientAuth를 넣으면 Traefik이 경고만 하고 CAFiles 없이 TLSOption을 등록해 websecure 라우터가 broken 상태가 되고 **443 핸드셰이크가 전부 끊긴다**. helm 스키마는 통과하므로 설치 Job 로그에도 안 보인다. `sniStrict`는 SNI에 맞는 인증서를 못 찾으면 기본 인증서 폴백에 가지 않고 끊는데, 인증서 탐색이 동적 인증서만 보기 때문에 와일드카드 인증서가 아직 없는 이 시점에 켜면 같은 결과가 된다. 두 값은 각각 인증서 task와 CA Secret task 뒤로 지연하고, 목표 상태와 투입 순서를 파일 헤더에 조각으로 보존했다.

## 결과와 검증
- 커밋 4개(구현 + 리뷰 반영 + 확인 명령 정정 + 런북 기록)와 정적 하네스 68 단언(변이 20종 검출 확인, fail closed), `tests/run-all.ps1`에 슬롯 추가. PowerShell에 YAML 파서가 없어 들여쓰기 기반 소형 파서로 키 경로를 뽑고 값까지 대조했으며, 파싱 불가한 줄이 하나라도 있으면 FAIL로 두어 "조용한 통과"를 막았다.
- 적용 뒤 Deployment args를 grep 해 40.1.x 철자가 그대로 인자로 나오는 것을 확인했다: 액세스 로그 JSON + 상태코드 필터 + 헤더 keep 3종, OTLP gRPC 트레이싱(샘플 10%), web→websecure permanent 리다이렉션, Cloudflare 대역 trustedIPs. **41.x 키 함정도, `spec.set` 우선으로 인한 무시도 없었다는 실증**이다.
- 롤아웃 성공, 새 파드가 플랫폼 역할 노드에서 Running·RESTARTS 0, 대시보드 IngressRoute 생성, 노드 내부에서 건 443 요청이 `http=302`(핸드셰이크 성공 + 라우터 응답), 최근 10분 로그에 `error|invalid|fail` 0줄 — clientAuth·`sniStrict`를 뺀 결정이 유효했다는 증거.
- 부수 증거: 같은 작업 창에서 운영자가 노드를 직접 재부팅했고 K3s와 Traefik이 사람 개입 없이 복구됐다. 뒤에 있을 재부팅 리허설 task의 사전 증거로 기록했다.

## 다음 학습
- **로그 필터를 좁힌 결정이 나중의 측정을 막았다**: 로드밸런서(klipper-lb)가 소스 IP를 보존하는지는 액세스 로그의 `ClientHost`와 기록된 클라이언트 IP 헤더를 비교해야 알 수 있는데, 액세스 로그가 4xx/5xx만 남기므로 302 응답으로는 관측되지 않는다. 일부러 404를 유발하는 프로브가 필요하다 — 관측 설계는 "무엇을 버리기로 했는가"가 곧 측정 한계가 된다.
- **정적 하네스가 확인할 수 없는 것**: 차트 values 스키마와 `spec.set` 우선순위는 파일만 읽어서는 알 수 없다. 실제 args만이 계약이다. K3s 업그레이드로 번들 차트가 40.1.x를 벗어나면 이 파일이 조용히 깨지므로, 업그레이드 절차에 설치 Job 로그 확인을 넣었다.
- 지연한 두 값은 뒤 task에서 실제로 투입됐고, 그 과정에서 "TLSOption만 바꾸는 변경은 롤아웃이 나지 않는다(파드 AGE가 그대로인 것이 정상)"는 또 다른 실측으로 이어졌다.

## 사고·오류
- **확인 명령 3건이 실전에서 작동하지 않았다.** ① 워크스테이션에서 공인 주소로 건 443 curl은 구조적으로 항상 `000`이다 — 방화벽이 443을 Cloudflare 대역에만 열어 두었으므로 이는 오리진 직접 접근이 차단된다는 증거이지 실패가 아니다. 확인은 노드 내부 사설 주소 요청으로 바꿨다. ② `logs --tail=200`은 옛 로그만 보여 무의미 → `--since=10m`. ③ `rollout status`가 helm upgrade보다 먼저 통과할 수 있어 첫 파드 조회에서 세 시간 된 옛 파드를 봤다 → AGE와 RESTARTS로 새 파드인지 재확인하라는 주의를 넣었다. 교훈: 확인 명령은 한 번 실제로 돌려 본 뒤에 문서에 남긴다.
- **승인된 task 문면의 키 철자가 upstream 41.x 표기였다.** 승인 문서도 외부 버전 사실 앞에서는 틀릴 수 있다. 구현은 실제 차트 values.yaml을 근거로 40.1.x 철자를 따랐고, 편차를 파일 헤더에 적고 문면 정정은 converge로 넘겼다.
- 파일 헤더에 적어 두었던 "롤아웃 시 수십 초 순단" 경고는 **실측 근거가 없는 문장**이었다. 차트의 updateStrategy 실제 값을 확인해 "신규 연결 공백 없음, 진행 중 연결만 끊김"으로 정정했다 — 경고문도 근거를 요구해야 한다.
