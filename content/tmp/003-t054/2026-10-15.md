# 003-platform-foundation T054 — 관문을 먼저 세우고 올리는 선언형 role·DB: 재실행 · TDD · 리뷰 두 라운드 · PR (2026-10-15)
> 2일차. 전날 한도로 멈춘 라운드 4를 다른 모델로 재실행해 결정 C1–C13을 반영하고, 새 validate 검사를 TDD로 세우고, 3렌즈 리뷰 두 라운드(r4 · r5)를 더 돌려 남은 low를 닦은 뒤 gitops 커밋 2건과 PR을 올렸다. 머지·라이브 판정은 운영자의 비밀 저장소 시드 뒤에 이어진다(아래 「결과와 검증」에 덧붙인다).

## 문제
라운드 4의 결정은 세 갈래였다 — ① PostSync Job에 pod owner 자격의 initContainer를 더해 CONNECT 제한을 먼저 걸기, ② 데이터 보존 관문(새 검사)을 **테스트 먼저** 세우기, ③ 운영자 시드 블록을 판정/변경/되돌리기로 쪼개고 수동 대체 경로를 런북에 적기. 재실행 뒤 리뷰 r4·r5는 high/medium 0, low만 남겼지만 그 low들은 모두 "관문이 보지 않는 틈"과 "확인 스크립트의 느슨함"에 관한 것이어서 그냥 넘기면 다음 사람이 같은 함정에 빠진다.

## 배운 개념
- **관문의 TDD는 red를 실측해야 의미가 있다.** 새 검사의 픽스처 6종(정상 · `ensure: absent` · reclaim `delete` · reclaim 누락 · 원본은 retain인데 kustomize patch로 렌더만 delete · 별칭 뒤에 숨긴 absent)을 먼저 만들고 자기검사가 6건 FAIL하는 것을 본 뒤 구현해 green으로 만들었다. 실제 트리에서는 Database 4 · DatabaseRole 6을 세어 PASS 한 줄로 보고한다.
- **원본 라벨과 렌더 라벨은 잡는 것이 다르다.** 원본 YAML에서 `!!binary` 같은 태그로 적은 값은 원본 판정이 평문으로 보지 못하지만, kustomize가 렌더에서 평문으로 직렬화하므로 렌더 라벨이 잡는다. 두 라벨을 다 보는 설계가 이 틈을 메우며, 한계는 문서의 「보지 않는 것」에 적는다.
- **"≥ n" 판정은 id가 고정되면 정확 집합으로 바꾼다.** 머지 뒤 확인 스크립트가 Job의 `RESULT` 줄을 "4개 이상"으로 세고 있었다 — initContainer가 더해져 id 6개가 고정된 뒤에는 하나가 빠져도 통과한다. 정렬한 집합의 문자열을 ordinal로 비교하는 쪽으로 바꿨다(중복 + 누락도 잡힌다).
- **선행 확인 규칙은 "표식 부재"가 아니라 "살아 있는 실행 없음"을 뜻한다.** 죽은 검사 실행이 남긴 빈 임시 디렉터리 하나가 "실행 중" 표식으로 읽혀 규칙을 영구 미충족으로 만들었다. 프로세스 목록이 비어 있으면 표식은 잔재이므로 치우고 진행한다 — 규칙 문장에 그 분기를 적어 두었다.
- **되살린 하위 에이전트는 "지금 사용자 메시지"를 자기 과제로 읽을 수 있다.** 진행 상황을 묻는 사용자의 질문이 하위 에이전트에게 보이면 읽기 전용으로 끝내 버린다(NEEDS_CONTEXT). 지시문에 "과제 출처는 컨트롤러의 지시이며 최근 사용자 메시지는 당신 과제가 아니다"를 명시해야 한다.
- **운영자 블록의 수동 대체는 명령 1순위를 적는다.** PostSync Job의 CONNECT 단계가 실패하면 운영자가 데이터베이스 파드 안에서 psql로 같은 문장을 직접 실행하는 경로가 1순위(클러스터 밖에서 포트를 여는 경로가 아니라) — 런북과 컴포넌트 README가 서로 그 절을 가리키게 했다.

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| `!!binary` 태그 우회 | 렌더 라벨이 잡는다는 사실을 문서의 한계 항목으로 적음 | 원본 라벨에 태그 해석 추가 — yq 표현식 복잡도 대비 이득 없음(렌더가 이미 잡는다) |
| Job RESULT 판정 | id 6개 정확 집합(정렬 · ordinal) | 개수 ≥ 6 — 중복 + 누락을 못 잡는다 |
| 죽은 표식 처리 | 프로세스 목록이 비면 잔재로 보고 삭제 후 진행 | 표식이 있으면 무조건 대기 — 영구 대기 |
| 문서 low 정정 | 매니페스트 값은 손대지 않는 소형 빌더(렌더 sha256 전후 동일 확인) | 컨트롤러 직접 편집 — 여러 README 교차 참조를 빠뜨리기 쉽다 |
| 시드 슬라이스 마무리 | 되살린 에이전트에 과제 출처를 다시 알려 이어가게 함 | 새 에이전트 투입 — 두 작성자 충돌(실제로 중복 투입된 에이전트는 올바르게 BLOCKED를 보고했다) |

## 결과와 검증
- 라운드 4 재실행(에이전트 10 · 다른 모델로 전부 명시): gitops 슬라이스 두 개 완료 — Job의 initContainer 분리(pod owner → 공유 owner → app) · 새 검사 `3.8 CNPG-retain`(자기검사 케이스 167 → 173 · 실제 트리 PASS 39 · FAIL 0 · WARN 4). 렌더 17장은 리뷰 두 라운드 내내 sha256이 같았다.
- 리뷰 r4 · r5(3렌즈): high/medium 0. 남은 low — 관문 한계 문구 · README의 검사 코드 표기 · 수동 대체 상호 참조 · 확인 스크립트의 느슨한 판정 · 죽은 표식 규칙 — 전부 반영.
- 모노레포 시드 슬라이스(판정/변경/되돌리기 블록 분리 · 모의 하네스 · 런북 절)는 되살린 에이전트가 마무리했고, 운영자·지시 준수 두 렌즈의 재리뷰(지적 medium 1 · low 8 — 클립보드 비우기 미반영 · 공유 DB 수동 대체 문장 · 운영자 문구 · 과도기 시나리오)를 한 라운드 더 반영했다 — 하네스 red(새 단언 22 FAIL) → green **92 시나리오 · 2771 단언 · exit 0**, 컨트롤러 단독 재실행도 같다. 변이 10개는 전부 의도한 곳에서만 FAIL.
- 최종 트리 `validate.sh` 단독 실행 PASS 39 · FAIL 0 · WARN 4(13분 — 리뷰어들의 읽기 활동과 겹쳐 전 과제의 6분보다 느렸지만 죽지 않았다) · 새 검사의 PASS 줄이 컴포넌트 README에 인용한 문구와 바이트 단위로 같았다. gitops 커밋 2건(관문 먼저 → 매니페스트) · PR #48 열림 · CI 판정 대기.

## 사고·오류
- **되살린 에이전트의 과제 혼동(2회)**: 사용자의 진행 상황 질문을 자기 과제로 읽어 읽기 전용 상태 보고로 끝났다. 과제 출처를 명시한 메시지로 이어가게 했다. 같은 시간대에 중복 투입한 에이전트는 두 작성자를 감지하고 BLOCKED로 끝났다(올바른 동작).
- **컨트롤러 편집 실수**: build-notes 끝 불릿을 고치며 old 문자열이 한 줄의 접두에만 맞아 나머지 조각이 공백으로 시작하는 새 줄로 떨어졌다 — 스크립트로 다시 붙이고 파일 끝 빈 줄을 정리했다.
- **빌더 보고의 지적 ID 라벨 오기**: 시드 슬라이스 빌더가 처리 표에 "O5 반영"이라 적었지만 실제로 반영한 것은 O3(정책 키 체크리스트)였고, O5(정리 블록과 토큰 붙이기 규칙 뒤의 클립보드 비우기)는 손대지 않은 채 "닫힘"으로 보였다. 두 렌즈의 재리뷰가 모두 잡았다 — **빌더의 "반영" 표기는 리뷰 원문의 ID·문장과 대조해야 닫힌 것으로 친다**는 교훈을 남긴다(라운드 6에서 반영).
