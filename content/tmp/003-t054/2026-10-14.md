# 003-platform-foundation T054 — 선언형 role·DB 위에 CRD가 표현하지 못하는 두 가지를 멱등 Job으로 얹기 (2026-10-14)
> 1일차(2026-10-14 착수). US3의 세 번째 구현 과제 — 전날 올린 PostgreSQL 클러스터 위에 데이터베이스 4개(pod DB 2 · 공유 DB 2)와 role 6개를 선언형 CR로 올리고, 자격은 비밀 저장소 → ExternalSecret 6장으로 만들고, 운영자가 비밀 저장소에 자격을 시드하는 블록을 런북에 적는다. 과제 문면이 요구하는 두 가지 — pod DB의 CONNECT 제한, app role의 세션 기본값 — 는 CRD에 자리가 없어 설계가 필요했다.

## 문제
오퍼레이터의 DatabaseRole CRD(1.30)는 role 속성(login · superuser · bypassrls · 비밀번호 Secret 참조 …)은 다루지만 **role 단위 설정값(GUC)** 을 적을 필드가 없다. 그런데 과제 문면은 app role에 `statement_timeout`·`idle_in_transaction_session_timeout` 세션 기본값을 요구한다. 또 pod DB에 "다른 테넌트가 접속할 수 없다"는 교차 거부 증거(검증 과제 T059)가 필요한데, 원래 CONNECT 제한을 맡을 migrate Job(T072)은 한참 뒤다. 한편 이 CR들은 데이터 삭제 경로를 품고 있다 — `ensure: absent`는 reclaim 정책과 무관하게 DROP DATABASE를 재시도하고, reclaim `delete`는 CR 삭제가 곧 DROP인데, 자동 sync + selfHeal인 Application에서는 **Git 변경의 머지가 곧 데이터 삭제**가 된다. CRD도 webhook도 그 값을 막지 않는다. 마지막으로 운영자 시드 블록은 비밀번호 6개를 만들어 비밀 저장소에 넣어야 하므로, 지난 과제(T044)의 사고 — 한 번에 붙여 넣은 블록이 저장하지 않은 비밀을 지워 버린 일 — 를 되풀이하지 않는 모양이 필요했다.

## 배운 개념
- **CRD가 못 적는 것은 hook Job이 "그 역할 자신"으로 적는다.** 세션 기본값은 `ALTER ROLE CURRENT_USER SET …`을 app role 자격으로 실행하면 superuser 없이도 멱등하게 들어간다(클러스터는 superuser 접근을 꺼 두었다). 오퍼레이터 소스를 읽어 보면 role 조정은 `rolconfig`를 건드리지 않으므로(ALTER ROLE에 SET/RESET을 내지 않는다) Job이 적은 값이 다음 reconcile에 되돌아가지 않는다.
- **같은 일을 두 주체가 멱등하게 하면 순서 의존이 사라진다.** pod DB의 `REVOKE CONNECT FROM PUBLIC` · `GRANT CONNECT`는 PostSync Job이 pod owner 자격으로 먼저 하고, 나중의 migrate Job도 같은 문장을 다시 실행한다(이중 멱등). 그래서 교차 거부 증거가 T072를 기다리지 않는다.
- **비밀번호 Secret의 username은 role 이름과 같아야 적용된다.** 오퍼레이터는 Secret의 username ≠ role 이름이면 그 role을 적용하지 않고(applied=false) 넘어간다. 비밀 저장소에 username 필드를 함께 시드하는 이유다. 비밀번호의 앞뒤 공백은 잘라 쓴다.
- **ExternalSecret의 template.metadata를 명시하면 ES의 메타데이터가 복사되지 않는다.** 그래서 만들어진 Secret에는 `cnpg.io/reload` 라벨만 남고 GitOps 추적 라벨이 섞이지 않는다(ESO 2.10 소스 확인).
- **Argo CD의 hook은 앱 health·sync 집계에 들어가지 않는다.** PostSync Job의 성패는 Application의 Synced/Healthy로는 보이지 않고 `operationState`·`hookPhase`·Job 로그의 `SUMMARY` 줄로 판정해야 한다. hook만 바뀐 커밋은 자동 sync를 일으키지 않는다는 점도 같은 뿌리다.
- **관문은 "값이 들어오는 모든 경로"를 본다.** YAML 별칭(anchor/alias) 뒤에 숨긴 값은 `explode` 뒤에 판정해야 잡히고, 원본 파일만 보면 kustomize patch로 렌더에서만 바뀐 값을 놓치므로 원본과 렌더를 둘 다 본다. 모양이 이상한 행은 fail-closed, 대상이 0개인 상태는 "대상 없음"을 **단언하는** PASS로 둔다(조용히 통과하지 않도록).
- **운영자 블록은 판정과 변경을 섞지 않는다.** 읽기 전용 판정(이미 시드됐나) · 변경(만들고 쓰기) · 되돌리기를 다른 블록으로 나누고, 비밀을 다루는 블록은 단어 입력 정지 · 해시 대조 되읽기 · 조건부 삭제로 사람의 손을 거치게 한다.

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| pod DB CONNECT 제한의 주체 | PostSync Job이 pod owner 자격으로 먼저(migrate Job과 이중 멱등) | migrate Job만 — 교차 거부 증거가 T072까지 막힌다 · DatabaseRole CRD — 해당 필드 없음 |
| app role 세션 기본값 | app role 자신이 `ALTER ROLE CURRENT_USER SET` | superuser로 — superuser 접근을 꺼 둔 설계와 충돌 · owner로 — 다른 role의 설정을 바꿀 권한 없음 |
| 데이터 보존 | validate 새 검사(ensure ≠ absent · reclaim retain 명시 · 원본+렌더 · 별칭 해제) | Argo 삭제 보호 어노테이션만 — `ensure: absent`는 삭제가 아니라 "변경"이라 막지 못함 · CRD 검증 — 값을 막지 않음 |
| Application sync 모양 | 전 과제와 같은 예외(`ApplyOutOfSyncOnly` + 명시 retry) | 기본 규약 — 시드 전 ExternalSecret Degraded 전이에서 다단계 operation이 Failed |
| Secret 노출 면 | 컨테이너마다 필요한 Secret만 마운트 · 비밀번호는 psql 한 호출의 환경으로만 | 한 컨테이너에 6장 — 한 단계의 실수가 모든 자격을 본다 |
| 시드 블록 | 판정 · 변경 · 되돌리기 분리 + 단어 입력 정지 + 해시 되읽기 | 한 블록 붙여 넣기 — T044 사고의 재현 경로 |
| 리뷰 구성 | 3렌즈(지시 준수 · k8s 보안/데이터 안전 · 운영자) × 라운드 반복 | 2렌즈 — 운영자 블록의 위험이 보안 렌즈에 묻힌다 |

## 사고·오류
- **모델 주간 한도로 워크플로 6명 전부 실패(16:45–17:08)**: 세션 모델 상속 + 빌더 에이전트의 모델 고정이 같은 한도를 공유했다. 재실행은 다른 모델로 전부 명시해 띄우기로 했다. 뒤에 확인하니 1차 시도가 부분 산출물(하네스 수정 · Job 코드)을 남겨 두었는데, 수정 시각 기준으로만 걸러 처음에는 놓쳤다 — "실패한 워크플로는 아무것도 안 남겼다"는 가정은 틀릴 수 있다.
- **컨트롤러 문서의 과장**: 데이터 모델에 "sync마다 적용"이라 적었으나 hook은 **전체 sync**에서만 돌고 selfHeal의 부분 sync · 리소스 선택 sync · Apply-only에서는 돌지 않는다. 리뷰가 잡아 정정했다.
