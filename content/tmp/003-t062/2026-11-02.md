# 003-platform-foundation T062 — 인증 미들웨어를 테스트로 먼저 못박기: 두 종류의 JWT · 거부 목록 fail-closed · 웹훅 HMAC (2026-11-02)
> 1일차(설계 · 계약 보정 3건 · 빌드 · 리뷰). 짝 구현(T070)이 이 테스트를 초록으로 만든다. 결과·검증 절은 마감 때 채운다.

## 문제
pod 공통 인증 미들웨어는 서로 다른 두 JWT(IdP가 발급한 Bearer 토큰 — JWKS는 클러스터 내부 DNS로 읽고 `iss`만 공개 URL로 검증 — 와 엣지 게이트웨이의 서비스 토큰)를 검증하고, 세션 거부 목록 캐시를 조회해 조회 실패면 **닫는 쪽으로**(503) 실패하되 200 ms 안에 판정해야 하며, 헬스 경로 세 개와 웹훅 경로 하나만 면제하고, 웹훅은 HMAC으로 대신 검증해야 한다. 테스트를 먼저 쓰려니 계약에 없는 이름(설정 키, 요청 속성, 헬퍼 시그니처)을 정해야 했고, 그 과정에서 계약 문장 세 개가 실제로는 성립하지 않는다는 사실이 드러났다.

## 배운 개념
- **라이브러리 기본값이 계약을 조용히 깨뜨린다.** redis 클라이언트 8.x의 기본 재시도는 지수 백오프 10회라서, 연결 거부는 4.7초, 응답 없는 소켓은 6.8초 뒤에야 실패했다(실측). "0.2초 타임아웃 · 200 ms 안에 판정"이라는 계약은 재시도를 끈 구현에서만 성립한다. 테스트는 요청 전체 경과 시간에 상한(판정 0.2초 + 처리 여유 0.3초)을 두어 이 경계를 고정하고, 계약에 "클라이언트 재시도 0"을 명문화했다. 기본 재시도 구현은 9배 밖에 있어 판별력이 크다.
- **서명 방식은 송신자가 만들 수 있는 것으로 정한다.** 세 문서가 "HMAC"이라고만 적고 한 문서가 "공유 비밀 헤더"라고 적어 충돌했다. IdP의 웹훅 전송 코드를 직접 읽어 보니 본문 매핑과 헤더 매핑이 **같은 알림 객체만** 받고 헤더 매핑은 전송될 본문을 보지 못한다. 그래서 "원시 본문 바이트의 HMAC"은 송신 측이 계산할 수 없다. 대신 두 매핑이 같은 이벤트 dict에서 독립적으로 계산할 수 있는 **정규형 JSON(키 정렬 · 압축 구분자 · ASCII)의 HMAC-SHA256**으로 확정했다 — 본문 전체가 서명에 묶이고 키 순서·공백은 서명에 영향이 없다. 문서가 아니라 소스가 결정을 바꿨다.
- **클레임의 실제 값은 문서에서 확인한다.** 서비스 토큰 JWT의 `common_name`은 토큰의 이름이 아니라 **Client ID**다(공식 문서). 계약은 토큰 이름을 기대값으로 적어 두었고, 그대로 배포했으면 모든 호출이 403이었을 것이다. 계약을 보정하고 ConfigMap 값·E2E 검증 과제에 인계했다.
- **OS가 다르면 실패의 모양도 다르다.** Windows에서 bind만 하고 listen하지 않은 포트는 즉시 거부(RST)가 아니라 타임아웃으로 끝난다. 테스트는 예외의 종류를 단언하지 않고 상태 코드와 경과 시간만 단언한다 — 계약이 약속한 것도 그 둘이다.
- **공격 벡터 테스트는 도구가 막아 주는 경로를 우회해서 만든다.** alg 혼동(공개키를 HS256 비밀로 쓰는 토큰)은 JWT 라이브러리가 PEM 모양 비밀을 거부해 `encode`로는 만들 수 없다 — base64url 세 조각을 손으로 이어 만들었다. 라이브러리가 `algorithms=["RS256"]`으로 거부하는 것까지 실측했다.
- **픽스처는 필요한 만큼만 띄운다.** 인증 테스트는 DB를 쓰지 않으므로 Postgres 컨테이너가 뜨지 않게 했고(테스트 프레임워크가 DB 접근을 막아 우연한 사용도 잡는다), 두 JWKS 경로는 스레드 하나의 로컬 HTTP 서버가 서빙한다. 키 자료·ACL 비밀번호·웹훅 비밀은 전부 세션마다 생성해 저장소에는 토큰 모양 상수가 하나도 없다.
- **계약에 없는 이름은 가정으로 표시하고 인계한다**(지난 과제의 패턴 재사용). 설정 키 11개, 요청 속성 3개, 헬퍼 시그니처, 면제 목록 기본값, 오류 응답의 `type` URL 규칙(슬러그의 밑줄을 하이픈으로)을 시험 설정과 테스트 머리에 "구현 과제가 확정한다"고 적었다.
- **테스트 실패 출력도 비밀을 새게 한다.** pytest는 실패한 트레이스백 항목의 함수 인자를 repr로 찍는다. 빌더가 참조 구현에 변이를 넣어 테스트의 판별력을 재다가, 노출 단언 헬퍼가 실패하자 세션 비밀번호가 그대로 출력됐다(파기된 시험 컨테이너의 것). 그래서 세션 비밀은 만들 때부터 repr만 가리는 문자열 하위 타입으로 감싼다 — 값은 그대로 쓰이고(비교 · 포맷 · 인코딩) 출력에서만 `***`가 된다. 리뷰가 덧붙인 것: 이 가림은 repr에만 미치므로 JSON 로거는 실값을 찍는다 — 로그 필드 금지는 구현·로깅 테스트의 몫이다.
- **`localhost`는 두 주소다.** Windows의 Docker Desktop은 게시 포트를 IPv4에만 열고 `localhost`는 `::1`이 먼저 풀린다. 0.2초 연결 타임아웃을 가진 클라이언트는 `::1`에서 예산을 다 쓴 뒤에야 IPv4로 넘어간다(0.21초 실측). 시험 컨테이너 주소는 IPv4 리터럴로 고정했다.
- **JWT 검증기의 표준 결함은 "있지만 틀린" 사례만으로는 잡히지 않는다.** PyJWT는 `require` 목록이 없으면 `exp`가 없는 토큰도 받아들인다(영구 유효). 만료·불일치 사례만 있던 테스트에 "필수 클레임 부재" 사례를 더했고, 변이(require 제거)로 테스트가 실제로 실패함을 확인했다. 같은 식으로 "헬스 경로는 거부 목록을 조회하지 않는다"는 오류 지표 불변만으로는 "조회하되 삼키는" 구현을 통과시켰다 — 캐시 서버의 연결 목록 id 차집합으로 바꿨다.
- **문자 집합도 입력 검증이다.** HTTP 헤더 값은 latin-1로 디코드되므로 비ASCII 문자가 실제로 들어온다. `hmac.compare_digest`는 비ASCII 문자열 비교에 TypeError를 던져 401이 아닌 500이 된다 — 헤더를 정규식으로 먼저 걸러 ASCII hex만 비교에 넣어야 한다. 테스트가 그 사례를 고정했고 변이로 확인했다.

## 선택과 대안
- **정규형 JSON HMAC vs 정적 공유 비밀 헤더 vs 원시 본문 HMAC**: 정규형 HMAC. 원시 본문은 송신자가 만들 수 없고, 정적 비밀 헤더는 본문을 묶지 못한다(요청마다 비밀이 그대로 전달된다). 송신 측 매핑 두 개가 실제로 pod 검증을 통과하는지는 IdP 설정 과제에서 실측하는 "검증 후 결정" 항목으로 남기고, 실패하면 정적 비교를 두 번째 모드로 더한다.
- **실제 캐시 컨테이너 + 런타임 ACL vs 가짜 클라이언트**: 실제 컨테이너. 읽기 전용 키 패턴·NOPERM·연결 타임아웃은 가짜로 재현되지 않는다. 사용자 네 명(관리 · 쓰기 · 읽기 전용 · 권한 없음)을 기동 뒤 명령으로 만들고 기본 사용자는 끈다 — 미들웨어 경로는 읽기 전용 사용자만 쓴다는 최소 권한을 테스트가 보여 준다.
- **실패 모드 재현**: 닫힌 포트 · 응답 없는 소켓(listen만 하고 accept하지 않음) · 권한 없는 사용자 — 전부 프로세스 안 소켓과 실제 컨테이너로, 모킹 없이.
- **면제 경로는 정확 일치**: 접두 일치면 `/health-…` 같은 경로가 인증을 건너뛴다. 부정 경로 테스트 세 개로 고정했다.
- **멱등 저장소는 pod의 몫**: 라이브러리 헬퍼는 서명·시각 검증과 `pk` 노출까지만 책임지고, 재전송 no-op은 시험 뷰의 모듈 집합으로 보여 주되 실제 저장은 애플리케이션 과제에 남겼다.

## 결과와 검증
- 신규 파일 9(계약 테스트 31케이스 · 캐시 ACL 인프라 스모크 1 · JWKS 인프라 스모크 3 · JWT·웹훅 민팅 헬퍼 · 비밀 가림 타입 · 시험 전용 urlconf 3파일) + 픽스처·설정 덧붙임 + 런타임 의존성 2(JWT 라이브러리 + 암호 extra · redis 클라이언트 + hiredis) + 잠금 파일(패키지 6 추가).
- 인프라 초록 `1 passed` · `3 passed`(캐시 컨테이너 기동 + 사용자 4명 ACL = 0.7초). 계약 테스트 빨강: 아직 테넌시 모듈이 없어 Django 설정 단계에서 멈춘다(구현 뒤에는 인증 모듈 부재가 원인 — 둘 다 실측).
- 판별력 검증: 저장소 밖의 일회용 참조 구현에서 31/31 통과(fail-closed 판정 요청 전체 0.24–0.29초 · 상한 0.5초) · 변이 19종(빌더 16 + 컨트롤러 3) 전부 검출 — 기본 재시도 변이는 6초대 · require 제거 · 헬스 조회 삼킴 · 비ASCII 비교 전부 실패로 잡혔다. 참조 구현은 검증 뒤 지웠다(구현 과제 빌더에게 완성형이 새지 않게).
- 리뷰 2렌즈 approve_with_fixes(medium 1 · low 10) → 결정 12개로 전부 닫음: 테스트 2개 추가(필수 클레임 부재 · 테넌트 클레임 없음/slug) · 사례 7개 추가 · hang 보호 · 연결 수 관측 · 구조 자기검사 · 한계 기록 · 계약 문구 2곳 좁힘.
- 계약 보정 3건(웹훅 정규형 HMAC 규약 신설 · 서비스 토큰 식별값 = Client ID · 거부 목록 클라이언트 재시도 0)은 설계 커밋으로 먼저 들어갔다.
- Docker 위생: 컨테이너 잔류 0 · 익명 볼륨 24 → 24. 비밀 스캔 3회 no leaks.

## 사고·오류
- 빌더의 변이 실측 중 테스트 실패 출력에 세션 비밀번호가 찍혔다(파기된 컨테이너의 것 · 저장소·보고에는 없음). 원인은 pytest의 프레임 인자 repr 출력 — 비밀 가림 타입 도입의 실측 근거가 됐다.
- 설계 단계의 계약 문구 "redis 클라이언트 ≥ 6의 기본 재시도"는 실제보다 넓었다(생성자 기본값만 10회 · URL 생성자는 0). 리뷰와 빌더가 소스로 확인해 문구를 좁혔다 — 지시("명시하라")는 맞았지만 근거 서술이 틀렸던 경우.
- 빌더가 권한 거부로 스크래치의 참조 구현을 지우지 못했다 → 컨트롤러가 검증 뒤 지웠다(우회 없음).
