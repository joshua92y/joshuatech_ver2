# 003-platform-foundation T075 — 검사기가 도구와 다르게 읽으면 경계가 샌다: kustomize 키 접기 · 디렉터리 소스 자동 판별 · 원격 패치 (2026-11-18)
> 빌드 조각 마감, 첫 push, GitOps 검사 PR(GP-1)의 네 차례 리뷰 기록이다. 라이브 배포는 뒤 기록에 있다.

## 문제
운영 렌더를 바꾸는 PR은 운영자 승인 없이 머지되지 않아야 한다. 이 저장소에서 그 경계는 둘이 함께 지킨다.
- 승인 관문: 바뀐 경로로 판정한다.
- 정적 검사(validate): 렌더 결과로 판정한다.
저장소 규칙상 사람 리뷰 수는 0이다. 그래서 「검사를 통과하고 관문 판정이 skip」인 PR은 사람 손을 거치지 않고 머지된다. 새 검사를 더한 PR을 리뷰했다. 리뷰어가 검사를 그대로 통과하면서 운영 렌더를 바꾸는 길을 사본 트리에서 실제로 셋 만들어 보였다.

## 배운 개념
- **같은 파일을 도구와 검사기가 다르게 읽으면 그 틈이 우회로가 된다.**
  - kustomize는 kustomization 파일을 YAML → JSON → Go `encoding/json`으로 읽는다. `encoding/json`은 필드 이름을 대소문자를 가리지 않고 맞춘다. 유니코드 단순 접기(예: 긴 s `ſ` → `s`, 켈빈 기호 → `k`)도 한다.
  - 그래서 `Components:` · `RESOURCES:` · `reſources:`는 kustomize에게 모두 같은 필드다.
  - 검사기는 소문자 키 `components`만 골라 읽었다. 대문자 키로 쓴 Component는 검사기 눈에 보이지 않았다. 그 Component는 관문 밖 개발 overlay에 있었고, 운영 Deployment에 명령을 주입했다.
  - 고친 방법: 키를 골라 읽지 않는다. 모든 키를 열거하고, 정본 철자가 아니면서 접으면 정본이 되는 키, 비ASCII 키, 중복 키를 FAIL로 둔다. 정본 철자 목록은 고정한 kustomize 판의 소스에서 뽑았다.
- **중첩 필드도 똑같이 접힌다.** 최상위 키를 막자 다음 길이 나왔다. `patches: [{Path: <URL>}]`이다. 중첩 구조체 필드 `Path`도 `path`로 읽히고, kustomize는 그 URL에서 패치를 가져온다.
  - 「load restrictor가 루트 밖을 막는다」는 믿음은 로컬 경로에만 맞았다. 파일 로더는 원격 주소를 restrictor보다 먼저 받아 온다(소스 확인).
  - 앱 kustomization은 모든 깊이에서 정확한 키 집합만 받게 했다. 패치는 인라인만 허용하고, 경로를 받는 중첩 자리는 아예 없앴다.
- **디렉터리 소스는 내용물을 보고 종류를 정한다.** Argo CD의 root Application은 디렉터리의 YAML을 그대로 읽는다. 그런데 그 디렉터리에 `Kustomization` 파일이 한 장 생기면 kustomize 렌더로 바뀐다.
  - 그러면 `.txt` 같은 파일 속 Application도 렌더에 들어간다. 파일 이름으로 운영 Application을 알아보던 관문(`*-prod.yaml`)과 파일 단위 검사를 모두 비켜 간다.
  - 고친 방법: 그 디렉터리에는 `*.yaml` · `*.yml` · README만 둔다는 검사를 더했다. 관문도 그 밖의 경로를 승인 대상으로 본다.
- **「네트워크 없는 렌더」는 방어 겹이지 경계가 아니다.**
  - 원격 참조가 키 검사를 어떻게든 지나가도 렌더가 실패하도록 겹을 하나 더 뒀다. 앱 렌더만 HTTP 프록시를 닫힌 로컬 포트로 돌리고 git 전송을 막는다.
  - Go의 HTTP 클라이언트는 루프백 주소에는 프록시를 쓰지 않는다. 그래서 이 겹으로는 루프백을 막지 못한다.
  - git 전송 허용 목록을 `file`로 두었을 때는 `file://` 로컬 저장소의 다른 ref가 렌더됐다. 이 렌더는 git이 필요 없으므로 전송을 전부 금지(`none`)했다.

## 선택과 대안
- **「키 철자 규칙」 대 「정확한 키 집합」**
  - 플랫폼 kustomization은 쓰는 필드가 다양하다. 정본 밖 키를 모두 막으면 거짓 FAIL이 많아진다. 그래서 접기 변형 · 비ASCII · 중복만 막고, 모르는 키는 kustomize의 엄격 모드(모르는 필드 거부)에 맡겼다.
  - 앱과 시험 kustomization은 지금 쓰는 키가 몇 개뿐이다. 그래서 정확한 집합으로 묶었다. 새 키가 필요하면 계약을 먼저 고치게 했다.
  - 리뷰어 권고를 받아 앱 패치에서 파일 경로 · 옵션을 빼고 인라인만 남겼다.
- **검사 번호.** 계약에 새 검사를 11.5로 적었는데 기존 11.5와 겹쳤다. 같은 번호에 다른 이름을 붙인 선례도 있었다. 그래도 목록이 헷갈리지 않게 새 번호(11.7)로 옮겼다.
- **받아들인 한계.** 다음 셋은 관문 밖으로 남는다. 이미 「관리자와 같은 권한」 구역으로 받아들였고, 문서에 적었다.
  - 같은 PR에서 검사 코드를 고쳐 끄는 길
  - 플랫폼 디렉터리 하위 구조체의 철자 변형
  - 루프백 HTTP

## 결과와 검증
- 리뷰는 네 라운드였다(설계 · 계약 렌즈와 우회 · 보안 렌즈). 우회 HIGH 셋을 사본 트리로 재현했고, 고친 뒤 같은 트리가 새 검사로 FAIL하는 것을 확인했다. 둘째 렌즈의 리뷰어가 같은 중첩 우회를 독립적으로 재현해 판단을 뒷받침했다.
- 자기검사:

  | 회차 | 결과 |
  |---|---|
  | 라운드 0 | 전체 266/0 |
  | 라운드 1 | 141/0 |
  | 라운드 2 | 176/0 |
  | 라운드 3 | 17/0 |

  실제 트리와 다음 PR(개발 · 운영 배포) 모양의 트리는 모두 거짓 FAIL 없이 PASS였다. 전체 자기검사(약 315 케이스)는 PR CI에서 처음 Linux로 돈다.
- 빌드 조각 둘도 마감했다.
  - 운영자 블록 하네스: 354 시나리오 · 11,241 단언 · 변이 생존 0
  - 동기화 하네스: 자기 시험 33
  - 두 조각을 첫 push로 올렸다.

## 사고·오류
- 계약에 새 검사 번호를 적으면서 기존 번호표를 확인하지 않아 번호가 겹쳤다. 빌더가 알려 계약을 고쳤다. 이제 새 번호를 정하기 전에 검사 코드 목록을 먼저 grep한다.
- 두 리뷰어의 로컬 탐침 HTTP 서버가 같은 포트를 잠깐 함께 잡았다. Windows의 주소 재사용 때문이다. 결론에는 영향이 없었다. 같은 발견을 다른 리뷰어가 독립적으로 재현했기 때문이다. 이후 지시에는 「임의의 높은 포트 · 끝나면 반드시 멈춤」을 넣었다.
- 시크릿 스캐너가 운영자 블록의 비밀번호 **형식 설명 주석**을 실제 비밀번호로 오탐했다. 같은 문구가 이전에 머지된 블록에도 있다. 코드는 그대로 두고 대시보드에서 오탐으로 처리하도록 했다.
