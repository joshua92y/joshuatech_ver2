# 003-platform-foundation T075 — 첫 앱 배포 전에 경계부터: Dragonfly ACL 좁히기 · 실 브로커 실측 · 승인 관문 넓히기 (2026-11-17)
> 설계 · 사용자 결정 · 로컬 실측 · 설계 커밋까지. 빌드와 라이브 배포는 뒤 기록에 있다.

## 문제
첫 업무 pod(identity-admin)를 GitOps로 dev와 prod에 올리는 과제다. 매니페스트 자체는 템플릿이 이미 만들어 두었다. 그런데 「처음으로 실제 앱이 돈다」는 사실이 그동안 미뤄 둔 질문 셋을 앞으로 끌어냈다.
- pod 하나의 캐시 자격이 캐시 전체를 쥐어도 되는가.
- 메시지 중계기의 장애 가정은 실 브로커에서도 맞는가.
- prod를 바꾸는 경로가 승인 관문 밖에 남아 있지 않은가.
배포 전에 이 셋을 정해야 했다.

## 배운 개념
- **ACL 카테고리는 제품마다 다르고, 문서도 틀릴 수 있다.** Redis 호환 캐시에서 `+@all -@admin -@dangerous`면 연결 강제 종료가 막힐 거라 생각했다. 실측해 보니 이 제품의 `CLIENT`는 하위 명령 구분 없는 「연결」 카테고리 한 명령이라 남았다. 공식 문서는 반대로 적혀 있었다. 그래서 `-client`를 따로 붙였다. 「카테고리를 빼는 방식」은 라이브러리가 새 데이터 명령을 써도 깨지지 않는다. 반면 「명령 허용 목록」은 명령 하나만 빠져도 작업 큐 워커가 죽었다.
- **설정 파일의 토큰 오류는 「안전한 실패」와 「무인증」 두 얼굴을 가진다.** 실행 중에 다시 읽으면(`ACL LOAD`) 오류가 나도 옛 규칙이 남는다. 같은 파일로 기동하면 파일 전체를 버리고 인증 없이 뜬다. 그래서 적용 순서는 「다시 읽기 먼저 · 재시작 금지」다.
- **AppProject의 금지 목록은 열린 문이다.** 금지 6종만 적어 두면 그 밖의 모든 kind가 허용된다. 예를 들어 TLS 기본 옵션을 하나 더 만들면 전체 443이 끊긴다. 허용 목록으로 바꾸면 빠진 kind는 동기화 실패로 드러난다. 조용히 통과하지 않는다.
- **경로 기반 승인 관문은 「무엇이 prod 렌더를 바꾸는가」를 다 알아야 한다.** 관문이 prod overlay만 보면, overlay가 끌어오는 base, prod Application 파일, 프로젝트 정의, Argo CD 본체가 모두 관문 밖이다. 검증하다 보니 이런 길이 계속 나왔다. kustomization의 하위 디렉터리로 다른 env를 끌어오는 길, 검사가 받아 주던 대체 경로 같은 것들이다. 관문을 넓히고, 나머지는 「관문 밖 = 관리자 등가」라는 받아들인 위험으로 정확히 적었다.
- **멱등 프로듀서의 권한 거부는 재시도가 아니라 치명이다.** 쓰기 권한이 하나도 없으면 브로커가 프로듀서 ID 발급을 클러스터 권한 오류로 거부한다. 클라이언트 라이브러리는 이를 치명으로 처리한다. 이 거부는 브로커의 인가 로그에도 남지 않아, 진단 근거는 클라이언트 쪽 한 줄뿐이다.
- **타이머 기반 가정에는 지연 경계가 있다.** 중계기의 「치명 뒤 대기를 두 배씩 늘린다」는 가정은 생성에서 치명까지의 시간이 1초 안일 때만 선다. 왕복 지연을 인위로 늘려 보니 약 30 ms 이상에서 간격이 고정되는 실패 꼴이 나왔다. 클러스터 안은 1 ms 미만이라 괜찮다. 그래도 경계를 숫자로 알게 됐다.
- **접근 로그는 무엇을 남기는지부터 확인한다.** 쿼리 문자열이 로그에 남는지 재려고 정상 요청을 쓰려 했다. 설정을 보니 로그는 400–599 응답만 남긴다. 그래서 일부러 400을 내는 요청을 표본으로 바꿨다.

## 선택과 대안
- **캐시 ACL(UD-9)**: 그대로 두기 · 관리 카테고리만 빼기 · `-client`까지 빼기 · 명령 허용 목록, 넷을 같은 이미지로 실측해 표로 견줬다. 사용자는 셋째(B2)를 골랐다. 대가는 둘이다. 하나는 키 이름 열람(SCAN)이 남는 것이다. 다른 하나는 옛 규칙을 글자로 박아 둔 닫힌 과제의 시드 블록 대신, 새 렌더 블록을 재렌더의 정본으로 세워야 하는 것이다. 그렇지 않으면 다음 비밀번호 회전 때 옛 규칙으로 조용히 되돌아간다.
- **중계기 실측(UD-12)**: 초안은 라이브 dev에서 쓰기 권한을 뺐다가 되돌리는 안이었다. 비판이 짚은 문제는 두 가지였다. dev에는 대기 행을 만들 지원 경로가 없고, 같은 사용자를 다른 검사 Job이 쓴다. 그래서 운영과 같은 판의 브로커(같은 인가기 · 같은 인증 방식)를 로컬에 띄우고 실제 중계기 코드를 붙이는 안을 골랐다. 라이브 변경은 0이고 측정 항목은 오히려 늘었다.
- **플랫폼 갱신(UD-13)**: GitOps 컨트롤러와 엣지 프록시에 보안 권고가 쌓여 있었다. 첫 prod 노출 전에 올리면 이 과제가 커지고, 갱신이 실패하면 과제가 막힌다. 이 과제는 검사로 완화하고, 바로 뒤 별도 정비 단계에서 올리기로 했다.
- **승인 관문(UD-14)**: 넓히면 base 사본 · 프로젝트 · Argo CD 본체를 바꾸는 PR마다 승인 한 번이 는다. 드물고 큰 변경이라 넓혔다.

## 결과와 검증
- 조사 다섯 → 초안 → 독립 비판 둘 → 사용자 결정 넷(+ 보완 하나) → 최종 설계 → 검증 둘 → 수정 두 라운드 → 마지막 확인을 거쳐 설계와 계약 보정을 커밋했다.
- 비판 29건, 검증 29건, 마지막 확인 6건을 모두 처리했다. 기각한 발견은 없다.
- 중계기 실측: 치명 갈래 · 재생성 간격 2 · 3 · 6 · 12초 · 회복 지연 약 5분과 약 10분이 이론값과 맞았다. 독립 반증자가 같은 값을 다시 냈다. 중계기 코드를 고칠 필요가 없으므로, 이미지를 다시 발행할 일도 없다.
- 반증 과정에서 옛 기록의 「첫 간격 약 1.5초」가 구조적으로 2초라는 정정이 나왔다.

## 사고·오류
- 첫 설계 검증에서, 결정의 「대상 없음이면 통과」를 검사 전부에 넓혀 적었다. 그러면 워크로드만 빼도 호스트 점유 검사와 이미지 검사를 비켜 갈 수 있었다. 두 검증자가 독립으로 같은 점을 짚었다. 결정 문장을 옮길 때는 범위 한정어를 놓치지 않는다.
- 비판 하나는 「복제 명령은 실측 목록에 없다」고 했는데, 실제로는 실행하지 않는 권한 점검(DRYRUN) 행에 있었다. 비판의 사실도 원문으로 다시 확인한다.
