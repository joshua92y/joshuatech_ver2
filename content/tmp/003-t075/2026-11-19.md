# 003-platform-foundation T075 — 라이브는 문서의 가정을 하나씩 깬다: 서비스 토큰 형식 · 불변 Job과 서버 측 diff · 마운트 갱신을 기다린 ACL 반영 (2026-11-19)
> 라이브 첫날 기록이다. 준비 관찰부터 개발 환경 첫 배포까지 다룬다(운영 배포는 뒤 기록).

## 문제
GitOps로 첫 앱(identity-admin)을 개발 · 운영 클러스터 네임스페이스에 올린다. 순서가 정해져 있다.
1. 검사 PR(GP-1) 머지
2. Dragonfly 사용자 권한 좁히기(UD-9 B2) 적용
3. 시험 Job PR(GP-A) 머지
4. 비밀 저장소(kv) 시드와 게이트
5. 개발 배포 PR(GP-2) 머지

단계마다 「관찰 블록 → 사람 확인 → 변경 블록 → 관찰 블록」으로 나눴다. 변경이 실패해도 상태를 읽고 되돌릴 수 있게 하려는 것이다. 이날은 설계 문서의 가정이 실물과 어긋난 자리를 셋 만났다.

## 배운 개념
- **외부 자격의 형식은 문서 예시가 아니라 실물로 정한다.**
  - 접근 토큰(Cloudflare Access 서비스 토큰)의 비밀 값을 「64자 소문자 hex」로 가정한 판정 줄이 있었다. 실제로 발급된 토큰은 54자(영숫자 · `_` · `-`)였다. 2026-08 이후 발급분의 새 형식이다.
  - 탐침 블록은 형식이 다르면 아무것도 보내지 않고 멈추도록 짜여 있었다(fail-closed). 그래서 잘못된 가정이 자격 유출이나 잘못된 요청으로 번지지 않았다.
  - 우리 조사 문서에는 새 형식이 이미 적혀 있었다. 설계가 그것과 대조하지 않았을 뿐이다. 값은 출력하지 않고 길이 · 글자 집합만 보는 진단 블록으로 원인을 확정했다.
  - 고친 방법(시험 먼저): 모의 하네스의 가짜 토큰도 옛 형식이라 같은 착각을 품고 있었다. 하네스를 실제 형식으로 바꾸고, 경계 사례를 더했다. 옛 64 hex, 끝 줄바꿈, 가운데 CR, 켈빈 기호처럼 대소문자 접기로 `K`가 되는 글자다. 정규식은 대소문자를 구분하는 판정으로 고정했다.
- **설정 파일이 바뀐 것과 프로세스가 그것을 읽을 수 있게 된 것은 다른 시점이다.**
  - Dragonfly ACL 파일은 외부 비밀(ESO, 5분 주기)이 Secret을 바꾸고, kubelet이 볼륨 안의 `..data` 심볼릭 링크를 원자적으로 바꿔 끼워야 pod에 보인다.
  - 그래서 변경 블록은 ① 비밀 갱신 시각 ② `..data` 링크가 가리키는 대상의 갱신 시각을 차례로 확인한다. 그다음에야 관리자 연결로 `ACL LOAD`를 보낸다.
  - 재시작은 하지 않는다. 재시작은 모든 연결을 끊고, 새 규칙이 틀렸다면 아무도 인증하지 못하는 상태가 된다. 반영 뒤에는 사용자마다 허용 · 거부 표(DRYRUN)로 새 규칙을 확인했다.
- **불변 필드를 바꾸면 서버 측 diff는 「동기화 실패」가 아니라 「비교 실패」로 멈춘다.**
  - 시험 Job의 템플릿을 바꾼 PR을 머지했다. Argo CD 3.5.2(서버 측 diff)는 Job 템플릿이 불변이라 비교 단계에서 오류(ComparisonError)를 냈다. 앱은 동기화 상태 Unknown으로 멈췄다.
  - 동기화 작업 자체가 시작되지 않았다. 그래서 「실패 → 5분 재시도 창」 같은 기존 운영 문서의 재실행 모델이 맞지 않았다. 옛 Job을 지우자 새 Job이 만들어지고 시험이 다시 돌았다.
  - 이 차이는 gitops 문서 정정 후보로 적었다.
- **필수 검사 「최신 브랜치」 규칙.** 저장소 규칙이 「PR 브랜치가 main의 최신을 포함해야 한다」를 요구했다. 앞 PR이 머지되자 다음 PR이 머지 불가가 됐다. 강제 push 없이 병합 방식의 브랜치 갱신으로 풀었다. 검사는 그 갱신 커밋에서 다시 돈다.

## 선택과 대안
- **토큰 형식 판정을 넓히는 방식.** 「길이 · 글자 집합 판정을 아예 뺀다」는 대안이 있었다. 판정이 하는 일은 출력 파싱 오류(다른 필드를 자격으로 읽는 것)를 보내기 전에 잡는 것이다. 그래서 판정은 두고 실제 형식으로 좁게 고쳤다. 옛 형식 토큰도 유효하다는 조사 기록이 있다. 그래도 이 저장소의 토큰 넷은 모두 새 형식이라, 옛 형식은 「형식 아님」으로 남겼다.
- **ACL 반영 순서.** 「Secret만 바꾸고 다음 재시작을 기다린다」는 대안은 반영 시점이 사람 손을 떠난다. 재시작 때 새 규칙이 틀렸다면 장애가 된다. 그래서 개발 환경 → 운영 환경 순서로 각각 사전 관찰 · 반영 · 사후 관찰을 돌렸다. 운영 쪽은 개발 결과를 본 뒤 다시 사람 확인을 받았다.
- **불변 Job 재실행.** Job 이름에 해시를 붙여 매번 새 객체로 만드는 방식도 있다. 그러나 시험 Job의 이름은 검사 · 문서가 고정 이름으로 참조한다. 이번에는 운영자가 옛 Job을 지우는 한 줄 절차로 처리했다.

- 클라우드 읽기 전용 세션이 만료돼 백업 관련 클러스터 시험 3건이 FAIL했다. 결함이 아니라 환경 만료다. 과제를 마감하는 전체 검사 전에 세션을 갱신한다.
