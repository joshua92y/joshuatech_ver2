# 003-platform-foundation T075 — 「통과」를 무엇으로 증명하나: 캐시 HIT · 같은 wave 안의 적용 순서 · 사람이 고른 첫 이미지의 출처 (2026-11-20)
> 라이브 둘째 날 기록이다. 개발 환경 관찰, 운영 비밀 시드, 운영 배포 PR(GP-3), 운영 관찰, 하네스까지 다룬다.

## 문제
운영 배포에는 개발 배포에 없던 것이 셋 있다.
- 관리자 화면 경로: 관리자 호스트용 Ingress와 경로 접두를 떼는 Traefik Middleware.
- 사람이 고른 첫 이미지(seed).
- 켜진 Authentik 쓰기 플래그.

이날의 질문은 「각 확인이 정말 무엇을 증명하나」였다. 브라우저의 200이 캐시 사본일 수 있다. 로그 「오류 0줄」은 적용 시점에 따라 흔들릴 수 있다. seed 이미지는 자동 승격의 출처 검증을 지나지 않는다.

## 배운 개념
- **사람이 고른 첫 이미지는 자동 승격의 출처 검증을 거치지 않는다.**
  - 승격 워크플로는 서명된 출처 증명(attestation)을 먼저 검증하고 나서 PR을 만든다.
  - 운영 overlay의 첫 이미지 항목은 사람이 여는 seed PR이라 그 단계를 지나지 않는다. 그래서 같은 플래그로 컨트롤러가 직접 검증하고 결과를 PR 본문에 남겼다.
  - 확인한 것: SLSA provenance v1, 서명 워크플로 = 발행 워크플로(main 브랜치), 소스 커밋 = 그 이미지를 발행한 main 커밋, GitHub 호스트 러너.
  - 값은 개발 환경에서 이미 돌며 확인을 통과한 이미지로 골랐다. 이후 바꾸는 것은 승격 워크플로의 몫이다. 그 워크플로는 digest 줄의 hex만 제자리에서 바꾼다.
- **같은 sync wave 안에도 적용 순서가 있다.**
  - Argo CD는 같은 wave의 리소스를 kind 순서로 적용한다. Ingress처럼 목록에 있는 kind가 먼저이고, Middleware 같은 커스텀 리소스는 마지막이다.
  - 그래서 둘을 같은 wave에 두면, Ingress가 아직 없는 Middleware를 가리키는 순간이 생길 수 있다. 그 틈에 Traefik이 일시 오류 줄을 남기면 「middleware 오류 0줄」 판정이 거짓 FAIL이 된다.
  - 리뷰어 두 명이 서로 따로 이 점을 짚었다. Middleware를 한 wave 앞(-1)으로 옮겼다. Middleware는 Argo의 health 판정이 없어서 그 wave의 대기가 늘지 않는다.
  - 실제 첫 sync에서 Middleware가 Ingress보다 먼저 섰고, 일시 오류 줄은 0이었다.
- **브라우저의 200은 원점 도달의 증거가 아닐 수 있다.**
  - CDN의 기본 캐시는 `.css` 같은 정적 확장자를 캐시한다. 운영자가 본 응답 헤더는 캐시 HIT였다(새로 고친 요청).
  - 그래서 판정 근거를 앱 로그로 옮겼다. 같은 시각 web 컨테이너의 요청 완료 줄(200 · 1.6 ms)이 원점 도달을 증명한다.
  - Traefik 액세스 로그는 상태 400–599만 남겨서 200의 증거가 될 수 없다.
  - 익명 접근은 자격 없는 `curl`로 302(Access 로그인)와 Location 호스트를 직접 확인했다.
- **「헤더 없이 부르면 403」은 Access 앱 종류에 따라 다른 코드로 나타난다.**
  - 명세의 수용 시나리오는 두 호스트 모두 「헤더 없이 부르면 Cloudflare가 403」이라고 적었다. 실측은 둘 다 403이 아니었다.
  - 서비스 토큰 전용 앱(m2m 호스트): 「서비스 인증 401」 설정이 켜져 있어 401을 돌려준다(첫날 측정).
  - 사람 로그인 앱(관리자 호스트 · GitHub 로그인): 로그인 화면으로 302 리다이렉트한다(이날 측정).
  - 둘 다 「Access가 막았다」는 같은 뜻이다. 다만 E2E 과제가 문면대로 403을 단언하면 틀린다. 그래서 편차로 적고 그 과제에 넘겼다.
- **kustomize 5.8.1의 JSON6902 `replace`는 없는 키를 오류 없이 더한다.**
  - 설계는 「키가 base에서 사라지면 렌더가 실패한다」고 가정했다. 실측해 보니 렌더는 실패하지 않고 키를 더했다.
  - base 드리프트를 실제로 잡는 것은 검사의 키 집합 정확 일치다. 두 overlay가 모두 덮어쓰는 키를 base에서 지우면 렌더만 봐서는 드러나지 않는다.
- **쿼리 원문이 남는 자리는 하나였다(UD-10).**
  - 개발 · 운영 모두 같았다. Traefik의 4xx 액세스 로그에는 요청 경로와 함께 쿼리(가짜 사용자 · 세션 값)가 그대로 실렸다. 앱 로그에는 경로만 남았다.
  - 같은 줄에 요청자의 공인 IP도 실린다(설계상 남기는 헤더). 기록 문서에는 그 값을 옮기지 않았다.
  - 지울지 받아들일지는 관측 과제(T098) 전에 정한다.

## 선택과 대안
- **Middleware 순서**
  - 대안은 파일을 그대로 두고 판정 창만 좁히는 것이었다(sync가 끝난 뒤의 로그만 본다).
  - 둘 다 했다. wave 어노테이션은 원인을 없애고, 판정 창은 Traefik 재시작처럼 순서가 정해지지 않는 경우까지 덮는다.
  - 대가: 설계에 없던 어노테이션이 하나 생겨 편차로 적었다.
- **정적 파일 판정**
  - 후보는 셋이었다: 캐시 상태 헤더 기록 · 쿼리 nonce · 앱 로그.
  - nonce를 붙였지만 운영자가 새로 고친 응답은 HIT였다. 원점 도달을 가장 직접 증명하는 앱 로그를 판정 근거로 썼다.
- **익명 확인**
  - 런북은 시크릿 창이라고 적었다. 같은 「자격 없음」 조건인 `curl`로 대신했다. 상태 코드와 리다이렉트 호스트가 정확히 남는다. 편차로 적었다.
- **리뷰가 찾은 낡은 문장 넷**
  - 이 PR에 섞지 않았다. `tests/` · `.github/`를 바꾸면 CI 자기검사(약 17분)가 배포의 임계 경로에 들어온다.
  - T075 뒤 문서 정합 PR로 모았다.

## 사고·오류
- **Git Bash 경로 변환**: 경로 변환을 끄는 `MSYS_NO_PATHCONV=1`은 `git -C /d/...`의 경로 변환도 끈다. 그래서 git이 그 경로를 찾지 못하고 실패했다. 그 변수를 쓸 때는 `D:/...` 꼴 경로를 준다.
- **클라우드 세션 만료**: 읽기 전용 세션이 또 만료돼 하네스의 백업 단언이 FAIL했다. 결함은 아니다. 전체 검사 직전에 갱신하는 순서를 지킨다.
