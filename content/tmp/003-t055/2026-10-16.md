# 003-platform-foundation T055 — 오퍼레이터 차트 하나와 CR 두 장으로 올리는 단일 노드 Kafka: 관문 · 예외 없음 · 코드가 정본 (2026-10-16)
> 1일차(2026-10-16 착수 · 같은 날 PR). US3의 네 번째 구현 과제 — Strimzi 오퍼레이터(헬름 OCI 차트)와 KRaft combined 단일 노드 Kafka 클러스터, 노드풀 하나를 gitops에 선언한다. 토픽·사용자·CA 미러는 다음 과제(T056), 검사 Job은 T059. 머지와 라이브 판정은 운영자 머지 뒤 이어진다(아래 「결과와 검증」에 덧붙인다).

## 문제
오퍼레이터 차트를 kustomize `helmCharts`로 인플레이트해 올리는 것은 네 번째지만(cert-manager · Vault · ESO · CNPG 선례), Strimzi는 몇 가지가 달랐다. ① CRD가 템플릿이 아니라 차트의 `crds/` 디렉터리에 정적 YAML로 들어 있어 `includeCRDs`를 켜지 않으면 렌더에 CRD가 하나도 없다. ② 차트 기본값이 NetworkPolicy를 **런타임에 생성**한다 — 이 저장소는 정책 객체의 정본을 한 디렉터리에만 두는 규칙이 있다. ③ 차트 기본 CPU limit을 저장소 관례(CPU limit 없음)대로 지우려 했는데 helm의 "null = 키 삭제" 규칙이 kustomize 인플레이트에서는 통하지 않았다. ④ Argo CD의 내장 Kafka health 매핑이 어떤 전이를 Degraded로 보는지에 따라 CNPG 때처럼 Application 예외가 필요할지 결정해야 했다. ⑤ 과제 문면과 연구 문서의 값이 한 곳(설치 네임스페이스)에서 달랐다 — 동결된 과제 문면이 우선이다.

## 배운 개념
- **같은 "헬름 인플레이트"라도 차트마다 CRD 위치가 다르다.** 템플릿 안에 CRD가 있는 차트(CNPG)는 그냥 렌더되지만, `crds/` 디렉터리에 둔 차트(Strimzi · cert-manager)는 `includeCRDs: true`가 필수다. 받은 차트를 직접 열어 확인하는 것이 유일한 방법이다.
- **kustomize의 `valuesInline`은 helm `-f`가 아니다.** kustomize가 차트 values에 자체 병합(mergo, override)을 하므로 `null`로 키를 지울 수 없다. CPU limit처럼 기본값을 **빼야** 하면 렌더 뒤 JSON6902 `remove` 패치가 정답이고, 경로가 없으면 빌드가 실패해 차트 변경을 소리 내어 잡아 준다.
- **오퍼레이터가 만드는 NetworkPolicy는 끌 수 있고, 꺼야 할 이유가 있다.** 정책 정본을 한 디렉터리에 두는 규칙을 지키려면 `generateNetworkPolicy: false`로 두고, 같은 네임스페이스 전 포트를 허용하는 기존 정책이 오퍼레이터 ↔ 브로커 ↔ 엔티티 오퍼레이터 통신을 덮는지, 매트릭스가 클라이언트(9093)와 스크레이프(9404)를 덮는지 확인한다. 대신 Strimzi 기본 정책이 좁혀 두던 내부 포트(9090/9091/9404)가 네임스페이스 안에서 넓어지는 교환을 문서에 적는다 — 9090/9091은 cluster CA mTLS가 필수라 인증 우회는 아니고, 9404(메트릭)는 무인증 HTTP다.
- **Argo health 매핑을 읽으면 예외가 필요한지 알 수 있다.** Argo CD 내장 Kafka health는 `NotReady`이면서 reason이 `Creating`이 아닐 때만 Degraded, `Ready`면 Healthy, 나머지는 Progressing이다. 첫 배포는 Creating → Progressing → Ready이고, Kafka CR을 **마지막 wave**에 두면 Degraded 전이가 와도 operation을 실패시키지 않는다. 그래서 CNPG 때 넣었던 `ApplyOutOfSyncOnly` + retry 예외를 이번에는 넣지 않았다. 반면 CRD와 CR이 같은 Application에 있으면 CRD 확립 직후 CR 적용이 "no matches for kind"로 미끄러질 수 있어 CR을 리소스 수준 wave 1에 두었다.
- **리소스 수준 security context를 적으면 오퍼레이터 기본값이 사라진다.** Strimzi는 사용자가 파드 securityContext를 적으면 그대로 쓰고, 안 적을 때만 영구 스토리지에 `fsGroup 0`을 넣는다. 일부만 적으면 기본값이 조용히 빠진다 — 소스 원문을 읽어 `fsGroup 0`을 명시했다.
- **업스트림 문서(adoc)를 베끼면 틀린다 — 자원 이름과 status 키는 코드가 정본이다.** 리뷰 세 라운드가 잡은 오류는 전부 문서 사실이었다: 브로커 인증서 Secret은 노드별(`<클러스터>-<풀>-<번호>`), 엔티티 오퍼레이터 RoleBinding 이름에는 `-role` 접미가 붙고(adoc에는 없다), 헤드리스 Service에는 메트릭 포트가 없다(컨테이너 포트만), 9093 리스너의 컨테이너 포트 이름은 하위 호환 규칙으로 `tcp-clientstls`, PDB는 custom controller라 `minAvailable` 절대값으로만 생성되며, `status.kafkaMetadataState`는 이미 폐기된 키다(확인 스크립트가 그 키를 요구했다면 건강한 클러스터에서도 FAIL이었다). 리뷰어가 `KafkaResources.java`·`KafkaStatus.java`·CRD를 열어 대조한 덕에 머지 전에 잡혔다.
- **Argo 서버 사이드 diff와 Kubernetes 필드 소유권.** 운영자가 라이브로 붙인 어노테이션(예: pause-reconciliation)은 Argo가 소유하지 않으므로 diff에 들어가지 않고 selfHeal도 지우지 않는다. 그러나 같은 어노테이션을 **선언에도** 넣으면 두 관리자가 공동 소유가 되어, 라이브로 값을 바꾸면 selfHeal이 되돌리고 선언에서만 빼면 라이브에 남는다. "라이브 선조치 뒤 선언 PR로 기록을 맞춘다"는 습관이 여기서는 함정이다 — 복구 절차의 pause/unpause는 라이브 어노테이션으로만 하고, 선언 PR은 내지 않는다.
- **CRD 삭제 보호와 되돌리기 순서는 GC로 설명한다.** Kafka CR을 지우면 오퍼레이터 생존과 무관하게 Kubernetes 가비지 컬렉션이 ownerReference로 StrimziPodSet·파드·Service·Secret을 연쇄 삭제하고, PVC만 `deleteClaim: false`라 ownerReference가 없어 남는다. 보존 PVC로 되살릴 때는 pause → 토픽·사용자 CR 선행 재적용 → 옛 cluster.id를 status에 복원 → unpause 순서여야 사용자가 지워지지 않는다(cluster.id 불일치는 포맷 쓰기 전에 실패하므로 데이터는 무사하다).

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| 설치 네임스페이스 | 과제 문면의 데이터 네임스페이스(브로커와 같은 곳 · 설치 ns만 감시) | 연구 문서의 별도 ns — 동결된 과제 문면이 우선 · 토픽/사용자 CR이 어차피 Kafka ns에 있어야 한다 |
| Application 동기화 정책 | 플랫폼 표준 그대로(예외 없음) + CR을 리소스 wave 1 | CNPG식 예외 — health 매핑상 첫 배포가 Degraded로 operation을 실패시키지 않으므로 불필요 · 필요해지면 실측 뒤 계약 개정 |
| NetworkPolicy | 오퍼레이터 생성 끔 · 기존 정책 세트와 매트릭스로 덮음 | 오퍼레이터 생성 허용 — 정책 정본 규칙 위반 · 라이브에만 있는 정책이 생긴다 |
| CPU limit 제거 | JSON6902 `remove` 패치 | `limits.cpu: null` — kustomize 병합에서 무효(실측 1000m 잔존) |
| 이미지 고정 | 오퍼레이터·TO·UO·init 이미지는 태그에 digest 병기 | 브로커 이미지 digest — 오퍼레이터가 버전 맵에서 고르는 구조라 불가(한계로 기록) |
| 리뷰 구성 | 3렌즈 × 2라운드 + 운영자 1렌즈 마지막 확인 · 사실 주장은 소스 원문으로 | 1라운드 — 문서 사실 오류(adoc↔코드)가 2라운드에서야 드러났다 |
| 복구 절차의 pause | 라이브 어노테이션만(선언 PR 금지) | 라이브 뒤 선언 PR — 공동 소유로 해제가 되돌아가거나 어노테이션이 남는다 |

## 결과와 검증
- 계약 선행 2건(차트 허용 목록 행 · 9404 용도 정정) 뒤 빌더가 렌더 29장(CRD 10 · ClusterRole 7 · RoleBinding 4 · ClusterRoleBinding 3 · 오퍼레이터 Deployment · Kafka · KafkaNodePool)을 냈고, 관문은 "허용 목록에 없는 차트"로 먼저 FAIL(red)한 뒤 행을 더해 PASS 39 · FAIL 0으로 닫혔다. Kafka/노드풀의 모든 잎 필드를 렌더된 CRD 스키마로 전수 대조했다(불일치 0).
- 리뷰 r1(3렌즈)은 매니페스트 결함 0 · 문서 지적 20건, 수정 뒤 r2(3렌즈)가 사실 오류 8건을 더 잡았고(전부 업스트림 문서↔코드 불일치), 수정 뒤 r3(운영자)가 복구 절차의 pause/unpause 소유권 함정 1건과 저수준 2건을 잡아 컨트롤러가 직접 반영했다. 렌더 sha256은 r1 수정에서 env 3줄(digest)만 바뀐 뒤 r2·r3에서 불변.
- 확인 스크립트는 리뷰로 두 번 고쳐졌다: agent-view 권한 밖 호출 한 줄이 전체를 중단시키던 구조(블록별 격리로), 그리고 폐기된 status 키 요구(실제 키로). 변수 뒤에 한글이 붙은 문자열 보간 버그도 pre 실행에서 스스로 드러났다.
- 머지 전 pre 확인 전부 PASS(노드 A 여유 메모리 12 GiB 이상 · 정책 9 · 오퍼레이터 생성 정책 0 · CRD 0 · 뼈대 Synced) · 최종 트리 validate PASS 39 · FAIL 0 · gitops 커밋 2건 → PR #50 · CI 대기.

## 사고·오류
- **문서 사실 오류의 연쇄**: 수정 라운드 1이 업스트림 adoc을 근거로 적은 자원 이름 두 개가 코드와 달랐고, 확인 스크립트는 폐기된 status 키를 요구했다. 코드(`KafkaResources.java` · `KafkaStatus.java` · CRD)를 정본으로 삼고 adoc은 참고로만 쓴다는 규칙을 남긴다.
- **Bash 도구의 `grep -c $'\r'`**가 빈 패턴으로 동작해 모든 파일을 "CR = 줄 수"로 보고한 적이 있다(빌더·리뷰어 모두 관측) — 바이트 위생은 `od`/`tr` 바이트 카운트로만 판정한다.
