# 003-platform-foundation T044 — 되돌릴 수 없는 한 줄과 fail-open 게이트: Vault auto-unseal (2026-09-17)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제
시크릿 원천(Vault)을 클러스터에 세우는 task다. 값을 맞추는 일이 아니라 **순서**를 맞추는 일이었다. 되돌릴 수 없는 것이 셋 있었다 — ① `vault operator init`의 출력(recovery key 3 + root 토큰), ② StatefulSet `volumeClaimTemplates`의 PVC 삭제보호 어노테이션(첫 apply에만 넣을 수 있다), ③ public 저장소 커밋 히스토리에 들어가는 KMS 키 식별자. 그리고 머지 순간부터 시계가 도는 것이 둘 있었다 — Application 전수 Healthy 단언이 init 전까지 깨지고, `svc vault`가 생기는 순간 백업 스크립트의 `--pre-upgrade` 게이트가 Vault 스냅샷 성공을 **필수**로 승격해 백업 role이 생기기 전에 주간 업그레이드 창이 열리면 업그레이드가 구조적으로 막힌다. 그래서 OpenTofu 쪽 정본을 머지 **전에** 완성해 두고, 머지 → init → 감사 → 재기동 드릴 → apply → 시드 → 백업 연결을 한 세션에 연속으로 끝내는 설계를 골랐다.

## 배운 개념
- **auto-unseal에서 recovery key는 unseal 수단이 아니다.** unseal은 KMS가 하고, recovery key는 `generate-root`·rekey 전용이다. 이걸 "봉인 해제 열쇠"로 오해하면 위험 평가가 전부 틀어진다.
- **Vault 2.0부터 `generate-root`·`rekey`는 recovery key 조각 *과* 유효한 토큰을 함께 요구한다.** 즉 "OIDC 도입 전에 Vault를 고쳐야 하면 recovery key break-glass뿐"이라는 ADR 0010 §6과 spec FR-041의 가정이 성립하지 않는다. root를 revoke하고 OIDC가 없으면 관리·복원 경로가 0이 된다(스냅샷 복원조차 권한을 요구한다).
- **seal 설정 실패는 "sealed 대기"가 아니라 프로세스 즉사다.** 키 식별자 오타·IMDS·DNS·IAM 어느 것이든 seal 설정 파싱 단계에서 `vault server`가 종료해 CrashLoop이 되고, seal-status는 `sealed:true`를 주는 게 아니라 연결 거부를 준다. "KMS 일시 장애 = sealed 대기"는 이미 살아 있는 프로세스에만 맞는 문장이다.
- **KMS 키 삭제 유예 30일은 취소 창일 뿐이다.** 삭제 예약 순간부터 복호화가 불가능하므로 "30일 동안은 복구 가능"이 아니다.
- **식별자와 자격증명은 다르다.** KMS 키 식별자와 crypto/management 엔드포인트를 public 저장소에 리터럴로 커밋해도 자격증명이 아니다 — OCI 호출 인가는 인스턴스 프린시펄의 x509 서명이고 권한 범위는 키 한정 IAM 조건이 정하며, Vault는 env 우회를 구조적으로 막는다. 대안(설정 전체를 Secret 볼륨으로)은 GitOps 추적성·self-heal·헬스 판정을 모두 깬다. 다만 되돌릴 수 없으므로 "안전하다"로 끝내지 않고 사용자 확정 항목으로 올렸다.
- **감사 장치를 stdout 하나만 두면 fail-closed다.** 감사 쓰기가 막히면 Vault가 모든 API 요청을 거부한다 — 노드 디스크 포화가 곧 전면 정지다. 보험용 두 번째 장치를 임시 파일시스템에 두는 안은 그 자체가 감사 유실 경로라 기각하고, 디스크 알림을 조기 경보로 문서화했다.
- **정적 단언은 "부분집합"으로 권한 이탈을 잡지 못한다.** 정책 경로가 `{read,list}` 안에 있는지 보는 단언은 경로가 늘어난 것을 못 잡는다. 경로 집합 동등·능력 정확 일치·bound ServiceAccount 전수 매핑으로 고정해야 한다.

## 선택과 대안
- **공개 진입점**: 차트의 Ingress 옵션 대신 순수 매니페스트 + 포트 **이름** 지정. 차트 경로는 HA 기본값이 active Service를 백엔드로 잡아 unseal 전에는 엔드포인트가 0이 되어 503 — 장애 시점에 관측 수단을 잃는다. 포트를 이름으로 쓰면 평문→TLS 전환 때 이름이 바뀌어 **눈에 보이게** 깨지고, 번호로 쓰면 조용한 502가 된다.
- **PVC 보호**: 데이터 볼륨 어노테이션만. 감사 볼륨을 켜면 어노테이션 없는 두 번째 PVC가 생겨 같은 검사가 오히려 FAIL한다. 차트의 `kubeVersion`을 명시해 기본값을 코드에 박는 안은 동작이 같은데 렌더 표면만 넓혀 기각.
- **init 실행 경로**: 운영자 워크스테이션 CLI + port-forward. 노드 셸 경로는 출력이 SSH 스크롤백과 sudo 컨텍스트를 지나고, 그 노드는 KMS 프린시펄 보유 호스트다. 브라우저 UI 초기화는 recovery key가 **다운로드 파일**로 남아 금지.
- **root 토큰**: 7번째 role을 만들어 관리 경로를 실증하고 이 task 안에서 revoke하는 안이 기술적으로 가장 깔끔했다. 그런데 동결된 문면 3곳(role 합계 6 · ADR · FR)을 동시에 위반한다 — 설계가 단독으로 내릴 수 없는 변경이라 기각했다. HCL로 `generate-root`를 무인증 허용하는 안은 보안 후퇴를 영구히 새기는 셈이라 기각. 결론: role 6만 만들고 root는 오프라인 보관, revoke는 OIDC 관리 role 실증 + quorum 드릴 뒤로 미루고 대체 경로는 converge·새 ADR로 인계.
- **이미지 고정**: 차트에 digest 키가 없어 태그 필드에 `<버전>@sha256:…`를 병기하는 것이 유일한 병기 방법이었다. kustomize의 이미지 치환은 digest를 주면 태그를 지워 병기 규약 자체를 깬다.
- **PR 분할**: 되돌리기 단위가 1인 단일 PR보다 **3분할**을 택했다 — ① 권한 축소(허용 소스 목록에서 helm 저장소 줄 제거) → ② 컴포넌트 → ③ 공개 진입점. 각 PR이 다음 단계의 선행조건을 실제 sync로 확인하게 되고, 공개 진입점을 init 뒤로 미룬 덕에 "제3자가 먼저 init해버리는" 표면이 아예 없어졌다.
- **후속 기능용 플레이스홀더**: 8경로를 지금 선점하고 값은 단일 sentinel 리터럴로 넣었다. 쓰기 토큰이 살아 있는 창에서 한 번에 끝나고 경로 오타를 조기에 잡으며, "sentinel 잔존 0 = consumer 활성화 전제"라는 불변식을 남길 수 있다.
- **X-Forwarded-For 스탠자 미도입**: 신뢰 주소 목록이 비면 래퍼가 설치되지 않지만, 설치되면 원격 주소를 보기 **전에** 헤더 부재를 검사한다 — readiness 프로브·port-forward seal-status·백업·시크릿 오퍼레이터·메트릭이 동시에 400이 된다.

## 결과와 검증
- gitops PR 3건 머지, 모노레포 4커밋(+완료 체크 1). 렌더 9장(Ingress 추가 뒤 10장) · 스키마 검증 통과 · 시크릿 스캔 0.
- helm test hook Pod가 렌더에 끼어들어(끄는 value가 없다) `helmCharts[].skipTests: true`를 채택했다.
- 기동: `tag@digest` 표기를 컨테이너 런타임이 수용(StatefulSet image ↔ pod imageID digest 일치) · 주입 webhook 0 · PDB 0 · seal-status `type: ocikms` · `recovery_seal: true` · `storage_type: raft`.
- 멱등 체크 `vault operator init "-status"` exit 2 = 미초기화. PowerShell에서 `-flag=value`는 따옴표로 싸야 통째로 전달된다(`tofu plan "-out=…"`도 같은 함정).
- auto-unseal 드릴: pod 삭제 → **8초** 만에 Ready(드릴 총 20초), PreStop 훅 실패 이벤트 없음.
- OpenTofu apply 15건(kv v2 마운트 · kubernetes auth · 정책 6 · role 6), 상태 파일 비밀 패턴 0행, 정적 단언 20건 추가로 61/0.
- 권한 스모크: 백업 role은 스냅샷 read 가능·강제 복원 엔드포인트 deny. E2E 읽기 role은 단일 경로만. 에이전트 조회 계정은 audience 지정 토큰을 자급할 수 없음(발급은 운영자 절차로 확정).
- 백업 연결: 컴포넌트 지정 env 파일을 지워 기본값으로 복귀 → 수동 스냅샷 1건(약 36 KB, age 암호화) + `--pre-upgrade` 게이트 exit 0 → 오브젝트 스토리지에 2건 확인.
- 플랫폼 하네스: cluster 31/6/11(남은 FAIL은 다음 task들의 컴포넌트) · ingress 12/0 · infra 61/0 · reboot 3/0/4.
- 공개 진입점: edge에서 Access 302 → 로그인 화면 렌더까지 확인(로그인은 하지 않음). 오리진 직접 프로브는 클라이언트 인증서 없이 `000` — 이전 task에서 켠 오리진 상호 TLS 하에서는 이것이 **정상 거절**이며, 설계에 적어둔 "노드 내부 200/307" 기대값은 그 조치 이전 기준이라 폐기했다. 대신 의도적 4xx 프로브 한 번으로 액세스 로그에 라우터·서비스·TLS 1.3·클라이언트 인증서 주체가 찍히는 것을 확인했다(양성 대조).

리뷰와 실측이 뒤집은 가정 다섯:
1. "정례 `plan`에는 sudo 권한이 필요하다" → auth backend refresh는 마운트 조회(read)라 sudo 불요. read 전용 정책 토큰으로 드리프트 확인이 가능하다(enable/disable만 sudo, 감사는 read도 sudo).
2. "E2E 읽기 role은 `vault kv get`이 preflight에서 403이라 `vault read`만 쓸 수 있다" → 실측은 **둘 다 정책 통과**(경로 미존재로 exit 2). 계약 문장을 정정했다.
3. "기동 배너에 `Seal Type` 줄이 있다" → 2.0.4에는 없다. seal 종류는 seal-status의 `type`으로 판정한다.
4. "helm 기본 `Capabilities.KubeVersion`은 v1.20" → helm 4에서는 v1.37이다(helm 3 기준 문장을 정정).
5. "OpenTofu `validate`가 locals 맵 중복 키를 잡아준다" → 잡지 않는다. 하네스 단언 하나가 유일한 방어였다.

## 다음 학습
- root revoke 이후의 관리 경로가 아직 없다. break-glass용 7번째 role과 quorum 드릴을 converge에서 정하고, 새 ADR로 ADR 0010 §4·§5·§6을 정정해야 한다(sealed 대기 → CrashLoop · 삭제 유예 → 예약 즉시 불능 · break-glass의 토큰 요구 · revoke 시점).
- 스냅샷 복원 뒤에도 그 시점의 recovery key·root 토큰이 유효한가는 실측하지 않았다(비운영·계획 창 과제). 백업의 "복원 가능성"은 아직 증명된 게 아니다.
- 감사 장치 장애 알림, 두 번째 독립 sink, 메트릭 스크레이프 주기 확정은 관측 task로 인계.
- gitops CI의 렌더 검증이 여전히 자리표시자다(helm 부재 시 fail-closed가 되는 컴포넌트가 이제 둘). 허용 helm 저장소 목록의 정적 검사도 이번 권한 축소로 생긴 공백이다.

## 사고·오류
init은 성공했다(10:27:42). 그런데 초안의 3단 블록(전사 → 검증 → 소거)을 운영자가 **통째로** 실행했다. 사람이 멈춰야 하는 지점이 주석으로만 적혀 있었고, 되가져오기 해시 검증 3건이 False로 흘렀고, `Read-Host`가 빈 입력을 받은 뒤 (3) 소거가 **무조건** 실행되어 변수가 지워지고 클립보드가 공백으로 덮였다. 재실행은 "already initialized"를 냈다. recovery key 3조각과 root 토큰이 **영구 유실**됐다 — 클립보드 기록 OFF · 전사 없음 · 히스토리 저장 없음이라, 비밀 취급 규칙이 잘 지켜진 만큼 사본도 0이었다.

근본 원인 셋: (a) 사람 동작이 주석으로만 표시됨 (b) 소거가 검증 결과에 **조건부가 아님** (c) 한 블록에 담겨 통째 실행이 가능함. 한 줄로: **주석으로 "여기서 멈춰라"는 멈추지 않는다.** 안전은 산문이 아니라 제어 흐름에 있어야 하고, fail-open 게이트는 게이트가 아니다.

마운트·정책·시드가 아직 0이었으므로 복구는 스토리지 초기화 + 재init이었다. 순서가 중요했다: PVC 삭제(`--wait=false`로 Terminating 대기) → pod 삭제 → StatefulSet이 새 PVC로 재생성(1분 44초), 강제 종료는 쓰지 않는다. 재init 전에 게이트를 세웠다 — 공개 진입점 0 · 오브젝트 스토리지에 스냅샷 0 · 비밀번호 관리자에 항목 0 · 업그레이드 Job 대기 0(즉 "잃어도 되는 상태"임을 먼저 증명).

다시 쓴 안전 블록은 같은 3단을 **코드로** 강제한다: 항목마다 `Read-Host`로 멈추고, 비밀번호 관리자에서 되가져온 값의 SHA-256이 원본과 같아질 때까지 반복하고, 4/4 일치 + 사본 토큰 `lookup` 성공일 때만 소거하고, 값은 화면에 출력하지 않는다. 재init에서 4/4로 통과했다. 이 저장소는 같은 방식(클립보드 → 즉시 삭제)으로 앞선 task에서 Argo CD 관리자 비밀번호를 이미 한 번 잃었다 — 두 번째였다. 그래서 교훈은 "다음엔 조심하자"가 아니라 "같은 절차가 남아 있는 곳을 찾아 조건부로 바꾼다"다.
