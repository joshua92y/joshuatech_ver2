# 003-platform-foundation T032 — 302는 Ingress의 증거가 아니다: 인그레스 검사에서 공허한 PASS 걷어내기 (2026-09-04)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제
T032는 US2(인그레스·오리진 보호)를 검사하는 하네스 `tests/platform/ingress.tests.ps1`을 **구현보다 먼저** 쓰고, 클러스터가 아직 없는 상태에서 FAIL이 나는 것까지 확인하는 task였다. 어려운 점은 단언의 개수가 아니라 관측 대상이 세 계층에 흩어져 있다는 것이었다. 로그인 리다이렉트는 Cloudflare edge가 내고, Ingress·인증서·Traefik 배치는 클러스터 안에 있고, 오리진 직접 접속 거부는 네트워크 경계에서 일어난다. 그리고 세 계층 모두 "아무 통제가 없어도 초록으로 보이는" 경로를 하나씩 갖고 있었다. 즉 잘못 쓰면 이 하네스가 거짓 안심을 제조하는 장치가 된다.

## 배운 개념
- **공허한 PASS(vacuous pass)**: 단언이 참인 이유가 "기대한 통제가 작동해서"가 아니라 "관측 대상이 아예 없어서"일 때다. "무엇이 실패해야 한다"는 형태의 음성 단언은 구조적으로 이 함정을 안고 있다. 아무것도 떠 있지 않은 주소가 응답하지 않는 것은 오리진 보호의 증거가 아니다.
- **Access 302는 edge에서 나온다**: Cloudflare Access 앱이 붙은 호스트는 인증되지 않은 요청을 팀 로그인 호스트(`<team>.cloudflareaccess.com` + `/cdn-cgi/access/login/…`)로 302 보낸다. 이 응답은 오리진이 무엇을 하든, Ingress가 있든 없든 나온다(2026-09-04 실측: T011의 Access 앱만으로 302). 따라서 302는 "Access 뒤에 있다"의 증거일 뿐이고, "인그레스가 구성됐다"의 증거가 아니다.
- **AOP(Authenticated Origin Pulls)** = 오리진이 Cloudflare가 제시하는 클라이언트 인증서를 요구하는 mTLS다. 이 프로젝트의 오리진 보호는 3중(네트워크 보안 규칙으로 443을 Cloudflare 대역에만 개방 · AOP · 앱 계층 JWT)이고, 인그레스 자체는 ADR 0003 D12(번들 Traefik + DNS-01 와일드카드 + proxied Full(strict) + AOP)로 정해져 있었다.
- **관측자의 위치가 무엇을 볼 수 있는지 결정한다**: 운영자 PC는 Cloudflare 대역 밖이므로 오리진에 직접 붙으려 하면 TLS 계층에 닿기 전에 네트워크 계층에서 끊긴다(curl 종료 코드 28, timeout). 즉 이 위치에서는 "직접 접속이 거부된다"만 확인되고 **AOP 자체는 관측할 수 없다**. 계층을 구분해 적지 않으면 나중에 보고서가 "AOP 검증됨"으로 과장된다.
- **curl 종료 코드는 거부와 도구 오류를 구분하지 않는다**: 3(URL 오류)·6(DNS 실패)·2(사용법)도 0이 아니다. "0이 아니면 거부"는 오타 하나를 보안 PASS로 바꾼다.
- **최소 권한 신원이 검사 방법을 규정한다**: 검사용 신원(`agent-view`)에는 Secret get이 없다(계약 §에이전트 자격). 그러면 인증서 만료를 Secret에서 읽을 수 없다. 대신 cert-manager의 `Certificate`(Ready 조건 + `status.notAfter`)를 프록시 증거로 쓸 수 있다 — cert-manager는 대상 Secret이 존재하고 유효할 때만 Ready=True로 두기 때문이다. 검사가 비밀 값을 만지지 않고도 성립한다.

## 선택과 대안
- **거부 판정** — (기각) 0이 아닌 모든 종료 코드를 거부로 인정: DNS·URL·실행 실패가 전부 보안 PASS로 위장된다. (채택) 거부로 인정할 종료 코드 화이트리스트 7·28·35·52·55·56만 PASS, 그 밖은 `unexpected curl exit N (not a refusal)`로 FAIL. PASS 근거 문자열에 "어느 계층에서 막혔는지"를 남겨 네트워크 계층 거부와 TLS 계층 거절을 사후에 구분할 수 있게 했다.
- **전제 게이트** — (기각) 직접 접속 단언을 단독으로 평가: 응답하지 않는 주소는 무조건 PASS. (채택) 대상 노드 확인(`node-1`)과 오리진이 실제로 Running이며 `role=platform` 노드에 있다는 확인(`traefik-2`)이 먼저 PASS했을 때만 `aop-1`을 증거로 인정한다(fail closed). 노드 주소 상수가 실제와 어긋나면 노드 집합을 확정하지 않으므로 뒤따르는 두 단언도 함께 FAIL한다 — 엉뚱한 주소를 두드리며 초록을 내는 경로를 막았다.
- **Ingress 증거** — (기각) 302만으로 인그레스 판정. (채택) `networking.k8s.io` Ingress의 `rules[].host` 존재를 별도 단언(`argo-2`/`vault-2`)으로 요구. Vault UI의 Ingress는 T044에서 생기므로 **그 전까지 `vault-2` FAIL이 정상**이고, 이것을 SKIP으로 감추지 않았다(SKIP은 "검사했다"는 착각을 남긴다).
- **Access 로그인 판정** — (기각) 리다이렉트 대상 호스트의 `.cloudflareaccess.com` 접미사 일치: 아무 팀 도메인이나 통과한다. (채택) 팀 도메인 정확 일치 + 로그인 경로 접두 일치. 쿼리 문자열(토큰)은 출력하지 않는다.
- **Traefik 대시보드** — 대시보드는 CRD(`traefik.io` IngressRoute)로 노출돼 검사 신원으로 읽을 수 없다. 리소스 단언을 포기하고 HTTP 302 단언만 남기고, 읽기 권한 확장은 "계약 변경 사안"으로 이월했다. 권한을 몰래 늘리는 대신 검증력의 공백을 문서화하는 쪽을 택했다.
- **게이트의 위치** — 하네스 안에는 SKIP 경로를 두지 않고 모든 전제 미충족을 FAIL로 했다. 대신 상위 러너가 kubeconfig 부재 시 스위트 전체를 SKIP한다. 게이트를 단언이 아니라 러너에 두면, 로컬 전체 검사는 초록을 유지하면서도 클러스터가 있는 실행에서는 어떤 단언도 조용히 넘어가지 않는다.
- **만료 임계** — 일수를 내림한 뒤 `> 30`이 아니라 `TotalDays > 30`(내림 없음)으로 바꿨다. 내림은 30일 갱신 창을 반나절 늦추는 쪽으로만 틀린다.

## 결과와 검증
- 단언 12개(전제 2 · Access 302 3 · 클러스터 3 · 직접 접속 거부 1 · 인증서 2)로 구성하고, 클러스터가 없는 상태에서 FAIL을 확인한 뒤 task를 닫았다(테스트 추가 `85b8b01` → 체크 `dc8d54c`).
- 리뷰가 Major 1건 + Minor 7건을 냈고 `22cafa2`로 한 번에 반영했다: 거부 코드 화이트리스트(공허한 PASS 제거), 팀 도메인·로그인 경로 고정, 노드 집합을 표류 검사 통과 뒤에만 확정, 인증서 판정을 `Certificate` 단일 경로로 일원화(Secret 직독 분기 삭제), 만료 임계 내림 제거, kubectl stderr에 섞여 나오는 kubeconfig 경로 마스킹.
- 파생 요구가 후속 task의 입력으로 빠져나갔다. cert-manager 설치(T042)에는 집계 ClusterRole 옵션을 기본값이라도 **명시값으로** 요구했다 — 이 테스트의 인증서 단언이 `view`에 집계된 `certificates.cert-manager.io` 읽기에 의존하기 때문이다. E2E 보고 문구에는 "네트워크 계층 거부, AOP 미관측"을 쓰도록 미리 못 박았다.
- 이 위치 설정은 실제로 유효했다. AOP가 라이브가 된 것은 T043(`RequireAndVerifyClientCert` 전환)이고, 강제 실효 판정은 Traefik 액세스 로그의 `TLSClientSubject` 필드로 했다. `aop-1`은 그 판정의 대체물이 아니라 보조 증거라는 위치가 확정됐다.

## 다음 학습
- 진짜 AOP 검증은 클러스터 내부 Job이나 Cloudflare 대역의 관측점에서만 가능하다(계약상 별도 자격이 필요해 이번 SP 범위 밖 후보로 남겼다). 운영자 PC 관측점으로 무엇을 증명할 수 있는지의 한계를 처음부터 계약에 적어두는 편이 낫다.
- TLS 1.3에서는 클라이언트 인증서 거절이 핸드셰이크 이후 alert로 오기 때문에 도구가 "성공"처럼 보일 수 있다(계약 §AOP 판정). 거부 코드 화이트리스트가 TLS 버전·도구 버전에 따라 흔들릴 여지가 있어, 종료 코드보다 서버 로그 필드를 1차 판정으로 두는 원칙이 옳았는지 다시 확인할 것.
- 검사 신원에 Traefik CRD 읽기를 추가할지(계약 변경)와, "음성 단언마다 전제 PASS를 요구한다"는 패턴을 다른 플랫폼 하네스에도 일반화할지.

## 사고·오류
초안(`85b8b01`)에는 스스로 만든 함정이 두 개 남아 있었다. ① 직접 접속 단언이 0이 아닌 모든 curl 종료 코드를 "거부"로 받아들였다 — 오리진 보호를 검사하겠다는 단언이 실은 "curl이 무슨 이유로든 실패했다"를 검사하고 있었다. 보안 단언에서 실패의 **이유**를 좁히지 않으면 단언이 아니라 장식이 된다. ② 인증서 단언이 먼저 Secret을 직접 읽고 Forbidden일 때만 `Certificate`로 내려가는 2단 경로였다. 계약상 검사 신원에는 Secret get이 애초에 없으니, 이 분기는 절대 쓰이지 않는 코드에 비밀 값을 다루는 위험만 얹은 것이었다. 교훈: 자격 계약이 "할 수 없다"고 못 박은 경로는 폴백으로도 남기지 않는다.
