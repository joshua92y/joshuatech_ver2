# 003-platform-foundation T042 — 와일드카드 TLS를 GitOps로 세우며 배운 "초록불이 거짓말하는 조건" (2026-09-10)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제

T041에서 Argo CD app-of-apps가 살아났지만 v2 호스트는 엣지에서 전부 526(오리진 인증서 무효)이었다. 오리진 Traefik이 내밀 인증서가 한 장도 없었기 때문이다. T042의 일은 네 단계를 GitOps로 잇는 것이다: cert-manager 설치 → ACME DNS-01 ClusterIssuer 2종(staging·prod) → 아펙스 + 와일드카드 Certificate 발급 → Traefik `TLSStore default`로 적재. 마지막에 `sniStrict`를 켠다.

제약이 설계를 지배했다. ① Let's Encrypt prod는 **같은 SAN 집합 기준 중복 발급 5/7일**이고 override가 없다 — 시행착오를 prod에서 할 수 없다. ② 서버 노드가 1대라 인증서가 끊기면 전 호스트가 동시에 죽는다. ③ 모든 변경은 PR을 거친다(ADR 0002: Git 정본·pull CD·PR 승격). 그래서 staging으로 리허설하고 prod로 승격하는 경로를 택했고, **그 승격 경로의 모양**이 이 task에서 가장 오래 고민한 지점이다.

## 배운 개념

**ACME DNS-01과 `followCNAMEs`.** DNS-01은 `_acme-challenge.<도메인>`에 TXT를 심어 도메인 지배권을 증명한다. cert-manager는 TXT를 조회하기 **전에** CNAME 체인을 따라간다(위임 패턴 지원). 그 이름에 CNAME이 남아 있으면 자기 존이 아니라 남의 존에서 TXT를 찾는다. Cloudflare는 같은 이름에 CNAME과 TXT를 동시에 보유할 수 있어(비표준 허용) 질의 타입마다 다른 답을 준다 — 사람이 TXT만 조회하면 존이 정상처럼 보인다.

**kustomize `helmCharts` 인플레이트 ≠ Argo 네이티브 helm source.** 전자는 kustomize가 helm 바이너리로 shell-out해 차트를 펼친 결과를 매니페스트로 내보내고(helm 릴리스가 생기지 않는다 — `helm list`가 비는 것이 정상), 후자는 repo-server가 차트 저장소를 직접 source로 삼는다. 표기 규칙이 정반대라는 점이 함정이다: kustomize는 OCI 레지스트리에 `oci://` 접두가 **필수**인데, Argo는 repoURL이 `oci://`로 시작하면 `IsOCI()`를 `IsHelm()`보다 먼저 평가해 `chart` 필드를 조용히 무시한다.

**Traefik의 적재 경로와 `sniStrict`.** `TLSStore`에 인증서를 넣는 길은 `defaultCertificate`와 `certificates:` 목록 두 개인데, `GetBestCertificate`는 **DynamicCerts만** 검색하므로 `sniStrict`를 켜면 `defaultCertificate` 폴백에는 도달하지 못한다. 즉 두 기능은 양립하지 않고, 와일드카드는 반드시 `certificates:` 쪽(동적 인증서)에 있어야 한다. `certificates:` 경로의 실패는 2단이다 — Secret/키를 못 읽는 1단은 로그가 남고, 파싱 실패(2단)는 **그 인증서만 조용히 탈락**한다.

**비율 기반 갱신.** `renewBeforePercentage: 33`은 "수명의 33%가 남으면 갱신"이다. 90일 인증서에서는 잔여 29.7일이고, 상시 검사가 "잔여 30일 초과"를 요구하므로 두 창이 60일마다 7.2시간 겹친다. 수명이 바뀌면 이 산수가 통째로 바뀐다.

**K3s `--egress-selector-mode: agent` + flannel `wireguard-native`.** API 서버는 admission webhook을 ClusterIP가 아니라 **엔드포인트 파드 IP:10250**으로 직접 dial하고, agent 모드에서 그 연결은 터널을 타지 않고 API 서버 노드의 호스트 netns에서 나간다. 백엔드가 `wireguard-native`면 파드 CIDR 경로의 출발 주소가 노드 private IP가 아니라 `flannel-wg` 장치 주소(그 노드 리스 서브넷의 네트워크 주소)다. `host-gw`였다면 정책에 적힌 노드 private IP가 정확히 옳았다 — **정책 작성자의 가정은 CNI 백엔드 선택 때문에 깨졌다.**

## 선택과 대안

**D1 = kustomize `helmCharts` 인플레이트**(research의 기본값은 Argo 네이티브 helm source였는데 뒤집었다). 이유는 취향이 아니라 기존 게이트였다. ① `tests/validate.sh` 검사 7.1이 `platform-<컴포넌트>` Application의 경로를 `source.path`로 뽑아 `platform/<컴포넌트>`와 정확히 비교하는데, 네이티브 helm source에는 `path`가 없어 즉시 FAIL한다 — 통과시키려면 계약과 검사 스크립트(T033·T041 산출물)를 함께 개정해야 한다. ② 검사 5.4b가 `helmCharts[].valuesInline`만 읽어 webhook 포트를 계약과 대조하는데, 값을 다른 곳으로 옮기면 이 대조가 **조용히** 사라진다. 대가도 알고 골랐다: `--enable-helm`이 저장소 전역에 걸려 어떤 kustomization이든 렌더 시각에 원격 차트를 당길 수 있고, Renovate는 `valuesInline`을 보지 못한다. 그리고 검수에서 드러난 더 큰 구멍 — `helmCharts`에는 digest 필드가 없어 `version`은 이름 참조일 뿐이고, **AppProject `sourceRepos`도 정적 검사도 인플레이트되는 차트의 출처를 보지 않는다**(validate는 `helmCharts[].repo`를 한 번도 읽지 않는다). 태그가 재푸시되면 다른 CRD·ClusterRole·webhook 설정이 들어오고 `selfHeal`이 PR 없이 적용한다 — 이 저장소에서 PR 게이트를 우회하는 유일한 경로다. ADR 0002의 "불변 digest"와 정면으로 어긋나는 예외를 문서·bump 절차로만 막고 있고, 허용 목록 단언은 T047로 넘겼다.

**D4 = 각색 D(승격을 한 커밋으로).** 원안은 `issuerRef`만 prod로 바꾸는 1줄 승격이었다. 기각한 이유는 **되돌리기의 성격**이다. 서빙 Secret 이름을 staging과 공유하면, `issuerRef` 1줄 revert가 곧 "성공한 staging 재발급이 서빙 Secret을 덮어써 전 호스트 즉시 장애"이고 `selfHeal: true`가 그것을 자동 적용한다. 그래서 전이 구간에는 **staging 전용 Secret 이름**을 쓰고 `issuerRef` + `secretName`을 한 커밋으로 승격해 그 경로 자체를 없앴다. 이 결정의 직접 근거는 상시 검사 `cert-1`이 **발급자를 보지 않는다**는 것이다 — `spec.secretName` 일치와 `Ready=True`만 보므로 staging 체인이 들어 있어도 PASS한다. 검사가 구별하지 못하는 차이는 **저장소 구조로** 구별해야 한다.

**D2 = 재귀 리졸버를 공개 리졸버 한 곳 단독**(+`dns01RecursiveNameserversOnly: true`). 두 번째 리졸버를 빼서 `dns01RecursiveNameservers` 목록이 정책 egress 허용 대상과 정확히 한 짝이 되게 했다. `Only: false`는 self-check가 권위 NS의 임의 주소로 나가 전부 드롭되므로 선택지가 아니다.

**D5 = `sniStrict`를 task 끝에서 단독 투입.** 인증서 적재가 확인되기 전에 켜면 폴백이 사라진 상태로 443이 막힌다. **D6 = webhook 출발지 add-only** — cert-manager를 API 서버 노드로 옮기는 안(kube-router가 파드 체인 머리에 `--src-type LOCAL` ACCEPT를 넣어 같은 노드면 무조건 통과한다)은 기술로는 성립했지만, 동결 문서 4곳의 배치 전제와 그 노드의 RAM 여유 때문에 기각했다 — **기술적으로 가능한 것과 지금 바꿀 수 있는 것은 다르다.**

## 결과와 검증

gitops PR 7건 + 모노레포 3건으로 끝났다. prod 와일드카드는 `rev 2`, SAN 2개(아펙스 + 와일드카드), `notAfter 2026-12-08`, 첫 갱신 ≈2026-11-08, **prod 중복 한도는 1슬롯만** 소비했다. TLSStore 적재 직후 인증 호스트가 **526 → 404**로 바뀌고 v2 호스트의 526이 0건이 됐다(v1 무영향).

검증에서 건진 두 가지. ① **머지 전 게이트를 공개 CT로 독립 확인했다** — staging 인증서는 CT에 오르지 않으므로 "발급일·만료일·발급자·SAN 2" 한 줄이 체인 진위를 확정한다. kubectl 없이 쓸 수 있는 게이트다(집계기 한 곳은 하루 넘게 보여주지 않았다 — 한 곳만 믿지 않는다). ② **회귀 경로 부재 논증** — 머지 직전 대상 호스트가 이미 526이었으므로 이 변경은 개선 아니면 현상 유지다. "되돌리기가 곧 장애"는 *좋은 상태로 못 돌아온다*는 뜻이고, 이미 나쁜 상태였다.

`sniStrict` 투입은 판별 실험 두 개로 게이트를 걸었다: SNI 일치는 정상 발급자, SNI 불일치는 `CN=TRAEFIK DEFAULT CERT` — 후자가 **`defaultCertificate` 미설정의 증거**(가릴 폴백이 없다는 확인)다. 투입 후 SNI 불일치는 `000`(핸드셰이크 거절)이 되고 일치는 그대로였다. 예상과 달랐던 실측: `tlsOptions` 변경은 `TLSOption` CR만 갱신하므로 **파드 롤아웃 0·443 순단 0초**였다(파드 나이가 그대로인 것이 정상이다). 회귀 검사는 68 → 69로 늘렸다 — 차트가 `{{- with }}`로 렌더해 `false`가 "끔"이 아니라 "미지정"이 되는 함정 때문에 리터럴 `true`를 따로 본다.

## 사고·오류

**DNS-01 107분 정체.** staging Challenge가 "DNS record not yet propagated"에 고정됐다. 원인은 존에 남아 있던 **v1 시절 `_acme-challenge` CNAME**(목적지는 이미 사라진 이름)이었고, cert-manager가 `followCNAMEs`로 그것을 따라가 있었다. 그동안 나는 캐시·정책·워크큐·컨트롤러 정지를 헛짚었다. 오진 3건: "재시작하면 풀린다"(고정된 `resourceVersion`은 status 동일 시 쓰기 생략, 로그 침묵은 재시도 로그가 `V(4)`인데 `--v=2`로 돌던 것 — 정지와 정상 재시도의 외부 신호가 **완전히 동일**했고 컨트롤러 sync 카운터 증가만이 판별 수단이었다), "egress가 안 걸린다", "솔버 Secret이 없으면 ClusterIssuer가 Ready=False다"(실제로는 Ready=True다 — ACME 계정 등록은 솔버 Secret과 무관하다). 결정적 단서도 흘렸다: 한 노드의 리솔버가 바로 그 CNAME 목적지를 "not found"로 뱉고 있었는데 "설명 안 됨"으로 넘겼다. **CNAME을 직접 조회하자는 판단은 내가 아니라 사용자가 했다.** → 런북 규칙으로 승격: **DNS-01이 pending이면 TXT보다 CNAME을 먼저 조회한다.** 이 잔재는 tofu 관리 대상에서 영구 제외된 이름이라 `plan`이 영원히 보지 못한다 — 런북이 유일한 기록 매체다. 방치했으면 **90일마다 조용히 실패하다 만료일에 전 호스트가 죽는** 형태로 모든 미래 갱신을 막았을 것이다.

**무증상 webhook 실패(VD-W).** API 서버가 webhook에 502를 받는데 파드는 Ready, Argo는 Synced/Healthy였다. kubelet 프로브는 kube-router의 LOCAL 예외로 **구조적으로 항상 통과**하기 때문에 이 실패 유형은 100% 침묵한다. 인증서가 한 장도 발급되지 않는 상태가 대시보드에서는 완전히 초록이다.

**15초를 "미적용"으로 오독.** 노드에 매니페스트를 놓고 반영까지 약 15초가 걸리는데, 그 창에서 조회하면 갱신 전 spec·`generation: 1`·옛 Job 로그가 보인다. 나는 이걸 적용 실패로 읽고 진단을 한 바퀴 돌았다. → 판정은 30초 뒤 한 번에 한다.

**10렌즈 전체 검수(원본 지적 103건)가 내 주장 7건을 뒤집었다.** ① "egress 포트 53 누수"는 정책 YAML과 kube-router 코드로 성립하지 않는다 — 응답을 요구하지 않는 UDP 프로브 1회가 거부보다 먼저 "성공"한 위양성일 수 있고, 나는 프로브 명령·프로토콜을 기록하지 않았다(재측정은 응답 요구 프로브로). ② "정적 검사가 TLSStore를 skip한다"는 오판 — 스크립트는 스키마를 넘겨 실제로 검증했고, "skipped"는 맨몸 실행 결과였다. ③ 되돌리기 경고의 **방향이 반대**였다 — 승격 커밋을 revert 하면 즉시 장애가 아니라 **조용한 만료 폭탄**이다. Traefik의 적재는 파싱만 하고 유효기간을 보지 않아 **만료된 인증서를 그대로 계속 내민다**(자체 서명을 찾는 진단은 여기서 헛돈다). ④ "TLSOption 중복 시 minVersion 소실"은 절반 오류 — 내장 기본값이 있는 설정은 집계기가 되메우고, 실제 회귀는 내장 기본이 없는 설정(`sniStrict`·`clientAuth`)에서 생긴다. ⑤ "hard refresh는 root에 걸면 무조건 틀리다"는 과일반화 → root 자신의 source가 바뀌면 root가 맞고, 기존 child의 디렉터리만 바뀌면 child가 맞다. ⑥ 갱신 비율 처방 "40%"는 90일 기준 산수였다. ⑦ 셸 인용 실패의 원인 서술이 오기였다. 초안이 "머지 차단 7건"이라 했던 것도 실제로는 **문서 2줄**이었다.

여기서 나온 일반 규칙 하나: **어떤 로그 목록도 닫힌 집합이 될 수 없다.** 지배적 실패 모드(staging 체인, 만료된 prod = 유효하지만 틀린 인증서)는 파싱에 성공해 로그를 한 줄도 남기지 않는다. "오류 로그 0건"을 적재 성공의 증거로 쓰면 안 되고, 정본 증거는 노드 내부에서 실제 핸드셰이크를 열어 발급자와 만료일을 보는 것이다. 이 task의 세 사건(CNAME · `cert-1` 거짓 초록 · webhook 침묵)은 모두 **관측 도구가 대상과 다른 경로를 본다**는 한 가지 구조였다.

절차 사고도 하나 남았다. 이 task의 설계 문서는 세션 스크래치패드에만 있다가 **보존 전에 유실**됐다(남은 것은 런북 실행 기록과 검수 보고서뿐이다). 그것이 "설계 문서는 task가 끝나는 시점에 저장소로 옮긴다"는 규칙의 계기가 됐다.
