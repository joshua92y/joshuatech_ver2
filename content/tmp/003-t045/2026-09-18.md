# 003-platform-foundation T045 — 머지가 곧 적용인 정책 · 로그인 없이 Ready가 되는 store · 기다리지 않는 상위 동기화 (2026-09-18)
> 2일차(컴포넌트 라이브 판정 → webhook 정책 실측·머지 → store 5장 → 토큰 발급 권한 축소). 시크릿 시드와 인수는 다음 세션.

## 문제
오퍼레이터를 올린 뒤 세 가지를 차례로 통과시켜야 했다. ① API 서버가 오퍼레이터의 admission webhook에 닿도록 네트워크 정책에 출발 주소 한 개를 더하는 일 — 이 정책 묶음은 자동 동기화라 **머지가 곧 적용**이다. ② Vault에 로그인하는 store 5장을 Ready로 만드는 일 — "Ready"가 진짜 로그인의 증거인지가 불분명했다. ③ 오퍼레이터가 받은 "임의 ServiceAccount 토큰 발급" 권한을 이름 5개로 좁히는 일 — 잘못 좁히면 store 5장이 한꺼번에 죽는다. 셋 다 "적용한 뒤 확인"으로는 늦는 종류였다.

## 배운 개념
- **같은 노드의 webhook은 정책 없이도 닿는다.** API 서버가 파드 IP를 직접 dial하는 구성에서, webhook 파드가 API 서버와 같은 노드에 있으면 출발 주소는 브리지 게이트웨이이고 네트워크 정책 구현체가 "노드 로컬 출발" 예외로 통과시킨다. 그래서 정책 PR을 머지하기 전에 이미 admission이 통과했다. 정책이 실제로 필요한 것은 **다른 노드의 webhook**으로 갈 때뿐이고, 그때의 출발 주소는 터널 장치에 붙은 주소(= 그 노드 파드 대역의 네트워크 주소)다.
- **실측 대상을 잘못 고르면 가짜 중단이 난다.** 설계는 "webhook 파드로 가는 경로의 출발 주소를 확인하라"고 적었는데, 그 파드는 같은 노드라 출발 주소가 브리지 쪽으로 나온다 — 기대값과 달라 멀쩡한 환경에서 절차가 멈췄을 것이다. 확인할 것은 "터널 장치의 주소"와 "**다른 노드** 파드로 가는 경로의 출발 주소"다. 설계 문서를 실행 전에 고쳤다.
- **네임스페이스를 빠뜨린 store는 로그인 없이 Ready가 된다.** 클러스터 스코프 store에서 ServiceAccount 참조의 네임스페이스를 생략하면 오퍼레이터는 "참조하는 쪽의 네임스페이스에서 찾는다(referent)"로 해석하고, store 검증 단계에서는 로그인을 시도하지 않은 채 `Ready=True / Valid`를 준다. 처음 가설은 "검증 불가 상태가 나온다"였는데 소스 판독으로 뒤집혔다 — 그 상태는 다른 provider의 권한 조회 실패에서만 나온다. 그래서 판정은 상태만이 아니라 **spec에 네임스페이스가 실제로 적혀 있는지**와 **Vault 감사 로그의 로그인 기록**으로 한다.
- **상위 동기화는 하위가 비정상이어도 그 단계에서 기다리지 않는다.** app-of-apps에서 하위 Application이 Degraded면 상위의 첫 작업은 실패하지만, 재시도는 "어긋난 것만 적용" 옵션 때문에 이미 만들어진 하위 CR을 건너뛰고 다음 단계로 간다. 남는 것은 상위의 **health**가 Degraded라는 표시뿐이다. "원천이 불가하면 상위가 거기서 멈춘다"는 계약 문장은 소스 판독으로 반증돼 고쳤다. 진짜 대기점은 health가 Progressing으로 남는 단계(Vault 자체)다.
- **권한 축소의 실패 문면은 provider마다 다르다.** 토큰 발급이 막히면 Vault 계열 store는 "서비스 계정에 묶인 시크릿을 찾을 수 없다"(TokenRequest 실패 → 레거시 방식 폴백 → 그것도 없음)로, Kubernetes 계열 store는 "토큰을 만들 수 없다"로 나온다. 한 문면만 알고 있으면 절반을 놓친다.
- **TokenRequest는 store가 가리키는 ServiceAccount의 네임스페이스에서 일어난다.** 그래서 5개 SA가 한 네임스페이스에 있으면 그 네임스페이스의 Role 하나로 덮인다. 다른 네임스페이스의 SA를 가리키는 store가 생기면 그쪽에 Role이 따로 필요하다.
- **정책의 "정확한 집합" 검사는 원본과 렌더 양쪽에서 해야 한다.** 원본 파일만 보면 렌더 단계의 이름 변경·네임스페이스 이동·List 포장으로 우회된다. 허용 주소 집합은 "포함"이 아니라 "일치"로 본다.

## 선택과 대안
- **정책 PR: 머지 전에 네 가지를 끝낸다** — 노드에서 출발 주소 실측, 비상 접속 세션 유지, 대기 중인 diff가 "주소 한 개 추가"뿐인지 확인, 하네스 단언 강화. 자동 동기화 묶음에는 "머지 후 확인"이 없다.
- **store PR과 권한 축소 PR을 분리.** store가 Ready가 안 될 때 원인이 store 정의인지 권한인지 가르기 위해서다. 대가는 두 머지 사이의 노출 창(약 22시간)이고, 이 구간에는 완화 수단이 없어 기록으로 남겼다.
- **권한 축소 뒤의 판정은 "5분 관찰"이 아니라 "전이 시각 불변"으로.** 관찰 창 동안 자리를 지키는 대신, 며칠 뒤 store 5장의 상태 전이 시각이 최초 Ready 시각 그대로인지를 봤다 — 한 번도 뒤집히지 않았다는 더 강한 증거다.
- **축소가 닫는 범위를 좁게 적는다.** 닫은 것은 TokenRequest 경로다. 오퍼레이터가 전역 Secret 생성·읽기를 갖는 한 레거시 SA 토큰 경로는 남는다 — 이 종류 오퍼레이터의 고유 잔여 위험으로 문서에 남겼다.

## 결과와 검증
- 컴포넌트 라이브 판정: server-side dry-run 양성(종료 코드 0 + 생성 메시지)과 음성 대조(webhook이 거절 문면으로 응답) 둘 다 확인 — "오류 없음"이 아니라 "webhook이 실제로 응답함"을 본 것이다. 드리프트 없음, 권한 조회 기대값 일치.
- 정책 PR: 노드 실측으로 터널 장치 주소 = 다른 노드 파드 경로의 출발 주소 = 파드 대역 네트워크 주소임을 확인. 대기 diff는 객체 1개 · 주소 1개 추가. 머지 뒤 하네스의 해당 단언이 FAIL → PASS.
- store 5장 `Ready / Valid` + Vault 감사 로그에 role별 로그인 기록. 정적 검사에 store 전용 검사(위치 · 인증 방식 · referent 금지 · 참조 허용 네임스페이스 집합)를 추가했다.
- 권한 축소: 렌더 차이는 ClusterRole의 규칙 1개 제거 + Role·RoleBinding 추가뿐, 렌더 전체에서 토큰 발급 규칙은 1건. 오퍼레이터 파드 재시작 없음. store 5장은 축소 전후로 한 번도 전이하지 않았다.

## 다음 학습
- 시드: 라이브 Secret 값을 화면·파일·클립보드 기록에 남기지 않고 원천으로 옮기는 절차(파이프 복사 · 되읽기 해시 · 첫 쓰기 CAS).
- 테스트용 ExternalSecret으로 인수 의미론 실측 — ownerReference 부재, 열거되지 않은 키의 운명, Secret을 지웠을 때 재생성까지의 시간.
- 노드 간 webhook 경로는 여전히 실측되지 않았다 — 데이터 노드에 webhook이 생기는 컴포넌트에서 확인.

## 사고·오류
- **설계 문서의 실측 지시가 틀렸다**(위 "실측 대상" 항목). 운영자에게 넘기기 직전에 경로를 머릿속으로 따라가 보다 발견했다. 절차서의 "기대값과 다르면 중단"은 기대값이 틀리면 그대로 가짜 중단이 된다.
- **계약 문장 두 개가 소스 판독으로 뒤집혔다**(상위 동기화 대기 · store 검증 상태). 둘 다 "그럴듯한 추론"이었고 문서 어디에도 근거가 없었다. 계약을 먼저 고치고 매니페스트 주석을 맞췄다.
- 권한 축소 PR의 리뷰 에이전트가 결과 없이 멈췄다. 기다리지 않고 핵심 세 가지(규칙 위치 · 렌더 차이 · 정적 검사)를 직접 확인한 뒤 진행했다. 검수 단계가 조용히 죽으면 "지적 0건"처럼 보인다 — 성공한 검수자 수를 먼저 센다.
- 조회 전용 토큰은 8시간, 클라우드 검증 세션은 60분 수명이라 긴 작업 중 두 번 끊겼다. 판정 직전에 수명을 먼저 확인한다.
