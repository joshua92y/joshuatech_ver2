# 003-platform-foundation T045 — 인수 판정과 파드 교체를 분리하는 운영 블록 (2026-09-22)

## 문제

터널 자격의 인수 판정과 커넥터 교체를 한 번에 수행하던 운영 블록은 재실행 안전성을 사람이 옮겨 적는 기록에 의존했다. 중단된 실행이 그 기록을 잃거나 인수 흔적이 지워지면, 판정을 다시 하려던 실행이 추가 교체로 이어질 수 있었다. 여러 번의 검수에서 같은 계열의 문제가 반복돼 작업 경계를 바꾸기로 했다.

## 배운 개념

- 읽기와 변경을 분리하면 판정 블록을 다시 실행할 때 부작용이 없는지 독립적으로 검증할 수 있다. 소스의 AST 검사, 외부 명령 모의의 변경 동사 거부, 모든 시나리오의 변경 기록 검사로 서로 다른 층을 확인한다.
- Secret을 환경 변수로 읽는 컨테이너는 파드가 교체될 때뿐 아니라 같은 파드 안에서 재시작될 때도 현재 값을 읽는다. 남은 커넥터가 옛 값을 유지한다는 전제에는 재시작 전까지라는 시간 제한이 있다.
- 삭제 요청이 서버에 도착한 뒤 응답만 유실될 수 있다. 따라서 요청 시도 기록은 외부 호출보다 먼저 남겨야 하며, 결과를 모르는 상태에서 삭제를 반복하면 안 된다.
- 필수 CI 이름이 녹색이어도 실제 검증 본체를 실행했는지는 별도로 확인해야 한다. 로컬 렌더와 계약 검증 결과를 CI의 비밀 검사 결과와 구분한다.
- 외부 CLI 모의가 입력 문법을 검사하지 않으면 실제 CLI에서 거부되는 명령도 정상 경로로 통과시킬 수 있다. 지원 문법을 공식 파서와 대조하고, 잘못된 식을 모의에서도 거부하도록 해야 한다.
- 복구 안내는 오류 원인뿐 아니라 현재 접근 가능성에 맞아야 한다. API까지 끊긴 상황에서 API를 먼저 조회하는 블록을 실행하라고 하면 복구 인계가 다시 막힌다. 정적 파일의 비상 절차로 바로 갈 수 있어야 한다.
- CLI의 오류 원문을 버리면 비밀 노출은 막아도 원인 구분을 할 수 없게 된다. 표준 출력과 오류 출력을 메모리에서 분리해 받고, 외부에는 고정된 결과 코드만 내보내면 진단 가능성과 비노출을 함께 유지할 수 있다. 로컬 리스너 접속, API 인증, 발급 권한, 실제 자격 발급은 각각 다른 증거다.

## 선택과 대안

- 인수 블록은 캡처·머지 대기·판정까지만 수행한다. 드릴 블록은 해시·객체 식별자를 다시 확인한 뒤 운영자가 타자한 대상 한 개만 교체한다. 복구 블록은 값 복구만 맡는다.
- 이전 드릴 상태를 접두어로 잇는 체계는 제거한다. 이미 교체된 파드로 보이면 경고와 별도 확인을 요구하되, 그 추정을 영구적인 실행 잠금으로 취급하지 않는다.
- 검수의 목적은 통과 숫자를 유지하는 것이 아니라 각 안전장치의 의미를 보존하는 것이다. 이동한 검사와 구조 제거로 불필요해진 검사를 구별해 기록한다.

## 결과와 검증

- 분리 전 기준 기록은 하네스 121개 통과였다. 이번에는 구현 전에 쓰기 금지 검사를 추가하자 기존 인수 블록의 삭제 경로가 실패해 RED를 확인했다.
- 분리 뒤 최종 하네스는 구현자와 컨트롤러의 별도 실행에서 모두 122/122, 정적 검사 실패 0을 확인했다. 실제 출력 조각을 추출한 대화형 bash 로컬 모의 3건도 포함된다.
- 독립 검토의 다섯 지적과 복구 인계의 남은 갈래를 수정했다. 최종 코드 검토는 Approved / Approved, 잔여 지적 0건이다. 삭제 대상이 남은 과도 상태와 API가 완전히 끊긴 상태를 각각 반례로 확인했다.
- 변이 전수는 223/223을 탐지했고 잠금 위험 표식 127개도 모두 탐지했다. 모든 결과에 실제 정적 검사 또는 시나리오 실패 근거가 있음을 감사했다. 결과 분류기도 보강하고 순차·병렬 각 6개 대조를 통과했다. 원시 종료 코드가 미저장이었던 과거 실행은 완료 요약으로 재평가했다는 한계를 구별했다.
- GitOps 기본 검증은 24 PASS / 0 FAIL / 기존 경고 4개, 부정 사례 검사는 44/44였다. 블록과 검증 보고서, 문서 세 곳을 각각 저장소의 한정된 커밋으로 보존했다.
- **라이브 인수(운영자 입회)**: 머지 전 기준값 캡처와 비밀번호 관리자 원본의 해시 대조가 일치했고, 머지 뒤 약 3분 만에 동기화됐다. 판정 블록은 값·객체 식별자 불변 · 소유 참조 없음 · 관리 흔적 두 가지(라벨·데이터 해시) · 추적 정보 미복사 · 커넥터 불변을 모두 통과했고, 클러스터 변경은 0건이었다.
- **라이브 드릴(운영자 입회)**: 실행 직전에 다른 에이전트가 이어받아 블록 전문·모의 하네스·라이브 상태를 독립으로 다시 확인한 뒤 진행을 판단했다. 두 커넥터의 시작 시각이 같아 이름 순서로 한쪽이 대상이 됐다. 게이트를 모두 통과한 뒤 커넥터 1개를 교체했고, 새 커넥터가 약 30초의 스케줄 대기 뒤 준비 상태가 되어 터널 등록 로그를 남겼다. 남은 커넥터는 재시작 없이 그대로였고, 클러스터 API와 노드 SSH 새 연결 모두 정상이었다. 클러스터 변경은 의도한 삭제 1건이다. 이어서 돌린 라이브 하네스에서 인수 관련 단언 네 개가 모두 통과했다 — 그중 하나는 인수 전에는 "두 번째 인수 정의 없음"으로 기대대로 실패하던 테스트 선행 단언이다. 두 번째 커넥터는 교체하지 않았다.
- 운영자는 조회용 단기 자격을 갱신하던 중 발급 실패를 보고했다. 별도 진단의 인증·발급 권한·대상 존재 조회는 모두 통과했다고 보고했지만, 최초 발급 실패의 원인은 아직 확인되지 않았다. 로컬 갱신 보조 파일은 실제 자식 프로세스를 사용하는 모의 19건으로 경고와 토큰의 분리, 실패 시 기존 파일 보존, 엄격한 개행 검사, 시간 초과 뒤 프로세스 종료를 확인했다. 운영자 재실행은 발급·저장 성공으로 끝났으며, 에이전트도 허용된 조회 자격의 신원과 실제 API 접근 성공을 확인했다. G4 전 상태는 노드와 터널 파드 각 2개 Ready, 터널 재시작 각 0, 저장소 연결 5개 유효, 애플리케이션 22개 Synced/Healthy였다. 이 조회는 Secret의 값 대조나 G4 인수 판정을 대신하지 않는다.

## 다음 학습

- 마무리 단계에서 문서·전체 검사를 정리하고 작업을 닫는다.
- 교체 블록을 토큰 회전 작업에서 다시 쓰기 전에 아래 「사고·오류」의 스케줄 대기 행 분류를 고치고, 그 상태를 재현하는 시나리오를 하네스에 넣는다.
- 모의가 "항상 완전한 응답"만 돌려주면 과도 상태(스케줄 대기·종료 중)의 분기가 검증되지 않는다. 모의에 과도 상태를 넣는 방법을 다음 블록부터 기본으로 둔다.

## 사고·오류

- 초기 분리판의 모의가 지원하지 않는 JSONPath 문법을 허용해, 테스트가 녹색이어도 실제 정상 경로가 막히는 결함을 놓쳤다. 공식 파서 대조와 문법 거부 회귀를 추가했다. 운영 환경에서 발생한 장애가 아니라 오프라인 검수에서 발견한 개발 오류다.
- **라이브 드릴에서 블록의 오분류가 드러났다.** 새 커넥터가 스케줄 대기인 동안 파드 조회 결과는 이름만 있고 나머지 필드가 빈 행으로 나온다. 블록의 행 형식 검사가 이것을 형식 오류로 처리했고, 대기 루프는 그 예외를 "조회 실패 — 터널 순단일 수 있다"는 경고로 두 번 출력했다. 처리는 안전 쪽(남은 커넥터 미접촉 · 기한까지 대기)이었고 결과도 정상이었지만, 가장 긴장된 순간에 운영자에게 틀린 원인을 보여 줬다. 모의가 네 필드가 모두 채워진 행만 돌려줘서 122개 시나리오와 223개 변이가 이 상태에 한 번도 닿지 않았다. 스케줄 대기의 원인은 옛 커넥터가 종료되는 동안 같은 노드에 둘 수 없게 한 반친화성 규칙이었다.
- 전체 저장소 검사는 필수 환경 변수 부재로 OpenTofu 검증 슬롯이 실패했다. 다른 검사 결과와 구별해 보존하고, 운영자 환경에서 확인할 항목으로 남긴다.
- 초기 자격 갱신 보조 파일이 오류 출력을 폐기해 실제 실패 원인을 확인할 수 없었다. 오류 원문을 요청하는 대신 고정 코드 진단을 마련하고, 갱신 요청도 두 출력 스트림을 별도로 받도록 보완했다. 여러 실행 파일이 검색되는 로컬 환경에서는 실행 경로 하나를 명시적으로 선택해야 한다는 점도 모의 과정에서 확인했다.
