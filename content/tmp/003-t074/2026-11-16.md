# 003-platform-foundation T074 — pod 이미지 발행과 dev 자동 bump: 「될 것 같은」 CI 안전장치를 소스와 변이로 확인하기 (2026-11-16)
> 설계 확정 · Environment 음성 탐침 · seed PR · 빌드와 수정 세 라운드 · 구현 커밋까지. push · 통합(main 머지) · VD-5 실측은 다음 날 파일에 적는다.

## 문제
main에 들어간 pod 코드를 arm64 이미지로 만들어 공개 레지스트리에 올린다(push 전에 단언 · attestation · 자기 검증). 그다음 gitops 저장소의 dev overlay digest를 봇 PR로 바꿔, 사람의 행동 없이 자동 머지되게 한다. 조건은 넷이다. 발행은 main에서만 한다. 봇은 digest 한 줄만 바꾼다. 실패하면 자기 흔적(PR · 브랜치)을 치운다. 그리고 「사람 없이 자동 머지된다」는 가정 자체(VD-5)는 실제로 재서 정한다. 기능 브랜치가 아직 main에 없으므로, 재려면 기능 머지 전에 한 번 통합해야 했다(사용자 결정).

## 배운 개념
- **CI 러너의 취소 신호는 스텝 프로세스 하나에만 간다.** 러너 소스(프로세스 호출 모듈)를 읽어 보니, 취소 · 시간 초과 때 SIGINT → 7.5초 → SIGTERM → 2.5초 → 강제 종료를 스텝 셸의 PID 하나에 보낸다(프로세스 그룹이 아니다). 그래서 `run: bash 스크립트`면 신호는 부모 셸에만 가고 스크립트는 고아로 남는다 — 정리 trap이 돌지 않는다. 늦게라도 돌면 이미 post 단계가 토큰을 폐기한 뒤라 정리도 실패한다. 해법은 `exec bash 스크립트`로 같은 PID를 받는 것이다. 정리 중에는 신호를 무시해 10초 창을 다 쓴다. bash는 전경 자식이 끝난 뒤에야 trap을 돌리므로, 기다림은 `sleep & wait`로 한다.
- **줄 단위로 YAML을 읽는 정적 검사는 GitHub이 읽는 것과 다른 것을 볼 수 있다.** 리뷰어가 사본에 변이를 넣었다 — 따옴표 키 · `key :` · 흐름 꼴 · 0칸 주석 · 줄 끝 주석 뒤에 숨긴 job · 값 있는 줄 아래의 이음 줄 · 접는 블록 머리 `>` · 줄 구분 문자. 그 사본에서 정적 검사 48개가 모두 통과했다(`continue-on-error` · `container:` · 스텝 env 주입을 놓쳤다). 고친 방법은 두 갈래다. 하나는 맵 단언을 「키 집합 정확 · 판독 못 한 줄 0 · 더 깊은 줄 0」으로 바꾼 것이다. 다른 하나는 워크플로가 쓸 수 있는 문법 자체를 좁히는 문법 단언이다(키는 따옴표 없는 꼴 · 블록 머리는 `|`만 · 흐름 꼴 · 앵커 · 별칭 금지).
- **오래된 실행의 재실행이 배포를 되돌릴 수 있다.** main 실행은 직렬로 돈다. 그래도 운영자가 옛 실패 실행을 다시 돌리면, 그 실행이 가진 옛 digest로 dev를 덮는다. 그래서 bump 앞에 「낡은 실행 가드」를 둔다. 원천 커밋과 main을 비교해, main이 앞서 있고 그 사이에 발행 경로가 바뀌었으면 bump하지 않는다. 판정할 수 없으면(뒤처짐 · 갈라짐 · 바뀐 파일 300개 이상 · 응답 꼴 오류) 멈춘다. 경로 판정은 워크플로의 경로 필터와 같아야 한다 — `*`는 `/`를 넘지 않는다. 처음 구현은 셸 패턴이라 넘었다.
- **응답 필드가 빠지면 조용히 「변화 없음」이 된다.** yq는 없는 필드의 길이를 0으로 내고, 없는 목록을 순회하면 빈 출력과 함께 성공한다. 그래서 compare 응답에 파일 목록이 빠지면 가드가 열린 쪽으로 통과했다. 꼴(시퀀스인지)을 먼저 본다. 이 규칙을 넣기 전에, 실제 API가 「동일」일 때도 빈 목록을 준다는 것을 GET으로 확인했다(정상 경로를 막지 않게).
- **패턴 일치는 생각보다 넓다.** `git ls-remote 원격 refs/heads/<b>`는 꼬리 일치라 `refs/heads/x/refs/heads/<b>`도 맞는다. 짧은 ref 이름(`main`)은 같은 이름의 태그로 풀릴 수 있다. 그래서 있음 · 없음은 출력에서 ref 이름이 정확히 같은 줄만 세고, 비교의 머리는 `refs/heads/main`으로 준다.
- **봇 편집은 「값만」 바꾼다.** 이미지 편집 명령을 탐침해 보니 newName 줄을 지우고 파일 전체를 재서식했다 — gitops의 봇 경로 lint와 승격 스크립트가 깨진다. 그래서 digest 줄 하나의 64자리 hex만 바꾼다. 확인은 셋이다: numstat(파일 하나 · 1줄 삭제 1줄 추가) · hex 밖 글자가 같음 · 다시 읽은 값.
- **auto-merge의 「고정」은 거는 순간의 head다.** `--match-head-commit`은 auto-merge를 거는 시점의 head만 확인하고, 그 뒤의 이동은 막지 않는다. 그래서 머지될 때까지 조회하며 head · base를 보고, 머지 뒤에는 결과(부모 하나 · 한 줄 교체 · digest · gitops main에 들어갔는지)를 대조한다.
- **출력 위생.** 외부 명령이 고른 글자(gh 출력 · 오류 · 파일 이름)는 형식을 확인한 값만 찍는다. 아니면 무작위 토큰으로 연 stop-commands 구간 안에서만 찍는다 — 러너는 stderr의 워크플로 명령도 해석한다. 취소가 그 구간을 찍는 도중에 오면 구간부터 닫는다.

## 선택과 대안
- **VD-5를 언제 재나**: 기능 머지 전에는 main 전용 발행이 돌지 않는다. 대안은 셋이었다. (가) 단계 통합(T074 한정 — merge commit · 이후 main 발행이 필요한 지점마다 다시 묻는다) (나) 마지막에 한 번 통합 (다) 발행 조건을 기능 브랜치까지 넓힌다. 사용자가 (가)를 골랐다 — (다)는 검증 전 이미지를 공개 레지스트리에 올리는 길을 연다.
- **빌드 캐시 없음**: main 범위의 캐시는 다른 main 워크플로도 쓸 수 있고 서명이 없다. 빌드 시간을 대가로 냈다.
- **BuildKit 판**: 최신 패치는 발행 14일이 안 되어 쓰지 않았다. 리뷰가 유지한 판도 권고 두 건에 해당한다는 것을 찾았다(권고의 판 범위 표기가 틀렸다). 이 빌드에는 도달 경로가 없다고 보고 받아들였고, 갱신은 뒤 과제로 넘겼다.
- **취소 신호를 스크립트에 닿게 하기 — exec vs 부모 셸에서 전달**: exec가 가장 단순하다. 이미지 단언 스크립트는 외부 부작용이 없어 그대로 `bash`로 둔다.
- **닫기 실패 뒤 머지됨 · 대조 통과 = 성공**: 종료 코드의 정의(0 = 머지 확인)에 맞춰 성공으로 둔다. 앞의 오류 주석과 요약의 「머지 확인 — [코드] 판정 뒤」 줄은 남는다.
- **되돌림 쌍(순 diff 0)은 낡음으로 세지 않는다**: 같은 소스를 다시 빌드한 digest가 올라갈 수 있지만, 의존성이 고정되어 있어 사실상 같은 이미지다 — 받아들인 대가로 적었다.

## 결과와 검증
- Environment 보호 규칙의 거부 쪽 음성 탐침: main이 아닌 임시 브랜치의 production job이 러너 배정 전에 거부됐다(PASS). 탐침 브랜치는 지웠다.
- seed PR(gitops dev overlay의 첫 이미지 항목 · 자리 값 digest): 검사가 모두 초록이다. 머지는 운영자 몫으로 기다린다.
- 하네스: 정적 단언 28 + 실행 사례 38(가짜 gh · docker · git + bare 원격 픽스처) = 66 통과 · 건너뜀 0. 라운드마다 옛 파일로 RED를 먼저 보이고 GREEN으로 갔다(48 → 64 → 65 → 66).
- 변이: 73개 모두 겨냥한 단언에서 빨강이다. 리뷰어가 만든 우회 사본 40건도 이제 모두 빨강이다(처음에는 8건이 통과했다).
- actionlint · zizmor · gitleaks 모두 0. 리뷰 두 렌즈(계약 · 빌드 가능성 / 보안 · 공급망)는 수정 세 라운드 뒤 approve.

## 사고·오류
- 컨트롤러가 처음 그린 취소 처리는 실제 러너에서 돌지 않는 것이었다. 시험은 스크립트 안의 trap만 증명했고, 신호가 그 프로세스에 닿는지는 보지 않았다. 빌더가 러너 소스로 찾았다. 신호 · 시간 초과처럼 실행 환경이 주는 입력은 그 환경의 소스로 전달 경로부터 확인한다.
- 그 소스를 읽다가 컨트롤러가 구멍을 하나 더 찾았다. 실패 처리의 정리 도중에 취소가 오면 정리를 버리고 끝났다 — 첫 수정 라운드의 trap 설계가 「지금 정리 중인가」를 보지 않았다.
- 계약 문장 「실패 갈래(취소 포함)에서는 정리 … 그사이 머지됐으면 대조」는 받아들인 편차(취소 중 머지는 메모만)를 반영하지 못해 재검토가 잡았다. 편차를 받아들일 때는 계약 문장도 같이 고친다.
- 정적 검사 첫판은 문서에 「정확히 비교」라고 적어 놓고 실제로는 부분 문자열 · 거부 목록으로 비교했다(검증 줄 · yq 설치 본문 · 데몬 플래그). 구현이 바뀐 뒤 설계 표의 문장도 갱신하지 않아 재검토가 잡았다.
