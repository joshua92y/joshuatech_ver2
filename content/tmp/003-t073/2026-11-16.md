# 003-platform-foundation T073 — identity-admin 시드와 닫기: 운영자가 손으로 돌리는 명령의 실패 안내까지 시험으로 붙들기 (2026-11-16)
> 빌드 마지막 조각(시드 명령 · 권한 저장소 클라이언트)과 과제 닫기. 조각 ⓪–⑥은 앞 날짜 파일에 있다.

## 문제
운영자가 한두 번 손으로 돌리는 시드 명령을 만든다. 이 명령은 정본(DB의 테넌트 · 멤버십 둘)을 쓰고, 그 파생 둘(IdP의 그룹 소속 · 사용자 속성, 권한 저장소의 관계 튜플)을 쓴다. 순서는 먼저 고정해 둔 인수 시험이 정했다 — IdP 그룹 조회(읽기) → DB(한 트랜잭션) → IdP 사용자 조회 → IdP 쓰기 → 권한 저장소 쓰기. 이 조각이 끝나면 인수 시험 76개가 모두 초록이어야 하고, 과제 전체의 닫기(pod 전체 실행 · 템플릿 하네스 · CI 드리프트 검사 · arm64 이미지 탐침)도 여기서 한다.

## 배운 개념
- **정본 먼저 · 파생 나중이 고정되면, DB 앞의 방어선은 인자 꼴뿐이다.** 사용자 조회에서 반드시 실패할 식별자(대문자 UUID · 관리 화면 주소의 숫자 번호 · 사용자 이름)도 그 판정이 DB 커밋 뒤라 멤버십 행을 남긴다. 명령은 그 행을 지우지 못한다. 그래서 식별자가 IdP 사용자 uuid의 소문자 정규형인지를 DB 앞에서 본다. 고쳐 쓰지 않고 거부한다 — 운영자가 무엇을 붙여 넣었는지 다시 보게 하려는 것이다.
- **「다시 실행하면 마저 쓴다」는 일시 오류에만 참이다.** 파생 단계가 멈추면 DB 행은 남는다. 처음에는 모든 실패 문구 끝에 「다시 실행하면 마저 쓴다」를 붙였다. 그런데 사용자를 찾지 못함 · 4xx · 다른 테넌트의 속성 같은 실패는 다시 돌아도 같은 자리에서 멈춘다. 꼬리를 오류의 일시성(429 · 5xx · 연결 · 시간 초과 · 마감)으로 갈랐다. 일시면 「다시 실행」, 그 밖이면 「인자 · 상태를 고친 뒤 다시 실행 — 틀린 인자의 흔적은 런북으로 지운다」다.
- **고친 실패 안내도 시험이 붙들어야 한다.** 꼬리를 나눈 첫 수정의 시험은 열두 raise 자리 가운데 셋과 일시 종류 하나(5xx)만 봤다. 그래서 「사용자 여럿」의 꼬리를 바꾸거나 권한 저장소의 꼬리를 한쪽으로 몰거나 「5xx만 일시」로 판정을 좁혀도 시험이 초록이었다. 오류 종류 전부를 꼬리 고르기에 넣는 단위 표 하나와 통합 사례 몇을 더해 닫았다. 그래도 하나가 남았다. 꼬리 고르기 함수를 시험해도, 호출 자리 셋(그룹 조회 · 소속 쓰기 · 속성 쓰기)이 그 함수에 어떤 꼬리 쌍을 넘기는지는 따로였다. 호출 자리마다 일시 하나 · 일시 아님 하나를 주입하는 사례를 더해 닫았다.
- **시험 주석이 가리키는 계약 문장이 없으면 주석보다 계약을 의심한다.** 시험 주석은 「429 · 5xx · 연결 · 시간 초과 · 마감만 일시」를 데이터 모델 문서에서 인용한다고 적었는데, 그 문서에는 「일시 오류」라는 말만 있고 정의가 없었다. 정의는 다른 계약의 IdP 행에만 있었고, 권한 저장소 호출의 일시 판정은 어느 계약에도 없었다. 주석의 출처를 바꾸지 않고, 데이터 모델 문서에 정의 문장(두 외부 호출 공통 · DB 앞 실패는 일시 여부와 무관하게 「DB는 쓰지 않았다」)을 더했다. 그런데 그 문장의 「DB 앞 실패」는 같은 문단이 든 다른 DB 앞 거부(인자 꼴 · 설정 꼴 · 표준 입력 · 환경 설정)까지 덮었다 — 그 문구들에는 이 꼬리가 없다. 다음 검증이 이것을 찾아, 범위를 그룹 조회 단계로 좁히는 괄호를 더했다. 시험 주석이 인용하는 앞 글은 그대로 두어 인용이 글자 그대로 남게 했다.
- **정규식 검사는 앵커까지 시험한다.** 「소문자 uuid 꼴이 아니면 거부」에 더한 사례 셋(대문자 · 숫자 · 64자 hex)은 모두 앞 8–9자 안에서 꼴이 어긋났다. 그래서 `fullmatch`를 `match`로 바꿔도 셋 다 여전히 거부됐다. 정규형을 부분 문자열로 품은 사례(uuid 뒤에 한 글자 · 튜플 꼴 `user:` 접두)를 더해야 앵커가 고정된다.
- **「출력이 한 줄뿐」은 두 스트림을 다 본다.** 성공 출력이 접두 줄 하나뿐이라는 단언이 stdout만 봤다. 그래서 그 줄 뒤에 표준 오류로 접속 URL을 찍는 변이가 살았다. 계약이 말하는 범위는 「명령 출력(stdout · stderr)」이다.
- **명령 단위 실패와 생존 신호는 따로 논다.** 30초 재적용은 키 쓰기를 묶음으로 보내고 명령마다 결과를 받는다. 마지막 명령은 「방금 다녀갔다」 신호 키다. 권한 규칙이 폐기 키만 막으면 신호 키는 써져서 값이 전진한다 — 쓰기가 실패하는데 생존 신호는 멀쩡하다. 반대로 메모리 한도나 읽기 전용 같은 서버 상태는 신호 키 쓰기도 막는다. 그래서 운영 절차는 신호 값이 전진하는지보다 먼저 실패 줄을 보고, 오류 클래스로 원인을 가른다(권한 오류면 권한 규칙, 그 밖이면 서버 상태).
- **터미널 판정은 컨테이너 쪽 입력을 본다.** 토큰을 표준 입력으로 받을 때 입력이 터미널이면 읽기 전에 거부하게 했다. `exec -it` 습관이면 친 토큰이 화면에 찍히기 때문이다. 다만 `-t` 없이 `-i`만 주고 손으로 치면 컨테이너 쪽 입력은 파이프라 이 검사를 지나고, 로컬 터미널은 친 글자를 화면에 보인다. 이 검사는 `-t` 습관만 잡는다. 실제 방어는 README의 꼴(화면에 찍지 않는 읽기 → 셸 내장 출력으로 파이프 → 변수 지우기)이다.
- **위험한 대상에는 닫힌 쪽으로 판정한다.** 이름으로 찾은 IdP 그룹에 소속을 쓰기 전에, 그 그룹이 관리자 그룹이 아닌지를 본다. 관리자 여부 필드가 정확히 거짓일 때만 쓴다. 필드가 없거나 비었거나 참이면 거부다 — 관리자 그룹에 소속을 쓰면 두 사용자가 IdP 관리자가 된다.
- **설정 꼴은 쓰기 앞에서 본다.** 권한 저장소의 store id는 호출할 때 경로 성분 꼴을 보고 거부했다. 그런데 그 호출은 일곱 단계 가운데 마지막이라, 틀린 값이면 DB와 IdP를 다 쓴 뒤 매번 같은 자리에서 멈춘다. 같은 정규식 상수를 DB 앞 단계에서도 쓰고, 두 검사가 같은 꼴인지를 시험이 고정한다.
- **재생성 절차의 git 함정(문서로 확인).** 충돌이 없는 cherry-pick은 바로 커밋되어 `--abort`가 듣지 않는다. 그래서 `--no-commit`으로 가져와 손 수정 블록을 본 뒤 커밋한다. 되돌리기는 `reset --hard HEAD`다(가져오기 전에 작업을 커밋해 둔다). 더러운 worktree는 `--force` 없이 지워지지 않는다. 순정 렌더 커밋에는 `git add -A`가 필요하다.
- **무엇을 다시 돌릴지는 그 검사의 입력으로 정한다.** 닫기 뒤에 시험 파일만 바뀌면 pod 전체 실행은 다시 돈다. arm64 이미지 탐침은 이미지 빌드 컨텍스트의 허용 목록(패키지 · 관리 진입점 · 의존 선언 · 잠금 · 공용 라이브러리)이 그대로이면 다시 돌지 않는다 — 그 판단은 파일 해시 대조로 남긴다.

## 선택과 대안
- **식별자를 고쳐 쓰기 vs 거부**: 소문자로 바꿔 주면 편하지만, 운영자가 잘못 붙여 넣은 다른 값(다른 사용자의 식별자 조각)도 조용히 받아들인다. 거부하고 문구에 값을 싣지 않았다.
- **운영 환경에서 IdP 쓰기 플래그가 거짓이면 오류로 멈추기**: 설계에 없는 새 정책이라 들이지 않았다. 출력에 환경 이름을 싣고, README에 운영 시드의 기대값(첫 실행 `written` · 재실행 `unchanged`)을 적어 어긋나면 운영자가 알아보게 했다. 첫 방어선은 배포 렌더 확인이다.
- **환경 설정이 없을 때**: 출력 줄을 만들 때 읽으면 DB와 파생을 다 쓴 뒤 출력 없이 죽는다. 읽기 · 쓰기 앞에서 읽고 없으면 거부한다(폐기 명령과 같은 판정).
- **꼬리 고르기의 시험 — 단위 vs 통합**: 통합 사례만으로는 오류 종류(연결 · 시간 초과 · 마감 · 잘못된 요청 · 너무 큰 응답 …)를 다 만들기 어렵다. 비공개 함수를 직접 부르는 단위 표 하나를 더했다. 기대값은 구현의 상수를 가져와 계산하지 않고 계약 문장대로 적었다 — 가져와 계산하면 동어반복이다.
- **운영 문서에 적을 오류 클래스**: 권한 오류는 실제 서버로 잰 클래스 이름을 적었다. 메모리 한도 · 읽기 전용은 그 서버의 응답 문구를 재지 않았으므로 클래스 이름을 적지 않고 「그 밖의 클래스」로 묶었다.
- **검증 렌즈의 low를 다음으로 넘기기 vs 지금 고치기**: 앞 조각들은 low를 다음 조각의 첫 단계로 넘겼다. 이 조각은 마지막이라 넘길 곳이 없다. 남은 빈칸은 운영자를 틀린 복구로 보내거나 지울 수 없는 행을 남기는 회귀를 막는 자리여서, 시험과 문서만 고치는 짧은 2차 라운드를 돌렸다. 2차 검증이 같은 부류의 빈칸(호출 자리의 꼬리)을 하나 더 찾았을 때도 같은 잣대로 시험만 고치는 3차 라운드를 돌렸다 — 매 라운드가 시험 파일을 바꾸므로 pod 전체 실행도 매번 다시 돌았다.
- **부분 상태의 차례를 시험으로 고정하기 vs 운영 절차가 차례에 기대지 않기**: 3차 검증은 IdP 쓰기의 차례(owner 먼저 · 사용자마다 소속 → 속성)를 바꿔도 시험이 모두 초록이라는 것을 찾았다. 그 차례는 어느 계약에도 없는 구현 세부다. 시험으로 고정하면 구현 세부가 사실상 계약이 된다. 고정하지 않고, 런북이 차례에 기대지 않고 두 사용자의 소속 · 속성을 따로 확인하게 인계했다. 4차 라운드는 돌지 않았다.

## 결과와 검증
- 인수 시험 76개가 모두 초록이다(조각 ⑥ 끝의 67 → 76). 이 과제의 완료 조건이다.
- pod 전체 실행: 빌드 끝 494 통과 → 수정 라운드 507 통과 → 2차 수정 라운드 515 통과 → 3차 수정 라운드 521 통과. 넷 다 실패 · 오류 · 건너뜀 0이다. 템플릿 하네스는 918 통과, CI 드리프트 검사 셋은 모두 통과다(이 둘의 입력은 수정 라운드에서 바뀌지 않아 다시 돌지 않았고, 해시로 확인했다).
- arm64 이미지: 에뮬레이션을 먼저 등록하고 빌드한 이미지의 아키텍처가 arm64인지 보고, 네트워크 없이 띄워 새 모듈과 관리 명령 둘이 적재되는지 봤다. 첫 닫기에서는 탐침 출력을 남기지 않아 판정이 보고 문장에만 기댔다 — 수정 라운드가 로그 다섯(등록 · 빌드 · 아키텍처 · 탐침 출력과 종료 코드 · 삭제)을 남기며 다시 돌았다.
- 변이: 빌드에서 갈래를 지운 변이 수십 건, 수정 라운드에서 열네 건, 검증 렌즈가 사본 트리에서 여덟 건을 돌렸다. 검증에서 살아남은 다섯(앵커 · 꼬리 셋 · 표준 오류)은 2차 라운드가 사례를 더해 빨강으로 만들었다. 2차 검증이 열한 건을 더 돌려 찾은 생존 셋(호출 자리의 꼬리)은 3차 라운드가 호출 자리마다 일시 · 일시 아님 사례를 하나씩 더해 빨강으로 만들었다. 3차 검증이 꼬리 쌍의 칸 하나만 바꾸는 변이를 더 돌려, 호출 자리 셋 × 꼬리 칸 둘의 여섯 칸이 각각 따로 고정됨을 확인했다.
- 리뷰 두 렌즈의 발견 17건(medium 4 · low 13)은 모두 반영했다. 검증 렌즈의 low 7건은 시험 · 문서로 고치거나 빌드 기록의 인계로 넘겼다. 2차 검증의 low 2건은 시험(3차 라운드)과 계약 문장으로 고쳤다. 3차 검증의 low 2건은 계약 문장의 범위 괄호와 런북 인계로 처리했다.
- 인수 시험 세 파일은 구문 트리 대조로 실행 문장이 생성 커밋과 같음을 확인했다.

- 구현 커밋 → push → 첫 CI 실행(Linux arm64 러너). 인수 시험이 처음으로 공개 로그에 실린다 — 빨강이면 실패 출력을 옮기지 않고 그 실행의 로그를 지운다.
- IdP에서 잴 것: 그룹 응답에 관리자 여부 필드가 실제로 실리는지(없으면 시드가 늘 멈춘다), 사용자 조회가 uuid로 정확히 하나를 돌려주는지. 권한 저장소: store id의 실제 꼴, 시드 전에 권한 모델을 먼저 써야 한다는 것(없으면 DB와 IdP를 쓴 뒤 400).
- 런북: 틀린 인자의 흔적을 지우는 절차(DB 행 · IdP 소속과 속성 · 관계 튜플). 지우기 전에 인자가 정말 틀렸는지부터 본다 — 「고친 뒤 다시」 꼬리는 인자가 맞는데 토큰 권한이나 모델이 없어서 멈춘 실패에도 붙는다. IdP 쓰기에서 멈춘 실행의 부분 상태는 사용자마다 다를 수 있으므로, 쓰기 차례에 기대지 않고 두 사용자의 소속 · 속성을 따로 확인한다. 재적용 실패 줄은 오류 클래스로 가른다.
- 사용자 결정 대기: 캐시 서버 사용자 권한 좁히기, 프록시 액세스 로그의 질의 문자열, 과거로 어긋난 웹훅 시각의 처리.

## 사고·오류
- 컨트롤러가 쓴 운영 문서 문장이 두 번 틀렸다. 처음에는 「신선도 값이 멈추면 실패 줄을 찾는다」로 써서, 폐기 키만 막혀 값이 계속 전진하는 경우를 놓쳤다. 고친 문장은 「명령 단위 실패면 값은 전진한다 — 권한 규칙을 고친다」였는데, 이번에는 권한 밖 원인(메모리 한도 · 읽기 전용)과 그때 신호 키도 막힌다는 것을 놓쳤다. 두 번 모두 앞 리뷰가 든 예(권한 오류)를 전제로 받았다. 운영 문장은 리뷰의 예가 아니라 코드가 만드는 갈래(명령마다 받는 결과)에서 원인 부류를 열거해 쓴다.
- 2차 라운드 지시가 꼬리 시험의 범위를 세 묶음(사용자 조회의 나머지 갈래 · 권한 저장소 쓰기 · 단위 표)으로 닫아, 꼬리를 고르는 호출 자리 셋이 다시 빈칸으로 남았다. 같은 부류의 빈칸을 지시가 두 번 남긴 셈이다. 갈래를 열거할 때는 실패를 올리는 자리뿐 아니라 꼬리를 고르는 호출 자리 전부를 원문에서 세어 지시에 적는다.
- 2차 검증의 발견을 고치려고 데이터 모델에 더한 정의 문장이 다시 범위를 넘었다(「DB 앞 실패는 「DB는 쓰지 않았다」로 끝난다」 — 같은 문단의 다른 DB 앞 거부에는 그 꼬리가 없다). 문장 하나를 더하면서 같은 문단의 다른 갈래와 견주지 않았다. 계약에 문장을 더할 때는 그 주어가 덮는 범위를 같은 문단 · 코드의 갈래와 대조한 뒤 쓴다.
- 리뷰 렌즈가 API 인증 오류로 두 번 끊겼다. 재로그인 뒤 같은 런을 이어 돌렸고, 빌더는 캐시로 다시 돌지 않았다.
- 수정 라운드 빌더가 실패 문구를 재려고 임시 시험 파일을 저장소의 시험 폴더 안에서 돌리고 지웠다. 닫기 전이었고 흔적도 남지 않았지만 「탐침은 저장소 밖」 규칙을 어겼다. 2차 라운드부터 탐침과 변이는 저장소 밖 사본 트리에서만 돌게 했다.
- 빌드의 새 노드 39개 가운데 10개는 구현 뒤에 썼다(스스로 더한 갈래를 고정하려는 것이었다). 각 노드는 그 갈래를 지운 변이에서 빨강임을 보여 보완했다.
