# 003-platform-foundation T073 — identity-admin 설계: 폐기를 「최종」으로 만드는 값은 어디에 두는가 (2026-11-12)
> 설계 단계(조사 · 초안 · 비판 · 폐기 최종성 분석 · 사용자 결정 · 설계 확정 · 검토 두 라운드와 마감 확인). 구현은 다음 파일부터.

## 문제
identity-admin pod는 테넌트 · 멤버십과 세션 폐기(로그아웃 · 관리자 폐기 · IdP 로그아웃 웹훅)를 맡는다. 폐기는 「거부 목록 키를 access 토큰 수명보다 조금 길게(330초) 둔다」로 설계돼 있었다. 설계 비판이 여기서 high 결함을 찾았다. IdP는 세션을 지워도 refresh 토큰을 남기고, 서비스 계정은 다른 사용자의 refresh 토큰을 지울 수 없다. 그래서 폐기 뒤 330초 넘게 쉬던 기기나 복사된 쿠키는 다음 요청에서 refresh로 되살아난다. 「전체 로그아웃」이 최종이 아니었다.

사용자는 문제 정의를 「세션 시작 시각에 하한을 둔다」로 받아들였고, 구현을 서버가 정본으로 들고 판정하는 session_epoch 정책으로 하면 어떤지 분석을 요청했다.

## 배운 개념
- **즉시 폐기와 최종 폐기는 다른 문제다.** 짧은 TTL의 거부 목록은 이미 발급된 access 토큰을 막는 장치다. refresh 토큰을 가진 세션은 새 토큰을 계속 받으므로, 「이 세션은 폐기됐다」는 사실을 세션이 살 수 있는 기간만큼 기억해야 한다.
- **시각(not-before)과 세대 번호(카운터)는 늦게 오는 이벤트에서 갈린다.** 폐기 이벤트가 늦게, 뒤바뀌어 도착하는 시스템(웹훅 재시도 · 뒤늦은 백필)에서는 이벤트 시각의 최댓값이 순서와 무관하게 같은 값으로 수렴한다. 번호는 「언제」를 잃어버려, 늦게 처리된 이벤트가 그 사이 새로 로그인한 세션까지 끊는다. 번호형 선례(보안 스탬프 · 세션 인증 해시)는 검증 때 정본 DB를 읽는 것이 전제인데, 이 저장소의 확인 엔드포인트는 DB를 읽지 못한다(고정된 시험).
- **세션 시작 시각은 세션이 들고 다녀야 한다.** 토큰의 발급 시각은 refresh마다 새로 찍힌다. IdP의 인증 시각은 IdP 로그인 세션의 시각이라, 그 세션이 살아 있으면 다시 로그인해도 같은 값이 나와 로그인 루프가 된다. 로그인 때 받은 ID 토큰의 발급 시각을 쿠키에 고정하고 refresh에서 바꾸지 않는 것이 답이었다.
- **「영구 보관」과 「수명 상한」은 서로 바꿔 쓸 수 있다.** 하한 값을 영구히 들면 세션 수명에 상한이 없어도 폐기가 최종이다. 반대로 세션에 절대 수명을 두면 하한은 그만큼만 살면 된다. 불변식은 「하한 수명 ≥ 세션 최대 나이」 하나다. 폐기 전에 시작한 세션은 하한이 사는 동안은 하한이, 그 뒤에는 나이가 막는다. 이 불변식으로 새 표가 필요 없어졌고, 덤으로 기록되지 못한 폐기(유실된 웹훅)도 절대 수명 안에 끝난다. 영구 표는 이것을 하지 못한다.
- **판정과 반박을 나누면 순위가 뒤집힐 수 있다.** 판정 역할은 주어진 변형 넷 가운데 최선(전용 표)을 골랐다. 반박 역할은 그 장점이 기대는 전제(세션 수명에 상한이 없다)를 공격해 다섯째 안을 찾았다. 같은 자료를 본 두 역할의 결론이 달랐고, 원문 대조로 반박 쪽이 맞음을 확인했다.
- **IdP 동작은 소스로 확인한다.** refresh 요청은 세션과 사용자 활성 여부를 보지 않는다. 회전 때마다 만료가 다시 30일로 밀려 절대 수명이 없다. 세션 삭제는 이벤트를 만들지 않는다. 교환 토큰에는 세션 식별자가 없어 pod 경계에서는 세션을 구별할 수 없다. 그래서 집행 지점은 BFF가 refresh · 교환 앞에서 하는 확인 하나다. 이 사실들은 전부 소스 판독이고, 라이브 실측은 IdP를 배포하는 태스크로 넘겼다. 계약 문장에도 「소스 판독 — 실측은 어느 태스크」 표시를 달았다.
- **시계가 여럿이면 비교마다 「어느 시계와 어느 시계인가」를 적는다.** 미래 시각의 폐기가 30일짜리 하한으로 들어가는 것을 막으려고 「기록 시각 ≤ DB 시계 + 여유」 관문을 모든 경로에 뒀는데, 검토가 경로별로 풀어 보니 API 경로에서는 그 관문이 막는 사례가 없었다. 값을 서버가 자기 시계로 정하고, 그 시계가 틀리면 토큰 검증이 먼저 깨진다. 남는 것은 DB 시계가 늦을 때 폐기를 아예 기록하지 못하는 부작용뿐이었다. 관문은 시계 창이 없는 경로(관리 명령)에만 남겼다.
- **보조 필드가 틀렸다고 진짜 이벤트를 버리지 않는다.** 웹훅 본문의 폐기 시각이 이벤트 시각보다 크면 거부하는 대신 이벤트 시각으로 낮춰 기록하고 경고를 남긴다. 거부하면 보내는 쪽이 재시도 끝에 포기해 로그아웃이 통째로 사라진다. 낮춘 값은 검증된 이벤트 시각을 넘지 않으므로 안전 쪽 성질은 같다.
- **방어선을 옮기면 그 방어선의 시험도 옮긴다.** 공통 관문을 걷어 내자 일 1회 대조 경로의 미래 이벤트 방어가 한 줄(시각 창의 위쪽 끝)로 줄었는데, 그 줄을 보는 시험이 없었다. 구현이 그 줄을 빠뜨려도 전부 초록이 되는 상태였다. 미끼 이벤트와 변이를 더했다. 경계 미끼는 처리 지연 1초에 뒤집히지 않는 값으로 골랐다.
- **「있다」는 신호에는 거짓 생존 창이 있다.** 재적용이 살아 있음을 알리는 키는 만료 시간 동안 남는다. 재적용이 죽은 직후에도 키는 있으므로, 사람이 판단할 때는 키의 존재가 아니라 값이 전진하는지를 본다.
- **부정 사례는 구현이 없어도 초록일 수 있다.** 「없는 경로는 404」 · 「없는 명령은 오류」라서, 404나 오류를 기대하는 시험은 구현 전에도 통과한다. 먼저 빨강을 확인하는 절차가 그 시험에서는 성립하지 않는다. 같은 준비물에서 한 가지만 바꾼 정상 사례를 짝으로 두고, 명령 시험은 명령이 등록됐는지부터 단언한다.
- **「최대 N초」는 무엇이 줄을 서는지까지 세어야 참이다.** 30초 주기 재적용의 복구 상한을 「30초」로 적었지만, 작업을 하나씩 도는 워커에서는 먼저 받은 작업이 끝나야 재적용이 돈다. 상한은 「다음 주기 + 먼저 받은 작업들의 마감 + 재접속」이었다. 승인 문면의 「30초」와 달라져 편차로 올렸다.

## 선택과 대안
- **고른 것**: 기존 폐기 로그에서 사용자별 not-before 키를 파생한다(30일 유지 · 30초 재적용이 캐시 유실을 복구). 확인 엔드포인트가 세션 절대 수명 30일을 함께 집행한다.
- **버린 것**
  - 전용 표에 영구 보관: 전역 표 허용 목록, 공용 라이브러리, 템플릿, ADR이 함께 바뀌고 폐기의 정본이 둘이 된다. 앞서는 조건은 「재로그인 없이 30일 넘게 이어지는 세션이 필요할 때」 하나였다.
  - 세대 번호: 로그인이 identity-admin과 DB에 묶이고, 늦은 이벤트가 새 세션을 끊는다.
  - IdP 사용자 속성에 쓰기: 전역 사용자 변경 권한이 든 장기 토큰이 필요하다.
  - 하한 키만 두고 refresh 수명을 줄이기: 폐기 며칠 뒤의 회전을 덮지 못한다.
- **일 1회 대조**: 승인 문면의 「활성 세션 목록 대조」는 성립하지 않았다. 목록에는 삭제 흔적이 없고 pod는 세션별 상태를 들지 않는다. 로그아웃 이벤트 대조로 구현하기로 했다. 읽기 권한 하나가 더 필요하고, 실제 부여는 IdP 설정 태스크에서 정한다. 하한이 생기면서 늦은 기록에도 보안 값이 생겼다(살아 있는 refresh 사슬을 끊는다). 권한이 없을 때의 응답 꼴(거부 · 빈 목록 · 없음)은 단정하지 않고 세 꼴 모두에서 안전하게 끝나도록 적었다.
- **관리 명령**: 관리자 폐기를 부를 HTTP 경로가 SP-1에 없어 관리 명령을 뒀다. 한 세션만 끊는 옵션은 뺐다. 그 폐기는 330초 차단뿐이라 세션이 그 안에 서버에 닿지 않으면 효력이 없는데, 명령은 성공을 알렸다. 거부 목록 쓰기가 실패하면 종료 코드로 알린다(인자 오류와 겹치지 않는 값).
- **빌드 순서**: 추가 시험을 한 조각에 몰아 먼저 쓰는 안은 버렸다. 고정된 인수 시험이 이미 있으므로, 시험 도우미만 먼저 만들고 각 구현 조각이 자기 시험을 먼저 쓴다. 가장 큰 조각은 둘로 갈랐고, 두 경로를 다 보는 시험 묶음은 사례 단위로 나눠 앞 조각이 자기 몫을 먼저 쓴다.
- **넘긴 것**: IdP 로그인 세션이 살아 있는 기기가 재인증 없이 돌아오는 한계(로그인 때 한 번 확인하는 안은 BFF 태스크 전에 결정), 한 기기 로그아웃의 기본 범위, 결정 기록(ADR)은 수렴 단계.

## 결과와 검증
- 흐름: 조사(발견 164 · 열린 질문 74) → 초안(결정 28) → 비판 2렌즈(high 2) → 컨트롤러 결정 24건 → 분석(사실 검증 2 · 변형 4 · 판정 · 반박) → 사용자 결정 2 → 결정 14건 → 설계 정본과 계약 보정 → 검토 3렌즈(high 0 · medium 6 · low 30) → 결정 36건 → 재검토 2렌즈(high 0 · medium 3 · low 19) → 결정 22건 → 변경분 확인(high 0 · medium 0 · low 2 — 직접 반영).
- 고정된 API 시험 76개는 바꾸지 않는다. 확인 엔드포인트 시험의 세션 시작 시각이 전부 현재 시각이라 나이 조건을 더해도 단언이 그대로이고, 웹훅 시험의 폐기 시각이 전부 이벤트 시각 이하라 상한 규칙을 바꿔도 그대로임을 원문으로 확인했다(실행은 구현 단계).
- 설계의 계약 보정 문면 151줄이 대상 문서 아홉에 글자 그대로 들어갔음을 스크립트로 대조했다(누락 0). 승인 고정 문서와 코드 · 시험 · 템플릿은 건드리지 않았다.
- 승인 문면과 달라진 것은 report 편차 후보 29행으로 모았다. 세션이 30일마다 다시 로그인되는 새 동작, 문면에 없는 관리 명령, 일 1회 대조의 자료원, 테스터 서비스 토큰의 직접 호출이 pod에서 거부되는 것, 캐시 유실 뒤 복구 시간의 상한이 들어 있다.

## 사고·오류
- 초안은 「330초 키」의 한계를 보지 못했고(비판에서 high로 발견), 판정 역할은 전용 표를 골랐다가 반박에서 뒤집혔다. 한 번의 설계 · 한 번의 판정으로 닫았다면 둘 다 구현까지 갔을 것이다.
- 컨트롤러 결정에도 오류가 있었다. 모든 경로에 둔 DB 시계 관문(막는 것 없이 폐기 불능만 만든다), 효력 없는 단일 세션 옵션, 웹훅 상한의 「거부」(진짜 로그아웃 유실), 종료 코드 겹침은 모두 검토가 구체적인 타임라인으로 깼다. 고친 결정이 다시 깨진 것도 있다 — 관문을 걷어 낸 결정은 다음 라운드에서 「그 관문이 지키던 다른 경로의 시험이 사라졌다」로 돌아왔다.
- 설계 문서에 전체 검사 스크립트를 조각마다 돌리라는 지시가 들어갔다. 그 스크립트에는 운영자 자격을 쓰는 슬롯이 있어 에이전트가 돌리지 않는 것이 이 저장소의 규칙이다. 검토에서 찾아 필요한 검사 파일 이름으로 바꿨다.
- 이미 메모해 둔 도구 함정(콘솔 인코딩 때문에 한글 출력이 죽는다)을 같은 날 다시 밟았다. 메모는 읽지 않으면 소용이 없다.
