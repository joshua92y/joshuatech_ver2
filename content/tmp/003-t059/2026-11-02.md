# 003-platform-foundation T059 — 머지 3분 뒤 1분 안에 끝난 첫 검사 실행, 그리고 US3 E2E (2026-11-02)
> 2일차(머지 · 첫 배포 관찰 · 하네스 · E2E tester · 기록). 1일차 기록은 2026-10-29 파일.

## 문제
10-29에 열어 둔 PR을 머지하면 처음으로 클러스터 안에서 검사 Job 둘이 돌아간다. 설계가 예측한 순서(루트가 Application을 만들고 → 시크릿 둘이 준비되고 → Job 둘이 생기고 → 완료되면 Synced/Healthy)가 실제로 그 순서로, 그 시간 안에 일어나는지, 완료된 Job이 GitOps 비교에서 "차이 있음"으로 남지 않는지(남으면 무한 재실행 위험이 있어 옵션을 뺐던 결정의 근거), 하네스 기대값이 맞는지, 그리고 E2E tester가 사용자 관점의 수용 기준 다섯 가지를 증거로 닫을 수 있는지가 이번 날의 질문이었다.

## 배운 개념
- **루트 Application의 폴링 주기가 곧 배포 지연이다.** 머지 뒤 약 3분이 지나서야 루트가 새 커밋을 봤고, 그 operation은 3초에 끝났다. 이 Application이 지금은 표의 마지막 wave라 루트는 health를 기다리지 않는다(단계표의 예측 그대로). 급하면 운영자가 refresh 어노테이션으로 당길 수 있지만 급할 이유가 없었다.
- **리소스 수준 wave는 초 단위로 보인다.** 시크릿이 준비된 시각과 Job이 만들어진 시각의 차이는 2초였다. ExternalSecret의 내장 health가 "동기화됨"을 Healthy로 보기 때문에 그 다음 wave로 넘어갈 수 있었다 — 설계 때 "전제"로 둔 두 가지(순서 · health 판정)가 한 번의 배포로 둘 다 확인됐다.
- **완료된 Job은 Synced로 남았다.** 서버 사이드 적용과 구조적 병합 diff 아래에서 Kubernetes가 채운 셀렉터·라벨 같은 live-only 필드는 차이로 잡히지 않았다. `ignoreDifferences` 후속 PR은 필요 없고, 재실행 옵션을 빼 둔 결정이 안전하다는 것도 같은 관찰로 확인됐다.
- **두 Job의 소요는 설계 상한의 10분의 1이었다.** DB·캐시 검사는 6초(이미지가 노드에 캐시돼 있었다), 메시징 검사는 37초(이미지 받기 9초 + JVM 둘 기동). 기동 경합(연결 거부 · 타임아웃) 흔적이 없어 메시징 검사에 기동 유예를 더하지 않기로 했다 — 스크립트 불변 결정 유지.
- **하네스 기대값은 설계 때 숫자로 적어 두는 것이 맞다.** 클러스터 46/0/9 · 데이터 15/0/1 · 메시징 17/0/0은 설계 문서에 미리 적은 값과 한 자리도 다르지 않았다. 새 단언(마지막 operation phase)은 23개 Application 중 operation 기록이 없는 3개를 통과로 세며 PASS했다.
- **부모 Application은 자식의 Progressing을 그대로 물려받는다.** Job이 도는 37초 동안 루트도 Progressing이었다. 그 창에 하네스를 돌리면 "전부 Synced/Healthy" 단언이 일시 FAIL한다 — 측정은 Job 완료 뒤에 한다는 조건을 tester 지시문에 미리 적어 둔 덕에 혼선이 없었다.
- **외부 읽기 세션은 사람이 만든다.** 오브젝트 스토리지의 백업 목록은 60분짜리 읽기 전용 세션이 필요하고, 그 세션은 운영자가 브라우저로 만든다. 에이전트 셸에서는 CLI가 실행되지 않아 세션 상태 확인조차 운영자에게 맡겼다. 세션 의존 검사는 재인증 직후 한 묶음으로 돌린다(지난 과제의 교훈을 이번엔 지켰다).

## 선택과 대안
- **머지는 사용자 확인 1회 뒤 컨트롤러가 실행했다.** 라이브 Job 실행이 생기는 변경이라 문서 PR과 달리 다시 물었고, 머지 명령에는 PR head 커밋을 고정하는 옵션을 붙여 "확인한 그 커밋"만 머지되게 했다.
- **관찰은 15초 폴링 + 종료 뒤 스냅숏.** 이벤트는 1시간 TTL이라 Job이 끝나는 즉시 이벤트·Application·ES·Job·로그를 파일로 남겼다.
- **tester와 후속 문서 빌더를 병행.** 서로 다른 저장소·파일을 다루고 라이브 쓰기가 없어 충돌이 없다. 하네스는 한 번에 하나만 돌린다는 규칙은 tester에게도 넘겼다.

## 결과와 검증
- 머지 → 루트 operation 3초 → ES 2 준비 → 2초 뒤 Job 2 생성 → 6초/37초 뒤 완료 → Application Synced/Healthy · 리소스 5 전부 Synced · 재시도 0 · Degraded 0.
- 로그: DB·캐시 검사 13/13 PASS(교차 DB permission denied · 카탈로그 CONNECT false · PUBLIC 회수 · TLS verify-full · 역할 속성 · 세션 타임아웃 · NOAUTH · ACL 목록의 읽기 전용 패턴 · 쓰기/읽기/거부 · NOPERM), 메시징 검사 2/2 PASS(왕복 3초 · 메시지 지연 304ms · 다른 환경 토픽 쓰기 TopicAuthorizationException).
- 하네스: 클러스터 46 PASS / 0 FAIL / 9 SKIP · 데이터 15 / 0 / 1 · 메시징 17 / 0 / 0 — 설계 기대값과 동일.
- E2E tester 결과(읽기 전용 · 쓰기 0 · 10분): 수용 기준 다섯 가지 전부 PASS · 예외 경로 네 가지 PASS · FAIL 0 · 하네스 재측정도 같은 값. 남은 공백은 소유자로 넘겼다 — 인가 검사 Job(대상 서비스가 생긴 뒤), 앱 파드가 있어야 하는 검사 넷(첫 파드 배포 과제), prod 자격으로의 왕복과 "다른 pod 사용자" 거부(두 번째 pod가 생기는 다음 스프린트 — 지금은 dev 자격과 dev→prod 교차로 대체), prod 캐시 실접속(운영자 수동). 문면과 실제의 편차 둘(버킷 이름 · "kcat"이라 적힌 왕복 측정 도구가 실제로는 Kafka 콘솔 클라이언트)은 마무리 보고의 편차 기록으로.
