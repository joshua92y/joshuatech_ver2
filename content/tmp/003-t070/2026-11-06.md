# 003-platform-foundation T070 — 인증 미들웨어 2일차: 경계는 값이 아니라 꼴로 잡고, 시험은 경계 양쪽을 찌른다 (2026-11-06)
> 2일차(4차 · 5차 · 6차 리뷰 반영과 마감). 1일차(설계 확정 · 1–3차)는 `2026-11-05.md`.

## 문제
3차 리뷰가 남긴 질문은 셋이었다.
- 인증 설정 문자열에 어떤 글자까지 받을 것인가.
- 호스트 이름이 「숫자」인지 무엇으로 판정하는가.
- 라이브러리 내부 잠금에 기대도 되는가.

4차 리뷰는 한 번 더 물었다.
- 시험이 규칙의 경계를 정말 가르는가.
- 비밀이 예외 프레임에 남지 않는가.
- BFF 프록시가 남의 세션 상태를 대신 물어 줄 틈이 없는가.

5차 리뷰는 내가 고친 계약 문장을 다시 찔렀다.
- 요청 쪽 경로를 닫았는데, 응답 쪽은 열려 있지 않은가.
- 배포 첫 단계에 넣는 임시 값이 보안 키 자리에 들어가지 않는가.

6차 리뷰는 넓힌 응답 규칙의 가장자리를 물었다.
- 상류 앞의 다른 층(엣지 · 리버스 프록시 · 접근 통제)이 만든 오류 페이지도 그대로 옮기는가.
- 로그아웃이 중간에 실패하면 쿠키는 어떻게 되는가.

## 배운 개념
- **「출력 가능」은 「보이는」이 아니다.**
  - `str.isprintable()`은 한글 채움 문자(U+3164)와 점자 빈칸(U+2800)을 참으로 본다. 눈에 보이지 않는데 출력 가능 글자로 분류된다.
  - 그래서 설정 문자열은 유니코드 범주가 아니라 글자 범위로 거른다. 공백 없는 출력 가능 ASCII(`!`–`~`)만 받는다.
    - 식별자 · URL 설정에는 그 밖의 글자를 담을 정당한 까닭이 없다(URL의 특수 글자는 퍼센트 인코딩).
  - 대가로 지금 동작하던 값 셋이 설정 오류가 된다.
    - 라이브러리가 공백을 떼거나 지워 주던 URL 설정 둘(URL 분해 함수는 앞 공백을 떼고 탭 · 줄바꿈을 자리와 무관하게 지운다. 끝 공백은 요청 객체 · 정수 변환이 받아 준다)
    - 맞지 않는 audience라서 해가 없던 값 하나
    - 「우연히 동작하는 값」도 숨은 결함으로 본다.
- **「숫자 같은 이름」은 WHATWG의 정의를 빌린다.**
  - 운영체제의 주소 해석(inet_aton)은 `0x` 16진 성분도 숫자로 푼다.
    - 마지막 라벨이 10진 숫자만일 때만 막으면, 16진 꼴은 이름으로 통과한다.
    - 그러면 이름 조회 없이 엉뚱한 주소(클라우드 메타데이터 주소 포함)로 연결을 시도한다.
  - WHATWG URL 표준의 ends-in-a-number 판정을 그대로 쓴다. 마지막 라벨이 10진 숫자만이거나 `0x` + 16진(빈 것 포함)이면 이름이 아니다.
  - 값이 아니라 꼴로 거르므로, 운영체제마다 다른 넘침 처리와 무관하다.
- **라이브러리 비공개 잠금을 다시 쥐면 안 된다.**
  - PyJWT 키 클라이언트의 잠금을 같이 쥐면 짧은 코드로 경합을 막을 수 있어 보인다.
  - 그 잠금이 재진입 불가 잠금으로 바뀌는 판에서는, 같은 스레드가 이미 쥔 잠금을 다시 쥐려다 요청이 멈춘다. 503보다 나쁘다.
  - 그래서 자기 잠금을 두었다. 라이브러리 소스로 잠금 순서(라이브러리 잠금 → 자기 잠금 · 반대 경로 없음)를 확인했다.
  - 대가: 중복 제거는 여전히 라이브러리 잠금 몫이다. 빈 캐시에 동시 요청이 몰려도 fetch를 한 번만 하는 성질을 말한다.
    - 그 결합을 시험으로 고정했다(카나리). 라이브러리를 올릴 때 그 성질이 사라지면 시험이 실패한다.
    - 같은 시험을 잠금 없는 가짜 부모로 돌리면 fetch 5번 · 계단 대기로 실패한다. 그래서 공허한 시험이 아님을 안다.
- **시험이 규칙의 경계를 양쪽에서 찌르는지는 변이로만 보인다.**
  - 4차 시험의 값 꼴 아홉은 공백 · 비ASCII뿐이었다. 그래서 틀린 규칙 둘도 시험을 모두 통과했다.
    - 「ASCII이고 공백이 아니면 받는다」
    - 「상한에 DEL을 넣는다」
  - 리뷰가 메모리 탐침으로 그 변이를 찾았다. 5차에서 ESC · DEL 꼴을 더했다.
  - 5차 리뷰는 반대쪽을 찔렀다. 시험이 받아들이는 값의 문장 부호가 여덟 개뿐이라 「`!`를 거부」 · 「`~`를 거부」 변이가 살아남았다. 거부 쪽만 늘려서는 경계의 반쪽만 고정된다. 6차에서 범위 안 94자 전부를 받는 사례를 더했다.
  - 같은 범위를 두 겹으로 거르면(설정 검사 + URL 원문 검사), 안쪽 검사의 변이가 바깥 검사에 가려진다. 안쪽 검사의 판별력은 바깥 검사가 없는 다른 설정으로 보여야 한다.
- **비밀은 예외 메시지만이 아니라 프레임 지역 변수에도 있다.**
  - 설정 오류를 이름만 실어 올려도, 트레이스백 프레임의 지역 변수에는 원문 값(비밀번호가 든 URL)이 남는다.
  - structlog의 기본 예외 렌더러(`dict_tracebacks`)는 지역 변수를 JSON으로 싣는다.
  - 한 함수에서 값을 `del`로 지워도 소용이 없다. 인증 경로의 다른 프레임도 원문 토큰을 쥐고 있다.
  - 통제 지점은 예외 렌더러 하나다. 지역 변수 없이 렌더하고, Sentry도 지역 변수를 끈다.
  - Django의 오류 보고서(관리자 메일 · DEBUG 페이지)는 세 길로 원문을 싣는다: 설정 덤프 · 요청 헤더(Access JWT 헤더 이름은 정리 규칙에 걸리지 않는다) · 프레임 지역 변수. 필터를 덧대서는 닫히지 않는다. 쓰지 않는 것이 통제다.
  - 「쓰지 않는다」는 기본 설정이 무엇을 붙여 두었는지부터 본다. Django 기본 로깅은 관리자 메일 핸들러를 늘 붙여 둔다. 메일 보고를 실제로 막는 것은 수신자 목록이 비었을 때의 조기 반환이다.
- **혼동된 대리인은 질의 · 경로 · 응답 세 쪽에서 막는다.**
  - BFF는 서비스 토큰으로 상류를 부른다. 클라이언트 질의를 그대로 넘기면, 로그인한 아무 사용자가 남의 세션 폐기 여부를 물을 수 있다. 그래서 질의는 세션 값으로 다시 만든다.
  - 질의를 닫아도 경로 판정이 느슨하면 틈이 남는다.
    - 접두 일치 + 인코딩된 `..`는 상류 URL을 정규화할 때 다른 경로가 된다.
    - 그래서 허용 경로는 정확 일치로 비교한다. 상류 URL은 「기준 URL + 허용 경로 상수」로 만든다(클라이언트 경로 문자열을 잇지 않는다).
  - 요청 쪽을 다 닫아도 응답이 열려 있으면 소용이 없다.
    - Cloudflare Access는 서비스 토큰으로 인증된 응답에 그 앱 범위의 세션 쿠키를 실을 수 있다(엄격 모드가 꺼진 조직 — 문서 기준 · 미실측).
    - 「응답을 그대로 중계」하면 그 쿠키가 브라우저로 간다. 사용자가 그 쿠키로 상류를 직접 부르면 질의 재작성을 건너뛴다.
    - 그래서 응답은 pod가 만든 JSON 응답(2xx · 4xx)의 상태 · 본문 · `content-type`만 옮기고, 3xx · 5xx · 그 밖의 응답은 503으로 바꾼다. 하류 응답 헤더는 어느 라우트에서도 옮기지 않고, 응답 쪽 쿠키 값도 로그에 남기지 않는다.
  - 자격을 싣는 호출은 리디렉션을 따르지 않는다. Fetch 표준의 기본 `follow`는 사용자 정의 헤더를 새 위치로 다시 보내고, 307 · 308은 본문(client secret)까지 다시 보낸다.
- **URL 파서는 핸들러보다 먼저 경로를 바꾼다.**
  - WHATWG URL 파서는 요청 객체를 만들 때 `..` · `%2e%2e` 세그먼트를 접는다(`//`는 남긴다).
  - 그래서 핸들러에서 「점 세그먼트면 404」를 검사해도, 그 꼴은 이미 정규 경로로 보인다.
  - 판정 기준을 「거부했는가」가 아니라 「정규 요청과 같은 결과이고 클라이언트 값이 상류에 닿지 않는가」로 잡았다.
  - 같은 까닭으로 「`/`로 시작하고 `//`가 아니면 같은 사이트 경로」라는 글자 검사는 열린 리디렉션을 막지 못한다.
    - 파서는 `\`를 `/`로 바꾸고 탭 · 줄바꿈을 지운다. 그래서 `/\evil.com` · `/<탭>/evil.com`은 다른 출처가 된다(질의에서는 `%5C` · `%09`로 들어와 디코딩 뒤 그 꼴이 된다).
    - 판정은 글자가 아니라, 파서로 해석한 결과의 출처가 요청 출처와 같은지로 한다. 로그인 뒤 돌아갈 곳과 프레임워크 리디렉션 위치가 같은 정의를 쓴다.
- **임시 값에도 방향이 있다 — 들어오는 쪽 검증 키는 처음부터 실값이다.**
  - 나가는 쪽 자격(상대에게 내미는 토큰)이 임시 값이면 호출이 실패할 뿐이다.
  - 들어오는 쪽 검증 키(웹훅 HMAC 비밀)가 임시 값이면 그 값을 아는 누구나 서명한다. 저장소 문서에 적힌 sentinel은 「누구나 아는 값」이다. 빈 키를 기동 실패로 막은 이유와 같은 부류다.
  - 그래서 웹훅 비밀은 첫 배포 전에 난수 실값으로 덮어쓰고, 나가는 쪽 자격은 sentinel을 그대로 두는 쪽을 권했다. sentinel을 다른 고정 값으로 바꿔 검사를 통과시키면, 남은 임시 값을 가르는 게이트가 눈을 잃는다.
  - 같은 값이 두 얼굴을 가질 수 있다. 권한 서버의 공유 키는 호출자에게는 나가는 쪽 자격이지만, 서버에게는 들어오는 쪽 검증 키다. 그래서 서버 쪽 값이 먼저 실값이어야 하고, 호출자 사본은 그 값을 복사한다.
- **실패 갈래는 사용자의 뜻으로 정한다.**
  - 「시간 초과 · 리디렉션을 폐기로 접지 않는다(쿠키를 지우지 않는다)」는 세션 확인 · 갱신에서는 맞다. 일시 장애로 모든 사용자가 로그아웃되면 안 되기 때문이다.
  - 로그아웃에서는 같은 문장이 반대로 읽힌다. 로그아웃의 정상 결과가 곧 쿠키 삭제이기 때문이다.
  - 그래서 로그아웃은 하류가 실패해도 쿠키를 지우고, 서버 쪽 폐기 실패는 503으로 알린다. 공용 기기에서 로그아웃을 누르고 떠난 사람의 세션이 남지 않게 하려는 것이다.
  - 단 CSRF 검사를 통과하기 전에는 지우지 않는다. 그 검사는 위조 요청으로 남을 로그아웃시키는 것을 막으려고 있다.
  - 그러면 CSRF 쿠키의 수명이 중요해진다. CSRF 쿠키가 브라우저 세션 쿠키이고 세션 쿠키가 30일이면, 브라우저를 다시 연 뒤에는 세션만 남는다. 그때 로그아웃은 CSRF에서 막혀 쿠키를 지우지 못한다. 그래서 두 쿠키의 수명과 싣는 자리를 맞췄다.

## 선택과 대안
- **isprintable vs ASCII 범위**:
  - isprintable은 짧고 국제화에 맞아 보이지만, 보이지 않는 글자를 통과시킨다.
  - 설정 값은 사람이 읽는 글이 아니라 비교에 쓰는 식별자다. 그래서 ASCII 범위를 골랐다.
- **비공개 잠금 재사용 vs 자기 잠금**:
  - 리뷰 제안은 재사용이었다. 재진입 불가 판의 교착 위험 때문에 자기 잠금을 골랐다.
  - 중복 제거까지 자기 상태로 하는 안은 고르지 않았다.
    - 기다리던 재조회가 자기 요청보다 먼저 시작된 fetch의 결과를 받게 된다. 그러면 키 교체 직후의 신선도가 바뀐다.
    - 카나리 시험이 이 결정을 다시 꺼낼 때를 알려 준다.
- **`del value` vs 렌더러 통제**: 리뷰 선택안(값 지우기)은 한 프레임만 고친다. 렌더러 한 곳에서 지역 변수를 끄는 쪽을 골랐다. 다음 태스크(T071)가 시험으로 고정한다.
- **허용 경로에서 빼기 vs 동작 보강**: 승인된 spec이 `/session/check`를 BFF 허용 경로로 둔다. 빼지 않고 질의 · 경로 · 응답 · 리디렉션 규칙으로 보강했다(문면 유지).
- **변형 경로는 404인가 308인가**: 프레임워크는 끝 슬래시 · 겹친 슬래시를 핸들러 앞에서 정규형 경로로 308 리디렉션한다. 404를 강제하려면 프레임워크 기본값을 꺼야 한다. 「상류 호출 0이고 리디렉션 위치가 같은 출처의 경로면 만족」으로 정하고 시험 층(핸들러 단위 · 통합)을 나눴다.
- **프록시 응답 판별: 상태 코드 vs 응답 꼴**: 같은 공개 호스트 뒤에서는 pod 말고도 엣지 · 터널 · 리버스 프록시 · 접근 통제가 응답을 만든다. 상태 코드만으로는 누가 만든 응답인지 모른다. pod는 JSON만 돌려주므로 2xx · 4xx JSON만 옮기고 나머지는 503으로 바꿨다. 다른 층이 JSON 오류를 낸다면 그대로 옮겨지는 한계가 남는다(실측은 BFF 구현 때).
- **정적 맵: 경로만 vs 경로 + 메서드**: pod 프레임워크는 허용하지 않는 메서드에 HTML 405를 낸다. 맵에 경로만 두면 그 405가 응답 꼴 규칙에서 「상류 장애 503」으로 바뀌어 가용성 지표를 더럽힌다. 맵에 메서드까지 두고 BFF가 상류를 부르기 전에 404로 거르는 쪽을 골랐다.
- **로그아웃 실패: 쿠키 유지(재시도) vs 쿠키 삭제**: 쿠키를 남기면 사용자가 다시 시도할 수 있다. 하지만 공용 기기에서 떠난 사람의 세션이 남는다. 쿠키를 지우고 서버 쪽 실패는 503으로 알리는 쪽을 골랐다. 서버 쪽에 남은 세션은 「모든 기기 로그아웃」이나 관리자 폐기로 거둔다.
- **웹훅 비밀: 임시 값 vs 처음부터 실값**: 승인된 tasks 문면은 「US6에 임시 값 → US4에 실값」이다. 들어오는 쪽 검증 키라 문면과 다르게 처음부터 실값으로 했다. 같은 내용이 승인 문면 네 곳에 있어 넷 모두 편차로 보고서에 적는다.

## 사고·오류
- 4차 결과를 받은 직후 컨트롤러가 작업 폴더 전체에 재귀 검색을 돌려 명령 시간 상한(120초)을 넘겼다. 하위 에이전트에게 금지한 일을 스스로 했다. 바로 멈췄고 바뀐 파일은 없다.
- 처음 쓴 4차 문자 규칙(isprintable)에 빈틈이 있었다. 빌더를 띄우기 전에 확인하고 고쳤다.
- 5차 지시문에 라이브러리 동작을 잘못 적었다(「캐시는 `finally`에서 채운다」). 빌더가 소스로 바로잡았고 결과에는 영향이 없었다.
- 5차에 고친 임시 값 문장을 쓸 때, 그 저장소 경로에 실제로 무엇이 들어 있는지(운영 기록)를 대조하지 않았다. 리뷰가 운영 기록과 어긋남과 웹훅 비밀 누락을 찾았다(medium). 계약 문장을 쓰기 전에 라이브 기록을 먼저 읽는다.
- 6차 결정 문장 넷도 근거와 어긋났다(low).
  - 편차 목록이 승인 문면 한 곳만 적었다. 같은 내용이 세 곳 더 있었다.
  - 「관리자 메일 핸들러 없음」을 통제로 적었는데, Django 기본 로깅은 그 핸들러를 늘 붙인다.
  - URL 문구에서 끝 공백 떼기를 URL 분해 함수 몫으로 적었다. 실제로는 요청 객체 · 정수 변환이 뗀다.
  - 다음 시험의 설계 초안에, 예외 프레임이 쥔 값을 원문 토큰으로 적었다. 실제로는 검증된 클레임이었다(결정 본문은 맞았고 옮기며 틀렸다).
  - 넷 다 승인 문면 · 라이브러리 소스 · 실측을 끝까지 대조하지 않은 탓이다. 마감 때 소스와 실측으로 다시 확인하고 고쳤다.
- 마감 확인이 설계 때 내가 쓴 BFF 계약 문면의 틈 둘을 찾았다. 돌아갈 곳 검사가 글자 접두만 봐서 열린 리디렉션 꼴을 통과시켰고, CSRF 쿠키의 수명이 정해지지 않았다. 구현 전에 계약에서 닫았다.
- 마감 정정 초안에서 로그아웃 「어느 갈래에서든 쿠키를 지운다」가 CSRF 실패 갈래까지 덮었다. 그대로면 위조 요청으로 남을 로그아웃시킬 수 있다. 적용 전에 사본을 검수하다 찾아 「세션 · CSRF 검사를 통과한 뒤」로 좁혔다.
