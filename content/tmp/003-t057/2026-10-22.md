# 003-platform-foundation T057 — 세션 거부 목록 캐시(Dragonfly)를 ACL 파일로 잠그기: 문서 대신 소스가 가르쳐 준 세 가지 함정 (2026-10-22)
> 1일차(설계 · 빌드 · 리뷰 2라운드 · PR). 라이브 배포와 실측(VD-4)은 운영자 시드 뒤에 이어진다.

## 문제
세션 거부 목록의 파생 캐시로 쓸 인메모리 저장소를 dev·prod 한 벌씩 올려야 했다. 요구는 분명했다. 비밀번호 대신 ACL 파일로만 인증하고, 거부 목록 키는 쓰기 계정 하나만 쓰고 나머지 계정은 읽기만 하며, 종료 때 스냅샷을 남기고, 영속 볼륨은 지워지지 않게 보호한다. 문제는 "ACL 파일이 키 패턴을 지원하는가"처럼 공식 문서와 실제 동작이 다를 수 있는 지점이 여럿이라는 것이었다. 문서만 믿고 배포하면 인증이 통째로 꺼진 채 "정상"으로 보일 수 있었다.

## 배운 개념
- **설정 파일이 거부되면 "안전한 기본값"이 아니라 "열린 기본값"으로 떨어질 수 있다.** 이 저장소의 ACL 파일 로더는 한 줄이라도 파싱에 실패하면 파일 전체를 버리고 기본 사용자(비밀번호 없음 · 모든 권한)로 기동한다. 로그에는 경고 한 줄뿐이고, 빈 파일은 그 경고조차 없다. 즉 "오류 로그가 없다"는 적재의 증거가 아니다. 적재의 증거는 비인증 명령이 거부되는지 직접 확인하는 것뿐이다. 그래서 검사 Job의 첫 항목이 "비인증 PING이 거부되는가"가 됐다.
- **파일에 기본 사용자를 명시하지 않으면 기본 사용자가 열린 채 만들어진다.** 기본 사용자 줄을 넣되, 로더가 토큰 네 개 미만인 줄을 거부하므로 `OFF`만으로는 부족하고 권한 토큰을 하나 더 붙여야 했다. 줄 형식은 서버가 스스로 저장할 때 쓰는 형식과 똑같이 맞추는 것이 가장 안전했다.
- **비밀번호 보호와 HTTP 콘솔 보호는 다른 스위치였다.** 전역 비밀번호가 비어 있으면 같은 포트의 HTTP 콘솔은 ACL 사용자와 무관하게 무인증이었다. 접근을 허용받은 어느 앱 파드든 콘솔을 읽을 수 있었으므로 콘솔을 끄고, 지표 수집은 뒤 과제로 넘겼다.
- **기본 스냅샷 이름에 타임스탬프가 들어 있으면 주기 스냅샷은 파일을 무한히 쌓는다.** 보존 정책이 없어서 작은 볼륨이 결국 찬다. 파생 캐시라 이력이 필요 없으니 고정 이름으로 덮어쓰기로 했다. 대가는 손상 시 되돌릴 이전 스냅샷이 없다는 것인데, 정본은 DB이고 30초마다 다시 채워지므로 받아들였다.
- **볼륨 바인딩 모드가 동기화 순서를 결정한다.** 첫 소비자가 붙을 때 바인딩되는 스토리지 클래스에서는 볼륨 요청이 파드 전까지 Pending이고, 동기화 도구는 Pending을 "진행 중"으로 본다. 볼륨을 파드보다 앞 단계에 두면 영원히 다음 단계로 넘어가지 못한다. 같은 단계에 두면 종류 순서로 먼저 적용된다.
- **"인증" 명령도 권한 검사를 받는다 — 누구의 권한으로?** 이 저장소는 인증 전 연결을 기본 사용자로 취급하고, 인증 명령(AUTH · HELLO)을 **기본 사용자의 ACL**로 검사한다. 기본 사용자에게 모든 권한을 빼면 인증 명령 자체가 거부되어 아무도 로그인할 수 없다. 첫 라이브 측정에서 정확히 이것이 났다(기본 사용자 `OFF -@all`). 올바른 최소 권한은 "꺼져 있되 인증·HELLO만 허용"이다. 비인증 연결의 다른 명령은 그 앞 관문(NOAUTH)이 먼저 막으므로 이 두 명령만 열어 두면 충분하다.
- **같은 이미지를 로컬 컨테이너로 띄우면 수수께끼가 몇 분 안에 풀린다.** 라이브 로그만으로는 "NOPERM default …"가 ACL 파일 미적재인지, 기본 사용자 권한 문제인지 가릴 수 없었다. 같은 버전의 이미지에 세 가지 ACL 파일 변형을 넣고 돌리자 현재 형식은 모두 실패, 두 수정안은 모두 통과했고, 덧붙여 읽기 전용 키 패턴이 파일에서 실제로 적재된다는 것(VD-4의 본래 질문)까지 함께 확인됐다. 처음에는 셸의 경로 자동 변환 때문에 컨테이너가 ACL 파일을 못 읽어 "로드 실패 = 무인증 기동"이 그대로 재현되기도 했다 — 함정이 두 겹이었다.
- **권한 범주와 키 패턴은 독립적으로 합쳐진다.** "이 키에는 읽기만"을 "읽기 범주 + 키 패턴"으로 적으면 뜻이 달라진다(둘이 짝지어지지 않아 쓰기도 허용된다). 읽기 전용은 읽기 전용 키 패턴으로만 표현해야 한다. 또 모든 명령 권한에는 관리 명령과 키 인자 없는 전체 삭제가 들어 있어, 자격이 새면 런타임 ACL을 바꾸거나 캐시를 비울 수 있다는 점을 받아들인 사실로 적었다.

## 선택과 대안
- **ACL 파일에 평문 대신 해시를 넣었다.** 로더가 해시 형식을 받는 것을 소스로 확인했기 때문이다. 공유 네임스페이스의 Secret에 평문이 실리지 않고, 목록 출력에는 축약 해시만 보인다. 대안인 평문은 더 단순하지만 Secret을 읽을 수 있는 모든 경로에 비밀번호를 노출한다.
- **프로브는 TCP 연결 확인으로 했다.** 처음에는 "이미지에 클라이언트가 없다"가 근거였는데 리뷰에서 틀린 것으로 밝혀졌다(클라이언트는 있었다). 결정은 유지했다. 기본 사용자가 꺼져 있고 컨테이너에 자격이 없으니, 자격 없는 실행 프로브는 결국 TCP 확인과 같기 때문이다. 근거가 틀렸는데 결정이 맞은 경우라, 근거를 고쳐 적었다.
- **Secret 변경 시 자동 재시작 도구에 이 네임스페이스를 더하지 않았다.** 더하면 그 도구가 네임스페이스의 모든 Secret(DB 관리자 자격 · 메시지 브로커 CA 키)을 읽게 된다. 회전은 서버의 ACL 재적재 명령으로 하기로 했다(기존 연결이 끊긴다는 사실은 회전 과제로 인계).
- **실측(VD-4)은 임시 Job으로 하기로 했다.** 운영자가 자격을 터미널에 붙여 넣지 않도록, 검사 Job과 그 자격 ExternalSecret을 임시로 적용하고 로그만 읽은 뒤 지운다. 아직 없는 서비스의 키 때문에 원본 ExternalSecret이 통째로 실패하므로, 필요한 다섯 키만 남긴 사본을 쓴다.

## 결과와 검증
- 매니페스트 8장 + 검사 Job 확장(검사 항목 2 → 7) + 운영자 시드 블록(경로 7 · 모의 하네스 시나리오 150 · 단언 4,798 · 변이 20 중 19 포착, 생존 1은 등가 변이) + 확인 스크립트(모의 9경로).
- 저장소 관문 PASS 39 / FAIL 0 / WARN 4(기존 항목) — 빌더 · 리뷰 1 · 리뷰 2에서 각각 단독 실행. CI 전부 pass.
- 리뷰 1라운드 4렌즈 지적 16건(전부 low) · 2라운드 2렌즈 6건(전부 low) — 매니페스트 변경 없이 문서·사유 문구 수정으로 전부 반영. 리뷰어들이 소스로 반증을 시도한 주장은 전부 성립했다.
- 머지 전 라이브 사전 확인 11항목 전부 PASS(읽기 전용 자격).
- 머지 뒤: 자동 동기화가 머지 2분 뒤 시작해 3초에 끝났고 재시도 0 · 사후 확인 34항목 전부 PASS(볼륨 바인딩 · 두 인스턴스 기동 · 5분 스냅샷 저장 확인) · 하네스는 기대값대로(Dragonfly 두 항목이 FAIL → PASS, 볼륨 보호 항목 SKIP → PASS). 저장소 밖 자격(오브젝트 스토리지 세션 만료) 때문에 백업 검사 3건만 별도 FAIL.
- VD-4 1차 측정(임시 검사 Job): DB 검사 6개 PASS, 캐시 검사 7개 중 4개 FAIL — 두 결함을 드러냈다(아래 사고·오류). 로컬 재현으로 수정안을 확정했고, 재측정은 수정 뒤에 한다.
- 리뷰가 잡아 준 오류: 해시 가림 정규식이 축약 길이보다 길어 **절대 매치되지 않던** 기존 코드, 기동 실패 임계값의 경계 오차(3 vCPU는 통과 · 4부터 실패), 명령 범주 분류 착오(전체 삭제는 관리 범주가 아님).

## 사고·오류
- 설계 메모에 사실 오류 세 건을 적었다가 리뷰에서 고쳤다(클라이언트 부재 · 비밀번호 개수 산술 · 보호 어노테이션의 효력). 세 건 모두 산출물에는 영향이 없었지만, 정본 설계 문서가 산출물과 어긋난 채 남을 뻔했다. 리뷰어에게 "지시서의 근거도 반증 대상"이라고 명시한 것이 효과가 있었다.
- 지시서에 적은 관문 기대 수치가 관문의 집계 방식(파일 + 렌더를 함께 센다)과 달랐다. 수치 기대값은 관문 코드를 읽고 적어야 한다.
- **배포된 ACL 파일이 모든 인증을 막았다(설계 결함).** 기본 사용자 줄에 `-@all`을 넣은 것이 인증 명령까지 거부했다. 소스를 읽을 때 "파싱 오류 = 무인증 기동" 함정에 집중하느라 "인증 명령은 어느 사용자의 권한으로 검사되는가"를 묻지 않았다. 리뷰 네 렌즈와 두 라운드 모두 놓쳤다 — 모두 파일 문법과 로더에 초점을 맞췄고 인증 경로를 따라가지 않았다. 다행히 방향은 fail-closed(아무도 못 들어감)였고 소비자는 아직 없었다. 복구는 ACL 파일 두 경로를 다시 렌더해 pod를 교체하는 것이다.
- **검사 Job의 첫 1–2초가 "연결 거부"였다.** 캐시 서버는 재시작도 없고 엔드포인트도 정상이었다. 새 pod가 뜬 직후 네트워크 정책 규칙이 아직 반영되기 전의 경합으로 보고, Job 첫머리에 짧은 기동 유예(최대 15초 · 거부가 사라질 때까지)를 넣기로 했다. 뒤 과제의 다른 검사 Job에도 같은 패턴이 필요하다.
- **시드 블록이 두 번 "Vault 도달 실패"로 멈췄다(쓰기 0).** 원인은 블록도 클러스터도 아니었다. 운영자 PC의 다른 애플리케이션이 로컬 포트 18200(IPv4)을 쓰고 있어, 포트 포워딩이 IPv6 주소 한 줄만 열고 조용히 넘어갔고, Vault CLI는 IPv4로 그 애플리케이션에 붙어 응답을 기다리다 시간 초과했다. 교훈: 포트 포워딩은 "`127.0.0.1`과 `[::1]` 두 줄"이 모두 보여야 성공이고, 연결 거부가 아닌 **시간 초과**는 "누군가 듣고 있는데 상대가 다르다"는 신호다. 점유 프로세스를 확인하는 한 줄 명령을 런북 실패 표에 넣을 후보로 적었다.
