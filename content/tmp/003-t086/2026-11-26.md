# 003-platform-foundation T086 — 콘텐츠 로더 시험 먼저: 순수 마크다운 계약과 「지우지 말고 실패」를 빨강으로 고정하기 (2026-11-26)
> 11-23 ~ 11-26을 함께 담는다. T086–T089를 한 설계로 11-23 ~ 24에 확정하고 11-24에 빌드했다. 그날 세션은 수정 라운드 도중 주간 사용 한도로 끊겨 기록을 남기지 못했다. 11-26에 재개해 수정 · 검증을 마치고 빨강을 다시 관찰했다. tick은 이 기록과 같은 커밋이다.

## 문제
- 노트 사이트의 콘텐츠 로더(T090)를 만들기 전에, 로더가 지킬 계약을 시험으로 고정하고 「구현이 없어서」 실패하는 것을 보여야 했다.
  - 과제 문면: 노트 2편 로드(제목 · 날짜 · 태그 · slug · lang) · `pubDate` 누락 오류 · 번역 연결 · ko 파일 없음 오류 · 프로덕션 draft 제외 · `updatedDate < pubDate` 오류 · 헤딩 앵커 · 읽기 시간.
- 설계 도중 사용자 결정(T086-e)으로 범위가 넓어졌다.
  - 노트 파일은 `.mdx`지만 본문은 순수 Markdown + GFM이다.
  - JSX · `import`/`export` 줄 · 중괄호 식 · 원시 HTML · 허용 밖 URL이 있으면 빌드가 실패해야 한다.
- 저장소가 공개라 CI 빌드 로그도 공개다. 오류가 위반 값(URL · 프런트매터 값 · 원문 줄)을 실어 나르면 안 된다.
- 이런 시험은 빈 PASS가 쉽다. 아무것도 막지 않는 가드도, 코드 블록까지 다 막는 가드도 초록이 될 수 있다.

## 배운 개념
- **MDX 실행 차단을 내장한 오픈 소스 콘텐츠 레이어는 없었다.**
  - 사용자가 「오픈 소스 중에 다 반영된 것은 없나」를 물어 조사했다. 가장 가까운 후보도 읽기 시간 · 프로덕션 draft 제외 · 「ko 없이 번역만 있으면 오류」 · MDX 가드가 빠졌고, 의존은 자체 조합의 약 2배였다.
  - `.mdx`를 remark-parse + GFM + 프런트매터로만 파싱하면 실행 경로가 없다. `import` 줄과 중괄호는 글자로 남고, 태그 꼴은 `html` 노드가 된다.
- **조용히 지우지 말고 실패시킨다.**
  - remark-rehype 기본값은 `html` 노드를 조용히 버린다. 지우기형 도구(sanitize 계열)도 같다. 노트를 쓰는 에이전트의 실수가 숨는다.
  - 그래서 거부 플러그인이 위반을 모아 빌드를 멈춘다. 오류에는 파일 · 줄 · 규칙 이름(`raw-html` · `esm` · `expression` · `unsafe-url`)만 싣고 값은 싣지 않는다.
- **URL은 차단 목록이 아니라 허용 목록으로 본다.**
  - 허용 = http · https · mailto(대소문자 무관) · 상대 경로 · `#`. React 19는 `javascript:`만 무해하게 바꾸고 `data:`는 그대로 둔다. 문자 참조 · 탭으로 만든 스킴은 해석한 뒤의 값으로 판정한다.
  - 소문자 차단 목록 스텁은 대소문자 섞인 스킴 · ftp · 꺾쇠 속 공백 · 탭 문자 참조 · `//` · 역슬래시 사례를 모두 놓쳤다.
- **파서 기본값도 공격면이다.**
  - 흔히 쓰는 gray-matter는 `---js` 프런트매터를 eval한다. → `yaml` 패키지로 읽고, 첫 줄이 정확히 `---`가 아니면 `fence` 오류.
  - Node의 `TextDecoder`는 기본으로 BOM을 지운다(실측). `ignoreBOM: true`로 남겨야 「첫 줄 = `---`」 판정이 BOM 파일을 거부한다.
- **기본값은 닫힌 쪽(N-1).**
  - 컴파일이 `next build` 밖의 Node 생성 단계로 옮겨 「빌드 = production」 전제가 깨졌다.
  - → `NODE_ENV`가 정확히 development · test일 때만 draft를 포함하고, 미설정 · staging은 뺀다.
- **빈 PASS는 스텁으로 막는다.**
  - 던지는 · 관대한(`[]`) · 가드 없는 · 과잉 가드(코드 블록 안까지 거부) · 소문자 차단 목록 스텁을 저장소 밖에서 돌려, 각 스텁이 통과하면 안 되는 사례의 통과가 0인지 본다.
  - 금지 사례는 한 root에서 한 번 호출해 issues 전체를 정확 비교한다. 한 파일만 빠져도 실패한다.
- **변이가 시험의 날을 세운다.** 리뷰 · 검증의 변이가 첫 시험을 그대로 통과한 곳이 넷이었다(아래 넷).
- **오류 객체로 새는 원문(B-1)**
  - 첫 시험은 message · issues만 봐서, 원문을 `cause` · 숨은 자기 속성 · `stack`에 싣는 구현이 47/47 초록이었다. Node와 vitest는 `[cause]`까지 찍으므로 공개 CI 로그로 나간다.
  - → 바늘 대상을 `util.inspect` 출력과 stack까지 넓히고, `cause === undefined` · 자기 속성 키 ⊆ `{issues, name, message, stack}`을 단언한다.
- **최상위만 도는 거부 플러그인(B-4)**
  - 금지 픽스처가 모두 최상위 블록이라 초록이었다. → 목록 항목 · 인용 · 표 칸 · 헤딩 · 링크 글자 · 각주 정의 안의 중첩 픽스처 여섯을 더했다.
  - CommonMark에서 `> <b>x</b>`는 html 블록이 아니다(유형 7 html 블록은 여는 태그 뒤에 공백만 와야 한다). 글줄 html 노드가 여는 태그 · 닫는 태그 둘이라 issue도 둘이다.
- **날짜 꼴(A-7)**
  - 시험이 문자열과 Date를 다 받아 어느 쪽이든 통과했다.
  - → `'YYYY-MM-DD'` 문자열 하나. YAML 1.2 core는 따옴표 없는 날짜도 문자열로 읽고, T091은 이 값을 `time[datetime]`에 그대로 쓴다.
- **「변형 파일마다」(V1-2)**
  - ko 없는 slug의 issue를 첫 변형에만 내는 구현이 통과했다(픽스처 변형이 en 하나뿐).
  - → ja 변형 픽스처를 더해 두 issue를 정확히 기대한다. 파일 이름 규칙 `(en|ja)`의 ja 쪽도 이 픽스처가 처음 고정했다.

## 선택과 대안
- **로더(사용자 결정 T086-e)**: (A) 자체 구현 + 순수 마크다운 · (B) 콘텐츠 레이어 채택 · (C) 혼합 가운데 (A).
  - 까닭: 어느 쪽이든 안전 가드는 직접 짜야 한다. (A)는 의존을 늘리지 않고 ADR 0004 D19(자체 로더)를 그대로 둔다.
  - 다시 볼 때: 본문에 컴포넌트가 필요해지면 remark-mdx + 허용 목록 거부 플러그인으로 옮기고 새 ADR을 쓴다.
- **본문 다섯 절 검증의 자리(리뷰 A-1 → 컨트롤러 결정)**
  - 설계는 이 검증을 T090 TDD로 넘겼다. 그런데 픽스처는 짧은 노트라 다섯 절을 가진 파일이 0이다. 절을 검증하는 변이는 48건 가운데 41건을 다른 이유로 실패시켰다.
  - → `getCollection`은 본문 절을 검증하지 않는다. 다섯 절은 사람 검토와 /finish가 맡고, 실제 노트 2편은 ld-1(h2 다섯 · 순서 · 앵커 id)이 지킨다. T090 지시문에 반드시 싣는다.
- **V1-2를 고친 길**: 주석을 「이 시험은 en 하나만 본다」로 좁히는 길 대신 픽스처를 더했다. 규칙은 글이 아니라 시험으로 고정한다.
- **자기 속성 키는 같음이 아니라 부분 집합**: private 필드 + 접근자 같은 정상 구현은 막지 않으면서, 누출 경로(cause · 다른 자기 속성)는 닫는다.
- **바늘 값**: stack까지 보게 되어, 새 바늘은 파일 경로 · 스택 프레임 글자와 겹치지 않는 값만 쓴다(겹치면 거짓 빨강).
- **커밋 몫 나누기**: data-model.md 한 파일에 T086 몫(`sources` 행)과 ⑤ 몫이 함께 있다. 대화형 `git add -p` 대신 덩어리를 거른 패치를 `git apply --cached`로 스테이징한다.

## 사고·오류
- **수정 라운드가 주간 사용 한도로 끊겼다.**
  - 11-24 19:14(KST) 수정 r1을 맡은 7명(수정자 5 · 검증 2)이 모두 보고 없이 오류로 끝났다. 작업 트리에는 빌드 r0와 r1 일부가 커밋 없이 남았다. 검증 둘은 수정 보고 없이 빈 입력으로 떴다가 같은 한도로 끊겼다.
  - 11-26 재개: 컨트롤러가 수정자마다 대화 기록의 도구 호출에서 「첫 시도 흔적」을 뽑아 지시문에 싣고 남은 것만 맡겼다. 수정자는 「고치기 전 사본」이 정말 r0인지 먼저 확인했고, 검증은 「수정 보고가 빠지면 건너뛴다」로 묶었다.
  - T086 수정자: 첫 시도는 중첩 픽스처 여섯과 참조 구현 확장까지 했고 시험 파일은 손대지 않았다. 첫 시도의 before 출력은 쓰지 않고 r0 사본을 새로 만들어 다시 돌렸다(결과 같음).
  - 재개는 7명 모두 오류 없이 끝났다. 첫 시도의 반쪽 수정 둘(T089 기록)은 재개한 수정자가 찾아 고쳤고, 검증은 중복 · 반쪽이 남지 않았음을 실물로 확인했다.
  - 교훈: 끊긴 작업의 흔적은 출발점일 뿐이다 — 재개는 before 사본과 diff 대조부터 한다.
- **하위 에이전트의 `cd`**: T086 수정자가 `cd <절대 경로> && …`를 여러 번 썼다(자진 신고 · 저장소 영향 0). 교훈: 실행 위치는 절대 경로 · `--directory` · spawn `cwd`로 준다.
