# 003-platform-foundation T036 — 노드 B 조인과 write-only 백업: 조용한 실패를 설계로 막기 (2026-09-04)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제
T035에서 노드 A에 K3s server가 올라갔지만, 서버 하나는 아직 클러스터가 아니다. T036은 두 가지를 같이 닫는 task였다. (1) 노드 B를 agent로 조인해 `role=platform`/`role=data` 2노드를 Ready로 만들고, (2) 그 순간부터 컨트롤플레인 상태(kine SQLite)의 백업을 갖는다. 백업을 뒤로 미루면 "복구 불가능한 클러스터 위에 플랫폼을 쌓는" 구간이 생기고, 그 구간이 길어질수록 되돌릴 수 없다.

두 작업의 공통 난점은 **실패가 조용하다**는 것이었다. 조인은 비밀(조인 토큰)을 사람 손으로 옮기는 일이고, 잘못된 토큰으로 조인하면 agent는 오류로 죽지 않고 영원히 재시도한다. 백업은 더 나쁘다 — "스크립트가 exit 0을 냈다"가 "복원 가능한 번들이 올라갔다"를 전혀 보장하지 않는다.

## 배운 개념
**K3s 조인 토큰에는 두 형식이 있다.** 짧은 형식(비밀번호만)과 보안 형식 `K10<CA sha256>::server:<pw>`. 보안 형식은 토큰 안에 서버 CA 인증서의 sha256을 담고 있어서, agent가 **조인하기 전에** 상대 서버의 CA를 검증한다 = 조인 시점 MITM 방어. 첫 서버는 CA가 생기기 전이라 짧은 형식만 쓸 수 있고, 그래서 "서버는 짧게 시작하고 agent는 보안 형식으로 조인한다"는 비대칭이 정상이다. 서버 토큰은 동시에 datastore bootstrap 데이터의 PBKDF2 암호이므로, 토큰을 잃으면 DB 스냅샷이 무용지물이 된다 — 백업 번들에 토큰이 들어가야 하는 이유가 여기서 나온다.

**비밀은 "어디에 남는가"로 판단해야 한다.** K3s 공식 install.sh의 `create_env_file`은 환경에 있는 `K3S_*` 변수를 전부 `k3s-agent.service.env`에 **평문으로** 기록한다. 편의로 `K3S_TOKEN=…`을 주면 비밀이 디스크에 영구히 남는다. 그래서 설치는 `env -i`로 환경 상속을 끊고 `INSTALL_K3S_VERSION`·`INSTALL_K3S_EXEC=agent`만 넘기며, `server`/`token-file`은 `config.yaml`(0600)에만 둔다. 토큰 자체는 파일로만 이동하고 스크립트는 읽되 출력하지 않는다.

**조용한 실패의 형태.** 토큰이나 CA가 어긋나면 k3s agent는 `Waiting to retrieve agent configuration; server is not ready`를 무한 반복하고, unit이 `TimeoutStartSec=0`이라 `systemctl enable --now`가 그대로 블록된다. 즉 "멈춘 것처럼 보이는 정상 종료 없음"이 유일한 증상이다. 그래서 설치 전에 서버 `/cacerts`의 sha256과 토큰 앞부분을 대조하는 사전 진단을 넣었다. 사후 로그 추적보다 사전 대조가 압도적으로 싸다.

**kine SQLite 백업은 파일 복사가 아니다.** K3s는 embedded etcd가 아니라 kine/SQLite를 쓰므로 `etcd-snapshot`이 없고, kine DSN이 WAL 모드라 실행 중 파일 복사는 `-wal` 누락 위험이 있다. `sqlite3 ".backup"`이 온라인에서 일관 스냅샷을 만드는 정식 경로이고, 그 뒤 `PRAGMA integrity_check`로 스스로 확인한다. 번들에는 DB만으로 부족하다 — `server/token`(없으면 복호화 불가), `server/cred/`, 그리고 `server/tls/`가 필요하다. `server/tls/` 없이 복원하면 서버가 인증서를 재생성하고 **노드 B의 재조인이 깨진다**. 번들 구성원을 `server/` 접두 그대로 둔 것도 학습이다: 평면 이름으로 담으면 복원 절차가 `mv`를 요구하고, 사고는 그 `mv`에서 난다.

**백업 경로는 노드를 신뢰하지 않도록 설계할 수 있다.** age 수신자 **공개키만** 노드에 두고 개인키는 오프라인 보관 → 노드가 침해돼도 자기 백업을 읽지 못한다. 업로드 자격은 OCI 인스턴스 프린시펄뿐이고 권한은 객체 생성·조회만(삭제·다운로드 없음), 보존은 버킷 lifecycle이 관리한다 = 노드가 과거 백업을 지울 수 없는 write-only 백업. 랜섬웨어 시나리오에서 "백업도 같이 지워졌다"를 구조로 막는다.

**감시할 수 없는 백업은 성공이 아니다.** 성공 시 node_exporter textfile collector 디렉터리에 `platform_backup_last_success_timestamp{component="k3s"|"vault"}`를 **컴포넌트 라벨별 별도 파일**로, 임시 파일 + `mv`로 원자 기록한다. 하나만 실패해도 stale 알림이 그 컴포넌트만 잡는다. 반대로 이 기록이 실패하면 업로드가 성공했어도 그 컴포넌트를 FAIL로 보고한다.

**bash 함정 하나.** `f || true`로 호출된 함수는 그 **동적 범위 전체**(안에서 부르는 함수까지)에서 `set -e`가 꺼진다. 컴포넌트 단위로 계속 진행하려고 `|| true`를 쓴 순간 errexit은 사라진다.

## 선택과 대안
- **조인 토큰**: `k3s token create`의 만료형 bootstrap 토큰은 더 안전하지만 재조인 자동화가 복잡해 기각. `K3S_TOKEN` 환경변수는 env 파일 평문 잔존으로 기각. → 보안 형식 `token-file`(research K3S-D5).
- **CA 해시 대조를 die로 올릴까**: 라이브 클러스터에서 한 번도 실측하지 않은 대조를 차단으로 쓰면, 대조 자체의 버그가 조인을 막는다. 그래서 첫 회는 **진단(warn)**으로 두고 실측 결과를 보고 승격을 판단하기로 했다. 실행에서 일치가 확인됐다.
- **백업 방식**: `systemctl stop k3s` 후 tar는 가장 단순하지만 제어평면이 수십 초 끊겨 기각. Litestream은 kine DSN에 옵션을 전달하는 경로가 미확인이라 기각(research K3S-D9).
- **`--pre-upgrade` 게이트 범위 — 이 task에서 가장 중요한 설계 판단**: 초안은 "백업 전부 성공해야 업그레이드 시작"이었다. 그런데 Vault는 T044에서야 배포되므로, vault를 무조건 필수로 하면 그 전까지 SUC prepare가 **항상** exit 1 → K3s 자동 업그레이드가 구조적으로 막힌다. 보안을 위한 게이트가 보안 패치를 막는 형태다. 그래서 k3s는 항상 필수, Vault는 **배포돼 있을 때만 필수**(Service 탐지)로 나눴다. 게이트 약화가 아니라는 근거: 없을 때만 WARN 후 건너뛰고, **있는데 실패하면 그대로 exit 1**이다. 덧붙여 `--pre-upgrade`는 `--components` 병용을 거부한다 — 인자로 게이트 범위를 좁히는 우회를 막기 위해서다.

## 결과와 검증

- 타이머 다음 실행 02:30 KST, `systemd-analyze calendar '*-*-* 02:30:00 Asia/Seoul'` 정규화 성공 = `OnCalendar`의 시간대 접미사가 실제로 해석된다는 확인(UTC 17:30).

## 다음 학습
- `--pre-upgrade` 실제 리허설은 SUC 도입(T037) 뒤로 넘겼다. 게이트 로직을 만든 시점과 그 경로를 처음 밟는 시점이 다르다는 사실 자체를 기록해 둘 가치가 있다(T044에서 k3s+vault 양쪽 PASS 확인).
- **"백업이 있다"와 "복원된다"는 다른 주장이다.** 이 task는 전자만 증명했다. 복호화 → `PRAGMA integrity_check`/스냅샷 inspect는 T048, 실제 복원 절차는 rollback 런북 몫이다. 이 간격을 잔여 위험으로 명시해 두는 편이 낫다.
- 지표는 썼지만 **라벨 부재를 잡을 알림**이 있는지는 아직 모른다 — `absent()`·stale 규칙이 컴포넌트 라벨별로 성립하는지 모니터링 task에서 확인할 항목.
- 같은 errexit 패턴과 같은 정적 테스트 구멍이 앞선 부트스트랩 스크립트 스위트에도 있는지 다음 하네스 라운드에서 점검한다(리뷰는 한 파일에서 찾았지만 습관은 파일 경계를 넘는다).

## 사고·오류
1. **`|| true`가 errexit을 삼켰다.** 리뷰가 잡은 핵심 결함: `cp` 실패와 textfile 기록 실패가 `RESULT=OK`·exit 0으로 보고되는 경로가 있었다. 즉 **빈 `cred/`·`tls/`가 든 "정상" 번들이 조용히 올라갈 수 있었다.** 수정은 두 겹 — 컴포넌트 함수 안에서는 errexit에 기대지 않고 명령마다 실패 분기를 두고, tar 뒤에 원본 파일 수와 번들 항목 수를 대조한다(GNU `cp`는 항목별 오류에도 나머지를 계속 복사하고 마지막에만 non-zero를 내므로 수 대조가 유일한 방어선이다).
2. **게이트가 업그레이드를 막는 설계 오류**(위 `--pre-upgrade`). 리뷰가 "Vault가 아직 없는 구간"을 지적해서야 드러났다. 교훈: 시간축에서 아직 존재하지 않는 의존을 필수로 요구하는 게이트는 fail-closed가 아니라 **stuck-closed**다.
3. **정적 테스트의 구멍.** "함수 본문이 존재한다"만 보는 단언은 호출부 삭제·순서 뒤집기·주석 처리를 잡지 못한다. 호출 그래프(존재 + 순서)와 unit 파일의 `키=값` 파싱까지 고정해야 변이가 걸린다.
4. **정상을 경고로 분류한 보고.** 낡은 성공 로그로 `confirmed`가 되는 것을 막으려고 등록 로그 검색에 "이번 실행 시작 이후" 시각 필터를 걸었는데, 이미 조인된 노드의 kubelet은 재실행에서 새 등록 로그를 남기지 않는다. 그 결과 멱등을 증명한 2회차가 `registration=unconfirmed` WARN을 냈다. 판정을 **이번 실행 / 이번 부팅 / 없음** 3단계로 나눠 정정했다(`ac9db59`). 교훈: "증거 없음"과 "실패"는 다른 상태이고, 자동 보고는 그 둘을 구분해야 한다. 엄격한 필터가 곧 정확한 보고는 아니다.
5. 노드 A 커널 버전이 T035 기록과 달라져 있었다 — 당시에는 **원인 미확인**으로 사실만 남겼고, 같은 날 T038 실행 기록에서 운영자가 노드 A를 직접 재부팅한 것으로 설명됐다(런북 §3 T038 절차 메모). 교훈: 설명되지 않은 관측은 추측으로 메우지 않고 '미확인'으로 남겨 두면 뒤 기록이 닫아 준다.
6. **후속 사건 — 파드 DNS 업스트림이 IMDS 주소였다(2026-09-08).** T041의 계약 정책 `deny-imds`(egress `0.0.0.0/0 except IMDS`)를 적용하려는 시점에 실측해 보니, kubelet이 파드에 물려주는 resolv.conf의 유일한 업스트림이 OCI VCN 리졸버 = IMDS와 같은 주소였다. K3s 소스가 그대로 설명한다: `locateOrGenerateResolvConf`는 `/etc/resolv.conf` → `/run/systemd/resolve/resolv.conf` 순서로 첫 "유효" 파일을 쓰고, `isValidNameserver`는 전역 유니캐스트가 아니어도 **IMDS 주소만은 예외로 통과**시킨다(일부 클라우드가 사설 DNS 포워딩에 그 주소를 요구하기 때문). 그대로 정책을 적용했다면 CoreDNS의 외부 이름 해석이 끊겨 Argo의 git 접근·ACME·터널 재해석이 동시에 죽었을 것이다. **뒤집힌 가정: "노드 기본 resolv.conf는 중립적인 값이다".** 결정 B는 계약을 고치지 않고 노드가 파드에 물려주는 파일만 공개 리졸버로 바꾸는 것 — 계약 매트릭스 변경 0. 두 스크립트에 `resolv.conf` 렌더 + `config.yaml`의 `resolv-conf` 키를 넣고 단언을 67→76(agent)·69→78(server)로 늘렸다. 여기서도 배운 것은 "파드가 새로 만들어져야 새 업스트림을 받는다"는 점이다 — sandbox의 resolv.conf는 생성 시점에 고정된다.
