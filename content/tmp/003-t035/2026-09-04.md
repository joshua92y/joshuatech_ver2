# 003-platform-foundation T035 — 클러스터의 첫 기동은 한 번뿐이다: 멱등 스크립트로 K3s server 세우기 (2026-09-04)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제

2노드 K3s의 첫 노드(server)를 세우는 일이었다. 그런데 어려운 쪽은 "설치"가 아니라 "재현 가능한 설치"였다. 세 제약이 겹쳤다. ① 저장소 규칙상 부트스트랩 스크립트는 멱등이어야 한다 — 두 번 돌려도 같은 최종 상태여야 하고, 2회차 요약의 `changes this run: 0`이 그 증명이다. ② K3s에는 **첫 기동에만 적용되는 설정**이 있다. 노드 라벨은 kubelet 등록 때 한 번만 반영되고, secrets-encryption은 서버 재시작 없이는 켤 수 없으며 나중에 켜면 기존 Secret 전체를 재암호화해야 한다. 즉 설치 명령을 실행하기 **전에** 선언 파일이 확정돼 있어야 한다. ③ 서버 토큰은 단순한 비밀번호가 아니라 데이터스토어 bootstrap 데이터의 암호다. 유출되면 클러스터가 열리고, 잃으면 백업 스냅샷이 복호화되지 않아 무용해진다. 그래서 스크립트는 토큰을 만들지도, 읽지도, 로그에 남기지도 않아야 했다.

## 배운 개념

- **선언 파일 한 곳 vs CLI 인자.** K3s는 플래그를 `/etc/rancher/k3s/config.yaml`로도 받고 키는 CLI 플래그와 1:1로 매핑된다. CLI 인자를 섞으면 리스트 값(노드 라벨 같은 것)을 **통째로 덮어쓴다** — 설정이 두 곳에 흩어지면 한쪽만 고치고 다른 쪽이 이긴다. 그래서 설치기에는 버전과 `server` 역할만 주고 나머지 전부를 파일에 뒀다.
- **설치 스크립트가 환경 변수를 파일로 굳힌다.** K3s 공식 install.sh는 자신이 본 `K3S_*` 환경 변수를 `/etc/systemd/system/k3s.service.env`에 그대로 기록한다. 토큰 경로나 값을 환경 변수로 넘기면 평문으로 디스크에 남는다는 뜻이다. 대응은 `env -i`로 상속을 끊고 필요한 두 변수만 명시 전달하는 것 — 설치기는 신뢰 경계이고, 그 경계를 넘는 것은 열거된 것뿐이다.
- **데이터스토어 선택이 백업·복구 절차 전체를 정한다.** 단일 서버 구성의 기본 데이터스토어는 kine 위 SQLite다. 여기서는 `k3s etcd-snapshot`이 존재하지 않고 `--cluster-reset`은 **금지**다(embedded etcd 전용이며 실행하면 etcd로 비가역 전환된다). 백업은 SQLite 온라인 스냅샷 API + 토큰·자격 디렉터리 묶음이고, 복구는 "버전 핀 재설치 → 정지 → 파일 교체 → 기동"이다. "어떤 DB를 쓰는가"가 운영 런북의 문장을 바꾼다.
- **라벨 하나가 스케줄링 정책을 반전시킨다.** 번들 로드밸런서(ServiceLB)는 특정 라벨이 **어느 노드에든 하나라도** 붙으면 allow-list 모드로 전환되고, 라벨 없는 노드에는 로드밸런서 파드를 아예 만들지 않는다. 덕분에 80/443 hostPort는 플랫폼 노드만 점유한다. 라벨을 빼먹으면 두 노드가 모두 진입점이 된다.
- **멱등은 "같은 최종 상태"이고 "같은 부작용"이 아니다.** 파일은 임시 파일에 먼저 쓰고 내용을 비교해 다를 때만 같은 디렉터리에서 rename으로 교체한다(반쪽 파일을 읽히지 않게). 그리고 config가 바뀌어도 **실행 중인 서버를 재시작하지 않고 경고만** 남긴다 — 재실행이 제어평면을 끊으면 그건 멱등이 아니라 재난이다.
- **노드에서 실행할 수 없는 코드의 테스트는 "원문 계약"이다.** CI에서 돌릴 수 없으니 테스트는 스크립트 본문을 읽어 형태를 고정하는 정적 단언 69개로 썼다(대상 파일이 없으면 전부 FAIL = fail closed). 금지 항목도 단언이다: 토큰 값을 읽는 명령이 검증 함수 본문에 없어야 하고, 셸 트레이싱(`set -x`)이 파일 어디에도 없어야 한다(켜면 토큰이 로그로 새어 나간다). 단언이 실제로 뭔가를 잡는지는 스크립트를 일부러 19가지로 망가뜨려 확인했다.

## 선택과 대안

- **버전 채널 기각.** `INSTALL_K3S_CHANNEL=stable`은 시점마다 다른 버전을 뜻해 재현성이 없다. 버전을 문자열로 고정하고 패치 승격은 별도 컨트롤러의 Plan에 넘겼다. 그래서 스크립트는 "다른 버전이 이미 설치돼 있으면 중단"한다 — 조용히 업그레이드하지 않는 편이 안전하다.
- **암호화 provider: 기본 aescbc 기각.** 쿠버네티스 공식 문서가 CBC padding oracle 때문에 권장하지 않는다. KMS v2도 기각(이 클라우드 KMS용 플러그인이 없어 과하다). secretbox를 첫 기동부터 켰다 — 나중에 바꾸려면 키 회전과 재암호화가 따라오기 때문이다.
- **노드 외부 IP 지정 기각.** 이 클라우드의 공인 IP는 NAT라 외부 IP를 선언하면 `externalTrafficPolicy=Local`이 오동작한다는 문서 경고가 있고, 원 클라이언트 IP는 어차피 CDN 헤더로 받는다.
- **번들 컴포넌트 끄기 기각.** Traefik·local-path·CoreDNS·메트릭 서버를 그대로 둔다. 번들 chart는 전용 CRD로 커스터마이즈할 수 있고, 2노드·arm64 규모에 MetalLB나 분산 스토리지를 얹는 건 과하다. 대신 "번들 버전이 K3s 버전에 묶인다"는 종속을 받아들였다.
- **토큰 형식은 역할별로 다르다.** 첫 서버는 CA가 아직 없어 짧은 형식(비밀번호만)만 가능하고, 조인용 보안 형식은 CA 해시를 품는다. 스크립트는 보안 형식이 들어오면 **거부**한다 — 타입 검사처럼 쓴 것이고, 다음 task에서 정확히 반대 방향의 검사를 넣게 된다.
- **`curl | sh` 기각.** 설치 스크립트 자체의 체크섬은 공개 문서에 없다(그 스크립트가 내려받는 바이너리는 릴리스 해시 자산과 대조된다). 그래서 운영자가 사본을 내려받아 버전 고정·바이너리 검증 코드를 눈으로 확인하고, 스크립트는 노드에 올라온 사본의 sha256이 그 사본과 같은지 사전 대조한다. **검증할 수 없는 것과 검증할 수 있는 것을 분리**해 신뢰를 사람 한 지점으로 모은 셈이다. 같은 이유로 토큰 생성 예시도 셸 기본 PATH에 없을 수 있는 `openssl`에서 런타임에 항상 있는 .NET 난수 API로 바꿨다 — 절차서는 "있을 법한 도구"가 아니라 "확실히 있는 도구"로 쓴다.
- **경계: 앞 task의 결과는 재구성하지 않고 검증만 한다.** cgroup·WireGuard 모듈·방화벽 규칙·시간대는 호스트 준비 스크립트 소관이고, 여기서는 없으면 "먼저 그 스크립트를 돌려라"며 멈춘다. 같은 상태를 두 스크립트가 각자 주장하면 결국 서로를 되돌린다.

## 결과와 검증

- 1회차 `changes this run: 2`(config 렌더 + 설치), 노드 Ready까지 약 5초. **2회차 `changes this run: 0`** — 설치 skip, 서비스 이미 enabled+active, Ready 대기 0초. 이것이 멱등의 실측 증거다.
- `secrets-encrypt status` = Enabled, 회전 단계 start, 서버 암호화 해시 전부 일치. 노드 1대 Ready(control-plane), 역할 라벨과 로드밸런서 허용 라벨 모두 확인.
- **가정이 측정으로 바뀐 지점 1:** `k3s.service.env` 크기가 **0바이트**였다. `env -i` 격리가 실제로 동작해 토큰 관련 변수가 서비스 env 파일에 남지 않았다는 직접 증거다. "그럴 것이다"가 아니라 파일 크기로 확인했다.
- **가정이 측정으로 바뀐 지점 2:** WireGuard 오버레이 인터페이스는 1회차 직후에는 **없었고** 2회차에서 **있었다**. 한 번 보고 "설정이 안 먹었다"고 결론 내렸으면 틀렸을 것이다. 기동 직후의 부재는 실패가 아니라 타이밍이었다.
- 정적 스위트 69 단언 통과(변이 19종 검출 확인), 저장소 전체 검사에 슬롯으로 등록. admin kubeconfig는 1회만 취득해 운영자 비밀번호 관리자에만 두고, 에이전트·tester·CI에는 배포하지 않는다(그들은 뒤 task의 읽기 전용 토큰 kubeconfig를 쓴다).

## 다음 학습

- 조인 노드는 같은 "토큰 파일" 규약을 쓰지만 요구 형식이 반대이고, 조인 **전에** CA 해시를 대조해 중간자를 막는다. 같은 추상에 역할별 검사를 붙이는 패턴이 어디까지 유효한지 보고 싶다.
- 첫 기동 이후 config를 바꿔야 할 때의 반영 절차. 실제로 뒤 task에서 파드 DNS 업스트림 키가 이 파일에 추가됐고, 살아 있는 노드에 적용하려면 별도 운영자 절차가 필요했다.
- 아직 리허설하지 않은 것 둘: 암호화 키 회전(`rotate-keys` → 재암호화 완료 확인 → 재시작), 그리고 백업 번들을 실제로 복호화해 SQLite 무결성을 확인하는 절차(재부팅·복원 리허설 task 몫).

## 사고·오류

- **Ready 판정이 문자열 완전일치였다.** `kubectl get nodes`의 STATUS 열을 `== "Ready"`로 비교했는데, cordon된 노드는 `Ready,SchedulingDisabled`로 표시된다. 자동 업그레이드는 노드를 cordon하므로 업그레이드 뒤 재실행이면 스크립트가 180초를 기다린 뒤 "Ready가 아니다"라며 죽는다. `^Ready(,|$)` 정규식으로 고쳤다. **배움: 사람이 읽도록 만든 표의 열을 완전일치로 비교하면, 부가 상태가 붙는 순간 깨진다.**
- **설치 실패가 조용히 지나갈 수 있었다.** 설치기 호출에 실패 처리가 없어서 뒤따르는 버전 재확인까지 가서야 이상해졌다. `|| die "실패(exit …)"`로 실패 지점에서 멈추게 했다.
- **문서의 용어와 런타임 출력의 용어가 달랐다.** 상태 출력의 키 타입 표기는 provider 이름이 아니라 알고리즘 이름(`XSalsa20-POLY1305`)이다. 'secretbox' 문자열만 찾던 검사는 **정상 상태에서 경고를 냈다** — 검사식이 틀린 거짓 경보였다. 두 표기를 모두 허용하도록 정정했다.
- **롤백 수단이라 믿었던 것이 더 비싼 되돌리기였다.** 번들 uninstall 스크립트는 설정 디렉터리를 통째로 지운다 — 토큰과 config까지 사라지므로 재부트스트랩이 "토큰 배치" 1단계부터 다시 시작된다. "절대 하지 않는 것" 목록에 넣었다.
- 운영자 워크스테이션의 ssh-agent 서비스가 꺼져 있어 확인 프롬프트를 붙인 키 로드가 실패했고, 매 접속마다 passphrase를 입력했다. 규칙이 요구하는 "사용마다 확인"을 더 강하게 충족하므로 그대로 진행했다(불편이 요건을 더 잘 만족하는 드문 경우).
