# 003-platform-foundation T041 — GitOps 권한 경계와 default-deny 네트워크를 같은 날 세우기 (2026-09-08)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제

T041은 살아 있는 클러스터에 성질이 다른 두 경계를 동시에 세우는 task였다. 하나는 GitOps 권한 경계(AppProject 5개 + app-of-apps로 Application 19개), 다른 하나는 네트워크·워크로드 경계(Namespace 14 + NetworkPolicy 93 + PSA 라벨 + ResourceQuota/LimitRange + 읽기 전용 `agent-view` RBAC)다.

둘 다 틀리면 손이 닿지 않는 종류라는 점이 어려웠다. Argo CD root Application은 이미 `automated` + `selfHeal`로 돌고 있어서 잘못된 파일이 `main`에 들어가면 3분 안에 스스로 적용한다. 그리고 앞선 task에서 클러스터·노드 접근 경로를 터널 하나로 좁혀 둔 상태였다 — default-deny 정책 한 장이 잘못 들어가면 고치러 들어갈 길 자체가 닫히고, AppProject를 잘못 봉인하면 Argo CD가 자기 자신을 고칠 수 없다.

## 배운 개념

- **NetworkPolicy는 allow의 합집합이다.** 같은 파드를 고르는 정책이 여러 장이면 허용이 더해진다. 그래서 직전 task에서 상류 Argo CD 매니페스트에 딸려 온 NetworkPolicy 5장을 먼저 지웠다(그대로 두면 계약 밖 허용이 조용히 합쳐진다). 같은 성질 때문에 "차단 정책"이라는 것은 default-deny가 **없는** 네임스페이스에서만 존재할 수 있다: `except`로 IMDS만 빼고 허용하는 `deny-imds`는 `kube-system`에서만 의미가 있고, default-deny가 있는 13개 네임스페이스에서는 규칙마다 `ports` + `except`를 쓰는 형식으로 같은 통제를 표현해야 한다.
- **NetworkPolicy는 DNAT 이후의 주소를 본다.** 파드는 kube-api를 Service ClusterIP 443으로 부르지만, 허용해야 하는 대상은 노드의 사설 주소와 6443이다. 프로브로 확인하기 전에는 이 차이가 "정책은 맞는데 왜 막히지"로 나타난다.
- **app-of-apps에는 구조적 순환이 있다.** root Application의 source가 `clusters/oci-k3s/apps/`(비재귀)라서 같은 층의 `projects/`(AppProject)는 root가 동기화할 수 없다. 그런데 root 자신이 AppProject에 속해야 한다. Argo CD 안에서는 풀리지 않는 순환이고, 바깥(부트스트랩 kustomization)에서 끊어야 한다.
- **Argo CD의 server-side apply는 항상 force다.** 수동으로 만들어 둔 객체를 Application이 인수할 때 field manager 충돌이 나지 않아서, 파드를 재시작하지 않고 소유권만 옮길 수 있다. "수동으로 먼저 만들고 나중에 GitOps가 인수한다"는 순서가 성립하는 근거가 이것이다.
- **`resourceTrackingMethod: annotation`이면 `argocd.argoproj.io/instance` 라벨은 존재하지 않는다.** 라벨 선택자로 한 번에 지우는 롤백을 쓰려면 라벨을 직접 붙여야 한다.
- **정지 스위치는 하나뿐이다.** 자식 Application만 `automated: null`로 패치해도 root의 selfHeal이 되돌린다. 실제 정지는 application-controller를 replicas 0으로 줄이는 것이고, 1차 break-glass는 노드 대화형 세션의 `sudo k3s kubectl`이다 — `kubectl`은 호출마다 새로 연결하므로 "열어 둔 터널 세션"은 안전망이 아니다.
- **읽기 전용 자격은 동사로 설계한다.** `agent-view`는 `view` 집계 + get/list/watch 확장(Secret 제외)이고 쓰기 동사는 `pods/portforward` create 하나다. 자격증명이 필요한 검사(`psql`·`kcat`·`fga`)는 tester에게 자격을 주는 대신 클러스터 안 Job으로 옮기고 tester는 로그만 읽는다 — 자격의 수명과 범위가 Job 매니페스트에 박히고 tester 쪽에는 아무것도 남지 않는다.

## 선택과 대안

- **순환 해소(D1=A)**: 부트스트랩 kustomization이 `projects/`를 base로 포함한다. 첫 투입만 운영자가 한 번 `apply -k`하고, 이후에는 자기 관리 Application이 소유한다. 기각: `apps/` 안에 projects Application을 두는 방식(순환이 그대로 남는다), 영구 수동 apply(Git 정본 원칙 위반 — ADR 0002).
- **4단계 PR 분할(D4)**: A 프로젝트 + root 이관 → B1 Argo CD 자기 인수 → B2 정책 → C 나머지 앱 17개. 한 PR로 묶으면 실패했을 때 원인 분리도 롤백 단위도 없다. 특히 **PR-A에는 `apps/` 파일을 넣지 않았다**: root가 자동 sync라 AppProject보다 자식이 먼저 생기면 InvalidSpecError가 되고, 봉인한 `default` 프로젝트에서 권한 실패 → retry 소진 → `Skipping auto-sync: failed previous sync attempt`로 자동 sync가 영구 정지한다. 순서를 지키는 것이 아니라 **순서를 어길 수 없게 파일을 배치**하는 쪽을 택했다.
- **AppProject destinations 모순(D2=A)**: 계약에는 "`platform` 프로젝트 destination에 `jt-dev`를 넣지 않는다"고 적혀 있었다. 그러나 정책 Application이 `jt-dev`·`jt-prod`에 NetworkPolicy·쿼터를 배포해야 하므로 성립할 수 없다. 계약 문장의 전제("destination을 특정 Application으로만 좁히는 개념은 Argo CD에 없다")는 맞고 결론이 틀렸다 — 그래서 `platform` destinations에 14개 네임스페이스를 전부 넣고, 검사 Job 전용으로 destination이 `jt-dev` 하나인 AppProject `tests`를 따로 만들었다. 계약 문장 정정은 converge로 인계했다(승인된 문서는 고치지 않는다).
- **정책 객체의 단일 출처**: `dev`/`prod` 프로젝트의 `namespaceResourceBlacklist`에 NetworkPolicy·ResourceQuota·LimitRange·Role·RoleBinding·ServiceAccount를 넣어, 앱 배포가 자기 경계를 스스로 넓히지 못하게 했다.
- **LimitRange에 `default.cpu`를 두지 않음**: defaulting이 CPU limit을 주입하면 버스트가 막힌다. `defaultRequest.cpu`와 memory `default`만 둔다. 기본값이 "안전"이 아니라 "제약"으로 작동하는 사례.
- **finalizer를 일부러 뺀 Application 2개**: 자기 관리 Application과 정책 Application에는 cascade finalizer를 두지 않았다. Application 삭제가 Argo CD 자신과 네임스페이스 14개를 지우는 경로를 아예 만들지 않는 편이 낫다.
- **롤백 라벨의 범위**: `app.kubernetes.io/part-of=platform-policies`는 정책·쿼터 97개에만 붙이고 Namespace·RBAC에는 붙이지 않았다. 라벨 일괄 삭제가 네임스페이스와 `agent-view`까지 지우면 복구 수단이 함께 사라진다.
- **DNS 문제(아래 사고 항목)의 해결책**: 계약과 정책을 고치는 대신 노드가 파드에 물려주는 resolv.conf만 공개 리졸버로 바꿨다. 허용 매트릭스 변경 0으로 끝났고, 승인된 계약을 건드리지 않았다.

## 결과와 검증

- 적용 전에 게이트 3건을 실측으로 통과시킨 뒤에만 정책 PR을 sync했다. **VD-EP**: kube-api 엔드포인트·Service 포트·Traefik 라벨이 정책 selector와 실제로 일치하는지. **VD-DNS**: CoreDNS 업스트림(아래). **VD-P**: 일회성 네임스페이스에 정책 4장 + 파드 2개를 띄워 — default-deny 아래서도 kubelet 프로브가 통과해 두 노드 모두 `2/2 READY`, kube-api는 401(= 연결 성립, 인증만 거부), 외부 443은 301(양성 대조), 외부 53·사설 대역 443·IMDS 80은 전부 차단. 여기에 **역검증**을 더했다: `allow-kube-api`를 지우면 즉시 연결 실패(exit 7), 되살리면 재통과. 허용 규칙이 실제로 그 통신을 살리고 있다는 증거를 남기는 절차다.
- 위험 구간인 정책 PR은 머지 **전에** root의 `automated`를 회수해 트리거를 손에 쥐고, 머지 뒤 운영자가 직접 적용했다.
- 적용 결과: NetworkPolicy **93장**(공통 49 + 내부 매트릭스 31 + 외부·노드 13) · Namespace **14**(PSA enforce/warn/audit 동일 레벨, restricted 8 · baseline 3 · privileged 3, `kube-system`은 K3s가 만든 것이라 라벨만 SSA로 인수) · 렌더 객체 123개 · root + **Application 19개 전부 Synced/Healthy**(리소스가 0인 뼈대 15개도 Healthy).
- 인수가 순수했다는 증거: 앞선 task에서 수동 생성한 터널 커넥터 네임스페이스와 파드가 **이름·AGE(28h)·RESTARTS 0 그대로** 유지됐고, Argo CD 자기 인수에서도 파드 5개가 불변이었다. 접근 경로도 정책 아래서 살아 있었다 — 새 터널 세션 연결 성공, 노드 2 Ready, CoreDNS의 `i/o timeout`/`SERVFAIL` 0줄.
- 부수 증명: 직전 task에서 넣어 둔 K3s 업그레이드 Plan 2개가 `LatestResolved=True`·`Validated=True`가 됐다 = default-deny 아래서 채널 서버로의 외부 443이 실제로 허용됐다는 뜻이다. `Complete=False` 사유는 "창 밖"(업그레이드 창은 일요일 03:00–05:00).
- 저장소 검사 `bash tests/validate.sh`는 PASS 18 · FAIL 0 · WARN 4(업그레이드 Plan 이미지의 채널 의존 예외).

## 다음 학습

- 정책이 "막아야 할 것을 막는지"는 양성 대조와 역검증을 함께 봐야 판정된다. 프로브 하나의 성공/실패만으로는 fail-open을 못 잡는다 — 특히 kubelet 프로브는 호스트에서 오기 때문에 정책과 무관하게 통과하고, 그래서 "파드가 Ready"는 네트워크가 통한다는 증거가 아니다.
- K3s의 정책 구현이 selector를 어떻게 ipset으로 바꾸는지는 아직 노드에서 확인하지 않았다. 정책 실효 검증은 후속 검사 task로 이어진다.
- 검사 Job 3종은 매니페스트와 AppProject만 넣고 Application 등재는 미뤘다(D3). 의존 컴포넌트가 아직 없어서 Job이 실패하면 Application이 Degraded가 되고 그 Degraded가 root까지 전파된다 — "지금 넣으면 초록이 아닌 구간이 길어진다"가 미룬 이유다.
- Argo CD 파드 배치(nodeSelector)와 남은 시스템 네임스페이스의 PSA 라벨은 이 task 밖으로 넘겼다.

## 사고·오류

- **가정이 실측으로 뒤집힌 것 — VD-DNS.** 계약의 `kube-system/deny-imds`는 "IMDS만 빼고 전부 허용"하는 egress 규칙인데 `ports`가 없다. 실제 클러스터를 보니 CoreDNS의 유일한 업스트림이 **IMDS와 같은 링크로컬 주소**(클라우드 VCN 리졸버)였다. K3s가 kubelet에 넘길 resolv.conf를 고르는 함수가 그 주소만은 클라우드 예외로 통과시키기 때문이다. 정책을 그대로 sync하면 CoreDNS의 53 egress가 그 규칙에 걸려 **클러스터 전체의 외부 이름 해석이 끊길** 상태였다 — Git 접근, ACME 발급, 터널 엣지 재해석(= 유일한 접근 경로) 전부. "IMDS 차단"이라는 이름만 읽고 넘어갔다면 스스로 문을 잠갔다. 정책의 이름이 아니라 그 규칙이 실제로 선택하는 파드와 그 파드의 트래픽을 봐야 한다.
- **런북 메모를 너무 일반화했다.** 머지 직후 정책 Application이 생기지 않아 root에 hard refresh를 걸어 당겼고, 이를 "머지 직후에는 root에 hard refresh"라고 적었다. 다음 날 다른 task에서 그게 **root 자신의 source가 바뀐 경우에만** 맞다는 것이 드러났다 — 기존 자식의 내용만 바뀐 PR에서는 root를 갱신해도 자식에 전파되지 않아, 옛 리비전인데 Synced/Healthy로 보인다. 범위를 적지 않은 절차 메모는 다음 사람을 조용히 속인다. 게다가 평소에는 reconciliation 주기(180초) 안에 저절로 반영되므로 먼저 기다리는 것이 맞았다.
- **뒤에 반증된 관찰.** 이후 task 구간에 "한 네임스페이스에서 53은 어느 목적지로든 새어 나간다"는 프로브 결과를 T041 산출물의 결함으로 기록했지만, 10렌즈 검수에서 매니페스트와 정책 구현 코드로는 성립 불가라는 판정이 나왔다. 응답을 요구하지 않는 UDP 프로브가 거부보다 먼저 "성공"으로 보인 **측정 방법의 문제**였다. 재측정은 응답을 요구하는 프로브(`dig +time=2 +tries=1`)로 하고, 인계처도 후속 검사 task로 바로잡았다.
