# 003-platform-foundation T066 — 아직 없는 pod의 API를 테스트로 먼저 못박기: 테스트 설계가 계약의 빈칸을 드러낸다 (2026-11-03)
> 1일차(설계 · 계약 보정 · 빌드 · 오라클 · 리뷰). 짝 구현(T073)이 이 테스트를 초록으로 만든다.

## 문제
identity-admin pod는 아직 없다(템플릿도 비어 있다). 그런데 이 pod의 HTTP API · 주기 작업 · 시드 명령을 테스트로 먼저 고정해야 했다. 단언을 쓰려고 하자 계약이 정하지 않은 것이 줄줄이 드러났다 — 서비스 간 경로는 어떤 인증만 요구하는가, 웹훅은 세션 단위로 폐기하는가 사용자 단위인가, 재전송 멱등 키는 어디에 두는가, 로그아웃이 그 요청을 부른 토큰까지 막으려면 기준 시각을 어떻게 잡는가, 관리자 판정은 무엇과 비교하는가. 테스트를 돌릴 환경(pod · 시험 픽스처)이 없다는 것도 함께 풀어야 했다.

## 배운 개념
- **테스트를 쓰는 순간 계약의 빈칸이 보인다.** "웹훅을 받으면 폐기한다"는 문장은 세션 식별자를 쓸지, 멱등 키를 어디 둘지, 다른 이벤트는 어떻게 할지 말하지 않는다. 단언은 값이 하나로 정해져야 쓸 수 있으므로 테스트 설계가 곧 계약 보정이었다.
- **같은 초 문제.** JWT의 `iat`는 초 단위다. 로그아웃 기준 시각(`nbf`)을 초 내림으로 잡으면 같은 초에 발급된 토큰 — 로그아웃을 부른 바로 그 토큰 — 이 "`nbf > iat`일 때만 거부" 비교를 통과해 살아남는다. 기준을 "내림 + 1"로 두고, 테스트는 초 경계에 맞춰 기다려 그 경우를 확정적으로 만든다(PyJWT가 미래 `iat`를 거부하므로 시계를 앞당기는 꼼수는 쓸 수 없다).
- **보장이 없으면 fail-safe 단위를 고른다.** 외부 이벤트가 토큰의 세션 식별자와 같은 값을 준다는 보장이 없으면, 세션 단위 폐기는 "폐기했는데 안 막히는" 보안 실패를 낳는다. 사용자 단위로 폐기하면 다른 기기까지 로그아웃되는 불편이 생기지만 보안 실패는 없다.
- **멱등 키는 부수효과와 같은 트랜잭션에 둔다.** 캐시의 TTL 키에 두면 캐시가 비정상 종료로 비었을 때 재전송이 중복 처리된다. 정본 테이블의 unique 컬럼에 두면 폐기 기록과 원자적으로 함께 남는다.
- **부분 일치는 권한 상승 구멍이다.** 그룹 클레임이 문자열로 오면 `"platform-admin" in claims`가 `"platform-admins"`에도 참이다. 목록인지, 원소가 정확히 같은지를 본다. 빈 문자열 설정값도 같은 함정이다 — 빈 문자열은 모든 문자열에 "포함"되므로 "관리 호스트가 비어 있으면 관리 화면 없음"이 "모든 호스트에 관리 화면"으로 뒤집힌다.
- **실행 환경이 없는 테스트의 판별력은 오라클로 증명한다.** 계약을 보고 만든 일회용 참조 구현으로 테스트가 전부 통과하는지(충족 가능성 · 과잉 규정 탐지), 일부러 틀린 변이를 넣으면 해당 테스트가 떨어지는지(판별력)를 확인하고 구현은 버린다.
- **가짜 서버에는 미끼가 있어야 한다.** 가짜가 정답 하나만 돌려주면, 조회 결과를 거르지 않고 첫 원소를 쓰는 구현도 통과한다. 운영이었다면 테넌트 사용자를 관리자 그룹에 넣었을 결함이다. 정답 앞에 이름이 비슷한 관리자 그룹 같은 미끼를 두고, 조회 질의의 필터까지 단언해야 이런 구현이 떨어진다.
- **"값이 출력에 없다"는 값 전체만 찾아서는 부족하다.** 설정 검증 라이브러리는 오류 메시지에서 긴 입력 표현을 앞뒤만 남기고 자른다. 필수값이 빠진 오류의 입력은 env 사전 전체라서, 비밀 값 전체는 안 보여도 마지막 값의 꼬리 조각이 실린다. 그래서 고정 길이 조각(12자) 단위로도 찾는다. 반대로 문자열 포함 단언은 트레이스백이 찍는 소스 줄의 주석까지 보므로, 라이브러리 표기(`input_value=`)처럼 우연히 맞기 어려운 표식으로 좁힌다.
- **닫힌 포트와 응답 없는 포트는 다르다.** Linux에서 닫힌 포트는 즉시 RST를 돌려줘서, 의존성을 하나씩 차례로 검사하는 구현도 응답 시간 상한 안에 끝난다. 연결은 받되 응답하지 않는 "블랙홀" 소켓(listen만 하고 accept하지 않음)을 쓰면 각 클라이언트가 자기 시간 초과까지 기다린다. 그래야 순차 검사의 합(약 3.2 s)과 병렬 검사(약 2.0 s)가 OS와 상관없이 갈린다. Linux 컨테이너에서도 수치를 재서 확인했다.
- **프레임워크가 설정 값을 캐시하는 시점을 확인한다.** Django는 상대 경로 정적 자산 URL에 처음 접근할 때의 경로 접두를 붙여 캐시한다. 그래서 요청마다 접두를 바꾸는 관리 화면에서 정적 자산만은 접두를 따라가지 못한다. 접두가 있을 때는 정적 자산 URL을 절대 경로로 둔다. 요청 단위 경로 접두 자체도 스레드 로컬이라, 요청이 끝날 때 되돌리지 않으면 같은 스레드의 다음 요청으로 샌다.
- **테스트 실행 순서가 판별력을 바꾼다.** pytest-django는 DB 테스트를 먼저 돌린다. 그래서 전체 실행에서는 앞선 테스트가 미들웨어를 이미 적재해 두고, 그 테스트만 따로 돌리면 이 테스트가 첫 적재가 된다. import 시점이나 생성자에서 설정을 읽는 구현은 단독 실행에서만 걸렸다. 설정을 바꾸기 전에 같은 클라이언트로 한 번 요청해 적재를 끝내 두면 어느 순서로 돌려도 같은 판정이 나온다.
- **이름으로 비밀을 고르면 비밀이 아닌 것도 걸린다.** env 이름에 KEY가 들었다고 값을 난수로 바꾸면, `GIT_CONFIG_KEY_0` 같은 git 설정 키가 깨져 자식 프로세스가 오류를 내거나, `SSLKEYLOGFILE`처럼 경로가 바뀌어 엉뚱한 곳에 파일이 생긴다. 경로형 이름과 묶음 설정은 건너뛰고, 필요 없는 env는 아예 뺀다.

## 선택과 대안
- **실행 위치**: 저장소 밖 미니 저장소(템플릿 시험 인프라의 시제품) — 대안 "지금 pod 디렉터리에 시험 설정을 만든다"는 다음 태스크의 템플릿 생성(copier)과 파일이 충돌해 기각.
- **Access만 요구하는 서비스 간 경로**: 라이브러리 미들웨어 설정 + 라이브러리 테스트 추가 — 대안 "뷰에서 직접 검증"은 미들웨어의 Bearer 단계가 먼저 막아 성립하지 않는다.
- **웹훅 폐기 단위**: 사용자 단위 — 대안 "세션 단위"는 세션 식별자 일치 보장이 없어 기각.
- **멱등 저장**: 정본 테이블 unique 컬럼 — 대안 "캐시 TTL 키"는 캐시 유실에 약해 기각.
- **외부 API 대역**: 실제 HTTP 모양을 흉내 내는 가짜 서버 — 대안 "파이썬 수준 가짜"는 요청 조립 · 인증 헤더 · 오류 코드 처리를 못 본다. 가짜의 모양 자체는 실측 태스크의 "검증 후 결정" 항목으로 넘긴다.
- **OpenAPI**: 계약 구조 단언 + 템플릿 내장 스냅샷 — 대안 "같은 API의 스냅샷 파일 2개"는 갱신 경로가 둘이라 기각.
- **/health 병렬성 판별**: 블랙홀 소켓 — 대안 "닫힌 포트"는 Linux에서 즉시 RST가 와서 순차 구현도 시간 상한을 지키므로 기각.
- **관리 화면 정적 자산**: 접두가 있으면 절대 경로 URL — 대안 "요청마다 접두를 바꾼다"는 Django가 첫 접근 값을 캐시해 성립하지 않는다.
- **관찰할 수 없는 계약 항목**(설정 모델의 입력 숨김 옵션 · 500 핸들러 · 호스트 밖 400): 이 테스트의 한계로 적고 템플릿 기본 테스트 항목으로 계약에 넘겼다 — 대안 "웹훅에 큰 본문을 보내 400을 일으킨다"는 웹훅 계약(거부는 모두 401)과 해석이 갈려 기각.

## 결과와 검증
- 산출물은 테스트 3파일이다: API 계약 테스트 76개, 가짜 서버 · DNS 가드 자기검사 26개, 합계 약 3,400줄. 여기에 공용 라이브러리 인증 테스트 1건(Access 전용 경로)을 더했고, 계약 · 데이터 모델 · 규칙도 보정했다.
- 빨강:
  - 저장소 안에서는 pod 환경이 없어 아직 실행되지 않는다(템플릿 · 구현 태스크 뒤에 돈다).
  - 미니 저장소에서는 설정 모듈 import가 "구현 없음"으로 실패한다.
  - 공용 라이브러리 쪽 추가 테스트는 인증 모듈이 없어 수집 단계에서 실패한다.
- 판별력:
  - 계약대로 만든 일회용 참조 구현으로 102개가 전부 통과했다(네 회차 · 반복 실행 모두 결정적).
  - 서로 다른 변이 127개 중 120개를 잡았다.
  - 남은 7개는 HTTP로 구별할 수 없는 순서, 출력으로 관찰할 수 없는 설정 옵션, 설계상 문턱, 시험으로 일으키지 않는 오류 처리기다. 전부 테스트의 한계 절과 템플릿 기본 테스트 항목에 적었다.
- 리뷰는 네 회차였다.
  - 1차는 high 1건(미끼 없는 가짜)이었고, 2차는 medium(잘린 조각 노출 · 정적 자산 접두)이었다. 3 · 4차는 low만 남았다.
  - 회차마다 오라클이 "같은 변이가 이전 시험 파일에서는 살아남는다"를 대조해, 잡힌 원인이 그 회차의 수정임을 보였다.
- 실험:
  - 이름에 KEY가 든 env를 난수로 바꾸던 규칙은 git 설정까지 깨뜨려 거짓 양성을 냈다. 이전 파일은 17 failed, 고친 파일은 17 passed다.
  - TLS 키 로그 env 때문에 pod 루트에 생기던 파일이 18개에서 0개로 줄었다.
  - Linux 컨테이너에서 잰 블랙홀 수치가 Windows와 같았다(순차 3.21 s · 병렬 2.00 s).
- 위생: BOM · CR · TAB · 줄 끝 공백 0, 줄 120자 이하, 비밀 스캔 통과, 시험 컨테이너 0, dangling 볼륨 변화 0.

## 사고·오류
- 첫 지시문에 학습 로그 경로 예외를 빠뜨렸다. 빌더의 "깨끗한 작업 트리" 규칙과 부딪히지 않도록, 학습 로그는 워크플로가 끝난 뒤에 썼다.
- 1차 설계의 가짜 서버는 정답만 돌려줘서, 필터 없는 구현도 통과시켰다(리뷰 high). 가짜에는 틀린 구현이 고를 법한 미끼가 함께 있어야 한다.
- 단언을 넓히다가 정상 구현을 떨어뜨릴 뻔한 일이 두 번 있었다.
  - 2차에 넣은 비밀 이름 규칙(KEY 포함)이 git 설정 env까지 바꿨다.
  - 3차에 넣은 `input_value` 낱말 단언이 트레이스백이 찍는 주석까지 잡았다.
  - 둘 다 오라클 실험으로 거짓 양성을 실제로 재현한 뒤 고쳤다. 단언을 넓힐 때마다 "정상 구현이 우연히 걸리는 경로"를 통제 변이로 같이 돌린다.
- 2차 오라클 보고는 별칭 변이를 두 번 세어 "116 중 112"라고 했다. 실제로는 서로 다른 110개 중 106개다. 집계에서 별칭은 한 번만 센다.
