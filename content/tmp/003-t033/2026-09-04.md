# 003-platform-foundation T033 — 계약을 코드로 옮긴 GitOps 정적 검사와 그 자기검사 (2026-09-04)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제

GitOps 저장소(`platform-gitops`)는 클러스터에 무엇이 들어가는지를 결정하는 단일 창구다. 사람이 PR로만 쓰고, 이미지 승격 봇도 PR로만 쓴다. 그러면 "PR에 무엇이 들어와도 되는가"를 판정하는 장치가 저장소 안에 있어야 한다. 그 판정 규칙은 이미 계약 문서에 글로 적혀 있었다 — `contracts/gitops-repo.md`의 §validate.yml·§ExternalSecret 검사 7항목·§sync-wave 단일 표·§이미지·승격, 그리고 `contracts/network-policy.md`의 네임스페이스 표(14개)·정책 세트·외부 egress 형식·포트 출처 각주. 글로만 있는 규칙은 지켜지지 않는다.

T033은 그 글을 실행 가능한 검사로 옮기는 task다. 어려운 점은 두 가지였다. 첫째, 검사 대상 트리가 아직 거의 비어 있었다(정책 트리는 T041, 앱 오버레이는 US5 몫). 검사 본체를 먼저 쓰는 test-first 태스크라서, 작성 시점에는 "실제 트리에서 FAIL"이 정상 상태다. 둘째, 검사 자체가 틀렸는지를 무엇으로 확인하나? 트리가 비어 있으면 검사는 아무 일도 하지 않고 초록을 낼 수 있다.

## 배운 개념

**검사는 두 계층을 함께 봐야 한다.** 매니페스트를 원본 파일로만 읽으면 overlay 패치로 우회할 수 있고, `kustomize build` 렌더링 결과만 읽으면 "이 오브젝트가 어느 경로에서 왔는가"를 잃는다. 그런데 계약의 핵심 검사 셋(scope ↔ 위치, `platform/` 5개 컴포넌트의 store 제한, `apps/**`의 Workers 경로 금지)은 전부 경로 기반이다. 그래서 스크립트는 검사 대상을 `file`과 `rendered` 두 종류의 "원본(source)"으로 모으고, 위치 판정은 파일 경로 또는 kustomization 디렉터리로 한다. 긍정 픽스처에서 ExternalSecret이 22개로 세어지는 이유가 이것이다(파일 + 렌더링).

**"도구가 없으면 통과"는 검사가 없는 것과 같다.** 필요한 도구는 `yq`·`kustomize`·`kubeconform`·`gitleaks`(helmCharts가 있으면 `helm`)다. 기본 동작은 fail-closed — 없으면 설치 안내와 함께 실패한다. 로컬 부분 검증용 탈출구(`VALIDATE_SKIP_TOOLS=1`)는 명시적 opt-in이고, 요약에 "불완전"이 찍힌다. 같은 원칙이 자기검사에도 걸려 있다: CI 환경(`CI=true`)에서는 SKIP 모드로 내려가지 않고 그냥 실패한다.

**"대상 0개"도 실패다.** gitleaks 검사는 스캔 대상 파일이 0개면 FAIL을 낸다. 빈 트리에서 조용히 초록이 나오는 것이 이 task가 가장 경계한 실패 양식이고, 부정 픽스처(`gitleaks-empty`)로 그 동작을 고정했다. 같은 이유로 PR 이벤트인데 작성자 정보가 비어 있으면 봇 경로 lint는 "대상 없음"이 아니라 FAIL이다.

**검사 스크립트를 PR head로 돌리면 검사가 아니다.** 봇 경로 lint(변경 파일 = dev overlay kustomization, 변경 줄 = `images[].digest`만)는 그 PR이 스크립트 자체를 고쳐 무력화할 수 있다. 그래서 CI는 base ref의 `tests/validate.sh`를 꺼내 같은 `tests/` 경로에 두고 실행해야 한다(경로가 바뀌면 저장소 루트 판정이 깨진다). 이 조건은 스크립트가 강제할 수 없어서 `tests/README.md`에 "T047 필수 조건"으로 적었다 — 강제할 수 없는 전제는 문서로 못 박는다.

**권한으로 못 막는 것은 lint로 막는다.** `vault-{env}` ESO 정책은 해당 환경의 KV 트리 전체를 읽을 수 있다. 그래서 Workers 전용 비밀(세션 암호화 키·Access 서비스 토큰)이 pod 쪽 ExternalSecret로 새어 들어오는 것을 정책만으로는 못 막는다 → 접두 금지 검사(⑦)가 그 자리를 메운다. 반대로 CA 미러 검사(④)는 위조 경로를 끊는 검사다: CNPG의 CA Secret에는 개인키가 같이 들어 있어서 `dataFrom` 전체 복사가 아니라 `property: ca.crt`만 허용해야 한다. 앱 네임스페이스에 CA 개인키가 있으면 서버 인증서와 복제 인증서를 위조할 수 있어 `sslmode=verify-full`이 무의미해진다.

**표는 한 곳에만 둔다.** sync-wave 표·네임스페이스 14개·정책 세트·helm 포트 키는 스크립트 안의 단일 사본이 유일한 코드 사본이다. 계약이 바뀌면 여기만 바꾼다는 규칙을 `tests/README.md`에 남겼다. 그리고 표에 없는 `platform/<component>/` 디렉터리 자체를 금지해(7.2) 표를 디렉터리 집합의 정본으로 만들었다.

## 선택과 대안

- **워크플로 YAML에 검사 로직을 넣기 → 기각.** 검사 본체를 독립 bash 스크립트로 분리했다. 이유: 로컬에서 같은 방식으로 돌릴 수 있고, base ref 버전으로 실행하는 위 방어가 가능해진다. 워크플로 연결(도구 4종 sha256 핀 설치, 작성자·base/head SHA 전달)은 T047로 분리했다.
- **도구 부재 시 SKIP을 기본값으로 → 기각.** 기본 fail-closed, SKIP은 opt-in + "불완전" 표시.
- **렌더링 결과만 / 파일만 검사 → 둘 다 기각**(위 개념 절의 이유). 비용은 스크립트 복잡도(원본 두 종류를 다루는 추출 계층)였고, 그 대가로 경로 기반 검사와 패치 우회 방지를 동시에 얻었다.
- **platform 이미지 digest 부재를 FAIL로 → 기각, WARN으로.** 검사는 `image:` 스칼라 줄만 본다. helm values의 분리형 `image.repository`/`image.tag`는 보지 않으므로 FAIL로 만들면 위양성이 나온다. 한계를 스크립트 머리 주석과 README "한계(명시)" 절에 적고, 그 구멍은 Renovate `pinDigests`와 컴포넌트 task의 수동 병기에 맡겼다.
- **긍정 픽스처 하나로 자기검사 → 기각.** 검사 항목마다 "그 항목이 실제로 실패 코드를 내는 최소 트리"를 두었다. 부정 픽스처에는 비밀처럼 보이는 값을 넣지 않고, 시크릿 검사의 실패 케이스는 "대상 0개"로 만들었다.
- **`automountServiceAccountToken: false`를 전 트리에 요구 → 기각.** 자체 ServiceAccount가 필요한 helm 차트 컴포넌트가 있어 범위를 `apps/**`와 컴포넌트 2개로 좁혔다. 검사 범위를 좁힌 근거를 남기지 않으면 나중에 "왜 여기는 예외지?"가 반복된다.

## 결과와 검증

`tests/validate.sh`(947줄, 검사 8군 + 도구·파싱 0군)와 `tests/validate.tests.sh`(238줄, 30케이스) + 픽스처 트리. PR #2 squash → gitops main `77b7236`(69파일 +3213줄). 자기검사 계약: 긍정 트리는 exit 0이고 각 검사군의 PASS 줄이 보여야 하며 FAIL 줄이 하나도 없어야 한다, 부정 픽스처는 exit 1 + **정확한 검사 코드와 메시지**, 저장소 밖 `--root`는 exit 2. 각 케이스는 작성자 관련 환경변수를 `env -u`로 지우고 시작한다(CI 환경변수가 새어 결과를 바꾸지 않도록).

경계 조건도 단언으로 고정했다: 봇 작성자 + 허용 파일/줄 = PASS, 다른 파일·다른 줄 = FAIL, 입력 없음 = FAIL, 사람 작성자 = 제약 없음, push 이벤트 = 대상 없음 PASS, PR 이벤트인데 작성자 공백 = FAIL. 스크립트는 `--root` 트리 밖을 읽거나 쓰지 않고 저장소 안에 임시 파일을 만들지 않는다(파이프와 변수만; 예외는 저장소 밖 임시 경로의 kubeconform 스키마 캐시 하나).

실제 트리에서는 FAIL이 정상이었다 — 정책 트리가 아직 없었다. 그래서 required check 연결을 T041 뒤(T047)로 미루고, 모노레포에서 체크만 틱했다(`8457b07`).

## 다음 학습

- T047: 워크플로 연결 시 도구 4종 sha256 핀 설치, base ref 스크립트 실행, 작성자·base/head SHA 전달이 실제로 성립하는지 실측. 이때 required check를 켠다.
- T041 정책 트리 투입 후 실제 트리가 처음으로 PASS로 넘어가는지(= 계약 표와 실물이 같은지)를 확인. 검사가 먼저 있고 대상이 나중에 오는 구조에서는 이 전환점이 곧 계약 검증 시점이다.
- helm values 포트 키 표는 현재 4개 컴포넌트뿐 — 이후 컴포넌트 배포 task가 행을 추가하지 않으면 그 컴포넌트의 포트 일치 검사는 조용히 비어 있게 된다. "표에 행이 없으면 검사도 없다"를 잡는 메타 검사가 필요한지 검토.
- 알려진 검사 공백(후속 후보): 삭제 패치의 target 부재, 원격 base의 태그 ref 금지, bootstrap 트리 이미지 digest 요구, 메모리 환경변수 ≤ limit 일치.

## 사고·오류

1차 구현을 리뷰한 결과 같은 PR의 2차 커밋에서 다섯 구멍을 메웠다: ① ExternalSecret 규약 보강(apiVersion·store kind·`dataFrom`은 extract만·`sourceRef` 금지), ② 정책 객체가 `platform/policies/` 밖(앱 트리)에 숨는 것을 잡는 위치 검사, ③ kustomization 밖 매니페스트도 스키마 검증(1b), ④ PR 이벤트에서 작성자 공백 = FAIL(조용한 비활성 금지), ⑤ 자기검사의 도구 필수 모드. 교훈은 하나다 — **긍정 픽스처만으로는 "검사가 실제로 잡는다"를 알 수 없다.** 부정 픽스처가 없는 검사는 있는 척하는 검사다.

구현 중 계약 모순 3건이 드러났다. ① CA 미러 ExternalSecret은 문면대로면 ES 검사 ③과 sync-wave 표의 디렉터리 위치가 서로 모순 → 미러는 ①②③ 면제·④만 적용으로 해석하고 기록. ② 계약이 가정한 이미지 승격 봇 로그인 이름이 실제 GitHub App 로그인과 달랐다 → 기본값에 두 이름을 함께 허용하고 환경변수로 덮을 수 있게 했다(계약·워크플로 문구 정정은 후속). ③ 모니터링 포트 표의 컴포넌트 순서가 상류 기본과 뒤바뀌어 있었다(집합 검사라 결과에는 영향 없음). task 줄과 계약은 승인 후 불변이므로 정정은 converge/report 경로에 큐로 쌓았다 — 구현 중 발견한 계약 오류를 즉시 고치지 않고 큐에 넣는 규율이 여기서 처음 무겁게 작동했다.

부수 발견: `kustomize build --enable-helm`이 컴포넌트 디렉터리 안에 `charts/`를 남긴다 → 첫 helmCharts 도입 시 gitops `.gitignore` 필요(후속 task로 이월). 검사 대상 수집에서 `tests/`와 `charts/`를 제외해 픽스처가 실제 결과에 섞이지 않게 했다.
