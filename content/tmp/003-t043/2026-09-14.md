# 003-platform-foundation T043 — 증거를 먼저 모으고 나서 오리진 mTLS를 강제하기 (2026-09-14)
> 백필: 2026-09-17 작성(런북 §3·커밋 기록·설계 문서 기반).

## 문제
AOP(Authenticated Origin Pulls)는 CDN 엣지가 오리진에 클라이언트 인증서를 제시하고 오리진이 그 CA로 검증해서, "엣지를 거치지 않은 직접 접속"을 TLS 핸드셰이크 단계에서 끊는 구조다. 존 설정은 앞 task에서 이미 켜져 있었지만 오리진(Traefik)이 `CertificateRequest`를 보내지 않으면 인증서는 아예 전송되지 않는다 — 즉 그때까지 AOP는 켜져 있으나 아무 일도 하지 않는 상태였다. T043은 오리진 쪽 `clientAuthType`을 `RequireAndVerifyClientCert`로 올려 이걸 실제 방어선으로 만드는 일이었다.

문제는 그 한 줄이 443을 **무증상으로** 죽일 수 있다는 것이다. CA Secret이 없거나 키 이름이 다르면 Traefik은 `CAFiles is required`로 TLSOption 빌드에 실패하고, websecure의 모든 라우터가 broken 상태가 되며 폴백 TLS 설정까지 nil이 된다. 그런데 파드는 Ready(liveness는 평문 포트 `/ping`), helm Job은 성공, INFO 로그는 조용하다. 장애 신호가 없는 장애다. 게다가 전제 하나가 문서로 확인되지 않았다: "Global AOP가 정말 **모든** origin pull에 인증서를 제시한다"는 명문이 없다. 강제부터 하면 이 전제가 틀렸을 때 전 호스트 5xx가 첫 증거가 된다. 여기에 Argo CD UI를 공개 진입점으로 여는 Ingress 신설까지 같은 Traefik·같은 TLSOption·같은 엔트리포인트를 건드렸다.

## 배운 개념
- **`VerifyClientCertIfGiven`과 `RequireAndVerifyClientCert`의 차이는 딱 하나**, "인증서가 없을 때"뿐이다. 인증서가 오면 둘 다 반드시 CA 검증을 하고 실패하면 거절한다. 그래서 Verify는 "무해한 관찰 단계"가 아니다 — CA 불일치라는 최악 시나리오에 대해서는 Require와 똑같이 443이 전면 실패한다. Verify가 사 오는 정보는 정확히 하나, **엣지가 인증서를 제시하는지**다.
- 그 증거는 승격 뒤에는 **다시 얻을 수 없다**. Require에서 거절된 연결은 핸드셰이크에서 끝나 액세스 로그에 도달하지 못한다. 관찰 창은 일회성 자원이다.
- **액세스 로그의 `TLSClientSubject`는 헤더가 아니라 core 필드**여서 헤더 drop 정책과 무관하게 이미 기록된다. 단 로그 필터가 4xx/5xx만 남기므로 200/302로는 증거가 안 남는다 → 일부러 404가 나는 경로를 프로브로 쓴다.
- `secretNames`만 주고 `clientAuthType`을 생략하면 **암묵적으로 Require**가 된다. 관찰 단계에서 한 줄 빠뜨리면 그 자리에서 강제다.
- **keep-alive가 판정을 오염시킨다.** TLSOption 변경은 새 핸드셰이크부터 적용되고, 엣지↔오리진 연결은 idleTimeout(기본 180초) 동안 옛 TLS 설정으로 살아 있다. 그래서 "적용 직후 프로브에 Subject가 없다 = 미제시"도, "승격 직후 응답이 정상이다 = 강제 실효"도 둘 다 오독이다. 판정은 설정 반영 시각 + 180초 뒤 새 연결로만.
- **TLS alert로 실패 원인을 가른다.** 인증서 부재는 TLS 1.3에서 `certificate required`(post-handshake alert, curl exit 56), 같은 부재가 TLS 1.2에서는 `handshake failure`(exit 35), 체인 불일치는 `unknown CA`/`bad certificate`, SNI 불일치는 `unrecognized name`. 겉으로는 다 같은 "연결 실패"인데 stderr 문구로만 갈라진다. 서버 인증서는 `CertificateRequest`보다 먼저 전송되므로 클라이언트 인증서가 없어도 `openssl s_client -servername`으로 계속 읽을 수 있다 — 승격 뒤 진단의 발판.
- **투입/되돌리기 순서가 곧 안전장치다.** 투입 = Secret 설치 → 지문 대조 게이트 → clientAuth. 되돌리기 = clientAuth 제거(clientAuth 없는 사본 재설치) → 설정에서 빈 값 확인 → **그다음에야** Secret 삭제. 역순은 443 전면 중단. 되돌리기 목표를 "Verify로 하향"으로 두면 CA 불일치 장애에서 복구가 안 되므로, 목표는 언제나 clientAuth 없는 사본 하나로 고정했다.
- 이 변경을 감히 할 수 있었던 전제: SSH·K8s 접근 경로가 터널 기반이라 Traefik 443을 경유하지 않는다. 443이 전면 중단돼도 손이 남는다.

## 선택과 대안
- **CA Secret의 정본(D1)** — 채택: 모노레포의 K3s manifests 파일 + 지문·만료를 리터럴로 고정하는 정적 테스트. 기각: ① 운영자 수동 `kubectl create secret`(지문·만료를 커밋으로 못 묶고 재부트스트랩 때 사람 기억에 의존, 키 이름 오타를 리뷰가 못 잡음) ② GitOps 저장소에 `kind: Secret`(값이 공개 인증서여도 "이 저장소에 비밀 없음" 규약 4곳을 고쳐야 하고, 린트·시크릿 스캔 어느 것도 반응하지 않아 규약 위반이 조용히 들어오며 선례가 확산된다) ③ 시크릿 관리자 경유(뒤 task에 막히고, 443 가용성이 나중에 뜨는 컴포넌트에 종속된다) ④ ConfigMap(TLSOption은 Secret만 받으므로 동작 불가). 그리고 "Traefik 설정 파일의 두 번째 YAML 문서로 끼워 넣기"는 명시 금지 — 나중에 분리할 때 objectset이 Secret을 함께 지우면서 443이 죽는 경로다.
- **승격 방식(D2)** — 채택: Verify 관찰 → Require 승격, 판정은 PASS/FAIL/INCONCLUSIVE 3상태. 기각: 직행(창 하나를 아끼지만 "미제시"와 "CA 불일치"가 같은 증상으로 겹쳐 원인 귀속이 불가능하고, 동결된 앞 task 문면·계약·테스트 리터럴과 편차가 생겨 정정 연쇄가 따라온다) · `RequestClientCert`를 낀 3단계(미제시 탐지는 Verify도 순단 없이 해내므로 새 정보가 0 → 비상 진단용으로만 남겨둠).
- **승격 뒤 판별 수단(D5)** — 기각: 진단용 자체 CA를 신뢰 앵커에 추가(공개 443의 신뢰 앵커를 넓히고, 지켜야 할 개인키 자산을 새로 만든다). 채택: 인증서 없이도 되는 판별로 교체(`openssl s_client`, 엣지 상태 코드, 프로브 로그의 Subject, curl exit/alert)하고 기존 실험은 "승격 전 마지막 점검·재투입 전용"으로 재분류.
- **작업 순서** — 과제 문면은 "AOP → Ingress"였지만 실제로는 **Ingress를 먼저** 했다. Argo UI 호스트는 Access가 앞단이라 외부 curl이 늘 302를 주어 오리진 상태를 비추지 못하고, 승격 뒤에는 노드 내부 curl이 인증서 없이 거절되어 "Ingress가 200을 내는가"를 오리진 쪽에서 볼 길이 브라우저뿐이 된다. 한 창에 한 원인.
- **게이트 패턴** — "로그에 `error` 0줄"은 게이트로 쓰지 않는다. 관측 스택 정비 전이라 항상 몇 줄이 있고, 그러면 매번 롤백하거나 게이트를 무시하는 습관이 생긴다. AOP 특정 문구로 좁혔다.
- **Argo Ingress 형태** — 표준 Ingress 1개. gRPC-Web은 HTTP/1.1 POST라 UI와 CLI가 이것 하나로 된다. 네이티브 gRPC용 h2c 라우트 2개 안은 기각 — 엣지 Access가 gRPC를 지원하지 않아 애초에 성립하지 않는다(이전 조사 결정이 이 지점에서 낡았다). 백엔드는 포트 이름 `http` 고정(443이나 `https*`면 Traefik이 평문 포트에 TLS를 시도해 502).

## 결과와 검증
- 커밋 5개(+리뷰 반영) · gitops PR 2개 · 라이브 창 4회(Ingress → Secret → Verify → Require)로 쪼개고, 창마다 합격 문면이 미리 고정된 실측 게이트를 뒀다.
- 다운로드한 CA PEM이 우리 측정값과 바이트 단위로 동일(2154바이트, PEM 블록 1개, notAfter 2029-11-01), 클러스터 Secret의 subject·만료·지문·키 이름·라벨 4중 대조를 통과한 **뒤에야** clientAuth를 넣었다.
- 관찰 단계(설치 06:49:41Z, +180초 뒤 판정): 프로브 가능한 8개 호스트 — 공개 3, Access 뒤 3, 서비스 토큰 뒤 2 — 의 액세스 로그 **전부**에 `TLSClientSubject=CN=origin-pull.cloudflare.net,…`와 TLS 1.3. 자체 서명 인증서를 제시한 음성 실험은 `unknown CA` alert로 거절, 인증서 없는 요청은 통과(404) → "제시된다 + 우리 CA로 검증된다"가 둘 다 실측으로 성립했다.
- **발견**: 대시보드 호스트만 20분간 액세스 로그가 0줄이었다. 원인은 그 호스트가 Traefik 내부 라우터(`api@internal`)로 가고 Traefik v3는 내부 리소스를 액세스 로그에서 기본 제외한다는 것(`accesslog.addInternals` 기본 false). TLSOption은 라우터와 무관한 전역 설정이므로 보안 구멍이 아니라 **구조적 관측 사각**이었다. 3상태 판정을 미리 정해둔 덕에 "1건 실패"가 아니라 "재프로브 1회 → 구조 진단 → 종결"로 닫혔다.
- 승격(설치 07:48:23Z): 인증서 없는 TLS 1.3은 `certificate required`, TLS 1.2는 `handshake failure`, SNI 불일치는 `unrecognized name`으로 판별표대로 갈라졌다. 엣지 경로는 404 유지(525/520 미발생) = 정상 트래픽 무영향. 파드는 교체 없이 유지(TLSOption CR만 갱신) → **443 순단 0초**.
- 승격 +3일(2026-09-14) 재확인: 같은 호스트들이 여전히 404 + `TLSClientSubject`, 엣지 콜로가 09-11과 달라져도 통과. 브라우저로 Argo UI에서 Application 20개 Synced/Healthy 로딩, 라우터의 TLS Options가 `default`임을 대시보드로 확인. 플랫폼 테스트 러너는 AOP 검사·Ingress 검사·Application 상태 검사 PASS, 남은 FAIL은 다음 task 전 상태.
- 정적 테스트는 단계마다 red→green으로 갈랐다(관찰 값 72/0 → 승격 값 73/0). 새 CA Secret 스위트는 17단언 + 변이 8종 확인.

## 다음 학습
- Cloudflare는 이 CA의 교체·만료 알림을 주지 않는다 → 분기 1회 원본 지문 대조를 캘린더로 돌리고, 회전 시 "옛+새 병기 → 교체"가 실제로 무중단인지 측정한다.
- 이 CA는 전 Cloudflare 계정이 공유한다 → AOP가 보증하는 것은 "Cloudflare 망에서 왔다"까지다. 계정 교차 우회의 오리진 측 통제는 Access + forward-auth + 앱 JWT의 몫이고, 그건 뒤 task다.
- Worker의 same-zone `fetch()`에도 AOP 인증서가 제시되는지는 문서에 없다 → BFF 착수 전 실측이 필요하다. 실제로 뒤 task 검증 중 "노드 내부 무인증서 프로브가 200"이라는 기대값이 T043 이전 기준이라 폐기되기도 했다 — 이제는 거절이 정상이다.
- CLI가 엣지 Access를 통과할 헤더 형태, 장시간 SSE 유지 여부는 UI task로 인계.

## 사고·오류
- **빌더가 파일째 스테이징해 남의 미커밋 변경이 커밋에 섞였다.** `reset --soft` 후 필요한 hunk만 `git apply --cached`로 재커밋. 근본 원인은 "파일 전체가 들어간다"는 슬라이스 지시 자체의 결함 → 이후 규칙: 빌더는 커밋하지 않고 컨트롤러가 파일 이름으로 스테이징, 부분 변경은 hunk 추출.
- **PowerShell에서 `"$pod:8080"`이 스코프 변수로 파싱**되어 URL이 `http://:8080/`이 됐고, 결과 000을 하마터면 "엔트리포인트 누출 없음"으로 잘못 읽을 뻔했다. `${pod}`로 고치니 기대값 404. 같은 계열로 큰따옴표 안 `\$p`가 원격 sed를 깨뜨렸다 → 원격 명령은 리터럴 here-string으로.
- **노드 안 `kubectl`에 `sudo`를 빠뜨려** 검증 블록이 실패했고, 워크스테이션 kubectl은 터널 세션 만료로 죽어 있었다 → 검증 블록은 터널에 의존하지 않고 노드 안에서 완결시킨다.
- 검토에서 **테스트 자체의 결함 5건**이 나왔다: 구조를 안 보는 단언(대상을 지워도 green), PEM "블록 1개" 단언이 CA 회전 중 옛+새 병기를 FAIL시키는 문제, 지문을 4바이트만 비교, flow-style 라벨 우회. 변이를 일부러 넣어 FAIL을 확인하지 않으면 green은 아무 뜻이 없다.
- 승격으로 **거짓이 되는 옛 문면**이 문서 여러 곳에 있었다("노드 내부 curl로 확인하라" 계열). 같은 창에서 갱신하지 않으면 다음 사람이 정상을 장애로 오독한다.
