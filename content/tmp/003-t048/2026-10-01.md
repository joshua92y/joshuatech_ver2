# 003-platform-foundation T048 — "재부팅 한 번"을 재려면: 측정 도구를 먼저 의심하고, 그 재부팅 안에 숨은 변경을 찾는다 (2026-10-01)
> 1일차(조사 → 재부팅 하네스의 틈 → 백업 검증 스크립트 → 실제 백업 검증 통과 → 사전 관찰 → 대기 중인 커널 발견 → 복구 경로 준비). 재부팅은 아직 하지 않았다.

## 문제
과제는 짧다. control plane 노드를 재부팅하고, 사람이 손대지 않아도 5분 안에 비밀 저장소가 스스로 열리고 동기화가 돌아오는지 본다. 그리고 최신 백업 둘을 내려받아 복호화해 "복원할 수 있는 물건인가"를 확인한다.

하루를 썼는데 재부팅은 하지 못했다. 재부팅 명령은 한 줄이지만, 그 한 번을 **믿을 수 있게 재는 일**과 **실패했을 때 돌아올 길을 만드는 일**이 준비돼 있지 않았기 때문이다. 재부팅은 되돌릴 수 없는 종류의 측정이다. 측정 도구가 틀리면 다시 재부팅해야 하고, 재부팅이 잘못되면 control plane이 없다.

## 배운 개념
- **관찰 도구는 "일어났는가"와 "그 뒤의 상태인가"를 따로 물어야 한다.** 재부팅 뒤의 복구를 폴링으로 확인하는 하네스가 있었다. 그런데 시작 시각만 기준으로 삼아서, 노드가 아직 내려가지 않았거나 재부팅이 먹지 않았을 때 재부팅 **전의** 건강한 상태를 보고 전부 통과했다. 부팅마다 새로 생기는 식별자가 기준값과 달라진 것을 본 뒤에만 나머지를 평가하게 고쳤다. 리뷰는 한 걸음 더 나갔다 — 재부팅이 일어난 것을 확인한 뒤에도, 조건 가운데 둘은 재부팅 전부터 그대로인 낡은 상태 값으로 통과했다. "재부팅이 일어났는가"를 막는 것은 절반이고, **조건마다 "지금 보는 값이 재부팅 뒤에 만들어진 것인가"** 를 물어야 한다.
- **가짜로 통과한 하네스도 실제 경로에서 한 번 돌려 봐야 한다.** 가짜 API로 180개가 넘는 단언을 통과한 하네스가, 실제 접속 경로에서는 한 조건이 **항상 실패하게** 돼 있었다. 실제 경로에서는 포트 전달이 수립되는 데 10–23초가 걸리는데 확인 한 번의 상한이 8초였다. 상한을 정한 때는 접속 경로가 지금과 달랐고, 그 뒤로 실제 환경에서 그 모드로 돌려 본 적이 없었다. 재부팅 없이 하네스 전체를 실제 경로에 돌려 보는 예행(일부러 틀린 기준값을 넣어 첫 조건을 통과시킨다)으로 나머지 조건을 전부 미리 확인했다.
- **측정의 0초를 어디에 두는가가 판정을 바꾼다.** "5분 안"의 시작점이 스크립트 시작이면, 사람이 명령을 늦게 치는 만큼 마감이 깎이고 일찍 치면 느슨해진다. 밖에서 "API가 끊긴 순간"을 감지해 시작하는 방법은 호출이 가끔 실패하는 경로에서는 믿을 수 없었다. 하네스를 먼저 켜 두고, **옛 상태를 마지막으로 본 시각**을 0초로 삼게 했다. 그런데 여기에도 함정이 있었다 — 재부팅 뒤 API가 먼저 돌아오면 저장돼 있던 옛 값이 잠깐 보인다. 그 관측으로 0초가 재부팅 뒤로 밀리면 마감이 꺼져 있던 시간만큼 느슨해진다. 한 번 굳은 기준점은 옛 상태를 연속 세 번 봐야 다시 움직이게 했다.
- **마감 판정은 "관측이 끝난 시각"이 아니라 "관측을 시작한 시각"으로.** 마감에 맞춰 줄인 마지막 폴링은 호출 시간 때문에 항상 마감 뒤에 끝난다. 그래서 마감 직전 몇 초 안에 충족된 상태는 늘 "늦음"으로 판정됐다. 정상 복구를 실패로 만드는 창이다.
- **"재부팅"이라는 한 단어 안에 다른 변경이 숨어 있을 수 있다.** 노드는 보안 패치를 자동으로 받되 자동 재부팅은 꺼 두었다. 그러면 새 커널이 설치만 된 채 쌓이고, **다음 재부팅이 곧 커널 전환**이 된다. 재부팅 리허설을 하려던 순간이 메이저 커널 전환의 첫 실행이었다. 사전 점검에 "재부팅이 필요한 패키지가 대기 중인가"를 넣어 두지 않았다면, 복구가 실패했을 때 재부팅 경로 문제인지 커널 문제인지 가릴 수 없었을 것이다.
- **돌아올 길을 먼저 만든다.** 서버의 부트로더 메뉴는 숨겨져 있고 대기 시간이 0이다. 새 커널이 부팅에 실패하면 콘솔에서 옛 커널을 고를 방법이 사실상 없다. 해법은 순서를 뒤집는 것이다 — **기본값을 지금 돌고 있는 커널로 고정**하고, 새 커널은 "다음 한 번만" 부팅하게 한다. 새 커널이 어떤 식으로 실패하든 재부팅 한 번이면 고정된 커널로 돌아온다. 그리고 이 길 자체를 덜 중요한 노드에서 먼저 실증한다(고정만 하고 그냥 재부팅해 옛 커널로 올라오는지).
- **위험이 몰린 한 점을 찾는다.** 계획 단계의 조사는 커널과 보안 모듈, 컨테이너 런타임 사이의 문제를 짚었고 그중 exec 관련 건은 미해결이었다. 클러스터에서 exec 프로브를 쓰는 것을 세어 보니 **비밀 저장소의 준비 상태 프로브 하나**였다 — control plane 노드에 있다. 그래서 다른 노드에 같은 이미지 · 같은 보안 설정 · 같은 모양의 프로브를 가진 시험 파드를 띄워 새 커널에서 먼저 본다.
- **평문은 필요한 만큼만 디스크에 닿게 한다.** 클러스터 백업 묶음에는 서버 토큰과 인증서 개인키가 들어 있다. 무결성 확인에 필요한 것은 데이터베이스 파일 하나다. 복호화한 묶음을 디스크에 풀지 않고, 파이프로 그 파일만 꺼낸다. 끝나면 성공이든 실패든 작업 디렉터리를 지운다 — 지워서 잃는 것이 없다(원본은 저장소에 있다).
- **"복원할 수 없는데 통과"를 찾는 리뷰.** 백업 검증 스크립트의 리뷰가 실행으로 보인 것: 신선도를 객체 **이름**의 시각으로만 봤더니 미래 시각의 이름이 통과하고 진짜 최신을 가렸다 · 표가 비어 있어도 통과했다 · 같은 파일을 가리키는 다른 표기의 항목이 "정확히 하나" 검사를 비껴갔다(복원하면 뒤의 것이 덮어쓴다). 검사는 "있는가"가 아니라 **"복원했을 때 쓸 수 있는가"** 를 물어야 한다.
- **비밀을 다루는 절차는 붙여 넣는 블록이 아니라 테스트가 있는 스크립트로.** 개인키를 쓰는 복호화와 부트로더를 고치는 작업 둘 다 스크립트로 만들고, 가짜 환경에서 실패와 과도 상태를 포함해 돌렸다. 블록은 한 번 쓰고 사라지지만 스크립트는 다음 복원 훈련과 다음 커널 전환에서 다시 쓴다.
- **스크립트를 표준 입력으로 넘겨 실행할 때.** 노드에 파일을 남기지 않으려고 스크립트를 원격 셸의 표준 입력으로 보낸다. 이때 스크립트 안의 어떤 명령이 표준 입력을 읽으면 스크립트의 나머지를 삼킨다. 본체의 표준 입력을 비워 두고, 끝을 명시적 종료로 닫아 뒤따르는 바이트를 해석하지 않게 한다.
- **측정 경로도 측정 대상이다.** 조회 한 번이 2–20초 걸리고 여섯에서 여덟 번에 한 번 실패했다. 오후에는 3초 안팎이었다. 같은 PC에서 돌던 테스트와 다른 세션이 남긴 오래 도는 프로세스가 원인일 수 있다. 한 번뿐인 측정을 할 때는 측정하는 쪽을 조용하게 만든다.

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| "30분 안에 전부 수렴" 기준의 근거(사용자 결정) | 재부팅부터 전 Application이 다시 수렴하기까지의 시간과 실제 이력을 기록하고, 문면 그대로의 구간(빈 클러스터에서의 첫 수렴)은 재지 않았다고 적는다 | 처음부터 다시 구축 — 문면 그대로지만 반나절 이상이고 복원 절차 문서가 아직 없다 · root 재적용 후 재측정 — 객체가 이미 있어 더 증명하는 것이 없다 |
| 대기 중인 커널(사용자 결정) | 덜 중요한 노드에서 새 커널을 먼저 시험하고, 그 노드의 완전 복구와 exec 프로브 확인을 조건으로 control plane 노드를 진행. **복구 경로가 없으면 먼저 준비** | 그대로 재부팅 — 가장 빠르지만 실패 시 원인 구분이 어렵고 돌아올 길이 없다 · 이번만 옛 커널로 — 원인은 분리되지만 미검증 커널이 다음 부팅에 그대로 남는다 |
| 새 커널을 시험하는 방법 | 기본값을 지금 커널로 고정 + 새 커널은 1회용 선택 | 기본값을 새 커널로 두고 실패하면 콘솔에서 고른다 — 메뉴가 숨겨져 있어 고를 수 없다 |
| 하네스의 0초 | 옛 상태를 마지막으로 본 시각(하네스를 먼저 켠다) | 스크립트 시작 — 사람의 타이밍에 마감이 좌우된다 · API가 끊기는 순간을 밖에서 감지 — 호출이 가끔 실패하는 경로에서는 잘못 시작한다 |
| 낡은 상태로 통과하는 조건 | 노드가 돌아온 시각을 기준으로 삼아 그 뒤의 갱신만 인정 | 그대로 두고 사람이 사후에 확인 — 통과 판정이 증거가 되지 못한다. 다만 한 조건(재조정 주기가 긴 것)은 하네스에 넣으면 정상 복구가 마감을 넘길 수 있어 사후 스냅샷으로 뺐다 |
| 백업 검증의 형태 | 스크립트 + 하네스(진짜 도구로, 원격 저장소 호출만 가짜) | 붙여 넣는 블록 — 개인키와 평문을 다루는데 실패 경로를 시험할 수 없다 |
| 무결성 검사 도구 | 표준 라이브러리의 SQLite 모듈(같은 엔진의 같은 검사) | 명령줄 도구 설치 — 과제 문구 그대로지만 설치 하나가 늘 뿐 검사는 같다. 표기가 다르다는 점을 기록에 적는다 |

## 결과와 검증
- 재부팅 하네스: 부팅 식별자 기준값 · 재부팅 뒤 기준 시각 · 마감 판정 · 실제 지연에 맞춘 대기 상한 · 0초 기준점. 독립 리뷰 두 번이 가짜 시나리오 실행으로 잘못된 통과 셋과 잘못된 실패 창 하나를 재현했고 전부 반영했다. 재부팅 없이 실제 경로에서 예행해 다섯 조건이 실제 응답과 권한에서 동작함을 확인했다. 뒤의 수정 셋은 리뷰가 진행 중이다.
- 백업 검증 스크립트: 실제 저장소 · 실제 개인키로 운영자가 실행해 13항목 통과(16초). 클러스터 번들은 복호화 인증, 항목 구성, 데이터베이스 무결성과 행 수를 확인했고, 비밀 저장소 스냅샷은 오프라인 검사를 통과했다. 작업 디렉터리는 지워졌다.
- 사전 관찰: 노드 · Application · 비밀 동기화 · 비밀 저장소 · 터널 커넥터가 전부 정상이고, 노드마다 터널 커넥터가 하나씩 있어 한 노드가 내려가도 접속 경로가 남는 것을 확인했다.
- 새 커널의 사전 점검(읽기 전용): 초기 램디스크와 필요한 커널 모듈이 있고, 클러스터 배포판이 요구하는 커널 설정에 두 커널 사이 차이가 없으며, 배포판의 설정 검사도 새 커널 설정에 대해 통과했다.
- 커널 시험 부팅 스크립트: 가짜 루트에서 85개 단언 통과. 독립 리뷰가 실제 부트로더 도구로(컨테이너 안에서) 핵심 동작 — 고정한 기본값이 옛 커널로 풀리고, 1회용 선택이 한 번 쓰이고 지워지는 것 — 을 확인했고, 고칠 것 다섯을 냈다(다른 설정 갱신과 겹칠 때의 깨진 설정 파일 · 접속이 끊길 때 남는 과도 상태 · 절차의 순서 둘 · 재부팅 전 읽기 전용 확인 추가).
- **노드에는 아무것도 바꾸지 않았다.**

## 다음 학습
- 실제 재부팅에서만 확정되는 것: 재부팅 뒤 노드가 처음 올리는 상태의 시각이 정말 부팅 뒤 값인가 · 낡은 값이 보이는 창의 길이 · 장애 뒤 비밀 동기화의 재시도 간격 · 실제 부트로더가 1회용 선택을 지우는가.
- 자동 재부팅을 끈 노드의 **운영 체제 패치 재부팅 절차**가 운영 문서에 없다. 이번에 만든 순서(고정 → 덜 중요한 노드에서 시험 → control plane → 고정 해제)를 절차로 남긴다.
- 고정된 커널이 자동 삭제될 수 있는 구간(새 커널로 도는 동안 더 새 커널이 설치될 때)이 있다 — 시험부터 고정 해제까지를 한 번에 끝내는 것 말고 다른 방어가 필요한지 본다.
- 하네스의 단위 테스트가 8분을 넘겼다. 판정을 약하게 하지 않고 줄이는 방법(가짜를 상주형으로)을 본다.

## 사고·오류
- **설계에서 "낡은 값" 문제를 한 조건에만 적었다.** 재조정 주기가 긴 조건의 낡은 값은 적어 두었는데, 같은 문제가 있는 다른 두 조건은 놓쳤다. 리뷰가 가짜 시나리오로 재현해 찾았다.
- **하네스의 대기 상한이 실제 경로와 맞지 않았다.** 그대로 재부팅했다면 한 조건이 복구와 무관하게 실패했을 것이다. 사전 관찰을 리허설과 같은 경로 · 같은 도구로 돌린 덕에 재부팅 전에 잡았다.
- **운영자에게 준 명령이 상대 경로였다.** 저장소 루트에서 실행하라고 적었지만 다른 디렉터리에서 실행돼 실패했다(아무것도 실행되지 않았다). 운영자 명령은 절대 경로로 준다.
- **"토큰 발급"과 "설정 파일 갱신"을 한 문장으로 안내했다.** 발급 명령만 실행되어 조회용 설정 파일은 옛 토큰 그대로였다. 지난번과 같은 블록(발급한 값을 화면에 내지 않고 파일에만 넣는)을 다시 주어 해결했다.
- **설정 하나가 다른 저장소에 적용됐다.** 같은 이름의 배포 환경이 두 저장소에 있어, 한쪽에 끌 설정이 다른 쪽에서 먼저 꺼졌다. 조회로 값을 대조하는 점검 명령이 "아직 켜져 있다"고 답해 바로 드러났다. 더 닫는 쪽의 변경이라 피해는 없다.
- **구현을 맡긴 작업이 사용자 임시 폴더에 디렉터리를 백 개 넘게 만들었다.** 명령줄 도구가 실행할 때마다 임시 폴더에 파일을 남기는 것을 몰랐다. 자기 실행 시간대의 것만 골라 지웠다고 보고했고, 스크립트는 자식 프로세스의 임시 폴더를 작업 디렉터리 안으로 돌리게 고쳤다.
- **조회 경로가 오후 늦게 느려졌다.** 구현 · 리뷰 작업이 같은 PC에서 테스트를 돌리고 있었고, 다른 세션이 남긴 프로세스가 네 시간 넘게 원격 마운트를 훑고 있었다. 원인을 확정하지는 못했다. 리허설 때는 다른 작업을 멈추고 지연을 다시 잰다.
