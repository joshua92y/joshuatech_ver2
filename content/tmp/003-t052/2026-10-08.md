# 003-platform-foundation T052 — 오퍼레이터를 들이는 일은 CRD를 들이는 일이다: CNPG operator · 백업 플러그인 · 이미지 카탈로그 (2026-10-08)
> 1일차(2026-10-08 착수 · 같은 날 완료). US3의 첫 구현 과제 — gitops 저장소에 PostgreSQL 오퍼레이터와 백업 플러그인, 이미지 카탈로그를 선언했다.

## 문제
pod별 데이터베이스(US3)를 담을 PostgreSQL 클러스터를 만들기 전에, 그것을 관리할 오퍼레이터(CloudNativePG)와 백업 플러그인(barman-cloud), 그리고 어떤 PostgreSQL 이미지를 쓸지 적은 카탈로그가 먼저 있어야 한다. 셋 다 gitops 저장소의 한 디렉터리에 선언해 Argo CD가 적용하게 하되, 오퍼레이터가 가져오는 CRD 12장이 실수로 지워지지 않게 보호하고, 이미지는 digest로 못박고, 조회 전용 자격으로 결과를 확인해야 했다.

## 배운 개념
- **"Application 둘"이라는 문면을 디렉터리 하나로 푸는 근거는 계약에 있다.** 과제는 오퍼레이터와 플러그인을 각각 Application이라 적었지만, 동기화 순서 표는 두 컴포넌트를 한 행에 두고, 표에 없는 디렉터리는 검사가 거부한다. 게다가 플러그인은 오퍼레이터와 같은 네임스페이스에 있어야 발견된다(오퍼레이터가 자기 네임스페이스의 라벨 붙은 Service를 찾는다). 문면보다 계약과 동작 원리가 구현 단위를 정한다.
- **차트의 사실은 받아서 읽는다.** 두 차트 모두 CRD에 어노테이션을 붙이는 값이 없고, 이미지 digest 키도 없고, 하나는 값 스키마가 오타를 전혀 잡지 못한다. 그래서 CRD 보호는 kustomize 패치로, digest는 태그 문자열에 병기로, 오타 방어는 렌더 결과 대조로 했다. 차트 하나는 "보기 전용" ClusterRole을 항상 렌더하고 집계 라벨만 값으로 켠다는 것도 원본에서 읽었다 — 켰다면 읽기 전용 자격이 넓어지고 권한 기준선 검사가 깨졌을 것이다.
- **카탈로그 vendoring은 바이트 단위 대조가 가능한 형태로 한다.** upstream 파일을 그대로 옮기고 출처 커밋과 파일 해시를 주석에 적었다. 참조하지 않는 항목(다른 major)을 깎지 않은 이유는, 갱신할 때 upstream과 diff 한 번으로 끝나게 하기 위해서다. 실제로 리뷰어 둘이 각자 upstream을 받아 diff로 같음을 증명했다.
- **같은 sync 안의 순서는 리소스 수준 wave로 보강할 수 있다.** CRD가 등록되고 오퍼레이터가 떠야 그 CRD의 객체(카탈로그)를 적용할 수 있다. Application 표의 wave와는 다른 층위의 리소스 wave "1"을 카탈로그에만 두었고, 첫 동기화가 재시도 없이 한 번에 끝났다. 다만 Argo가 같은 wave에서도 CRD를 먼저 적용하므로 이 보강이 꼭 필요했는지는 재지 않았다 — "해롭지 않은 보수적 선택"으로 기록했다.
- **클러스터 범위 CR은 AppProject 허용 목록에 kind가 있어야 적용된다.** 지시문에 없던 사실을 빌더가 렌더의 클러스터 범위 kind를 허용 목록과 대조하다 찾았다. 열거형 허용 목록은 "빠진 kind는 sync 실패로 드러난다"가 설계였고, 그 실패를 머지 전에 잡은 셈이다.
- **webhook이 무엇을 가로채는지는 렌더가 말해 준다.** 지시문은 다른 컴포넌트의 문장을 복사해 "삭제까지 거부된다"고 적었는데, 렌더의 webhook 규칙은 생성·갱신뿐이었다. 리뷰어 둘이 같은 줄을 각자 잡았다. 복사한 설명은 원본 컴포넌트의 사실이지 새 컴포넌트의 사실이 아니다.
- **네트워크 정책 아래에서는 오퍼레이터와 그 인스턴스가 다른 네임스페이스라는 점이 경로가 된다.** 오퍼레이터는 인스턴스 파드의 상태 포트로 직접 접속한다. 계약은 이 통신을 "같은 네임스페이스"로 분류했는데 둘은 다른 네임스페이스다. 이번 과제의 동기화는 막히지 않지만 다음 과제의 클러스터는 고착된다 — 계약을 먼저 고치는 순서로 다음 과제에 넘겼다.
- **하네스의 "소유 과제"는 하네스를 쓴 과제가 아니라 대상이 존재해야 하는 과제다.** 검사 Job의 소유를 하네스 작성 과제로 적어 둔 탓에, 그 과제들을 체크하자 "체크됐는데 없다"는 거짓 FAIL이 났다. 소유를 E2E 과제로 옮겼다.

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| 구현 단위 | Application 하나 · 디렉터리 하나 · helm 차트 2항목 | Application 둘 — 순서 표에 없는 디렉터리는 검사가 거부하고, 플러그인은 같은 ns에 있어야 발견된다 |
| 차트 버전 | 과제 문면의 동결 판(0.29.0 · 0.7.1) | 최신 판(0.29.1 · 0.8.1) — 동결된 과제 문면이 우선, 올림은 별도 결정(Renovate) |
| 카탈로그 범위 | upstream 6 major 전부, 바이트 동일 | major 18만 — 갱신 때 upstream과 diff 대조가 안 된다 |
| CRD 보호 | kustomize 패치로 12장 전부 | 차트 값 — 두 차트 모두 그런 값이 없다 |
| 집계 ClusterRole | 라벨 끄기(기본값 명시) | 켜기 — 읽기 전용 자격이 넓어지고 권한 기준선 검사가 깨진다 |
| 머지 뒤 확인 | 조회 전용 자격의 스크립트 + 하네스 | 운영자 kubeconfig — 에이전트 자격 규칙 위반 |

## 결과와 검증
- 머지 뒤 약 5분 만에 Argo가 한 번의 operation(26초 · 재시도 0)으로 리소스 35장을 Synced/Healthy로 올렸다. 오퍼레이터와 플러그인 파드는 데이터 노드에서 재시작 0, 플러그인 인증서 2장은 cert-manager가 같은 초에 발급했다.
- 확인 스크립트 19항목 전부 PASS(Application 상태 · 리소스 개수 · 배치 노드 · 이미지 digest 3 · 설정값 · CRD 12장 보호 · 인증서 Ready · 오퍼레이터 오류 로그 0). 삭제 보호 하네스가 처음으로 PASS(12장).
- 머지 전: 렌더 35장, 검사 PASS 38 · FAIL 0, 자기검사 25 케이스 0 실패, 독립 리뷰 두 렌즈가 빌더의 결과를 전부 재현한 뒤 문구 지적 10건(렌더 불변)을 반영.
- 다음 과제에 넘긴 것: 오퍼레이터 → 인스턴스 8000 네트워크 경로의 계약·정책·하네스 보강, 플러그인 인증서 첫 갱신 관찰, 자원 요청값 교정.

## 사고·오류
- **세션이 두 번 끊겼다**(에이전트 한도 · PC 재부팅). 리뷰어는 기록을 이어받아 재개했고, 하위 에이전트 보고는 받는 즉시 파일로 저장하는 습관을 굳혔다.
- **지시문에 틀린 전제를 적었다** — webhook이 삭제도 거부한다는 문장과 "같은 네임스페이스" 분류. 둘 다 리뷰가 렌더와 문서로 바로잡았다.
- **로컬 검사를 동시에 둘 돌리자 거짓 FAIL이 났다**(Git Bash의 fork 오류). 하네스는 한 번에 하나만 돌리고 판정은 CI에 맡긴다.
- **조회 세션 만료**로 백업 단언이 FAIL했다 — 토큰과 세션의 만료 시각이 달라, 하네스 전에 둘 다 확인한다.
