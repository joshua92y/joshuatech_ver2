# 003-platform-foundation T046 — 정적 검사는 "무엇을 세는가"보다 "무엇과 똑같은가"를 물어야 한다 (2026-09-28)
> 2일차(반영분 적대적 검증 → 수정 → 범위를 좁힌 재검증 → PR). 배포 뒤 실측은 머지 다음.

## 문제
1일차에 만든 정적 검사는 "Secret 변경 감시 컨트롤러가 정해진 네임스페이스만 본다"를 렌더 결과에서 확인한다. 리뷰 지적을 반영한 뒤 그 검사가 정말 속지 않는지를 다시 공격해 보았더니, 실제 트리를 조금씩 바꾼 변형 47개 중 19개가 검사를 통과했고 그중 세 갈래는 계약이 금지한 상태였다. 검사는 있었지만 **물어보는 방식**이 틀렸다.

두 번째 문제는 일하는 방식이었다. 수정 한 번마다 자기검사 전체(약 1시간)를 다시 돌리고 있었다.

## 배운 개념
- **명령줄 인자는 "있는지"가 아니라 "목록이 똑같은지"로 검사한다.** 검사는 `--namespaces=…` 인자가 하나 있고 값이 맞는지를 셌다. 그런데 명령줄 파서는 **값을 받는 플래그를 값 없이 쓰면 바로 뒤의 인자를 그 값으로 삼킨다**. 로그 형식 플래그를 값 없이 앞에 끼워 넣으면 뒤따르는 네임스페이스 인자가 "로그 형식의 값"이 되어 사라지고, 감시 목록이 비어 컨트롤러는 전역 모드로 뜬다. 인자 목록에는 기대한 문자열이 그대로 보이므로 세는 검사는 통과한다. 같은 플래그를 반복하면 목록형 플래그는 값이 **합쳐지고**, 문자열형 플래그는 마지막 값이 이긴다. 컨테이너 런타임이 펼치는 변수 참조는 검사 시점에는 없던 인자를 실행 시점에 만든다. 이 모든 경로를 하나씩 막는 대신 "인자 목록이 기대 목록과 원소 수·순서·값까지 같다"로 바꾸니 한 번에 닫혔다.
- **렌더를 검사해도, 배포 도구가 다른 렌더를 적용하면 소용없다.** 정적 검사는 디렉터리를 직접 빌드해서 본다. 그런데 GitOps 도구는 Application 객체가 정한 방식으로 렌더한다 — Application에 패치 한 줄을 넣으면 **적용되는 렌더와 검사한 렌더가 갈린다**. 검사는 아무것도 바뀌지 않은 트리와 똑같이 통과했다. 그래서 "Application은 source를 덮어쓰지 않는다"를 검사에 넣었다.
- **우회 경로 열거는 끝이 없다 — 어디서 멈출지를 정해야 한다.** 위 검사를 넣고 다시 공격하니 source 디렉터리 안의 파라미터 파일이 나왔고, 그것을 막으니 다른 필드가, 또 그것을 막으니 동기화 요청 필드가 나왔다. 세 번째에서 열거를 멈추고 문서에 **"이 검사는 아는 경로를 막은 목록이며 전부 덮는다고 주장하지 않는다"**고 적었다. 과장된 보증은 빈틈보다 나쁘다 — 읽는 사람이 그 뒤를 확인하지 않게 만든다. 전수 조사는 이 검사를 CI에 연결하는 다음 태스크로 넘겼다.
- **"1개 이상이면 통과"는 관찰이 끊겨도 통과한다.** 5분 동안 30초마다 상태를 보고 끝에 판정 줄을 찍는 절차를 만들었는데, 표본 기준이 "1개 이상"이었다. 대화형 셸에 붙여 넣으면 도중의 오류는 그 문장만 중단시키고 뒤 문장은 계속 실행된다. 2분에서 끊긴 관찰이 "전부 OK"로 찍혔다. 표본마다 기준 시각에서 지난 초를 함께 담고 "첫 표본이 충분히 이르고 마지막 표본이 충분히 늦은가"를 판정에 넣었다. 가짜 시계와 가짜 명령으로 늦은 시작·도중 끊김을 재현해 확인했다.
- **필드 이름은 구조체 이름이 아니라 직렬화 태그로 확인한다.** 자동 복구 횟수를 읽는 조회에 소스의 필드 이름을 그대로 썼는데, 직렬화되는 키 이름은 달랐다. 없는 키를 조회하면 오류가 아니라 **빈 출력과 성공 종료**가 나온다 — "0회"처럼 보이는 가짜 값이다.
- **완료 조건도 실행해 본다.** "이 문자열이 0건이면 제거 완료"라는 조건을 적었는데, 제거를 정확히 마치면 기대 개수가 하나씩 줄면서 다른 단언의 숫자가 바로 그 문자열이 된다. 조건을 만족시킬 수 없는 완료 조건이었다. 남는 것이 정상인 항목을 이름으로 적어 두는 쪽으로 고쳤다.

## 선택과 대안
| 질문 | 택한 것 | 버린 것과 이유 |
|---|---|---|
| 인자 검사 | 목록 정확 일치 | 위험한 플래그를 하나씩 금지 — 파서 동작을 다 알아야 하고 새 플래그가 생기면 뚫린다 |
| 배포 도구의 렌더 변경 | 아는 경로 금지 + 한계 명시, 전수 조사는 다음 태스크 | 이 태스크에서 끝까지 열거 — 본래 목적(실측)이 밀리고 끝을 보장할 수 없다 |
| 반복 중 검사 실행 | 바뀐 검사에 해당하는 케이스만 실행, 전체는 태스크 마무리에 한 번 | 수정마다 전체 실행 — 한 번에 약 1시간, 바뀌지 않은 검사를 반복해서 확인할 뿐이다 |
| 부분 실행의 위험 | CI 환경에서는 부분 실행을 거부(실패 종료) | 요약 줄에만 "부분 실행"이라 표시 — 종료 코드만 보는 소비자는 전체 통과로 읽는다 |
| 마지막 지적 6건 | 직접 고치고 영향 받는 케이스만 확인 | 다시 검증 워크플로 — 작은 수정에 비해 비용이 크고 열거를 멈추기로 한 결정과 맞지 않는다 |

## 결과와 검증
- 검증 지적 21건을 반영하고, 범위를 좁힌 재검증의 6건까지 반영했다.
- 부분 자기검사(바뀐 검사의 케이스) 실패 0 · 실제 트리 정적 검사 실패 0 · 매니페스트 렌더는 첫 리뷰 시점과 바이트 동일(검사와 문서만 바뀌었다) · 비밀 검사 0건.
- 라이브 하네스의 단언도 같은 규칙(인자 목록 정확 일치 · `command` 금지 · 컨테이너 1개)으로 바꿨다.
- PR을 열었고 CI가 통과했다. 머지 전 클러스터는 모든 Application이 동기화·정상 상태다.

## 사고·오류
- **긴 검증을 도중에 멈춰 50분어치 결과를 잃었다.** 검사 실행 방식을 바꾸려고 돌고 있던 워크플로를 멈췄는데, 수정과 한쪽 검증은 이미 끝나 있었고 다른 쪽 검증은 거의 끝나가던 중이었다. 멈추기 전에 어디까지 진행됐는지 먼저 확인했어야 했다.
- **멈춘 작업이 남긴 프로세스가 다음 실행을 느리게 했다.** 같은 검사가 평소의 몇 배 걸렸다. 긴 작업을 멈춘 뒤에는 남은 프로세스가 없는지 확인한다.
- **검사 출력을 파이프로 잘라 보면서 종료 코드를 놓쳤다.** 비밀 검사 결과를 마지막 몇 줄만 보고 커밋했다(결과적으로 추적되는 파일에는 문제가 없었다). 그 뒤로는 통과 여부를 종료 코드로만 판정한다.
- **내가 고친 완료 조건 패턴이 다른 컴포넌트의 문장에 걸렸다.** 패턴을 실제 저장소에 돌려 보고서야 알았다. 문서에 넣는 명령도 실행해 본 뒤에 적는다.
