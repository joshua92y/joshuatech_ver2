# 003-platform-foundation T067 — 게이트 앞에서 무엇이 도는가: 액션의 "버전 출력"이 PR 코드를 실행하던 길 (2026-11-04)
> 2일차(r3–r8 수정과 리뷰 · 독립 검증 · 마감). 1일차(설계 · r1 · r2)는 `2026-11-03.md`.

## 문제
1일차 끝에 게이트는 두 원칙을 세웠다. 하나는 "PR 코드를 돌리지 않는 job"이고, 다른 하나는 "기준 커밋의 검사기로 비교"다. 2일차의 질문은 그 원칙이 실제로 지켜지는가였다.

- 게이트 job이 PR 내용에서 무엇을 읽는가.
- 게이트 스텝 전에 이미 무엇이 실행되는가.
- 게이트가 본 바이트가 머지될 바이트와 같은가.
- 이 게이트가 머지 뒤 스스로를 잠그는 길이 있는가.

## 배운 개념
- **"PR 코드를 돌리지 않는다"는 스텝 목록이 아니라 실행되는 모든 것에 대한 주장이다.** 게이트 job에는 체크아웃 · Node 설치 · 게이트 스크립트 세 스텝뿐이었다. 그런데 Node 설치 액션(setup-node v6.5.0)은 설치가 끝나면 조건 없이 작업 공간에서 `node` · `npm` · `yarn`의 `--version`을 돌려 로그에 찍는다. 러너의 Yarn 1은 `--version`을 처리하기 **전에**, 작업 디렉터리와 그 위 디렉터리의 `.yarnrc` · `.yarnrc.yml`에 적힌 `yarnPath`를 Node로 실행한다(프로젝트별 Yarn 판 고정 기능). 이 탐침이 체크아웃 뒤에 돌면 결과는 이렇다: `.yarnrc.yml` 한 줄과 스크립트 하나를 더한 PR이 게이트 파일을 하나도 바꾸지 않고도 게이트보다 먼저 같은 러너에서 코드를 돌린다. 두 원문(액션 소스의 고정 SHA · Yarn 1.22.22 소스)을 읽어 확인했다.
- **순서가 곧 경계다.** 해법은 Node 설치를 체크아웃 **앞**으로 옮기는 것이었다. 그러면 탐침이 도는 순간 작업 공간이 비어 있다(호스티드 러너는 job마다 새 VM). 그 대가로 Node 버전을 `.node-version` 파일에서 읽을 수 없게 되어 ci.yml에 고정값을 적었다. 고정값과 파일이 갈라지면 위험해지므로, 같음을 CI가 도는 테스트로 지킨다.
- **같은 구멍을 막는 두 방법 중 무엇을 고르는가.** 리뷰는 Node 배포판을 버전 + sha256으로 고정해 직접 내려받는 방법을 권했다. 우리는 액션을 체크아웃 앞으로 옮기는 방법을 골랐다. 둘 다 이번 구멍(체크아웃 뒤 PR 내용이 실행되는 길)을 막는다. 액션 방식은 다른 job이 이미 신뢰하는 고정 SHA 액션을 재사용하고 수동 해시 갱신을 피한다. 고른 방식이 실제로 구멍을 닫는지는 다음 리뷰가 원문으로 다시 확인했다.
- **커밋 객체에서 읽고, 작업 트리는 대조만 한다.** 체크아웃은 PR의 `.gitattributes`로 작업 트리 바이트를 바꿀 수 있다. 그래서 CI에서 변경 쪽 스키마와 부트스트랩 검사기는 HEAD 커밋 객체에서 꺼낸다. 작업 트리는 `hash-object --no-filters`로 그 blob과 바이트가 같은지만 본다. 같지 않으면 오류다. 소비자의 체크아웃이 게이트가 본 것과 다른 내용을 읽기 때문이다.
- **fail-closed 게이트도 스스로를 잠글 수 있다.** 머지되면 다음 기준이 될 트리가 기준 꺼내기 규칙을 어기면, 그 뒤 모든 PR이 오류로 막힌다. 그것을 되돌리는 PR도 마찬가지다. 그런 트리가 생기는 경우는 둘이다.
  - 이름 꼴 밖의 스키마 파일.
  - 검사기 경로가 심볼릭 링크.

  그래서 변경 쪽도 "다음 기준의 모양"을 지켜야 한다. 검사기를 더 엄격하게 하거나 잘못 고친 변경도 같은 교착을 만든다. 이것은 게이트 안에서 막을 수 없다(게이트는 PR 코드를 돌리지 않는다). 머지 전 방어는 테스트 job에 둔다. 그 테스트는 머지 뒤 게이트와 **같은 조건**으로 돌아야 의미가 있다: 패키지 밖에 둔 검사기 사본으로 실제 스키마를 비교한다.
- **방어 문장은 실제 범위와 같아야 한다.** "복구는 운영자 우회 머지뿐"은 너무 강했다. 게이트 스크립트를 함께 고친 PR도 복구할 수 있고, 우회 머지는 다른 required check까지 비켜 간다. "같은 PR이 시험을 고치지 않을 때만"은 너무 좁았다. 패키지의 test 스크립트나 vitest 설정을 바꾼 앞선 PR도 방어를 끈다. 리뷰가 이런 문장의 정확도까지 원문 대조로 지적했다.
- **시험 자식 프로세스는 시험 러너의 환경을 물려받는다.** "패키지 밖에서 돈다"를 시험하려고 검사기를 임시 디렉터리에 복사해 돌렸다. 그런데 패키지 매니저(pnpm)가 시험 러너를 띄울 때 넣은 모듈 검색 경로(`NODE_PATH`)를 복사본도 물려받아, 의존성이 없어야 할 자리에서 의존성을 찾았다. 직접 실행할 때는 그 경로가 없어 시험이 맞게 보였다. 시험이 재현하려는 조건(의존성 없음)은 자식 env에서 그 변수를 지워 만들고, 그 조건이 성립하는지를 먼저 단언한다. 변이 증거는 CI와 **같은 명령**으로 낸다.
- **검사의 범위를 먼저 정해야 리뷰가 수렴한다.** Node 판 고정값이 ci.yml과 `.node-version`에서 갈라지지 않게 하는 줄 단위 검사를 두었다. 그러자 리뷰는 라운드마다 새 꼴을 찾아냈다. YAML 이어짐 줄, 이스케이프, 별칭, 가짜 job 블록처럼 ci.yml을 **일부러** 꼬아 쓰면 검사가 놓친다는 것이었다. 그런데 ci.yml을 고칠 수 있는 PR은 게이트를 통째로 지울 수도 있다. 그런 편집은 처음부터 코드 소유자 리뷰의 몫이다. 그래서 "실수로 생긴 드리프트를 잡는 줄 단위 검사"로 범위를 문서에 고정하고, 그 안에서만 고쳤다.
- **간헐 실패는 꼴을 기록하고 좁게 다룬다. 원인 추정은 반증될 수 있다.** Windows 하네스에서 픽스처 git이 드물게 `git: '<자기 경로>' is not a git command`로 끝났다. 처음에는 git 런처 탓으로 보고 실제 바이너리를 직접 부르게 바꿨다. 그러나 실제 바이너리에서도 같은 꼴이 다시 나 그 추정은 반증됐다(원인 미상). 결국 재시도는 정확히 그 한 줄 꼴, "프로세스가 돌지 못한 꼴", "시험 대상의 git 위치 확인 실패 꼴"로만 좁혔다. 재시도마다 횟수를 note 줄로 드러냈고, 판정 단언은 약하게 하지 않았다.

## 선택과 대안
- **setup-node 위치**: 체크아웃 앞 + 고정 `node-version`을 골랐다. 대안은 둘이었다.
  - "Node tarball + sha256 직접 설치": 같은 구멍을 막지만 수동 갱신이 생겨 미채택.
  - "`YARN_IGNORE_PATH=1`만 추가": npm 탐침 · 이후 판의 동작 변화에 약해 기각.
- **Node 고정값 드리프트 방어**: CI가 도는 패키지 테스트가 ci.yml의 고정값과 `.node-version`을 비교한다. 대안 "로컬 하네스만"은 CI에서 돌지 않아 기각했다. 대안 "게이트 스크립트가 `.node-version`을 읽는다"는 게이트가 PR 파일을 하나 더 읽게 되어 기각했다.
- **변경 쪽 읽기**: CI = 커밋 객체 + 바이트 대조, 로컬 = 작업 트리. 대안 "CI도 작업 트리"는 속성 변환 바이트를 검사하게 되어 기각했다.
- **교착 방어 위치**: 테스트 job(패키지 밖 사본 · 실제 스키마)에 두었다. 대안 "게이트에서 변경 쪽 검사기도 돌려 본다"는 게이트 job에서 PR 코드를 돌리게 되어 기각했다. 게이트 스크립트를 읽는 bash와 같은 러너에서 PR 코드가 돌면 실행 중인 스크립트 파일까지 바꿀 수 있다.
