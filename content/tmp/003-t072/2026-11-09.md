# 003-platform-foundation T072 — pod 템플릿 구현: 시험이 비밀을 찍는 길 · 이미지 컨텍스트 허용 목록 · 플랫폼마다 다른 도구 동작 (2026-11-09)
> 2일차(사용자 결정 둘 · uv 판 올림과 푸시 검증 · 조각 ① 수렴 · 조각 ② 생성 Python 프로젝트와 시험 7파일 r1–r3 · 조각 ③ 이미지 · compose r1). 조각 ③ r2 · 조각 ④(deploy/base · CI)는 뒤 파일.

## 문제
설계를 코드로 옮기는 날이었다. 하네스(조각 ①)는 이미 빨강을 만들어 두었고, 템플릿이 생성하는 Python 프로젝트 · 시험 7파일(조각 ②)과 컨테이너 이미지 · 로컬 compose(조각 ③)를 채워 그 빨강을 초록으로 바꿨다. 조각마다 빌더 하나와 리뷰어 둘(설계 · 계약 일치 렌즈, 보안 · 실패 양상 렌즈)이 돌았고, 리뷰가 코드 수정이 필요한 발견을 남기면 라운드를 더 돌았다. 「시험이 통과한다」보다 「시험이 실패할 때 무엇을 찍는가」와 「다른 플랫폼에서도 같은 판정인가」가 더 많은 결함을 냈다.

## 배운 개념
- **pytest 단언 재작성은 실패 때 호출 인자의 repr을 찍는다.** `assert load(env) is None`이 실패하면 설명 줄에 `where None = load({...})`가 붙고, 그 매핑이 통째로 나온다. `-vv`는 자르지도 않는다. 셸 env 전체를 인자로 넘기는 단언은, 지키려는 회귀가 생기는 날 개발자나 CI의 env 값을 실패 출력에 쏟는다. 결과를 지역 변수로 받은 뒤 그 변수를 단언하고, 넘기는 매핑도 시험 래퍼가 정한 이름으로 좁혔다. 시험이 만든 토큰을 인자로 넘기는 단언도 같은 꼴로 고쳤다.
- **conftest가 import하는 도우미 모듈의 `assert`는 재작성되지 않는다.** 그대로 두면 `python -O`에서 단언이 사라져 시험이 공허하게 통과한다. 도우미를 `pytest.register_assert_rewrite`로 등록하고, 실행 가드가 `-O` · 넓은 트레이스백 · 지역 변수 출력을 로컬 실행에서도 거부하게 했다.
- **pytest-django는 설정 모듈을 옵션 > 환경 변수 > ini 순으로 고른다.** ini에만 시험 설정을 적으면 셸에 남은 `DJANGO_SETTINGS_MODULE`이 시험 래퍼를 비켜 간다. `addopts`에 `--ds=tests.settings`를 넣어 막았다.
- **설정 라이브러리는 「주어진 매핑만」 읽지 않을 수 있다.** pydantic-settings의 검증 진입점은 넘긴 값 위에 process env를 다시 합친다. 기동 규칙을 순수한 매핑으로 시험하려고 값의 출처를 좁힌 하위 클래스를 두었다.
- **Django 시스템 검사는 모든 프로세스에서 미들웨어 클래스를 import한다.** admin 검사가 relay(관리 명령)와 Celery 워커에서도 미들웨어 모듈을 읽기 때문에, import 시점에 Prometheus 지표를 등록하면 웹 지표가 다른 프로세스의 레지스트리에도 생긴다. 등록을 미들웨어 인스턴스가 처음 만들어질 때로 미뤘다.
- **생성 시점에 막아야 하는 이름이 있다.** pod 패키지 이름이 `auth`나 `messages`면 Django 기본 앱과 앱 라벨이 겹쳐 기동이 죽는다. `deploy`나 `compose`면 생성 트리의 같은 이름 디렉터리와 합쳐진다. 대소문자를 가리지 않는 파일 시스템에서는 `dockerfile`이 최상위 `Dockerfile`과 부딪친다. 생성기 검증기가 파이썬 키워드 · 표준 라이브러리 모듈 · 의존 패키지의 최상위 import 이름 · 템플릿 내부 이름 · 앱 라벨 · 트리 최상위 이름을 거부한다. 이름 341개는 생성 환경에서 기계적으로 뽑았다.
- **검증된 설정을 대신하는 환경 변수는 기동에서 거부한다.** Celery는 `CELERY_BROKER_URL`을, gunicorn은 `GUNICORN_CMD_ARGS`를 설정 파일보다 앞세운다. 이런 값이 있으면 설정 모델이 검증한 값이 조용히 바뀐다. 그래서 다섯 이름은 빈 값이어도 기동 실패다. gunicorn의 `forwarded_allow_ips` 기본값도 환경 변수에서 오므로 설정 파일에 값을 고정했다.
- **keep-alive는 프록시의 유휴 시간보다 길어야 하고, 대가가 있다.** 역방향 프록시가 백엔드 연결을 90초 재사용하는데 서버가 먼저 닫으면 재사용 경합으로 502가 난다. 서버 keep-alive를 95초로 두면 그 경합은 사라진다. 대신 종료 신호를 받았을 때 유휴 연결이 남아 있으면 워커는 유예 시간(30초)을 다 쓰고 끝난다. 실측은 연결이 있을 때 30.3초, 없을 때 0.9초였다. pod의 종료 유예(90초) 안이라 받아들였다.
- **Dockerfile별 `.dockerignore`를 허용 목록으로 써도, 다시 포함한 디렉터리 안은 거부 목록이 된다.** `*` 뒤에 `!apps/<pod>`를 두면 그 디렉터리 전체가 다시 들어오고, 그 뒤의 재제외는 이름 꼴 몇 개뿐이다. 리뷰어가 작업 트리에 IDE 설정 · `*.env` · SSH 키 꼴 파일 12개를 심고 빌드해 보니 11개가 공개 이미지 층에 실렸다. pod 안의 패키지 · `manage.py` · `pyproject.toml` · 잠금 파일만 다시 포함하도록 바꾸고, 저장소 루트 `.dockerignore`는 `*`로 둔다. Dockerfile별 ignore를 모르는 빌드가 빈 컨텍스트로 실패하게 하려는 것이다(닫힌 쪽).
- **같은 도구도 플랫폼마다 다르게 동작한다.** 빌드 컨텍스트에 호스트의 가상 환경이 섞였을 때를 보자. Windows에서 만든 venv가 들어가면 uv는 그대로 두고, 합쳐진 venv로 웹 서버가 뜬다. 리눅스에서는 「없는 인터프리터에 연결된 venv」로 보고 지우고 다시 만든다. 그래서 「venv 감시 파일이 이미지에 없다」는 판정이 리눅스(CI)에서는 공허하다. 플랫폼과 무관한 정적 검사(생성된 ignore 파일의 꼴)를 따로 두었다. Celery 워커도 Windows에서는 내장 beat(`--beat`)를 거부해, 시험이 운영체제마다 갈래를 둔다.
- **읽기 전용 루트 파일 시스템에서는 홈 디렉터리도 쓸 수 없다.** gunicorn 26은 제어 소켓을 `$HOME/.gunicorn`에 만든다. 홈이 없는 비-root 사용자로 읽기 전용 루트에서 띄우면 쓰기 오류가 난다. `--no-control-socket`으로 끄고, 쓰기 경로는 `/tmp`(메모리 볼륨) 하나로 모았다. Celery beat 일정 파일도 sqlite dbm이라 `-shm` · `-wal` 파일이 함께 `/tmp`에 생긴다.
- **비밀번호가 든 SQL은 실패할 때 서버 로그에 남는다.** PostgreSQL은 기본으로 오류 난 문장을 로그에 쓴다. 로컬 부트스트랩 절차를 다시 돌려 `CREATE ROLE … PASSWORD`가 「이미 있다」로 실패하자 비밀번호가 평문으로 서버 로그에 남았다. 부트스트랩 세션 첫머리에서 실패 문장 기록을 끈다.
- **잠금의 상대 숙성 창은 기간 그대로 기록된다.** uv 0.13.7에 `exclude-newer = "3 days"`를 주면 잠금 파일에 계산된 시각이 아니라 기간(`P3D`)이 기록된다. 그래서 날이 지나도 `--locked` 검사가 깨지지 않는다.

## 선택과 대안
- **uv 판: 계획의 0.12.8 대신 0.13.7**(사용자 결정): 0.12.x에 High 권고가 걸려 있었다. CI · 빌더 이미지 · 로컬을 한 번에 올리고, 계획과 다른 점은 보고서 후보로 남겼다. 올린 직후 푸시해 CI 6 job이 통과하는 것을 먼저 확인했다.
- **생성 pod 잠금의 숙성 창 3일**(사용자 결정): 갓 올라온 판을 잠금 후보에서 뺀다. 긴급 보안판은 패키지별 예외로만 연다.
- **시험의 실패 출력 위생을 가드로 강제**: 규칙은 「넓히는 옵션은 로컬에서만」이었지만, 생성 pod의 가드는 몇 가지를 로컬에서도 막는다. 더 닫힌 쪽이라 규칙 문장을 가드에 맞췄고, 가드 밖에 남은 옵션은 README에 적었다.
- **compose 로컬 의존**: Dragonfly는 운영 ACL 규칙에서 비밀번호만 `nopass`로 바꿨다(저장소에 비밀 0). 포트는 루프백에만 열고, 주 포트의 HTTP 상태 페이지는 운영처럼 껐다. 호스트에 psql이 없는 경우가 있어 DB · role 부트스트랩은 컨테이너 안 psql로 한다.
- **버린 것**: 설계의 「dockerignore를 지우면 이미지 기동 시험이 실패한다」는 전제. 실측하니 Windows에서는 기동이 성공했다. 그 변이를 잡는 일은 새로 넣은 이미지 내용 판정(최상위 허용 목록 · 감시 파일 · 정적 검사)이 맡는다.

## 결과와 검증
- 생성 pod 시험 159개가 통과한다. 리뷰 라운드마다 기존 시험 ID를 하나도 잃지 않았다. 하네스 인프라 자기검사는 619개, 렌더 변이는 렌더 검사 하나만 위반하게(교차 0) 두었다.
- 판별력은 변이로 확인했다. 조각 ②는 21개 변이를 모두 잡았다. 조각 ③은 이미지 변이 8개를 실측했고, 그 가운데 하나(ignore 삭제)는 새 판정만 잡는다. 누출 시험은 가짜 토큰을 심고, 기본 출력과 `-vv` 출력에 그 값이 0회 나오는지 본다.
- 이미지: 빌더와 런타임 Python 판이 같다(3.13.18). 공용 라이브러리는 비-editable로 설치돼 런타임에 원본 경로가 필요 없다. 숫자 UID로 읽기 전용 루트에서 웹 · relay · celery · 관리 명령 넷이 뜨거나 정해진 꼴로 실패한다(QEMU arm64에서 웹 준비까지 약 15초).
- compose: 세 서비스가 35초에 준비되고, README 절차대로 role · DB 생성 → migrate → 기동 검사까지 실제로 통과했다.

## 사고·오류
- **탐침 로그에 실제 세션 토큰.** 누출을 재현하려던 리뷰 탐침 둘이 실제 process env 전체로 시험을 돌렸다. 그 결과 `-vv` 실패 출력에 세션 토큰 몇 개가 평문으로 남았다(저장소 밖 임시 로그 · 커밋 경로 없음). 이름만 세는 검색으로 파일 4개를 찾아 지웠고, 남은 임시 파일과 세션 기록에 실제 값이 없음도 대조했다. 이후 지시문에는 「누출 탐침은 허용 목록 env와 심은 가짜 값으로만」을 넣었다.
- **셸 heredoc 안 파이썬 문자열의 역슬래시 쌍이 줄었다.** 지시문 파일 경로에 탭 · 폼피드 문자가 들어갔다. 역슬래시가 든 파일은 셸이 아니라 파일 쓰기 도구로 만든다는 규칙을 다시 확인했다.
- **설계 전제 하나가 거짓이었다**(위 「버린 것」). 빌더 실측과 리뷰어 재현이 같은 결론이었고, 설계 줄 끝에 정정 표식을 달았다.
