# 003-platform-foundation T072 — pod 템플릿 설계: 첫 배포 순서 · 숫자 UID · 「조용한 실패」를 기동 실패로 앞당기기 (2026-11-07)
> 1일차(조사 · 설계 초안 · 비판 2렌즈 · 설계 확정과 계약 보정). 2일차 이후(조각 ① 하네스 test-first부터)는 뒤 파일.

## 문제
T072는 Django pod 템플릿(copier)을 실제로 채우는 일이다. 생성 Python 프로젝트 · 생성물 시험 7파일 · 이미지 · 배포 매니페스트 · CI 배선까지 한 번에 맞물려야 하고, 앞선 태스크(T065 하네스 · T066 identity-admin 시험 · T068–T071 공용 라이브러리)가 남긴 가정과 인계가 수십 개였다. 조사 리더 다섯이 찾은 사실만 250개, 열린 질문이 60개를 넘었다. 결정을 한 문서에 모으고, 그 문서를 두 렌즈로 반박하게 한 뒤에 구현을 시작했다.

## 배운 개념
- **Argo CD PreSync hook은 Sync 단계 리소스보다 먼저 돈다.** migrate Job이 ConfigMap을 `envFrom`으로 참조하면 첫 배포에서 그 ConfigMap은 아직 없다(Sync 단계에서 만들어진다). Job은 시작하지 못하고 Sync 단계는 hook이 끝나야 시작하므로 교착이 된다. 그래서 migrate Job은 자기 Secret 하나만 참조하게 하고, 설정 프로필(migrate)은 그 Secret의 DB URL 하나로만 뜨게 설계했다. 그 Secret을 만드는 ExternalSecret도 PreSync hook(더 앞선 wave)으로 둔다.
- **hook 리소스는 Argo의 추적 밖이다.** hook만 바뀐 커밋은 자동 sync를 일으키지 않고, hook의 상태는 Application health에 들어가지 않으며, hook이 끝내 Healthy가 되지 않으면 sync operation이 시간 제한 없이 멈춘다. 설계가 정할 수 있는 것은 아니고, 운영 런북에 적어 넘긴다.
- **kubelet의 `runAsNonRoot`는 이미지 USER가 이름이면 판정하지 못한다.** `USER app`이면 kubelet은 그 이름이 root가 아닌지 알 수 없어 컨테이너를 거부한다. 이미지는 `USER 10001:10001`(숫자), pod는 `runAsUser`/`runAsGroup` 10001로 둔다. 하네스의 「비-root」 검사도 이름을 통과시키지 않게 숫자로 단언한다.
- **「조용한 실패」는 기동 실패로 앞당긴다.** 배포 base는 dev 값을 담고 prod overlay가 고친다. overlay가 환경 이름 · Kafka 사용자 이름을 빠뜨리면 outbox relay는 그 잘못을 로그와 백오프로만 남기고 살아 있다(liveness는 포트 열림만 본다). 그래서 pod가 자기 네임스페이스(downward API)를 읽어 환경 이름 · Kafka 사용자 · DB 사용자 · 서비스 이름의 짝을 기동 때 견주게 했다. 이름 규칙에 결합되지만, 어긋나면 크게 실패한다(닫힌 쪽).
- **비밀 스캐너의 휴리스틱도 설계 제약이다.** 설계 문서에 적은 자리값 한 줄(접근 계열 설정 이름 = 「PLACEHOLDER-」 + 태스크 번호)을 generic-api-key 규칙이 비밀로 잡았다. 실측해 보니 숫자가 섞인 10자 이상 값이 걸리고, 숫자 없는 자리값은 통과했다. CI의 비밀 스캔은 필수 검사라, 템플릿 · 시험 · 문서의 자리값을 숫자 없는 꼴로 정하고 빌더 규칙에 넣었다.
- **Windows의 `os.execv`는 프로세스를 바꿔 끼우지 않는다.** 새 프로세스를 띄우고 원래 프로세스를 끝내므로, 부모 `subprocess.run`은 자식이 끝나기 전에 종료 코드 0을 받는다. 리눅스 컨테이너용 스크립트를 Windows에서 시험하면 거짓 통과한다. 컨테이너 PID 1의 신호 동작도 차이가 없어서 `sys.exit(subprocess.call(...))`로 바꿨다.
- **정적 파일 경로 탈출은 404가 아니라 400이다.** Django `staticfiles`의 `serve`는 `../`가 든 경로를 `safe_join`에서 `SuspiciousFileOperation`으로 올리고, 이는 handler400으로 간다. 시험 기대값을 소스로 확인해 고쳤다.

## 선택과 대안
- **pod는 루트 uv 워크스페이스의 멤버가 아닌 독립 프로젝트**(T065 결정 · 사용자 고지 뒤 이의 없음): 멤버로 두면 생성 시점의 잠금이 루트 잠금을 바꾸고, 저장소 밖에 생성한 샘플은 워크스페이스 소스를 풀지 못한다.
- **kubelet 프로브 Host = downward API `POD_IP`를 허용 호스트에 더하기**: 프로브마다 `Host` 헤더를 박으면 네임스페이스마다 overlay가 프로브 셋을 고쳐야 한다. 대가는 클러스터 안에서 pod IP를 Host로 쓸 수 있다는 것이고, 인증 계층이 막는다.
- **DB URL은 Secret 템플릿에서 조립**: kv의 완성 URL을 그대로 쓰는 대신 사용자 · 비밀번호만 가져와 TLS 매개변수(검증 모드 · CA 경로)를 매니페스트에 고정했다. 렌더 검사가 볼 수 있고, kv 값이 바뀌어도 TLS가 풀리지 않는다.
- **웹 서버는 gunicorn gthread 워커 1 × 스레드 4**: 워커를 늘리면 Prometheus multiprocess 모드가 필요하고, 그 env가 relay 컨테이너로 새면 relay가 기동 전에 죽는다(공유 `envFrom`). 용량은 replica로 늘린다.
- **사람 admin 경로는 미룸**: Access GitHub 신원 확인의 실측이 없어 지금 구현할 근거가 없다. 그때까지 admin은 서비스 자격일 때만 열리고 사람은 거부된다(닫힌 쪽).
- **사용자 결정으로 넘긴 둘**: 계획이 고정한 uv 판에 보안 권고(High)가 걸린 문제, Python 잠금의 숙성 창(갓 나온 판 거르기). 둘 다 계획과 다르거나 공급망 정책이라 설계가 혼자 정하지 않았다.
