## recommendation
D0는 '전환/추가'가 아니라 '확인'으로 닫는다. 순서: (1) Billing & Cost Management > Upgrade and Manage Payment에서 Plan Type 확인(Free Tier면 Always Free 전용, 아니면 PAYG). (2) Compute > Instances 또는 `oci compute instance list --query`로 v1 VM의 shape·OCPU·GB·상태 확인 — 2026-08-18 집행 이후인 오늘 4/24 VM이 RUNNING이면 테넌시가 PAYG이거나 집행 예외이고, 2/12 이하면 무료 테넌시 그대로일 가능성이 크다. (3) Limits, Quotas and Usage(Compute, standard-a1-core-count/memory-count)와 `oci limits resource-availability get`으로 used/available을 기록해 spec에 첨부. 판정: (a) Always Free + v1 ≤ 2/12 → 'Always Free 유지' 채택, v2는 남는 슬라이스에 맞춰 트랙 A 또는 B2를 우선하고 B1(K3s+Argo CD)은 12 GB 안에서 v1 병행이 어려우므로 v1 폐기 이후로 미룬다; 절대 인스턴스 종료 금지, 축소는 재부팅 감수하고 1회만. (b) 이미 PAYG + 4/24 RUNNING → 그대로 두고 $1·$5 예산 알림(Actual+Forecast)과 월 1회 Cost Analysis 점검을 붙인다; 4/24는 B1 트랙을 허용하는 유일한 무료 경로지만 과금 상한 ≈ $28/월을 spec 위험 항목으로 명시. (c) Always Free인데 4/24가 이미 비활성/종료됐거나 부족하면, 지금은 '유료 노드 추가'를 기각하고(예산 ≈ 0 위반) PAYG 전환은 Oracle이 PAYG 무료 한도를 공식 문서화하거나 한 달치 $0 청구가 확인될 때까지 보류 — 그 사이 v2는 트랙 A(Cloudflare-native)로 2/12 의존을 줄인다. 어떤 경우든 유휴 회수(7일 <20%)를 피하도록 헬스체크·백업 잡을 상시 돌린다.

## recommendation
웹: Pages 유지 대신 'Workers static assets'로 간다. Cloudflare가 Pages 랜딩에 \"Start new projects with Workers\"를 게시했고(2026-08-25), 모든 어댑터 문서·신규 기능(Cron/Queues/Logs/versions·rollback/프리뷰 별칭)이 Workers 전용이며, 정적 자산 요청 무료·Free 20,000 파일·3,000 빌드분으로 취미 규모 비용은 $0이다. 선행 조건은 v1 도메인이 활성 Cloudflare 존인지 확인하는 것뿐. 프레임워크는 Astro(콘텐츠 컬렉션 내장, SSR 최소화로 Free 10 ms CPU 회피)가 가장 안전하고, Next.js를 택하면 vinext(베타)가 아니라 OpenNext 1.20.x(Next 16.3+) + Paid 10 MB 한도를 전제해야 한다.

API(트랙 A 성립 여부): 기술적으로는 성립하지만 조건부다. $0로 성립하는 경로는 'API도 Workers(TS)'(Hono + Hyperdrive→Neon/OCI Postgres 또는 D1) 하나뿐이고, 이는 FastAPI+Django Admin 전면 재작성과 Django Admin 대체 부재를 감수해야 한다. 'Python Workers'는 2026-08-26 기준 open beta이며 Django·Postgres 드라이버(TCP 소켓 미지원)가 막혀 SaaS급 운영 규율 목표와 맞지 않으므로 프로덕션 API 후보에서 제외한다. 'Containers'는 GA이고 v1 이미지를 그대로 올릴 수 있으나 Paid $5 전용(실사용 ≈$7/월)이라 예산 ≈0 제약에 걸린다. 따라서 SP-1에서 트랙 A는 'TS 재작성을 받아들일 때만' 살아 있는 옵션이고, Python 스택(FastAPI/Django)을 유지하려면 B1/B2(OCI)가 자연스럽다 — 이 경우에도 웹은 Workers static assets, 큐/Cron/캐시 일부는 Workers Free(Queues·Cron·KV)로 흡수하고, OCI Postgres는 Hyperdrive(Workers VPC 베타 또는 Tunnel+Access)로 붙여 나중에 API의 일부를 Workers로 옮길 여지를 남긴다.

배포: OIDC/키리스는 아직 없으므로 GitHub Actions에서는 계정 소유 토큰(cfat_, 'Edit Cloudflare Workers'를 계정 단위로 축소, TTL·IP 제한) + wrangler-action@v4로 `versions upload`(PR 프리뷰) → `versions deploy`/`deploy`(main) → 문제 시 `rollback`을 표준 절차로 삼는다. 토큰 자체를 없애려면 Workers Builds(Git 연동, Free 3,000분)를 쓰는 것이 유일한 대안이다.

## open_questions
- v1 도메인(joshuatech)의 존이 Cloudflare에 활성 상태인지 — Workers 커스텀 도메인은 활성 존 필수이고 기존 CNAME이 있는 호스트명에는 생성 불가(Pages 시절 외부 CNAME이었다면 존 이전이 선행됨).
- R2 무료 구간 사용 시 결제 수단(신용카드) 등록이 필요한지 — pricing/get-started 문서 어디에도 명시가 없음(대시보드에서 직접 확인 필요).
- Gradual deployments·`--preview-alias`·rollback이 Free 플랜에서 제한되는지 — 관련 문서(2026-07/08)에 플랜 제한 언급이 전혀 없어 '제한 없음'으로 추정만 가능.
- Python Workers에서 Postgres 접근 방법 — 블로그가 native TCP sockets를 향후 계획으로 언급하므로 asyncpg/psycopg 사용 가능 여부, Hyperdrive 바인딩의 Python 지원 여부를 실측해야 함; Python Worker의 번들 크기 한도(3/10 MB와 동일한지)와 Workers Builds에서 pywrangler 빌드 지원 여부도 미확인.
- Workers Free 10 ms CPU 한도로 Astro/OpenNext SSR 페이지 1건이 실제로 처리되는지 — 마크다운 렌더·DB 호출 포함 시 초과 가능성이 있어 prerender 비율 결정 전에 계측 필요.
- Cloudflare Zero Trust Free(Access+Tunnel) 좌석 50명·카드 불필요는 커뮤니티/3자 사이트(2026-05 확인)에서만 확인됨 — Hyperdrive→OCI 사설 Postgres를 Tunnel+Access로 붙일 계획이면 공식 플랜 페이지에서 재확인. 대안인 Workers VPC는 베타 기간 무료지만 GA 시 가격 미정.
- Containers 슬립 후 콜드스타트 시간과 Django Admin+FastAPI를 lite(256 MiB)에서 함께 띄울 수 있는지 — 문서에 시작 시간 수치가 없어 실측 필요.
- Neon(또는 다른 관리형 Postgres) 무료 티어 한도와 리전(한국 트래픽 지연) — 이 주제(R2) 범위 밖이라 별도 조사 항목으로 이관.
- Workers의 '브랜치 별칭(Custom Branch Aliases)'이 호환성 매트릭스에서 '곧 제공'으로 남아 있음 — Pages 수준의 PR별 고정 프리뷰 URL이 필요하면 `versions upload --preview-alias` + Workers Builds 조합으로 충분한지 검증.

## recommendation
웹 프레임워크는 Astro 7.x(@astrojs/cloudflare, Workers)를 추천한다. 근거: (1) 요구사항의 핵심인 '저장소 안팎의 content/study/*.mdx를 스키마 검증된 컬렉션으로 발행'이 Astro만 내장(글롭 로더 base가 프로젝트 루트 기준 임의 경로, Zod 4 스키마, MDX frontmatter, draft 필터)이고 Next.js·SvelteKit은 서드파티+수작업이다. (2) 어댑터가 13.0부터 Workers 전용·dev부터 workerd라 A/B1/B2 어느 트랙이든 웹은 동일하게 Cloudflare Workers 정적 자산(무료·무제한)에 올라가 비용 $0·운영 1~2h/월이 현실적이며, Cloudflare 인수(MIT·다중 타깃 유지 약속)로 어댑터 지속성 위험이 오히려 줄었다. (3) Next.js on Workers는 OpenNext의 Windows 비보장·3 MiB Free 한도·CPU 10ms·2026년 내 어댑터 경로 재편(공식 어댑터/vinext 베타)이라는 운영 변수를 콘텐츠 사이트 규모에 비해 과하게 떠안는다. 이력서 상쇄책: 국내 채용에서 Astro는 0건이므로 React 역량은 @astrojs/react 아일랜드로 유지하고, 'Next.js→Astro 전환 근거'를 ADR과 학습 노트로 공개해 의사결정 역량으로 포장하며, 시장 가치가 높은 기술 선택은 API/인프라 트랙(SP-1의 B1/B2 결정)에서 가져간다. 다만 취업 가중치를 최우선으로 두거나 앱형 대시보드(테넌트별 로그인 화면)가 v2 초기 범위라면 Next.js 16.3 + OpenNext(WSL 개발, Velite로 스키마 검증, Workers Paid 각오)로 가되 2026 말 공식 어댑터 이행을 계획에 넣어야 한다. SvelteKit·TanStack Start는 시장 신호와 메이저 전환 시점 때문에 기각. 외부 콘텐츠 배치는 '같은 모노레포의 루트 content/study + Astro base "../../content/study"'를 1순위로, 별도 repo가 꼭 필요하면 git submodule + GitHub Actions(checkout submodules) 빌드 후 wrangler deploy를 쓰고 Workers Builds는 서브모듈 지원이 미문서라 피한다.

## recommendation
권장: 'Python FastAPI on OCI(컨테이너)'를 v2 API 트랙으로 채택하고 Django Admin을 버려 단일 백엔드로 수렴한다(B1/B2 트랙과 정합). 구체적으로 (1) Python 3.13 + uv 멀티스테이지(ghcr.io/astral-sh/uv:python3.13-trixie-slim 빌드 → python:3.13-slim-trixie 또는 distroless/python3-debian13 런타임, arm64) 이미지; (2) 관리자는 SQLAdmin(0.31.0)이나 Starlette Admin(1.0.1) 중 하나로 시작해 Cloudflare Access(GitHub IdP, Free 50 users) 뒤에 두고 오리진에서 Cf-Access JWT를 JWKS로 검증; (3) 웹(Workers)→API(OCI)는 브라우저 직접 호출 대신 Worker 서버사이드 fetch로 통일해 CORS 표면을 없애고, API 호스트는 cloudflared Tunnel + Access 'Service Auth'(CF-Access-Client-Id/Secret) 정책으로만 열며 Smart Placement를 켠다; (4) 인증은 Better Auth를 Python에서 쓸 수 없고 fastapi-users는 유지보수 모드이므로, 사용자 인증이 실제로 필요해지기 전까지는 Access 위임 + 서비스 토큰으로 버티고, 필요해지면 '웹(Workers)에 Better Auth + JWT 플러그인, API는 /jwks로 검증'을 1순위, FastAPI 자체 세션/JWT를 2순위로 둔다(ADR 항목). (5) 멀티테넌트 최소 경계는 'tenant_id 컬럼 + RLS'로 확정: 모든 도메인 테이블에 tenant_id NOT NULL + (tenant_id, …) 복합 인덱스, ENABLE + FORCE ROW LEVEL SECURITY, 정책은 current_setting('app.tenant_id', true) 비교, 앱은 테이블 비소유·비슈퍼유저 롤로 접속, 요청 단위 트랜잭션 안에서만 SET LOCAL(풀 acquire 훅에서 SET 금지, statement 모드 풀러 금지)을 FastAPI Depends로 강제하고 테스트 하네스에 '다른 tenant_id로 0행' 케이스를 넣는다. 스키마 분리·DB 분리는 실제 유료 테넌트가 생길 때로 미룬다(1인 포트폴리오에는 과잉). 대안: 사용자가 A(Cloudflare-native)를 고집하면 'TS Hono on Workers + Hyperdrive→Tunnel→OCI Postgres + Better Auth'는 $0으로 성립하며 문서 근거도 충분하나, 전면 재작성·CPU 10ms·Admin 부재·락인을 받아들이는 결정이어야 한다. Python Workers는 beta이고 Postgres 드라이버 경로가 없어 이번 사이클에서는 기각. Django(+Ninja)는 인증·Admin 일체형 장점이 있지만 v1 API 재작성과 RLS 수동 배관 때문에 FastAPI 유지보다 이득이 작다.

## recommendation
주 DB는 'Postgres 컨테이너 on OCI VM'을 기본값으로 두고 B2(compose-pull)와 짝을 짓는 것을 권한다: v1과 동일 경로라 이행 위험이 가장 낮고, 2026-06-15 쿼터 반감(2 OCPU/12 GB) 아래에서 v1과 동거 가능한 유일하게 가벼운 셀프호스트 선택지이며, pgBackRest→OCI Object Storage(S3 호환, 20 GB) + 주간 pg_dump→R2 교차 사본으로 'SaaS급 백업·복구 훈련'이라는 학습 목표를 채운다. B1(K3s+Argo CD)을 고른다면 CNPG + barman-cloud 플러그인(v0.14, CNPG ≥1.30)이 정답이지만, 그 전에 실제 VM에서 v1 스택 + K3s + CNPG의 RAM을 측정해 여유를 확인해야 한다. Track A를 고른다면 D1이 아니라 Neon Free + Hyperdrive(무료 10만 쿼리/일)로 Postgres를 유지하되 싱가포르 리전·5분 콜드 스타트·0.5 GB를 감수해야 하고, Supabase Free는 일시정지·무백업 때문에 공개 포트폴리오의 주 DB로는 비권장(서울 리전이 꼭 필요하면 예외). 객체 저장소는 공개 자산(이미지·MDX 첨부)은 R2(10 GB, egress 무료, 엣지 제공), 백업·아카이브는 OCI Object Storage 20 GB로 역할을 나눈다. 캐시/큐는 Dragonfly(BSL, RAM 소모)를 버리고 v2 초기에는 큐 없이 Postgres 네이티브 큐(procrastinate 3.9 또는 pgmq 1.12)로 가며, 캐시가 정말 필요해질 때만 Valkey 9.x(BSD)를 추가하고, Track A라면 KV(무료 1 GB)·Queues(일 1만 ops)·Durable Objects(SQLite)로 대체한다. 멀티테넌트는 tenant_id + Postgres RLS(앱 역할은 BYPASSRLS 없이, FORCE ROW LEVEL SECURITY)로 어느 옵션에서도 동일하게 설계한다.

## recommendation
'B2 + 나중에 K3s 전환'을 권장한다. 근거: (1) 12 GB/2 OCPU에서 v1 compose를 종료하지 않은 채 K3s(0.6–1.6 GB, CPU 유휴 부하)+Argo CD(공식 실측 없음, 커뮤니티 권장 0.5–1 GB)+Alloy(0.2–0.7 GB)를 얹는 것은 수치상 가능해 보여도 v1 실측 RAM이 미확인이고 포트 80/443·Traefik v2→v3 전환까지 한 번에 겹쳐 v1 이행 위험이 가장 크다. (2) B2는 digest 고정 이미지(GHCR, compose `image@sha256`)·git 정본·pull 기반(Komodo Resource Sync 웹훅 또는 doco-cd 폴링)·cloudflared+Access 서비스 토큰·Grafana Cloud Free로 SP-1 CI/CD 원칙(ADR 0002)을 손실 없이 만족하면서 운영 부담 1–3 h/월로 1인 운영에 맞는다. (3) 이력서 가치는 K8s가 높지만 주니어 K8s 공고는 5% 수준이고 채용 신호는 '프로덕션 운영 시간'이므로, v1 폐기 후 K3s+Flux(경량, 30 MB/컨트롤러) 또는 Argo CD Core(인지도)로 전환하는 '마이그레이션 서사'가 홈랩 단일 노드보다 설득력이 있다. 도구 선택: Komodo(UI·diff 알림·웹훅, MongoDB/FerretDB 부담)와 doco-cd(경량·0.x)를 SP-1 spike로 실측 비교하고, systemd timer는 폴백. Watchtower·Dockge는 제외. 전환 트리거를 스펙에 명시: v1 종료 완료 + 테넌시 한도 확정 + 관측 기준선(Grafana Cloud Free 10k 시리즈 이내) 확보 시 K3s 전환 스펙 착수. Cloudflare-native(A) 대비 검토는 R1~R5 결과와 합쳐 SP-1에서 최종 결정.

## notes
성숙도 판정: MSA 정책 성숙도 보고서(2026-08-25, 8차원×분석+검증 16에이전트)는 v1을 평균 2.7/10, 'L2 분리 시작' — 정확히는 "앱은 넷으로 나눴지만 신뢰·데이터·배포 계약이 없는 분산 모놀리스"로 판정했고, 테스트·품질 차원은 L1(2/10)이다(docs/user/msa-maturity-comparison/README.md §3.3, §3.6). 디자인 시스템 보고서는 once-ui를 5.9/10으로 평가하되 "좋은 남의 디자인 시스템을 가져다 38%만 쓰는 상태"이며 강점이 업스트림의 것이지 프로젝트의 것이 아니라고 결론지었다(docs/user/design-system-comparison/README.md §2.3~2.4). 코드베이스는 2025-06 이후 휴면 상태이고 마지막 커밋이 '마이그레이션 전 백업'이므로 v2는 재작성 전제가 맞다.

v2가 고쳐야 할 핵심 3가지:
1. 경계와 데이터 소유권 — 기술 계층(Admin/API/Worker)이 아닌 도메인 단위로 서비스를 자르고, 각 서비스가 자기 데이터·마이그레이션·설정 계약(필수값 누락 시 부팅 실패, .env.example)을 소유하게 한다. Django 모델을 codegen으로 복제해 공유하는 방식과 FastAPI façade는 폐기하고, 인증은 비대칭키(RS256/JWKS)로 로컬 검증 가능하게 설계한다(01-boundaries-data.md, 02-comm-auth.md, 03-config-shared-governance.md).
2. 배포 정책의 코드화 — 브랜치 전략과 PR 게이트(테스트·린트 필수, 헌법 II), 불변 이미지 태그(sha/digest)와 롤백 경로, 잡 단위 최소권한·github.token·SHA 핀 액션, 시크릿을 build-arg/heredoc/debug 로그에 노출하지 않는 주입 방식, 단일 배포 타깃(Render/Fly 잔재 제거), 컨테이너 healthcheck·리소스 제한·네트워크 분리·Traefik 대시보드 잠금(05-build-deploy-ci.md).
