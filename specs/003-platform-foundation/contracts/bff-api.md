# Contract: BFF (apps/web Route Handlers)

Workers에서 실행되는 유일한 서버 코드. 브라우저는 BFF만 호출하고, BFF가 Authentik 토큰 교환과 pod 호출을 맡는다(청사진의 "게이트웨이"). 모든 응답은 `x-request-id`(BFF 생성 — pod 수락 꼴 `^[A-Za-z0-9._:-]{1,128}$` 안의 값(예: `crypto.randomUUID()`) · 꼴 밖이면 pod가 새 값으로 바꿔 BFF ↔ pod 로그 상관이 끊긴다 · T071 r2, `traceparent`와 함께 하류 전파)를 갖고, 오류는 RFC 9457 `application/problem+json`이다.

## 세션 쿠키

| 이름 | 내용 | 속성 |
|---|---|---|
| `__Host-jt_session` | AES-256-GCM JWE compact(`v1.` 접두 · `dir` · `A256GCM` · `typ` `jt-session` · IV는 봉인마다 새로)로 암호화한 `{refresh_token, sub, sid, tenant_id, issued_at, email?, name?}`(키 = Workers Secret `SESSION_ENCRYPTION_KEY`, 32바이트 = 16진 64자). `sid`는 callback ID 토큰의 `sid`이며 필수다(없으면 세션을 만들지 않는다). `email` · `name`은 ID 토큰에 있을 때만 싣는다. 이름은 `__Host-` 접두다 — 형제 서브도메인이 같은 이름 쿠키를 심지 못한다. 접두 없는 `jt_session`은 읽지 않는다(B-6 · T089 보정 2026-11-24). `issued_at` = **세션 시작 시각** — callback의 코드 교환 응답 ID 토큰 `iat`(정수 epoch 초 · Authentik 시계)다. refresh 때 새 쿠키에 **그대로 옮긴다**(갱신하지 않는다 — 갱신하면 폐기된 세션이 refresh 한 번으로 세션 하한 위로 올라간다). `auth_time`은 쓰지 않는다(Authentik 로그인 세션이 살아 있으면 재로그인도 같은 값이라, 폐기 뒤의 로그인이 되풀이해 inactive가 된다). ID 토큰 `iat` · `auth_time`의 이 동작은 소스 판독이다(실측 T081 · VD-T081-4: 다르면 `issued_at`의 원천을 고친다) · T073 보정 2026-11-12 | `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=2592000`(30일 · `Domain` 없음 — `__Host-` 조건) |
| `__Host-jt_csrf` | 랜덤 128비트(16진 32자) | `Secure; SameSite=Lax; Path=/; Max-Age=2592000` — 상태 변경 요청은 `x-csrf-token` 헤더와 일치해야 함. `__Host-jt_session`과 같은 자리(callback · refresh)에서 같은 수명으로 싣는다 — 브라우저 세션 쿠키면 재시작 뒤 `__Host-jt_session`만 남아 logout · refresh가 CSRF에서 막힌다(T070 r6 마감 · 이름 B-6 · T089 보정 2026-11-24) |
| `__Host-jt_pkce` | 봉인(`typ` `jt-pkce`) `{state, verifier, return_to, created_at}` — login이 싣고 callback이 성공 · 실패 모두 지운다 · `created_at` + 300 s를 넘으면 `invalid_state` · 같은 이름이 둘 이상 오면 `invalid_state` + 삭제 · 여러 탭에서 로그인하면 마지막 것만 유효하다(받아들인다) | `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=300` — `__Host-` 접두라 형제 서브도메인이 `Domain`을 넓혀 같은 이름을 심지 못한다(login CSRF · 세션 고정 차단 — `__Secure-`는 `Domain`을 막지 않는다). 대가: 최대 300 s 동안 같은 origin 요청마다 실린다(HttpOnly · 봉인 · 로그 0 · B-6 · T089 보정 2026-11-24) |

세 쿠키 모두 `Domain` · `Partitioned` · `Expires`를 싣지 않는다. 속성은 위 꼴 그대로다(대소문자 무관 · 내부 refresh가 회전시킨 새 쿠키도 「설정」 꼴). 삭제는 같은 속성 + 빈 값 + `Max-Age=0`이다. `Max-Age`는 남은 수명으로 줄이지 않는다. 같은 이름이 둘 이상 오면 무효 쿠키다. 접두 없는 옛 이름(`jt_session` · `jt_csrf`)은 읽지 않는다 — 없는 것과 같다(B-6 · T089 보정 2026-11-24).

**봉인 꼴**(T089 보정 2026-11-24): 쿠키 값 = `v1.` + JWE compact `<보호 헤더>..<IV>.<암호문>.<태그>`(키 관리 `dir` — 암호화된 키 칸이 비어 있다). 보호 헤더는 정확히 `{alg: "dir", enc: "A256GCM", typ}`이고 `typ` ∈ {`jt-session`, `jt-pkce`}다(보호 헤더가 AAD라 `typ`이 봉인에 묶인다). 복호는 `dir` · `A256GCM`만 받는다. IV(12바이트)는 봉인마다 JWE 층이 새로 만든다. `__Host-jt_session` 평문은 필수 `refresh_token` · `sub` · `sid` · `tenant_id`(UUID) · `issued_at`(정수)와 선택 `email` · `name`이다.

**쿠키 판독 · CSRF**(T089 보정 2026-11-24): 세션 쿠키가 없으면 401 `session_revoked`(`Set-Cookie` 0 · 상류 0). 무효(복호 실패 · 모르는 접두 · `typ` 다름 · 키 집합 다름 · 필수 `sid` 없음 · 같은 이름 둘 이상)면 두 쿠키를 지운 401 `session_revoked`(상류 0)다. `__Host-jt_csrf`는 16진 32자이고 상태 변경 요청의 `x-csrf-token`과 같아야 한다 — 없거나 다르면 403 `csrf_mismatch`(상류 0 · `Set-Cookie` 0). 라우트마다 판정 순서는 §엔드포인트 「판정 순서」다.

access 토큰은 쿠키에 넣지 않는다. BFF isolate 메모리 캐시 `Map<sub+aud+issued_at, {token, exp}>`(유효 = 저장 시각 + `min(expires_in, 300) − 30` s · `expires_in`이 없거나 꼴 오류면 캐시하지 않는다 · T089 보정 2026-11-24)에서 재사용하고, 없으면 refresh → exchange. 캐시 키에 `issued_at`을 넣는다 — `sub+aud`면 전체 로그아웃 뒤 5분 안에 다시 로그인한 세션이 옛 세션의 교환 토큰을 받아 pod에서 401 `session_revoked`가 된다. 캐시 사용 · refresh · 교환은 모두 폐기 확인 뒤다(§하류 호출 규약 · T073 보정 2026-11-12). `tenant_id`는 UUID.

## 엔드포인트

| 메서드·경로 | 인증 | 동작 | 응답 |
|---|---|---|---|
| `GET /api/auth/login?return_to=/ko/…` | 없음 | PKCE `code_verifier`·`state`를 임시 쿠키 `__Host-jt_pkce`(5분 · 위 표)에 저장하고 Authentik `/application/o/authorize/`로 302. **`return_to`(returnTo)는 `/`로 시작하고 `//`로 시작하지 않는 상대 경로만** 허용 — 절대 URL·스킴 상대 URL은 400 `invalid_return_to`. 판정은 표 아래 「같은 origin 경로」다(T070 r6 마감) — `return_to`만의 규칙(원문 · 중복 · 출력 가능 ASCII · 직렬화 · 바이트 상한)도 거기에 있다(T089 보정 2026-11-24). 인가 요청의 scope에는 `openid`와 `offline_access`가 있어야 한다(ID 토큰 `iat` = 세션 시작 시각 · refresh 토큰 발급의 전제 — T081 · T092 · T073 보정 2026-11-12) | 302 / 400 |
| `GET /api/auth/callback?code&state` | 없음 | `state` 검증(`__Host-jt_pkce` — 없음 · 복호 실패 · `created_at` + 300 s 초과 · 같은 이름 둘 이상 · `state` 불일치면 400 `invalid_state`) → 봉인된 `return_to` 재검증(코드 교환 **앞** — 표 아래 「`return_to`만의 규칙」 · 어긋나면 400 `invalid_return_to` · 토큰 호출 0) → 토큰 엔드포인트(client_secret은 Workers Secret) → ID 토큰 검사 → `__Host-jt_session` · `__Host-jt_csrf` 설정 → 그 `return_to`로 302. 어느 결과든 `__Host-jt_pkce`를 지운다(T089 보정 2026-11-24). 코드 교환이 시간 초과 · 3xx · 5xx면 세션 쿠키를 만들지 않고 503 `upstream_unavailable`이다(코드 교환 4xx의 응답은 T092가 §오류 형식 슬러그 안에서 정한다 · T070 r6 마감). 코드 교환이 200이어도 본문이 깨졌거나(JSON이 아님 · 잘린 JSON) 필드 꼴이 어긋나면(`access_token`이 문자열이 아님(숫자 등) · `id_token`이 base64url 세 조각(JWS compact)이 아님 · `expires_in`이 있는데 정수가 아님(문자열 등)) 같은 503 `upstream_unavailable`이다 — 세션 쿠키 0 · `__Host-jt_pkce` 삭제(T089 보정 2026-11-24 · 시험 G17). **이 7개가 BFF 라우트의 전부다**(`/api/auth/{login,callback,logout,refresh}` · `/api/session` · `/api/health` · `/api/proxy/[pod]/[...path]`). spec FR-027과 T092의 목록은 이 표와 글자 그대로 같아야 한다 — `/api/session/check` 같은 별도 라우트는 없다(폐기 확인은 세션 쿠키를 쓰는 네 라우트 — `/api/session` · `/api/auth/refresh` · `/api/proxy/*` · `/api/auth/logout` — 가 저마다 하류 호출 앞에서 상류 `/session/check`를 부른다 · T073 보정 2026-11-12 — 이전 문구 「`/api/session` 안에서」).

**판정 순서**(T089 보정 2026-11-24): 설정 무효(§Worker · 환경 「설정 유효성」)의 503은 상류 0 · 로그 1줄(`upstream: null`)이다.
- **proxy**: 맵 · 메서드 · 경로(404 — 설정이 무효여도 먼저 판정한다) → 설정(503) → 세션 쿠키(없음 · 무효 401) → 폐기 확인 → (교환 캐시가 비면) refresh · 교환 → 하류.
- **session · refresh**: 설정(503 · `Set-Cookie` 0) → 세션 쿠키(없음 · 무효 401) → CSRF(refresh만 · 403) → 폐기 확인 → 각 행.
- **logout**: 세션 쿠키 없음(401) → CSRF(403) → body(400) → 설정 무효(두 쿠키를 지운 503) → 쿠키 무효(두 쿠키를 지운 401) → 폐기 확인 → logout 행.
- **login · health**: 설정(503 · `Set-Cookie` 0) → 각 행. **callback**: 설정이 무효면 503이고 `__Host-jt_pkce`를 지운다(세션 쿠키 0) → 각 행.

**같은 origin 경로**(`return_to` · 프레임워크 리디렉션 `Location`이 함께 쓰는 정의 · T070 r6 마감): 퍼센트 디코딩한 값이 `/`로 시작하고 `//`로 시작하지 않으며, `\` · 공백 · C0 제어 문자(탭 · CR · LF 포함) · DEL을 담지 않고, 요청 origin을 기준으로 WHATWG URL 해석(`new URL(value, origin)`)한 결과의 origin이 요청 origin과 같다. 글자 접두만 보는 검사는 `/\evil.com`(질의 `/%5Cevil.com`을 디코딩한 값) · `/<탭>/evil.com`(`/%09/evil.com`)을 통과시킨다 — WHATWG 해석은 `\`를 `/`로 바꾸고 탭 · 줄바꿈을 지워 둘 다 다른 origin이 된다(컨트롤러 Node 실측 · T089 사례 = 400 `invalid_return_to`). WHATWG 해석 결과의 pathname이 `//`로 시작하면(예: `/..//evil.com` · `/.//evil.com` · `/a/..//evil.com` · 질의 디코딩 뒤 `/%2e%2e//evil.com`) 같은 origin 경로가 아니다. 디코딩한 값이 2,048자를 넘어도 아니다(컨트롤러 Node v24.11.1 실측 · T089 보정 2026-11-24).

**`return_to`만의 규칙**(T089 보정 2026-11-24 — 프레임워크 리디렉션 `Location`(프록시 끝 슬래시 308 등)은 이 규칙 밖이다): ① 질의에 `return_to`가 둘 이상이면 400 · 없으면 기본 `/` · 빈 값은 400. ② 원문(디코딩 전)에 깨진 퍼센트 인코딩(`%` 뒤가 16진 두 글자가 아님 — `/%` · `%E0%A4%A` · `%G1`)이 있으면 400. ③ 디코딩은 한 번이다(`URLSearchParams` 의미 — `+`는 공백이라 400). 디코딩한 값은 출력 가능 ASCII(`!`–`~`)만 담는다 — 비ASCII(퍼센트 인코딩된 UTF-8 `/ko/%ED%95%9C` 포함) · 공백 · 제어 문자 · DEL은 400. ④ 302 `Location`과 `__Host-jt_pkce`에 봉인하는 값은 요청 origin 기준 WHATWG 해석 결과의 pathname + search + hash다(WHATWG 직렬화 — 출력 가능 ASCII · 점 세그먼트가 접힌 꼴이라 헤더 바이트 예외가 생길 수 없다). ⑤ 봉인한 `__Host-jt_pkce`의 `이름=값`이 4,096바이트를 넘으면 400이다(글자 상한만으로는 4 KB를 보장하지 못한다 — 브라우저가 버리면 callback이 `invalid_state`가 된다). ⑥ callback은 코드 교환 **앞에서** 봉인 값을 다시 판정한다 — 다시 디코딩하지 않고 그 값을 위 정의의 입력으로 써서 같은 origin 경로 · 출력 가능 ASCII를 보고, `Location`은 그 값의 WHATWG 직렬화다(예: 봉인 `/%2F/evil.com` → 같은 값으로 302). 어긋나면 400 `invalid_return_to` · 토큰 호출 0 · `__Host-jt_pkce` 삭제. 클라이언트는 `return_to`에 `encodeURIComponent(pathname + search + hash)`를 싣는다(T091 · T092).

## 하류 호출 규약

- 헤더: `Authorization: Bearer <exchanged access>`, `CF-Access-Client-Id`, `CF-Access-Client-Secret`, `x-request-id`, `traceparent`(BFF가 자기 span으로 만든 값 — 브라우저가 보낸 `traceparent` · `tracestate`는 옮기지 않는다 · T071 r3 Z8 · r5), `x-forwarded-user-sub`(정보용, 신뢰하지 않음 — pod는 이 헤더와 `CF-Access-*` · `Authorization`을 로그에서 지우고 Sentry에 보내지 않는다 · T071 보정 2026-11-05). 이 목록 밖의 클라이언트 요청 헤더(`cookie` · `cf-access-token` · `authorization` 포함)는 하류로 옮기지 않는다(T070 r6). 상류마다 싣는 헤더는 정확히 아래 집합이다(T089 보정 2026-11-24 — 클라이언트 요청 헤더 `cookie` · `authorization` · `cf-access-*` · `traceparent` · `tracestate` · `x-request-id` · `x-forwarded-user-sub`는 어느 상류에도 옮기지 않는다):

  | 상류 | 헤더 |
  |---|---|
  | Authentik(토큰 · 교환 · revoke — `client_secret_post`) | {`accept`, `content-type`} |
  | `/session/check` | {`accept`, `cf-access-client-id`, `cf-access-client-secret`, `x-request-id`, `traceparent`, `x-forwarded-user-sub`} — Bearer 없음 |
  | 프록시 GET | 위 + `authorization: Bearer <교환 토큰>` |
  | `/sessions/revoke` | 프록시 + `content-type: application/json` |
  | `/health` | {`accept`, `cf-access-client-id`, `cf-access-client-secret`, `x-request-id`, `traceparent`} |

  `traceparent`는 요청마다 새 trace-id(16바이트 · 0이 아님)와 span-id(8바이트)로 만든다. sampled 플래그는 표본 추출(기본 10%)이 참이면 `01`, 아니면 `00`이고, 로그 `trace_id`는 그 trace-id다. end-session은 상류 호출이 아니라 브라우저 이동이다(logout 행).
- 응답 헤더: BFF 응답의 헤더는 BFF가 만든다. 어느 라우트에서도(`/api/session` · logout · callback · refresh 포함) 하류(pod · Authentik) 응답 헤더(`set-cookie` · `location` · `cf-*` · `x-request-id` 포함)를 옮기지 않는다. 예외는 프록시가 옮기는 `content-type` 하나다(T070 r6 마감).
- BFF가 만드는 헤더 가운데 다른 주소를 가리키는 것은 둘뿐이고, 설정과 검증된 값으로만 만든다: login · callback 302의 `Location` · logout의 `x-end-session-url`.
- 모든 BFF 응답에 `cache-control: no-store` · `x-request-id`(`crypto.randomUUID()`) · `x-content-type-options: nosniff`를 달고, `access-control-allow-origin`은 달지 않는다.
- T089가 응답 헤더 이름 집합을 라우트 × 결과마다 정확히 단언한다(T089 보정 2026-11-24 — 이전에는 프록시 응답만 nosniff였고, 상류 `Set-Cookie` · `Location` 비전달만 라우트마다 단언했다).
- 토큰 교환(RFC 8693, Authentik 2026.8 OSS) — **기본은 impersonation**: `POST https://auth.joshuatech.dev/application/o/token/` `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `subject_token`=사용자 access(web-bff), `subject_token_type=urn:ietf:params:oauth:token-type:access_token`, `audience=<pod>`, `client_id/secret`=web-bff. **`actor_token`은 보내지 않는다**(OSS에는 authentik `Actor`를 만드는 지원 경로가 없어 client-credentials 토큰을 actor로 쓰면 `invalid_grant`). 호출자 식별은 **Access 서비스 토큰의 `common_name`**(서비스 토큰 `web-bff-<env>`의 Client ID `<32 hex>.access` — 토큰 이름이 아니다 · T070 정정)이 맡는다 — contracts/identity-admin-api.md §호출자 식별. 실패(400/403) → BFF 401 `exchange_denied`(쿠키 삭제 0 — 앞선 내부 refresh가 회전했으면 새 쿠키는 싣는다). 401 · 그 밖의 4xx · 3xx · 5xx · 시간 초과 → 503 `upstream_unavailable`(T089 보정 2026-11-24).
  - **VD-1(검증 후 결정)**: T081 착수 시 OSS에서 `Actor` 생성이 되면 `actor_token`(BFF client-credentials)을 붙인 delegation으로 바꾸고 pod는 `AUTH_ACTOR_SUB`로 `act.sub`를 검증한다(옵션 A). 안 되면 위 impersonation 그대로(옵션 B). BFF 코드는 `actor_token` 파라미터를 붙일지 여부만 달라진다.
- 폐기 확인: `GET <IDENTITY_M2M_URL>/session/check?sub=<sub>&iat=<issued_at>&sid=<sid>`(`iat`에는 쿠키의 `issued_at`(세션 시작 시각)을 보낸다 — 토큰의 `iat`가 아니다 · T073 보정 2026-11-12 · `sid`는 쿠키의 필수 키다(callback이 ID 토큰 `sid` 없이는 세션을 만들지 않는다 · T089 보정 2026-11-24 — 그래서 모든 질의에 원문 `sid`가 실린다: 접근 로그 노출 면은 UD-10 · T098 전 질문) · 빈 `sid=`는 400 · T070 r2) → `{ active: boolean }`. 결과를 **2 s** 캐시한다(키 = `sub` + `issued_at` + `sid`). 그 밖의 캐시는 쓰지 않는다 — 이 fetch는 `cache: "no-store"`이고 pod도 응답에 `Cache-Control: no-store`를 단다(같은 URL의 저장본이 폐기 뒤에도 `active: true`를 답하지 않게 · T073 보정 2026-11-13). **자리**: 세션 쿠키를 쓰는 네 라우트(`/api/session` · `/api/auth/refresh` · `/api/proxy/*` · `/api/auth/logout`) 모두 Authentik 토큰 엔드포인트 호출(refresh · 교환)과 교환 토큰 캐시 사용 **앞**이다 — 확인 없는 회전 경로를 두지 않는다(gateway의 관문 하나를 거친 세션만 refresh · 교환 함수가 받는다 — T092). `active=false`면 ① 쿠키의 refresh 토큰을 RFC 7009로 폐기(3 s · 실패해도 진행) ② `__Host-jt_session` · `__Host-jt_csrf` 삭제 ③ 401 `session_revoked`(logout은 `/sessions/revoke`를 부르지 않고 204 — 본문이 `all_devices: true`를 명시했으면 401 · 엔드포인트 표). 상류 503(슬러그와 무관 — `denylist_unavailable` · `auth_keys_unavailable` 등) → BFF 503 `upstream_unavailable`(fail-closed; 쿠키는 유지하고 refresh · 교환을 하지 않는다 — 회전 0 · logout만 쿠키를 지운다(엔드포인트 표) · T070 보정 · T073 보정 2026-11-12). 판정에 쓰는 상류 응답은 200이면서 본문 `active`가 boolean인 것뿐이다 — 그 밖의 응답(400 `validation_error` · 403 `access_required` 같은 4xx · 5xx · 시간 초과 · 본문 꼴 오류 · `active` 없음)은 모두 503 `upstream_unavailable`(쿠키 유지 · 활성으로 보지 않는다 — 서비스 토큰 만료 403은 모든 세션에서 한꺼번에 난다 · T092 시험 · T070 r3). 세션 하한과 세션 절대 수명(시작한 지 30일)은 `/session/check`가 집행한다 — BFF는 `active`만 본다(쿠키 `Max-Age`는 계약 값 그대로다 · T089 보정 2026-11-24). **한계**: 세션 하한이 막는 것은 폐기 전에 만든 BFF 세션이다. Authentik 로그인 세션이 살아 있는 기기는 사용자 단위 폐기 뒤에도 재인증 없이 새 BFF 세션을 얻는다(callback 입장 판정은 두지 않는다 — UD-8 (나) 2026-11-24 · 그 브라우저의 Authentik 세션은 로그아웃의 end-session이 끝낸다(UD-7a) · 계정 탈취 대응의 완결은 Authentik 사용자 비활성화 — 런북 T114 · T073 보정 2026-11-12 · T089 보정 2026-11-24).
- `access_token`·`code`·`state`를 URL 경로·쿼리에 싣지 않는다(교환·폐기 확인은 헤더/본문).
- 리디렉션: 자격(서비스 토큰 `CF-Access-Client-*` · 교환 토큰 · client secret · refresh 토큰)을 싣는 하류 호출(Authentik 토큰 엔드포인트 전부 — callback 코드 교환 · refresh · 토큰 교환 — · Authentik revoke · 폐기 확인 · `/api/health` · `/sessions/revoke` · 프록시)은 리디렉션을 따르지 않는다(`redirect: 'manual'`). Fetch 표준의 기본 `follow`는 사용자 정의 헤더를 지우지 않고 `Location`으로 다시 보낸다 — 307 · 308은 메서드와 본문(client secret · refresh 토큰)도 그대로 보낸다(Workers 런타임 동작은 T092가 로컬 서버로 확인한다). 어느 호출이든 상류 3xx는 시간 초과와 같은 갈래(503 `upstream_unavailable`)다 — refresh · `/api/session` · 프록시(그 안의 refresh · 교환 포함)에서는 만료 · 폐기 갈래(401 · 쿠키 삭제)로 접지 않고, logout은 엔드포인트 표의 실패 갈래(쿠키를 지운 503)를 따른다(폐기 확인은 위 규칙과 같다 · T070 r5 · r6 · r6 마감).

## Cloudflare 존 설정 · Workers 한도

- **`run_worker_first`**: `wrangler.jsonc`의 `assets.run_worker_first`에는 `/api/*`처럼 Worker가 반드시 먼저 봐야 하는 경로만 넣는다. **`/ko`·`/en`·`/ja` 같은 페이지 경로는 넣지 않는다** — 넣으면 정적 자산으로 서빙될 수 있는 요청까지 Worker 호출로 계상된다.
- **Workers Caching(`[cache]`) 비활성 유지**: 활성화하면 자산 요청까지 과금 대상이 된다. 기본값(비활성)을 명시적으로 유지한다.
- **Free 한도 초과 시(VD-8, 관찰만)**: 기본 가정은 "Worker를 거치는 요청이 429/1027을 받는다"이고, 자산 요청(`.open-next/assets`)은 무제한이라 영향이 없다. 의도적으로 초과시키지 않으며, 실제로 발생하면 그때의 fail 모드를 `report.md`에 기록한다. 감시는 Cloudflare Notifications "Workers usage" + 주간 GraphQL 검사(T097·T101). 완화책은 VD-2 실측 결과에 따른다.
- **페이지(`app/[lang]`)와 `/` 응답에 `Set-Cookie`를 넣지 않는다**(위생 규칙). 언어 · 테마 선택은 URL 경로와 `prefers-color-scheme`으로 표현한다.
- BFF 라우트는 이 계약이 정한 쿠키(`__Host-jt_session` · `__Host-jt_csrf` · `__Host-jt_pkce`)를 정한 자리에서만 설정 · 삭제한다: `/api/auth/*` · 내부 refresh가 회전한 프록시 응답의 새 두 쿠키 · 폐기 확인 inactive · 무효 쿠키의 삭제(`/api/session` · `/api/proxy/*`).
- T087이 `/ko` · `/en` · `/ja` · `/` 응답에 `Set-Cookie`가 없음을 단언한다(T089 보정 2026-11-24 — 이전 문구 「쿠키는 `/api/auth/*`에서만 설정한다」).
- **이미지 로더**(`apps/web/src/lib/image-loader.ts` — FR-030 · T091 · T089 보정 2026-11-24): `https://cdn.joshuatech.dev/<path>` → `https://cdn.joshuatech.dev/cdn-cgi/image/width=<w>,quality=<q ?? 75>,format=auto,onerror=redirect/<path>`(Cloudflare 이미지 변환 — 변환이 실패하면 원본으로 리디렉션) · 루트 상대 경로는 그대로 · 그 밖의 호스트는 오류. `fallbackSrc(변환 URL)` = 원본 URL · 변환 URL이 아니면 `null`.

### VD-2 (검증 후 결정) — 존 Cache Rule이 Worker 응답을 edge에서 서빙하는가

- **기본 가정(문서 기본값)**: Workers는 캐시보다 **먼저** 실행되고 커스텀 도메인 Worker는 그 존의 오리진이 아니므로, 존 Cache Rule("Cache Everything, edge TTL 600")은 페이지 HTML에 효과가 없다 → **Cache Rule을 두지 않는다**.
- **옵션 A**: 실측에서 `cf-cache-status: HIT`가 나오고 대시보드의 Workers 요청 수가 늘지 않으면 Cache Rule을 유지한다.
- **옵션 B**: 효과가 없으면 삭제하고, 대신 **프리렌더 HTML을 `.open-next/assets`의 정적 자산(`/ko`·`/en`·`/ja`)으로 내보내는 방식**을 시험한다(자산 요청은 무제한). RSC 프리페치 부작용은 `e2e/hello.spec.ts`의 prefetch 가드로 판정한다.
- **실측(사용자 동석)**: 기본이 미생성이므로 T093 배포 직후 **임시 Cache Rule을 1회 apply**한 뒤 `curl -I https://joshuatech.dev/ko` 10회 → `cf-cache-status` 분포 + 대시보드 Workers 요청 수 비교 — HIT면 규칙 유지(옵션 A), 아니면 제거해 기본(미생성)으로 되돌린다(옵션 B). 자산화 시험도 같은 task에서.

### VD-3 (검증 후 결정) — Free Rate Limiting 표현식에 host 조건을 쓸 수 있는가

- **기본 가정(문서 기본값)**: Free 플랜의 Rate Limiting 규칙은 1개, 기간 10 s, 특성 IP, 표현식 필드는 Path·Verified Bot만 → 표현식은 **경로만** `/api/auth/*` + `/if/flow/*`, action `block`.
- **옵션 A**: 대시보드·API가 host 필드를 받으면 `joshuatech.dev/api/*`로 범위를 넓힌다.
- **옵션 B**: 받지 않으면 경로만 유지한다.
- **실측(사용자 동석)**: T011 apply 시 대시보드·API 오류로 확정.
- 어느 쪽이든 자동화 호출(T095·T087·T079)은 **호출 간격 ≥ 200 ms**를 지켜 스스로 규칙에 걸리지 않게 한다.

## 오류 형식

```json
{ "type": "https://joshuatech.dev/problems/session-revoked", "title": "Session revoked", "status": 401, "detail": "...", "instance": "/api/session", "request_id": "..." }
```

`type` 슬러그: `invalid_state`, `invalid_return_to`, `invalid_request`(logout 본문 꼴 — T089 보정 2026-11-24), `session_revoked`, `exchange_denied`, `upstream_unavailable`, `csrf_mismatch`, `not_found`. BFF problem 본문의 키는 정확히 `type` · `title` · `status` · `detail`(선택) · `instance` · `request_id`다 — `type` = `https://joshuatech.dev/problems/<slug>`(슬러그의 `_`를 `-`로 바꾼다) · `instance` = 요청 URL의 pathname(질의 0 — 프록시도 라우트 템플릿 `/api/proxy/[pod]/[...path]`가 아니라 그 요청의 경로다) · `detail`은 고정 문구(입력 · 상류 값 0) · `request_id` = 응답 헤더 `x-request-id`와 같은 값(T089 보정 2026-11-24). 예외: 프록시가 옮긴 pod 4xx 본문(슬러그 · 필드 — `request_id` 필드가 없다)은 pod 계약(contracts/identity-admin-api.md) 몫이고, `x-request-id` 헤더는 BFF 값이다(T070 r6 마감).

## 로그 · 마스킹

- wrangler.jsonc `observability: { enabled: true, head_sampling_rate: 1 }`(Workers Logs, Free 200k 이벤트/일).
- 로그는 `console.log(JSON.stringify(...))` 한 줄: `ts`, `level`, `request_id`, `route`, `status`, `upstream`, `upstream_ms`, `exchange_result`(캐시 적중 / 교환 성공 / 거부 / 오류), `trace_id`. 교환 실패율은 이 로그 기반 지표. 요청마다 정확히 한 줄이고 키는 정확히 이 9개다(T089 보정 2026-11-24): `level` = 상태 ≥ 500이면 `error` · 4xx면 `warn` · 그 밖 `info` · `route` = 라우트 템플릿 7개 가운데 하나 · `upstream` = 그 요청의 마지막 상류 호출 종류(`IDENTITY_M2M_URL` 호출 = `identity-admin` · Authentik 호출 = `authentik` · 상류 호출이 없으면 `null`) · `upstream_ms` = 그 호출의 정수 ms(상류 호출이 없으면 `null`) · `exchange_result` ∈ {`cache_hit`, `exchanged`, `denied`, `error`, `null`} — 교환 캐시를 쓰지도 교환을 시도하지도 않은 요청은 `null`이고, 교환이 성공했으면 그 뒤의 호출(pod · `/sessions/revoke` 등)이 실패해도 `exchanged`다. 원문 `sub`와 `x-end-session-url` 값은 싣지 않는다. gateway는 주입된 로그 함수 하나로만 그 줄을 내고, 그 밖의 `console.*` 호출은 0이다.
- **마스킹(금지 값)**: `Authorization`, `Cookie`(`__Host-jt_session` · `__Host-jt_csrf` · `__Host-jt_pkce` · 접두 없는 옛 이름 포함 — T089 보정 2026-11-24), `CF-Access-*`(`CF-Access-Client-Id`·`CF-Access-Client-Secret`·`Cf-Access-Jwt-Assertion`) 헤더 값과 `code`·`state` 쿼리 값은 로그·오류 `detail`·Sentry 이벤트 어디에도 남기지 않는다. 응답 쪽 자격도 같다 — 모든 응답의 `Set-Cookie` 값(BFF 자신의 세 쿠키와 상류의 것 모두) · `CF_Authorization` 값 · 상류 응답 헤더는 로그 · 오류 `detail` · Sentry 어디에도 싣지 않는다(T089 로그 단언에 더한다 · T070 r6 마감). URL을 남길 때는 쿼리스트링을 제거한다. `sub`는 해시로만.
- 클라이언트 Sentry(`@sentry/nextjs` 브라우저 측만): replay `maskAllText: true`, `tracesSampleRate 0.1`. 서버 SDK 없음.

## 번들 예산

서버 번들(`.open-next/worker.js` 계열) gzip ≤ 2.5 MiB. 허용 의존성: `jose`(JWT/JWE 프리미티브 — FR-027의 "인증 라이브러리" 금지에서 제외), 표준 Web Crypto, `ulid`. 금지: `@sentry/nextjs` 서버 측, `next-intl` 런타임, ORM, `better-auth`. `e2e/hello.spec.ts`는 로드 후 30초 내 `Next-Router-Prefetch: 1` 요청 ≤ 10을 가드한다(prefetch 폭주 → Free 한도 소진 방지).

- **`next.config` `serverExternalPackages: ['jose']`는 유지한다.** OpenNext의 workerd 가이드가 `jose`처럼 workerd 조건부 export를 가진 패키지를 여기에 넣도록 명시하고 있고, 이 설정은 Next의 서버 번들러만 건너뛰게 할 뿐 **OpenNext의 esbuild 단계가 `jose`를 Worker 번들에 그대로 포함**한다("Workers에는 node_modules가 없어 external은 실행 실패"는 이 조합에서 성립하지 않는다). 설정 옆에 이 근거를 주석으로 남겨 다시 제거되지 않게 한다.
