# Contract: Django pod 템플릿 (`templates/django-pod`, copier)

`copier copy --trust --defaults --data pod_name=<pod> templates/django-pod apps/<pod>`로 생성되는 pod의 계약(`--trust`는 `copier.yml`의 `_tasks: uv lock` 때문에 필수 — 2026-11-02 T065). 생성물은 수정 없이 테스트를 통과하고, `packages/django-common`에 의존한다. 거부 목록 키·ACL은 contracts/denylist.md, 네트워크 허용은 contracts/network-policy.md, Vault 경로는 data-model §8.

**생성 위치·버전 규칙(2026-11-02 T065 보정)**: pod 디렉터리는 저장소 루트 기준 `apps/<pod>`에 있고 `packages/django-common`은 두 단계 위의 형제다 — 템플릿은 이 상대 배치(`../../packages/django-common`) 하나만 가정하므로 다른 깊이(예: `tests/fixtures/generated/<pod>`)에 바로 생성하면 의존성이 풀리지 않는다(검사 하네스는 임시 미니 저장소 `<tmp>/apps/sample-pod` + `<tmp>/packages/django-common` 복사본으로 같은 배치를 재현한다 — 아래 §기본 테스트 6). 모노레포 안의 템플릿 경로는 git 저장소 루트가 아니므로 copier는 clone·태그 선택 없이 **작업 트리를 그대로** 읽고 `.copier-answers.yml`에 `_commit`을 남기지 않는다 → `copier update`는 SP-1에서 지원하지 않는다(재생성 뒤 diff로 갱신; 템플릿을 태그가 있는 독립 저장소로 내는 것은 후속 기능 — research DJANGO-D18의 "저장소 `pod-template`" 가정과의 편차, report.md 후보).

## 테이블 등급 (헌법 III · FR-034)

| 등급 | 모델 | RLS | 접근 |
|---|---|---|---|
| **A 테넌트 범위** | `TenantModel` 상속(`tenant_id` UUID NOT NULL, 인덱스 `(tenant_id, id)`) | `ENABLE` + `FORCE ROW LEVEL SECURITY` + 정책 `tenant_isolation`(`rls_policies(<table>)`) | 요청 트랜잭션의 `app.tenant_id` 컨텍스트로만. 컨텍스트 없으면 0행 |
| **B pod 전역** | `GlobalModel` 상속. 허용 목록: `tenant`, `tenant_membership`, `outbox`, `session_revocation_log` | 미적용 | app role이 컨텍스트 없이 읽고 쓴다: outbox 릴레이·Authentik 웹훅·기동 시 거부 목록 재적용·`/tenants/me` |

- owner role(prod `<pod_snake>_owner` / dev `dev_<pod_snake>_owner`)은 `bypassrls: true` — 마이그레이션·시드 전용, 런타임 pod에는 자격이 없다. app role(`<pod_snake>_app` / `dev_<pod_snake>_app`)은 `NOBYPASSRLS`.
- `check_rls`(CI·기동 검사 — 함수 `django_common.tenancy.check_rls(*, using=…, require_rls_role=False)` + 같은 이름의 management command `--database`(기본 `default`) · T068 보정 2026-11-04 · 시그니처 T068 r3): 시스템 스키마(`pg_catalog`·`information_schema`·`pg_toast*`·`pg_temp_*`)가 아닌 모든 스키마의 관계(`relkind` r·p·v·m·f — 모델이 아닌 테이블도 카탈로그에서 센다 · **superuser가 소유한 확장**의 멤버만 제외한다 — owner role이 만든 trusted 확장에 표를 넣어 빼돌리지 못하게 · T068 r2)를 아래로 판정하고, 하나라도 어긋나면 위반을 전부 테이블 이름과 함께 담아 실패한다. 스캔은 트랜잭션 하나 안에서 `search_path`를 `pg_catalog`로 고정하고 돌며 끝나면 롤백으로 되돌린다(바깥 atomic 안이면 savepoint — DB·세션 수준 `search_path`에 둔 사용자 연산자가 스캔 SQL과 deparse를 가리지 못하게 · T068 r3). ① 아래 프레임워크 면제 `FRAMEWORK_TABLES` → `django_migrations`가 있는 스키마의 표(`r`)일 때만 면제 — `django_migrations` 표가 있는 스키마가 정확히 하나가 아니면(0개·2개 이상) 위반 한 줄을 내고 면제·B 등급을 인정하지 않는다(전부 ③ · T068 r3) ② B 등급 허용 목록 `GLOBAL_TABLE_ALLOWLIST` → 같은 스키마의 표(r·p)이고 **RLS가 꺼져 있어야** 한다(켜면 릴레이·웹훅이 0행을 본다) — 다른 스키마의 같은 이름 관계는 ③으로 판정한다(T068 r2) ③ 그 밖의 모든 관계 = A 등급 → 표(r·p)여야 하고(뷰·matview·foreign table은 위반 — 뷰는 소유자 권한으로 기저 테이블을 읽어 RLS를 우회한다) `pg_class.relrowsecurity`·`relforcerowsecurity` 둘 다 켜져 있고, 정책 `tenant_isolation`이 `FOR ALL`·PERMISSIVE·대상 PUBLIC이며 `USING`과 `WITH CHECK`의 `pg_get_expr` 결과가 **둘 다 정본 식과 정확히 같아야** 한다(PG 18 정본 `(tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::uuid)` — 이름만 같은 `USING (true)`를 막는다 · 정본이 정의되지 않은 PG 주 버전이면 위반(fail-closed — 정본 추가는 이 계약 개정) · T068 r2). 정책 식은 표·열 밖의 객체에 의존하지 않아야 한다 — `pg_depend`에서 그 정책(`classid` = `pg_policy`)이 참조하는 것 가운데 `pg_class`(표·열)가 아닌 것이 하나라도 있으면 위반(사용자 정의 연산자·함수·타입·콜레이션·형변환 함수 — deparse에 찍히지 않는 객체(예: NULLIF 안의 연산자 — PG 18.6 실측)와 고정 전 세션에서 비한정으로 보이던 사용자 객체를 잡는다 · initdb 부트스트랩 객체(OID < 12000 — 정본 식이 쓰는 객체는 전부 여기)는 pinned라 행이 없고, initdb 후반 객체(OS 콜레이션·시스템 뷰·`information_schema`·plpgsql)와 사용자 객체는 행을 남긴다 · T068 r3 · 문구 r4). A 표의 정책은 `tenant_isolation` 하나뿐이어야 한다 — 다른 정책은 PERMISSIVE든 RESTRICTIVE든 위반(PERMISSIVE는 OR로 합쳐져 격리를 넓히고, RESTRICTIVE 식은 `tenant_isolation`보다 먼저 모든 행에 평가될 수 있어 형변환 오류·부작용으로 다른 테넌트 값이 샌다 · T068 r4). A 등급 관계가 낀 상속·파티션 링크(`pg_inherits`)는 양쪽이 모두 A 등급이어야 한다 — 부모를 거친 질의에는 부모의 RLS만, 자식을 직접 읽는 질의에는 자식의 RLS만 적용되므로, A 표의 부모가 A가 아니거나(B·프레임워크·스캔 밖 관계 · T068 r4) A 표의 자식이 A가 아니면(허용 목록·프레임워크 이름을 쓴 상속 자식·파티션 — 직접 읽으면 RLS 없이 읽히고, 파티션이면 부모로 쓴 A 행도 그 파티션에 저장된다 · T068 r5) 위반. B·프레임워크끼리의 링크는 양쪽 다 RLS가 없어 판정하지 않고, 스캔 밖 자식(다른 세션의 TEMP 상속 자식·superuser 소유 확장의 멤버)도 판정하지 않는다(T068 r5) ④ 같은 우회 원리의 다른 객체 — 비시스템 스키마의 `SECURITY DEFINER` 함수(소유자 권한으로 실행되어 RLS를 비켜 간다 · superuser 소유 확장의 멤버 함수는 관계와 같이 뺀다 · T068 r3)와 표의 재작성 규칙(`CREATE RULE` — 뷰의 `_RETURN`은 뷰 판정으로)은 위반(T068 r2) ⑤ 모델 검사 — `TenantModel` 하위의 `db_table`이 ①·②에 있거나 카탈로그에 A 등급 표로 없으면 위반 · `GlobalModel` 하위의 `db_table`이 ② 밖이면 위반 · ②의 이름을 쓰는 관리 모델은 `GlobalModel` 하위여야 하고 ①의 이름은 Django contrib 앱(`auth`·`contenttypes`·`sessions`·`admin`)만 쓴다(T068 r2). 권한에 기대는 판정(`has_table_privilege` 등)은 쓰지 않는다 — app role(기동)과 owner(CI·migrate Job) 어느 쪽에서도 같은 결과. 기동 검사는 `--require-rls-role`(함수 인자 `require_rls_role=True`)을 더한다 — 연결의 `session_user`가 superuser·`BYPASSRLS` role이거나 그런 role의 멤버면(`pg_has_role(session_user, …, 'MEMBER')` — `SET ROLE`이나 Django `OPTIONS["assume_role"]`로 `current_user`만 app role인 경우 포함 · T068 r3), 또는 스캔 범위 관계의 소유자(`relowner`)이거나 그 멤버면(소유자는 `NO FORCE`·`DROP POLICY`로 RLS를 끌 수 있다 — 마이그레이션이 app 자격으로 돈 오설정 · T068 r4) 위반 한 줄(런타임에 owner 자격이 들어간 사고를 막는다 · role 이름은 싣지 않는다 · CI의 owner 실행에는 붙이지 않는다 · T068 r2). **검사 범위의 경계**(T068 r4): `check_rls`는 RLS의 카탈로그 모양(관계 등급·정책 모양과 식·상속)과 소유자 권한으로 도는 객체(뷰·`SECURITY DEFINER`·재작성 규칙)와 런타임 role을 본다. 데이터 흐름(트리거·애플리케이션 코드가 A 행을 B 표로 옮기기 등)은 보지 않는다 — 마이그레이션·코드 리뷰가 맡는다. 성공 출력은 `check_rls: OK - A 등급 N · B 등급 M · 프레임워크 K`(ASCII 하이픈 — cp949 콘솔).

## 기본 테스트가 검증하는 것 (헌법 II)
