### Findings

**F1 (high) — K3s admin 자격증명 번들이 평문으로 Object Storage에 올라가고, 같은 IAM 키가 tfstate까지 관리한다**
- 어디: spec FR-047, tasks T010(`svc-s3-backup` manage objects on jt-backup·**jt-tfstate**), T036(`sqlite3 .backup + server/token + server/cred → jt-backup/k3s/`), T052(CNPG `s3Credentials` ExternalSecret `oci-s3-backup`), T005(`svc-tfstate`·`svc-s3-backup` 2 사용자).
- 무엇: `server/cred/`에는 cluster-admin 클라이언트 인증서·CA 키, `server/token`은 노드 조인 토큰이다. 이 번들이 암호화 없이 `jt-backup`에 가고, 그 버킷을 읽는 키가 `data` 네임스페이스의 CNPG 사이드카 Secret에도 주입되며, 동시에 `jt-tfstate`(Access 서비스 토큰 secret·터널 토큰 평문, plan A17)까지 읽는다. `data` 네임스페이스 Secret 1개 유출 → 클러스터 admin + Cloudflare 터널 + BFF 서비스 토큰으로 상승한다. T005의 사용자 2개 분리 의도와 T010의 정책이 모순된다.
- 수정: (a) T010 정책을 `svc-s3-backup`→`jt-backup`만, `svc-tfstate`→`jt-tfstate`만으로 분리하고 T006 단언에 "교차 버킷 정책 0"을 추가. (b) T036 타이머는 `age`(수신자 공개키만 노드에, 개인키는 운영자 오프라인)로 번들을 암호화한 뒤 업로드하고, 접두 `k3s/`는 CNPG가 쓰는 `pg-main/`과 별도 버킷(`jt-k3s-backup`) 또는 별도 IAM 사용자로 분리. (c) `jt-backup`도 T007처럼 `--public-access-type NoPublicAccess`를 명시하고 T006에서 단언. (d) 복원 런북(FR-047)에 복호화 절차를 넣는다.

**F2 (high) — 운영자 본인의 GitHub·Google 계정 자격증명을 서브에이전트가 실행하는 Playwright에 환경변수로 넘긴다**

(b) T076·T077에 `storageState` 경로를 `.gitignore`·실행 후 삭제·trace `mask` 옵션을 명시. (c) `tester-write-guard`와 별개로 에이전트 환경에 개인 계정 자격증명을 넣지 않는다는 규칙을 `.claude/rules/infra.md`(T108)에 적는다.

**F5 (medium) — PR 프리뷰 버전이 prod Worker의 시크릿을 상속하고, 같은 repo PR(Renovate)이 배포 권한 토큰을 가진 CI에서 실행된다**

**F6 (medium) — 레이트 리밋이 없고, A1 이후 Workers Free 한도 소진은 "BFF만"이 아니라 사이트 전체 장애다**

**F10 (medium) — pod→Postgres TLS 모드 미명시, Dragonfly는 평문으로 노드 A↔B를 건너고 노드 간 오버레이는 암호화되지 않는다**

**F11 (medium) — Dragonfly 공용 비밀번호로 모든 pod가 거부 목록을 쓰거나 지울 수 있다**
- 어디: spec D7·FR-024(모든 pod가 Dragonfly 1회 조회), Key Entities SessionRevocation(소유 identity-admin), tasks T056(`kv/{env}/dragonfly` 단일), T074(identity-admin에 같은 키), T069(`Denylist` redis-py).

- 수정: Dragonfly ACL(`ACL SETUSER`)을 ConfigMap으로 선언 — `identity-admin`(RW `revoked:*`, RW `celery:identity-admin:*`), 각 소비 pod는 `+get ~revoked:*`만; ExternalSecret도 `kv/{env}/dragonfly/<pod>`로 pod별. T050에 "다른 사용자로 `DEL revoked:x` → NOPERM" 단언.

**F12 (medium) — GitHub App이 gitops ruleset bypass 주체이므로 CI 코드 실행 = prod overlay 직접 push**

**F13 (low) — Sentry PII·헤더 스크러빙, Traefik 신뢰 IP, prod provider의 `localhost` redirect, Playwright 토큰 파일**

### Findings

**F-1 [High] FORCE RLS 아래에서 "테넌트 컨텍스트 없는" 읽기 경로가 정의되지 않아 설계끼리 충돌한다**
- 위치: spec §FR-034, §US6 AC2, §Key Entities(OutboxEvent·SessionRevocation); plan §Constitution Check III("전 테이블 tenant_id + FORCE RLS"); tasks T053, T059, T067, T068, T071, T072, T074
- 문제: T053은 owner role을 `bypassrls false`로 만들고 FR-034는 `FORCE ROW LEVEL SECURITY`를 건다. FORCE는 테이블 owner에게도 정책을 적용하므로 T059의 "owner role 전체" 기대는 명시적 owner 정책 없이는 성립하지 않는다. 더 큰 문제는 app 자격증명으로 도는 경로다: `relay_outbox`(T068; T071 "Deployment 2 컨테이너 web+relay", T074 env는 `…/app`)는 모든 테넌트의 outbox 행을 `SELECT … FOR UPDATE SKIP LOCKED`로 읽어야 하고, 기동 시 거부 목록 재적용(T072 `expires_at > now()`)과 Authentik 웹훅 처리(T072, 요청에 테넌트 토큰 없음)도 컨텍스트 없이 실행된다. US6 AC2·T059의 fail-closed(컨텍스트 없음 → 0행)가 그대로면 이 세 경로는 0행을 읽고 조용히 아무 일도 하지 않는다.
- 조치: (a) contracts/pod-template.md와 ADR 0007(T023)에 테이블 등급을 정의 — "테넌트 범위"(TenantModel, FORCE RLS + 정책) / "pod 전역"(`outbox`, `SessionRevocationLog`, `Tenant` 자체: RLS 미적용 또는 `USING (true)`), `check_rls`(T067)는 테넌트 범위 테이블이 FORCE RLS인지와 전역 테이블이 허용 목록에 있는지를 함께 검사; (b) owner에 대해 `CREATE POLICY … TO identity_admin_owner USING (true)`를 헬퍼가 자동 생성하거나 owner에만 `BYPASSRLS`를 부여하도록 T053·T067 중 하나를 고친다; (c) 릴레이·웹훅·기동 재적용이 어떤 role·컨텍스트로 실행되는지(예: 전역 테이블만 접근, 또는 `app.tenant_id` 대신 `app.system=on` 정책 분기) 문서화; (d) T059에 owner 정책 케이스, T060에 "테넌트 A·B 행이 모두 릴레이됨" 케이스를 추가.

**F-2 [Medium] spec Key Entities에 실제 저장 엔티티 2개가 빠져 있다**
- 위치: spec §Key Entities; plan §Constitution Check III("Key Entities 13개"); tasks T072(`Tenant`·`TenantMembership`·`SessionRevocationLog`, data-model §1–3)
- 문제: 헌법 III는 소유자·격리 키를 "spec의 Key Entities"에 요구한다. `TenantMembership`(사용자↔테넌트 조인, 격리의 핵심)과 `SessionRevocationLog`(폐기의 DB 정본)가 spec에 없고 data-model.md에만 있다. spec은 12항목, plan은 13개라 하여 수도 어긋난다. `SessionRevocation`(Dragonfly 캐시)과 `SessionRevocationLog`(DB)의 관계·어느 쪽이 정본인지도 spec에 없다.
- 조치: spec Key Entities에 `TenantMembership`(소유 identity-admin, 격리 키 `tenant_id`, Authentik `sub`는 참조만)과 `SessionRevocationLog`(소유 identity-admin, `sub` 단위 pod 전역, 보존 기간)를 추가하고, `SessionRevocation` 항목을 "Dragonfly는 파생 캐시, DB 로그가 정본(기동 시 재적용의 원천)"으로 고쳐 plan의 개수와 맞춘다.

**F-3 [Medium] Dragonfly가 pod 경계 없는 공유 키공간이며 거부 목록 키 계약이 코드에만 있다**
- 위치: spec §FR-020, §FR-024, §Key Entities(SessionRevocation); tasks T056, T061, T069, T074(`kv/{env}/dragonfly`)
- 문제: env당 인스턴스 1개에 비밀번호 1개를 모든 pod(현재 identity-admin, SP-2부터 4개)가 공유한다. 어떤 pod든 identity-admin이 소유한 `revoked:*`를 덮어쓰거나 다른 pod의 Celery 큐·캐시를 읽을 수 있어 "교차 서비스 읽기는 명시 계약" 원칙이 저장소 차원에서 깨진다. 키 이름도 불일치한다 — spec은 `revoked:{sub}`·`revoked:{sid}`, T061은 `revoked:sub:{sub}`·`revoked:sid`. 모든 pod가 읽는 이 키의 스키마(이름·값 의미 not-before·TTL)는 contracts/ 6종 어디에도 없고 `django_common.auth.Denylist`(T069)가 사실상 계약이다.
- 조치: Dragonfly ACL 사용자를 pod별로 두어(identity-admin: `revoked:*` RW + `identity-admin:*`; 그 외 pod: `revoked:*` read-only + `<pod>:*` RW) Vault 경로를 `kv/{env}/dragonfly/<pod>`로 나누거나, 최소한 pod별 키 접두 규약 + DB index 분리를 규칙(`rules/django-pod.md`, T108)으로 강제한다. `contracts/`에 denylist 키 스키마 문서를 추가하고 spec·T061·T069의 키 이름을 하나로 통일한다. T050에 "다른 pod 사용자로 `revoked:*` 쓰기 거부" 검사를 추가한다.

**F-4 [Medium] 테넌트 멤버십의 정본이 없고 세 곳에서 쓰인다; 사용자당 테넌트 1개가 암묵 전제다**
- 위치: spec §Key Entities(Tenant "Authentik 그룹 `tenant:<id>`·OpenFGA `tenant#member`와 매핑"), §FR-021(`tenantid`), §FR-022(ScopeMapping `tenant_id`), §FR-025; tasks T072(`TenantMembership`), T080(ScopeMapping ← `user.attributes`, 그룹 `tenant:joshuatech`), T082(그룹 수동 부여·FGA 튜플 스텁)
- 문제: 멤버십이 identity-admin `TenantMembership`, Authentik 그룹/`user.attributes.tenant_id`, OpenFGA 튜플에 각각 존재하고 T082는 셋을 서로 다른 경로(시드·수동·스텁)로 쓴다. 어느 것이 소유 데이터이고 어느 것이 참조·파생인지가 헌법 III가 요구하는 "서비스 경계마다 소유/참조 선언"에 없다. `user.attributes`는 단일값이라 한 사용자가 두 테넌트에 속하면 토큰 `tenant_id`·`identity-admin.session.revoked`의 `tenantid`·Kafka 파티션 키(OutboxEvent 격리 키)가 모호해진다. 식별자 형식도 UUID(`TenantModel`)와 slug(`tenant:joshuatech`, `seed_tenant joshuatech`)가 섞여 있다.
- 조치: ADR 0007(T023)·`architecture.md`(T028)에 "identity-admin `TenantMembership`가 정본, Authentik attribute·그룹·FGA 튜플은 identity-admin이 이벤트/API로 갱신하는 파생"을 명시하고 T082의 쓰기를 identity-admin 경유 하나로 모은다. claim·그룹명·FGA object id의 테넌트 식별자 형식을 하나로 정한다. Assumptions에 "SP-1은 사용자당 테넌트 1개, 다테넌트 선택·`tenantid` 다중값은 SP-2"를 적고, 사용자 단위 이벤트(session.revoked)의 `tenantid`는 optional 또는 멤버십 전체로 스키마(T066)에 정의한다.

**F-5 [Medium] CNPG PITR 롤백은 클러스터 전체 롤백이라 다른 pod의 소유 데이터를 되돌린다**
- 위치: plan §Observability & Rollback("DB = CNPG recovery(barman-cloud PITR)"); spec §FR-016(pg-main 1 클러스터에 10 DB), §SC-011; tasks T052, T057, T105
- 문제: `pg-main` 하나에 `identity_admin`·`authentik`·`openfga`(SP-2부터 pod DB 추가)가 공존하므로 PITR은 어떤 pod의 마이그레이션 사고를 되돌리려 해도 Authentik 사용자·OpenFGA 튜플·다른 pod 데이터까지 함께 되돌린다. "마이그레이션은 단일 서비스 소유"인데 롤백 수단은 전 서비스 공유다.

**F9 (high) — "recovery 키로 수동 unseal"은 auto-unseal 구성에서 불가능**
- 어디: spec §Edge Cases("Vault 자동 unseal 실패 … recovery 키(3/5)로 수동 unseal"), FR-049(recovery key 3/2), tasks T044(`-recovery-shares=3 -recovery-threshold=2`), FR-041(vault-unseal 런북)
- 무엇: ocikms seal에서 recovery key는 `generate-root`·rekey 용도이며 unseal에 쓸 수 없다. KMS 장애 시 Vault는 KMS가 돌아올 때까지 sealed이고, seal 마이그레이션도 기존 seal(KMS)이 살아 있어야 한다. 따라서 이 Edge Case의 완화책은 실행 불가하다. 키 수도 3/5(spec) vs 3/2(FR-049·T044)로 어긋난다.
- 수정: Edge Case와 `vault-unseal.md`를 다시 쓴다 — (a) KMS 장애: 대기, ESO는 마지막 Secret 유지, pod 재시작 금지, `vault_core_unsealed` 알림; (b) KMS 키 손실 = Vault 복구 불가이므로 키 `prevent_destroy`·자동 회전 off(A16)·삭제 대기 기간 최대(30일)를 T010에 명시; (c) recovery key 수를 3/2로 통일하고 용도(generate-root·rekey)를 명기.
