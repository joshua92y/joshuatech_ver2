**신규 (round-3, 2차 시정이 남긴 것)**

**R3-1 (medium) — OpenFGA 단일 인스턴스·단일 preshared 값이 dev↔prod 인가 경계를 비운다**
- 어디: spec FR-025("env 사본 `kv/{env}/openfga/preshared`"), contracts/gitops-repo §공유 컴포넌트("`preshared` 값은 `kv/platform/openfga/preshared`와 **같아야** 하며"), T082(같은 값·회전 동시), contracts/network-policy 매트릭스 `jt-dev·jt-prod → identity 8080`.
- 무엇: 2차 시정이 dev/prod DB role(R29)·Kafka user·Dragonfly 인스턴스는 갈랐지만, OpenFGA는 서버가 하나이고 preshared 인증은 **서버 전역**(store 단위 스코프 없음)이며 dev pod의 키 값이 prod와 동일하다. `jt-dev → identity 8080`이 열려 있으므로 손상된 dev pod가 `ListStores`로 prod store id를 얻어 prod 튜플을 읽고 쓸 수 있다 — round-2에 막은 "dev 자격 → prod 자원" 경로가 이 한 곳에서 남는다. SP-1은 튜플 쓰기가 `seed_tenant`뿐이라 폭발 반경이 작지만 SP-2 pod 4개부터 커진다.
- 수정: 값을 다르게 해도 preshared는 서버 전역이므로 해결이 아니다. (a) 최소: 이 사실을 ADR 0006(T022)과 `report.md` 수용 위험에 명시하고 T111 k8s-security 경계 항목에 "OpenFGA env 격리 없음"을 추가, (b) 구조: SP-2에서 `openfga-dev` 인스턴스 분리(또는 store 검증 프록시)를 결정 항목으로 등재.

**R3-2 (medium, N14 잔여) — T072·T075의 m2m Ingress 경로가 spec·계약·T066과 모순**
- 어디: T072("Ingress PLACEHOLDER(m2m 경로 허용 목록 `/api`·`/health`·**`/healthz`·`/ready`**·`/session`·`/sessions`·`/tenants`·**`/webhooks`**)"), T075(같은 8개) ↔ spec FR-036·US6 AC6, contracts/identity-admin-api §호스트("`/webhooks`·`/healthz`·`/ready`는 공개 호스트에 없다 → 404"), T066(404 단언).
- 무엇: R37이 spec·contracts·T066만 고치고 두 구현 task를 놓쳤다. T072·T075대로 구현하면 T066이 FAIL하거나, 웹훅이 공개 m2m 호스트에 노출되어 BFF 서비스 토큰 유출 시 방어가 HMAC 하나로 줄어든다(정확히 N14가 지적한 표면).
- 수정: T072·T075의 경로 목록을 `/api`·`/health`·`/session`·`/sessions`·`/tenants` 5개로 교체(webhook·프로브는 svc DNS·kubelet 전용 유지).

**R3-3 (medium, N2 잔여) — T077이 폐기된 e2e 시크릿 경로를 참조**
- 어디: T077("비밀번호·TOTP 시드는 Vault `kv/{env}/e2e`에서") ↔ FR-022·FR-044·Assumptions·contracts/gitops-repo·hostnames(`kv/platform/authentik/e2e` 단일 경로, `e2e-reader` 정책 = `kv/data/platform/authentik/e2e` read)·T081.

- 수정: T077 문구를 "Vault role `e2e-reader`로 `kv/platform/authentik/e2e`에서"로 교체.

**R3-4 (low, N13 잔여) — v1 SSH 개인키 파기 게이트의 task 번호 오참조**

### Findings

**F1 [High] T072·T075의 m2m Ingress 경로 목록이 2차 시정 전 값으로 남아 spec·계약·T066 단언과 정면 충돌한다 (`/webhooks`·`/healthz`·`/ready` 노출)**
- 위치: tasks T072("Ingress PLACEHOLDER(m2m 경로 허용 목록 `/api`·`/health`·`/healthz`·`/ready`·`/session`·`/sessions`·`/tenants`·`/webhooks`)")·T075("경로 `/api`·`/health`·`/healthz`·`/ready`·`/session`·`/sessions`·`/tenants`·`/webhooks`만") vs spec §FR-036("m2m Ingress 경로는 `/api`·`/health`·`/session`·`/sessions`·`/tenants`만"), contracts/identity-admin-api §호스트 표(공개 호스트에 셋 없음 → 404), contracts/hostnames-and-access §호스트 규약, tasks T066("m2m 호스트로 `/webhooks/authentik`·`/healthz`·`/ready` → 404" 단언); 결정표 R37("m2m Ingress 경로에서 `/webhooks`·`/healthz`·`/ready` 제거", tasks 열에 T072·T075 포함)
- 문제: R37이 T066에는 404 단언을 넣었지만 T072(템플릿 base)·T075(identity-admin overlay)의 경로 목록은 갱신하지 않았다. task 줄만 받는 서브에이전트가 T075대로 8경로 Ingress를 만들면 `/webhooks/authentik`이 Cloudflare 뒤 공개 호스트로 노출되고(HMAC만 남음 — 웹훅을 svc DNS 전용으로 좁힌 설계 의도 훼손), T066·T076 E2E는 404 단언에서 실패한다 — 구현 시점에 반드시 어긋나는 tasks ↔ spec 모순이다.
- 조치: T072·T075의 경로 목록을 `/api`·`/health`·`/session`·`/sessions`·`/tenants` 5개로 교체(두 task 다른 내용은 그대로).

**F2 [Medium] 공유 컴포넌트(`authentik`·`openfga`) DB의 role 표기·개수가 문서마다 다르고, 그 database의 CONNECT 경계 SQL은 실행 주체가 없다 — US3 AC1 대체 검증이 설계상 성립하지 않는다**
- 위치: spec §FR-016("공유 컴포넌트 … `authentik_{owner,app}`·`openfga_{owner,app}`" — app role 명시) vs tasks T054("공유 컴포넌트 role `authentik_owner`·`openfga_owner`"만, DatabaseRole 합계 6) vs data-model §7("SP-1의 DatabaseRole은 4개") vs tasks T050("`databaseroles` 4개 Ready")·spec §US3 Independent Test("role 4개"); CONNECT: spec §FR-016·§US3 AC1("각 database의 migrate Job 첫 단계가 멱등 SQL로 CONNECT를 제한 … 대체 검증: `identity_admin_app`으로 `authentik` DB 접속 거부")·T054·pod-template §마이그레이션
- 문제: (a) app role이 있는지(FR-016) 없는지(T054·data-model §8은 `owner` 경로만·Deployment는 owner로 접속)가 갈리고, DatabaseRole 개수도 4/6으로 갈려 T050 단언이 애매하다. (b) CONNECT 제한의 유일한 실행 주체가 "각 database의 migrate Job 첫 단계"인데 `authentik`·`openfga`는 helm 컴포넌트라 migrate Job이 없고, identity-admin의 migrate Job(`identity_admin_owner`)은 타 DB의 소유자가 아니라 `REVOKE CONNECT ON DATABASE authentik`을 실행할 권한이 없다. PUBLIC의 기본 CONNECT가 남으므로 `identity_admin_app` → `authentik` DB 접속은 거부되지 않는다 — US3 AC1·Independent Test·T050의 교차 DB 거부 단언이 그대로면 실패한다.
- 조치: FR-016의 `{owner,app}`를 `authentik_owner`·`openfga_owner`(owner만, 자기 스키마 자가 마이그레이션)로 정정하고 DatabaseRole 개수를 6(또는 "pod role 4 + 공유 owner 2")으로 통일(FR-016·data-model §7·T050·US3 IT); 공유 DB의 CONNECT SQL 실행 주체를 명시 — 권고: `platform/cnpg-databases/`에 PostSync SQL Job 1개(`kv/platform/db/{authentik,openfga}/owner` 자격, 멱등 `REVOKE CONNECT … FROM PUBLIC; GRANT CONNECT … TO <db>_owner`)를 추가하고 T054에 적는다(팩트체크 P4의 "또는 SQL Job" 경로).

**F3 [Medium] dev "읽기 전용" Authentik 서비스 계정 토큰은 메커니즘이 없고, dev revoke 쓰기 경로와 충돌한다 — VD 항목도 아니다**
- 위치: tasks T081("dev용 토큰은 읽기 전용")·T084(회전 매트릭스 "prod·dev 분리, dev는 읽기 전용"); data-model §9 User 행("dev용 서비스 계정 토큰은 읽기 전용"); identity-admin-api §`/sessions/revoke`(Authentik revoke 호출, Celery 5 s × 3회)·§주기 작업(`reconcile_authentik_sessions`)
- 문제: Authentik API 토큰은 계정(서비스 계정)의 권한을 그대로 가지며 토큰 단위로 권한을 좁힐 수 없다 — 단일 서비스 계정 `identity-admin`의 "읽기 전용 토큰"은 그대로는 만들 수 없고, 실현하려면 권한이 다른 **별도 dev 서비스 계정**이 필요하다(어느 문서에도 없음). 또 읽기 전용이 실현되면 dev identity-admin의 `/sessions/revoke`·웹훅 경로의 Authentik revoke 호출이 dev에서 **항상 403**이 되어 재시도 루프(5 s × 3회, 최대 5분)가 상시 발생하고, dev에서는 refresh 토큰이 revoke되지 않는다 — T085가 dev 체인에서 폐기 3경로를 측정할 때 이 차이를 어떻게 판정하는지 기준이 없다. 벤더 동작을 단정한 문장인데 VD 목록에도 없다.
- 조치: 내부 설계로 닫는 쪽 권고 — blueprint에 dev 전용 서비스 계정(예: `identity-admin-ro`, 사용자 read만)을 추가해 `kv/dev/authentik/identity-admin.api_token`의 주체로 명시(T081·data-model §9)하고, dev의 revoke·reconcile 쓰기 호출은 "시도하지 않고 로그만"(설정 플래그)으로 명시한 뒤 T085에 "dev 폐기 검증은 denylist 401까지(Authentik revoke 제외)"를 적는다. 토큰 권한 축소가 가능하다고 보면 그때는 VD 각주(실측 task = T081)로 처리한다.

**F4 [Low] FGA 모델 정본이 spec과 data-model에서 다르다 (2관계 vs 3관계)**

**F1 (medium) — T072·T075의 m2m Ingress 경로 허용 목록이 2차 시정 전 값(`/healthz`·`/ready`·`/webhooks` 포함)으로 남아 spec·계약·테스트와 모순된다**
- 위치: tasks T072("Ingress PLACEHOLDER(m2m 경로 허용 목록 `/api`·`/health`·`/healthz`·`/ready`·…·`/webhooks`)")·T075("경로 …`/webhooks`만") ↔ spec §FR-036("`/api`·`/health`·`/session`·`/sessions`·`/tenants`만"), contracts/hostnames §호스트 규약(`/webhooks`·`/healthz`·`/ready` → 404), T066(m2m 호스트 404 단언)
- 내용: 구현자가 T072·T075대로 만들면 HMAC만으로 보호되는 `/webhooks/authentik`이 공개 m2m 호스트(Cloudflare + BFF 서비스 토큰 보유자)에 다시 노출된다 — 라운드-2 N7이 닫은 바로 그 경로다. T066이 404를 단언하므로 빌드 중 테스트·매니페스트가 충돌하고, 어느 쪽이 정본인지 재논쟁이 생긴다.
- 수정: T072·T075의 목록을 FR-036과 동일한 5개(`/api`·`/health`·`/session`·`/sessions`·`/tenants`)로 교정(어드민 Ingress는 별도 유지).

**F2 (medium) — 공유 컴포넌트 DB(`authentik`·`openfga`)의 CONNECT 제한을 실행할 주체가 없고, FR-016의 role 표기가 T054와 어긋난다**
- 위치: spec §FR-016(CONNECT 제한 = "각 database의 migrate Job 첫 단계") ·US3 Independent Test/AC1("`identity_admin_app`으로 `authentik` DB 접속 → `permission denied`") ↔ tasks T054(migrate Job은 pod DB 전용 — authentik·openfga에는 migrate Job이 없음)·T080·T082(helm 배포, REVOKE 단계 없음); FR-016 "`authentik_{owner,app}`·`openfga_{owner,app}`" ↔ T054·FR-017·contracts/gitops-repo §공유 컴포넌트(owner만)
- 내용: 설계가 정의한 유일한 CONNECT 강제 수단은 pod 템플릿의 migrate Job인데 authentik·openfga DB에는 그 Job이 없다. PG 기본값은 PUBLIC에 CONNECT를 허용하므로 `identity_admin_app`이 `authentik` DB에 접속 가능하고, US3의 대체 검증(permission denied)은 실패한다. 또 FR-016은 공유 컴포넌트에 `_app` role까지 명시하지만 T054는 owner만 선언한다(사용처도 owner뿐) — spec ↔ tasks 드리프트.
- 수정: (1) authentik·openfga DB의 `REVOKE CONNECT … FROM PUBLIC; GRANT CONNECT … TO <db>_owner`를 실행할 주체를 지정 — DB owner role은 자기 DB에 REVOKE 권한이 있으므로 bootstrap 런북 §4의 멱등 단계 또는 `platform/policies/tests/`형 1회 Job(owner 자격, `vault-platform`)으로; (2) FR-016의 공유 컴포넌트 role 표기를 `authentik_owner`·`openfga_owner`로 교정(또는 `_app`을 실제로 선언·사용).

**F3 (medium) — dev 자격만 받는 `data-assert` Job으로는 prod role 방향의 교차 접속 거부 단언을 실행할 수 없다**
- 위치: tasks T050("`identity_admin_app` → `authentik` DB 거부", "`identity_admin_app` → `dev_identity_admin` DB 거부") ·spec §US3 Independent Test ↔ contracts/hostnames §자격이 필요한 검사("Job은 prod 자격을 절대 받지 않는다", dev scope ExternalSecret만)
- 내용: PG에서 CONNECT 거부를 관찰하려면 그 role로 인증해야 하는데(비밀번호 오류는 auth 실패이지 permission denied가 아니다), `identity_admin_app`의 비밀번호는 `kv/prod/db/identity_admin/app` — dev scope Job이 받을 수 없다. R30(자격 검사 Job 이관)과 R29(교차 env 단언)가 결합하며 생긴 라운드-3 모순이다.
- 수정: prod role 방향 단언은 로그인 없이 카탈로그로 검증 — dev 세션에서 `SELECT has_database_privilege('identity_admin_app','dev_identity_admin','CONNECT')` = false(·`'authentik'` 동일)를 단언하고, 실제 접속 시도 단언은 dev 자격 방향(`dev_identity_admin_app` → `identity_admin`·`authentik`)으로 한정. T050·US3 Independent Test 문구를 이에 맞게 교정.

**F4 (medium) — "platform AppProject destination에 `jt-dev`를 이 Application 한정으로 추가"는 Argo CD에서 구현할 수 없고, 실제로는 프로젝트 전체의 폭발 반경이 넓어진다**
- 위치: contracts/hostnames §자격이 필요한 검사(마지막 문단, T041 지시) ↔ contracts/gitops-repo §Application 규약(AppProject `platform` destinations = 플랫폼 ns; dev/prod에만 `namespaceResourceBlacklist`)
- 내용: AppProject `destinations`는 프로젝트 단위 속성이라 특정 Application에만 한정할 수 없다. 계약대로 적용하면 `platform` 프로젝트의 **모든** Application이 `jt-dev`에 리소스를 만들 수 있게 되고, `platform` 프로젝트에는 `namespaceResourceBlacklist`가 없어 앱 네임스페이스에 Role/RoleBinding/NetworkPolicy까지 쓸 수 있다 — dev/prod 프로젝트에 걸어둔 정책 객체 금지가 우회된다.
- 수정: `platform/policies/tests/` Application을 `dev` AppProject 소속으로 옮기거나(Job·ExternalSecret은 blacklist 대상 아님), 전용 AppProject(`tests`: source = gitops, destination `jt-dev`만, cluster 리소스 금지)를 만들고 "Application 한정" 문구를 삭제.

**F5 (medium) — T044(Vault helm)에 securityContext 4항목 values가 없다 (라운드-2 N6 잔여)**
- 위치: tasks T044 ↔ spec §FR-045·contracts/network-policy §네임스페이스 표(마지막 불릿: Vault·Authentik·OpenFGA·Reloader values 4항목 명시)·§검증(T044 대조 대상)
- 내용: `vault` ns는 PSA `restricted`인데 Vault 차트 0.34.x 기본값은 `allowPrivilegeEscalation`·`capabilities.drop`·`seccompProfile`을 컨테이너에 지정하지 않아 첫 sync가 admission에서 거부될 수 있다. T080·T082·T046은 시정됐고 T044만 누락 — 실패 시 가장 쉬운 우회(라벨 하향)를 계약이 리뷰 대상으로 잡아두긴 했으나, task가 값을 지정하지 않으면 그 압력이 실제로 발생한다.
- 수정: T044에 server 컨테이너 securityContext 4항목(`runAsNonRoot`·`allowPrivilegeEscalation: false`·`capabilities.drop [ALL]`·`seccompProfile RuntimeDefault`; `disable_mlock=true`라 IPC_LOCK 불필요 주석) values를 명시.

**F6 (low) — tester가 `k8s` Access 앱을 비대화형으로 지나는 서비스 토큰의 생성·보관 task가 없다**

**F7 (low) — 13번째 알림 규칙 이름·`absent()` 목록이 spec ↔ plan/tasks에서 갈린다 (경계 인접: 감시 침묵 방지 규칙 자체의 드리프트)**

**F8 (low) — `identity` ns의 메일 발송 egress가 매트릭스에 없다(443만)**

**F10 (low) — Workers 전용 Vault 경로를 pod ExternalSecret에서 금지하는 validate lint가 없다**
