## 잔여 finding 1건

### G4-R1-02 잔여 — P2 / medium: 삭제 후 API·SSH 완전 단절에서는 R3 파일 안내가 나오지 않는다

- 현재 위치: `specs/003-platform-foundation/design/t045-blocks/g4/g4-drill.ps1:300`, `:301`. 관련 회귀: `harness-g4.ps1:998`의 D-16.
- 재현 조건: 최초 게이트와 삭제 직전 값·UID 확인까지 정상 → 파드 삭제 요청 1회 → 이후 남은 터널 경로까지 상실해 kubectl 조회가 계속 실패하고 SSH도 사용할 수 없는 상태. 삭제 후 대기 루프가 만료될 때 `$recover`는 빈 문자열이고 `$changes.Count`는 1이다.
- 추가된 “g4-adopt.ps1을 **실행하지 않고 파일의 R3 노드 셸 절차를 읽는다**”는 안내는 `$recover='value'` 분기 안에만 있다. 이 사후 단절은 그 분기를 지나지 않는다. 대신 :301은 여전히 “g4-adopt.ps1으로 값·UID를 판정하고 그 복구 안내(R1/R2/R3)를 따른다”고 지시한다. API가 끊긴 상태에서는 adopt를 실행해 판정하거나 값 오류 분기의 R3 출력을 얻을 수 없다.
- 삭제 재실행 금지와 남은 파드 미접촉은 유지되므로 추가 자동 삭제 결함은 아니다. 실제 비상 상황에서 실행할 수 없는 블록을 경유하도록 안내하여 복구 인계가 끊기는 기존 G4-R1-02의 잔여다.
- **추출 finally 로컬 모의:** 원본 본체 전체를 실행하지 않고 AST의 finally 문만 추출했다. Set-Clipboard는 빈 로컬 함수로 대체했고 가짜 hash/UID 및 변경 로그만 넣었다. 결과:

| 입력 분기 | value 인계 | UID 인계 | 실행하지 않고 R3 파일 읽기 | adopt로 판정하라는 안내 |
|---|---:|---:|---:|---:|
| recover=value, 변경 0 | 있음 | 없음 | 있음 | 없음 |
| recover=uid, 변경 0 | 없음 | 있음 | 없음 | 없음 |
| recover='', 변경 1, 사후 완전 단절 | 없음 | 없음 | **없음** | **있음** |

- 수정 방향: 변경 후 공통 안내에서 API 접근 가능 시 read-only adopt 판정과, kubectl·SSH가 막힌 경우 파일의 R3를 읽는 경로를 함께 명시한다. R3 정적 안내를 value 분기에만 묶지 않는다. 실제 단절 여부를 추가 운영 호출로 알아낼 필요는 없다. D-16에 “실행하지 않고 파일의 R3” 안내가 포함되고 추가 삭제가 없다는 단언을 넣는다.

## 변경 부위의 추가 확인

삭제 후 while문만 AST에서 추출하고 시간·파드 조회를 로컬 모의했다. 기존 대상이 끝까지 남는 3파드 상태는 가상 **300초** 후에도 `newName=''`이었다. 30초 시점에 대상이 사라져 생존자+새 Ready 파드 2개가 되면 가상 **30초**에 `newName='new-pod'`로 완료했다. 원본 운영 블록·kubectl·ssh·oci를 실행하지 않았다.

삭제 직전의 별도 생존자/대상 이름 검사가 제거됐지만, 앞선 정확히 2개 검사와 전체 정렬 서명 동일성 및 모든 Ready 조건이 남아 있다. 서명에는 이름·재시작 수·시작시각이 들어가므로 제거된 개별 검사의 의미는 이 비교에 포함된다. 이 변경으로 별도의 삭제 허용 경로가 열린 증거는 없다.

restore :220의 최종 출력이 정규 재인수 PASS→g4-drill과 ES 없는 R3 수동 경로를 구분한다. 앞선 “값 검증 미완이면 파드를 건드리지 않는다”와 5분 뒤 SKIP 재확인 안내도 유지됐다. 이 출력 변경에서 추가 문제는 찾지 못했다.

새 R3 bash 회귀는 실제 adopt 실행 대신 출력 전용 문자열 9줄을 AST로 뽑고, 기존 고정 계약과 일치할 때만 실행한다. `sudo`는 로컬 payload/hash 응답 함수이고 kubectl·ssh·oci는 거부 함수로 가려 readonly로 고정된다. 프로필·rc를 읽지 않고 HISTFILE은 `/dev/null`, 표본은 반복 문자 가짜 토큰이며 임시 스크립트는 finally에서 지운다. 타임아웃과 프로세스 종료도 있다. 이 코드 검토에서 새 운영 호출 경로는 발견하지 않았다. Git Bash가 없으면 명시적 SKIP이므로 모든 환경의 대화형 검증을 보장하지는 않지만, 확인한 구현자 로그에는 세 사례의 PASS가 있다.
