# Rules for Django pods (`apps/<pod>/`, `packages/django-common/`, `templates/django-pod/`)

Scope: Django pod file shapes (`*.py`, `pyproject.toml`, `Dockerfile`) under `apps/*`, plus `packages/django-common/` and `templates/django-pod/`. `apps/web` is a JS tree and matches none of these globs, so this rule never loads there (`web.md` governs it). Contract of record: `specs/003-platform-foundation/contracts/pod-template.md` (+ `contracts/events.md` for outbox). On conflict, the contracts prevail; amend them first.

## Template and structure

- Pods are generated with `copier copy --trust --defaults --data pod_name=<pod> templates/django-pod apps/<pod>` (`--trust` is required by the template's `_tasks: uv lock`); the generated pod must pass its tests unmodified and depends on `packages/django-common` (never copy common code into a pod).
- A generated pod is a standalone uv project — its own `uv.lock` (written by copier `_tasks: uv lock`), never a member of the root workspace (root `pyproject.toml` excludes `apps/*` and `templates/*`). It depends on `django-common` through a `tool.uv.sources` **path** source `../../packages/django-common` (editable), so the only supported layout is `<root>/apps/<pod>` next to `<root>/packages/django-common`; never generate a pod into another depth (such as `tests/fixtures/generated/<pod>`) — the source would not resolve.
- Images build from the repository-root context: `docker buildx build --platform linux/arm64 -f apps/<pod>/Dockerfile .` (the Dockerfile copies `packages/django-common` as well, keeping the `../../packages/django-common` layout inside the image); `publish-pod.yml` uses `context: .` + `file: apps/<pod>/Dockerfile`.
- The in-monorepo template path is not a git repository root, so copier reads the working tree and records no `_commit`; `copier update` is unsupported in SP-1 — regenerate and diff instead.
- Template harness (`templates/django-pod/tests/`, its own `pyproject.toml`/`uv.lock`, not a workspace member): it generates a sample pod into a temporary mini-repository (`<tmp>/apps/sample-pod` + a copy of `packages/django-common`), then runs `uv sync --locked`, the generated suite, the arm64 build, `kustomize build` + `kubeconform`, and the render assertions of `contracts/pod-template.md` §기본 테스트 6. Run it with `uv run --directory templates/django-pod --locked pytest -q` (Docker, `kustomize`, `kubeconform` on PATH); `JT_SAMPLE_POD_ROOT=<dir>` keeps the generated tree (a relative path is resolved against the repository root, because `uv run --directory` changes the cwd; the repository root, its parents, and anything under the template directory are refused), and the harness deletes only a directory it created itself (marker file `.jt-sample-pod-root`).
- Template changes must keep the generated output green; run the generated pod's suite (the harness above) before committing a template change.

## Table grades (TenantModel / GlobalModel)

- Grade A (tenant-scoped): inherit `TenantModel` — `id` UUID v4 PK, `tenant_id` UUID NOT NULL (a value reference, never a FK), index `(tenant_id, id)` named `<lowercased class name>_tenant_id_idx`, `ENABLE` + `FORCE ROW LEVEL SECURITY` + `tenant_isolation` policy via the `rls_policies(<table>)` migration helper. Rows are reachable only through the request transaction's `app.tenant_id` context; no context → 0 rows. Keep grade-A class names at 16 characters or fewer (or declare the same index under a shorter name — `models.E034`); a child that adds indexes writes `indexes = [*TenantModel.Meta.indexes, …]` (a new `Meta.indexes` replaces the parent's); grade-A many-to-many uses an explicit `through` model inheriting `TenantModel` (an auto-created join table has no RLS and fails `check_rls`). Managers and `save()` never filter or fill `tenant_id` — RLS alone filters rows.
- Grade B (pod-global): inherit `GlobalModel`. Allowlist only: `tenant`, `tenant_membership`, `outbox`, `session_revocation_log`. Adding a B-grade table requires amending `contracts/pod-template.md` and this rule FIRST.
- `check_rls` (CI + startup; the function `django_common.tenancy.check_rls(*, using=…, require_rls_role=False)` and the management command of the same name with `--database`) must pass. It scans every relation (`relkind` r, p, v, m, f) in every non-system schema, excluding only members of superuser-owned extensions (an owner-created trusted extension cannot hide a table), inside one transaction with `search_path` pinned to `pg_catalog` and rolled back afterwards (a savepoint inside an outer atomic block), so user operators on a database- or session-level `search_path` cannot subvert the scan SQL or the deparse: `FRAMEWORK_TABLES` are exempt only as tables in the schema that holds `django_migrations` (unless exactly one schema holds it, one violation is reported and no exemption or grade B applies — everything is graded A); `GLOBAL_TABLE_ALLOWLIST` (grade B) must be tables in that schema with RLS OFF — a same-named relation elsewhere is graded A; everything else is grade A and must be a table (a view, materialized view or foreign table fails — a view reads its base tables with the owner's rights and bypasses RLS) with both `relrowsecurity` and `relforcerowsecurity`, a `tenant_isolation` policy that is `FOR ALL`, PERMISSIVE, `TO PUBLIC`, whose `USING` and `WITH CHECK` both deparse (`pg_get_expr`) exactly to the canonical expression (PG 18: `(tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::uuid)`; a PG major without a canonical form fails closed until this rule and the contract add one) and that depends on nothing but its table and columns (any `pg_depend` reference of the policy outside `pg_class` — a user-defined operator, function, type, collation or cast function, including objects the deparse does not print such as the operator inside NULLIF — fails; initdb bootstrap objects (OID < 12000, which covers everything the canonical expression uses) are pinned and leave no rows, while late-initdb objects such as OS collations, system views, `information_schema` and plpgsql leave rows like user objects). `tenant_isolation` must be the only policy on a grade-A table: any other policy fails, PERMISSIVE or RESTRICTIVE (permissive policies are OR-ed and widen isolation; a restrictive expression can run on every row before `tenant_isolation` and leak another tenant's values through cast errors or side effects). Both sides of an inheritance or partition link (`pg_inherits`) that involves a grade-A relation must be grade A: a query through the parent applies only the parent's RLS and a direct query on a child only the child's, so a grade-A table whose parent is grade B, framework or outside the scan fails, and so does a non-grade-A child of a grade-A table (a child named after an allowlisted or framework table is read without RLS when queried directly, and as a partition it would also store the parent's grade-A rows). Links between grade-B and framework tables carry no RLS on either side and are not judged; children outside the scan (another session's temporary child, a member of a superuser-owned extension) are not judged either. `SECURITY DEFINER` functions outside system schemas (members of superuser-owned extensions excepted, as for relations) and rewrite rules on tables (other than a view's `_RETURN`) fail too — they run with the owner's rights just like a view. Model checks: a `TenantModel` whose table is allowlisted or framework, or that has no grade-A table in the catalog, fails; a `GlobalModel` whose table is not allowlisted fails; a managed model using an allowlisted name must be a `GlobalModel`, and framework names belong to Django's contrib apps (`auth`, `contenttypes`, `sessions`, `admin`) only. It never relies on privilege checks, so the app role (startup) and the owner (CI, migrate Job) get the same answer; at startup add `--require-rls-role` (`require_rls_role=True`), which fails when the connection's `session_user` is a superuser or `BYPASSRLS` role or a member of one (`pg_has_role(session_user, …, 'MEMBER')` — this also catches `SET ROLE` and Django's `OPTIONS["assume_role"]`, where only `current_user` is the app role), or owns a relation in the scan or is a member of its owner (an owner can run `NO FORCE` or `DROP POLICY` — migrations that ran with app credentials) — this catches owner credentials leaked into the runtime. Scope boundary: `check_rls` checks the catalog shape of RLS (relation grades, policy shape and expression, inheritance), objects that run with owner rights (views, `SECURITY DEFINER`, rewrite rules) and the runtime role; it does not police data flows (triggers or application code copying grade-A rows into grade-B tables) — migration and code review own those. The success line is `check_rls: OK - A 등급 N · B 등급 M · 프레임워크 K` (ASCII hyphen, cp949-safe). Framework tables are the exact-name list of Django framework tables (`django_migrations`, `django_content_type`, `django_session`, `django_admin_log`, `auth_permission`, `auth_group`, `auth_group_permissions`, `auth_user`, `auth_user_groups`, `auth_user_user_permissions`) fixed as a constant in `django_common.tenancy`. Pods cannot widen it and no prefix rule applies; a contrib table outside the list requires amending `contracts/pod-template.md` and this rule FIRST.
- Roles: owner role has `bypassrls` and is used by migrations/seed only — NEVER at runtime; app role is `NOBYPASSRLS`. DB and role names are env-separated (`dev_` prefix in dev); never share a role across envs.

## Outbox and events

- Publish only via `django_common.outbox.publish(topic, subject, data, *, tenant_id=None)`, inside `transaction.atomic()`. No tenant context AND no `tenant_id` argument → `OutboxUsageError`; contextless paths (webhooks, admin revoke, startup jobs) MUST pass `tenant_id` explicitly. `tenant_id` must parse as a UUID (never a slug) and must not contradict the request's tenant context — both raise `OutboxUsageError`.
- Relay runs as the app role, selects `dead_at IS NULL` only (`FOR UPDATE SKIP LOCKED`); `attempts >= 10` → publish envelope to the env DLQ (prod `<pod>.dlq` · dev `dev.<pod>.dlq` — the relay prefixes the env; `contracts/events.md` §토픽 규약 is the source of truth) and set `dead_at`; dead rows purge at `dead_at + 30 d` (Celery beat, the template's only default beat job; pods without Celery run the `outbox_purge` CronJob).
- `publish` validates before inserting (`OutboxUsageError`, no values in the message): the logical topic matches the envelope `type` pattern and starts with `OUTBOX_SOURCE` (own pod, never an env-prefixed or foreign topic; prefix + topic ≤ 249 chars), `subject` matches its pattern, `data` is a dict that round-trips through jsonb unchanged (only dict with str keys, list, str, int/bool, float and None; depth ≤ 64; no NUL in keys or strings; floats finite and not in exponent notation, because PostgreSQL numeric writes exponents out in full; `data` itself is depth 1 and each nested dict or list adds 1; values that fail serialization — unpaired surrogates, ints beyond Python's 4300-digit string limit — are JSON errors too), the relay's bytes — the PostgreSQL jsonb text form, `json.dumps(…, ensure_ascii=False, separators=(", ", ": "))` — stay ≤ 900,000 (a byte lower bound kept during the same walk rejects as size as soon as it passes the limit, before shared references expand), and the tenant parses as a UUID (normalized to lowercase); a malformed context GUC is an `OutboxUsageError` too. The gate is `publish()`; never write the model directly. It never touches Kafka. Build envelopes as plain dicts (`specversion` "1.0", monotonic ULID `id`, UTC `Z` `time`) — no CloudEvents SDK.
- The relay is `manage.py outbox_relay` (no arguments; defaults are the contract values) over the library call `relay_once(*, producer=None, batch_size=100, batch_bytes=8 MiB) -> RelayResult(published, failed, dead)`, which must run outside any atomic block. One pass = one `atomic(durable=True)` that starts with `SET LOCAL idle_in_transaction_session_timeout = '120s'`, locks `id` plus `octet_length(payload::text)` for up to `batch_size` rows whose text is at most 900,000 bytes (the publish limit, same measure — a larger row can only be hand-inserted; it is never locked, read, sent or updated and stays pending for `OutboxOldestPending` and manual deletion, because its DLQ copy would fail too and a dead row is purged without an alert), keeps the leading rows within `batch_bytes` (at least one), and produces each to its main topic (value = the stored envelope as PostgreSQL jsonb text, never decoded or regenerated in Python; headers `ce_type` = row topic, `ce_source` = `OUTBOX_SOURCE`, `ce_id`, `content-type`), flush (35 s; purge leftovers as failures), then in the same pass send rows whose `attempts + 1 ≥ OUTBOX_MAX_ATTEMPTS` to the DLQ (+ `error` header). Success deletes with a direct SQL `DELETE` (no Django collector, no `pre_delete`/`post_delete` signals, no read before the delete); failure does `attempts += 1` and `last_error` (first 1000 chars of `str(err)` only); a DLQ success sets `dead_at`, a DLQ failure keeps the row and the next pass retries the main topic first. Backoff belongs to the command loop and grows only on errors and passes without progress: the wait is `max(previous, poll interval, 0.5 s) × 2` up to 300 s, so the first error waits 1 s even when `--poll-interval` is 0 (a test-only value). The relay shares the web pod, so it never exits on an error inside its loop (a crash-looping container takes the pod's Ready condition, and the web endpoints, with it): it opens 9464 first, then logs and backs off on producer-construction, configuration, database and unexpected errors — event names, exception classes and value-free diagnostics only (the `KafkaError` name, also through a `SystemError` whose `__cause__` (else `__context__`) is a `KafkaException`; the SQLSTATE; or the innermost frame's file, line and function — never messages, arguments or locals); a fatal producer error (`KafkaError.fatal()` or code `_FATAL`) comes from a produce exception, from `flush`/`poll` — confluent-kafka raises it as a `KafkaException` instead of calling `error_cb`, wrapped in a `SystemError` when a delivery callback follows in the same call — or from a delivery report; the pass is committed (successes deleted, failures recorded, the DLQ stage skipped after a fatal main stage), then `relay_once` raises `ProducerFatalError` and the command discards and rebuilds the producer. The command calls `poll(0)` before every pass, so a fatal error raised while idle also rebuilds the producer before any row is touched; after a fatal error, the first pass that returns a result keeps the current wait when it is empty (the new producer's fatal error arrives asynchronously after it connects, so an empty pass proves nothing; iterations that end in an error before that pass leave the mark set), so a persistent cause such as a missing ACL rebuilds at a growing interval even while idle — about 1.5, 3, 6 … s, then about every 600 s (the kept wait plus one backoff) at the 300 s cap, assuming the fatal error lands within the first kept second (T075 measures it); after the fix an event can wait up to about twice the maximum backoff (≈ 600 s) unless the pod is restarted, and while the wait is long the age of rows added to an empty outbox reaches the metrics only at the next refresh; `error_cb` logs only the names of non-fatal error events (confluent drops them without a user callback), and librdkafka's own FAIL/SSL/FATAL lines go to stderr regardless. Only SIGTERM/SIGINT end the loop normally. It exits only before the loop starts (settings import, system checks, argument errors, metrics initialization) or when 9464 cannot be opened.
- Settings (read at call time): `OUTBOX_SOURCE`, `OUTBOX_TOPIC_PREFIX` (`""` or `"dev."`), `OUTBOX_MAX_ATTEMPTS`, `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_CLIENT_CONFIG` (confluent keys), validated by `django_common.kafka.client_config()`: `security.protocol` is required and only `SASL_SSL` or an explicit `PLAINTEXT` is accepted; `SASL_SSL` needs `sasl.mechanism` `SCRAM-SHA-512`, `sasl.username`, `sasl.password` and `ssl.ca.location`; `bootstrap.servers` and its alias `metadata.broker.list`, `transactional.id`, `delivery.report.only.error`, `partitioner`, `enable.gapless.guarantee` and `default.topic.config` are forbidden, compared after stripping a `topic.` prefix (librdkafka reads `topic.<property>` as that topic property); a NUL in any key or string value is refused (confluent passes C strings, so a truncated name or value would slip past the checks); under `SASL_SSL` the TLS keys are allow-listed — `ssl.endpoint.identification.algorithm` absent or `https`, `enable.ssl.certificate.verification` absent or `True`, `1`, `"true"`, `"t"` or `"1"` (case-insensitive) — and anything else is refused; the library owns `enable.idempotence` (true) and `delivery.timeout.ms` (30000) — including the alias `message.timeout.ms` and `topic.`-prefixed spellings — and overriding them makes producer construction fail (logged and retried). Errors name keys only; never log or repr the config dict.
- Import `django_common.outbox.metrics` only in relay processes (a web process registering zero-valued outbox metrics would mask `MetricsAbsent`); no `PROMETHEUS_MULTIPROC_DIR` in the relay env (pointing at a missing directory makes metric initialization fail before the loop starts — mind shared `envFrom`). Dead purge is `purge_dead()` (DB clock, direct `DELETE`), wrapped by the template's Celery task, or `manage.py outbox_purge` from a CronJob in pods without Celery; reprocess dead rows with `manage.py outbox_requeue` (resets `dead_at`, `attempts`, `last_error`).

## Auth

- Request auth chain: Bearer JWT (JWKS via svc DNS; verify `iss` public URL, `aud`, `exp`, `nbf`) + `Cf-Access-Jwt-Assertion` (`aud` in {M2M, ADMIN} AND `common_name == ACCESS_EXPECTED_CN` — the service token's Client ID `<32 hex>.access`, not its name) + denylist (`revoked:sub:{sub}`, `revoked:sid:{sid}`). Denylist lookup failure = 503 `denylist-unavailable`, fail-closed (0.2 s timeout). The denylist client passes `retry=Retry(NoBackoff(), 0)` and a 0.2 s connect timeout explicitly, whatever the construction path (redis-py's `Redis(...)` constructor defaults to 10 exponential retries, `from_url` to 0 — rely on neither), so the verdict lands within the 0.2 s timeout; retries belong to the caller. Bearer verification requires `exp`, `iat`, `sub`, `aud`, `iss` (`options={"require": [...]}` — PyJWT otherwise accepts a token without `exp`), RS256 only, leeway 5 s; `sub` must be a non-empty string, `sid` (if present) a non-empty string, and `tenant_id` (if present) the lowercase canonical UUID string — anything else is 401 `invalid_token`. Signing keys (Authentik JWKS, Access certs) come from a `PyJWKClient(lifespan=3600, timeout=2)` per middleware instance and URL; a key fetch failure (connection, malformed key set, non-JSON) is a dependency outage, 503 `auth_keys_unavailable` (an expired cache is never reused), while an unknown `kid` is a token defect (403/401). `DRAGONFLY_URL` must carry no query string (redis-py lets the query override the timeout and retry arguments) and a non-integer denylist value is a lookup failure (503); exception messages carry the key (`sub`), so neither responses nor logs repeat them. Non-exempt paths call `request.get_host()` before any credential check. No Ninja auth callable: the middleware judges every non-exempt path before URL resolution (T070).
- `AUTH_ACTOR_SUB` set → additionally verify `act.sub`; unset (empty) = impersonation mode, no `act` check. Empty string is a VALID value for `AUTH_ACTOR_SUB` and dev `ADMIN_HOST` — required-setting checks assert presence, not non-emptiness.
- Exempt (exact path match, never a prefix): the three health endpoints plus the explicitly listed webhook paths. Webhook paths use HMAC instead: `X-Authentik-Signature: sha256=<hex>` = HMAC-SHA256(shared secret, canonical JSON of the body — `json.dumps(obj, sort_keys=True, separators=(",", ":"), ensure_ascii=True)`), body `pk` + `created` (ISO 8601 with tz) within ±5 min, `pk` as the idempotency key; every failure is 401 `webhook_signature_invalid` (`contracts/identity-admin-api.md` §웹훅 서명 규약).
- Access-only paths (`AUTH_ACCESS_ONLY_PATHS`, exact match, library default empty; identity-admin sets `("/session/check",)`): only the `Cf-Access-Jwt-Assertion` step runs — no Bearer verification, no actor check, no middleware denylist lookup; the request carries `access_claims` only (no `auth_claims`, no `tenant_id`). Paths that carry no Bearer (webhooks, access-only paths) must also be in `TENANT_CONTEXT_EXEMPT_PATHS`.
- `TenantContextMiddleware` (sync only, right after `JwtAuthMiddleware`): a path in `TENANT_CONTEXT_EXEMPT_PATHS` (library default `("/healthz", "/ready", "/health")`; a tuple, list, set or frozenset of str, else `ImproperlyConfigured`; read per request; exact match on `request.path_info`) passes through untouched — no transaction, no query. Otherwise `request.tenant_id` must be a `uuid.UUID` or the response is 403 `tenant_required`; the middleware opens `transaction.atomic(durable=True)` (the request transaction is outermost — never use a durable atomic in request code), runs `SELECT set_config('app.tenant_id', %s, true)` with `str(uuid)` (a UUID object binds as a `::uuid` literal and the call fails), and calls the view. A view exception marks the transaction for rollback in `process_exception` (Django turns view exceptions into responses inside the middleware chain, which would otherwise commit); a 4xx/5xx response returned without an exception commits, as with `ATOMIC_REQUESTS`. Ninja turns exceptions into responses inside the view, which skips this rollback: never install a catch-all `Exception` handler in Ninja (Django's handler500 produces 500 `internal_error`); if one is unavoidable, call `transaction.set_rollback(True)` in it; raise `HttpError`/`ValidationError` before writing. Wrap cross-tenant work in `tenant_context(tenant_id | None)` (switches inside a savepoint and restores the previous context on exit; only inside an outer atomic block — outside one it raises `TransactionManagementError`; an exception or `set_rollback(True)` inside the block is undone by the savepoint rollback). Never set `OPTIONS["assume_role"]` in runtime database settings: the `session_user` stays the credential's role, so startup `--require-rls-role` fails it whenever that role could bypass RLS (an owner credential, for example). A `StreamingHttpResponse` (FileResponse included) builds its body after the transaction, without context — no DB access there; the middleware emits a `RuntimeWarning`. Do not wait on slow external calls inside the request transaction (the app role's `idle_in_transaction_session_timeout` is 30 s). Use `set_tenant_context(tenant_id | None)` (inside an atomic block only) and `current_tenant_id()` (NULL and `''` both mean none) instead of raw GUC SQL.
- Admin urlconf mounts only when `request.get_host() == ADMIN_HOST` (exact equality — never substring or containment, so an empty value matches no host); dev `ADMIN_HOST` is empty → no admin at all.
- The admin path prefix (env `FORCE_SCRIPT_NAME=/<pod>` → setting `ADMIN_SCRIPT_NAME`, optional, default empty) applies only to `ADMIN_HOST` requests — `reverse()`, redirect `Location`, `request.path` — and is restored when the request ends; apply it inside Django's request handling (middleware), not in the WSGI entry point. Never set Django's global `FORCE_SCRIPT_NAME`: it would prefix m2m `reverse()` results and OpenAPI path keys. The admin Ingress strips the prefix (Traefik `stripPrefix`), so the pod receives `/admin/…`. Static assets cannot follow a per-request prefix (Django caches a relative `STATIC_URL` together with the script prefix of its first access), so when `ADMIN_SCRIPT_NAME` is set the settings make `STATIC_URL` the absolute path `<ADMIN_SCRIPT_NAME>/static/` (only admin pages need static assets); how the pod serves the stripped `/static/…` path is the template's decision (T072), and its baseline tests prove it (`/static/…` on the admin host → 200). Behind Traefik the pod receives plain HTTP, so Django's CSRF Origin check expects `http://<host>`: when `ADMIN_HOST` is set, put `https://<ADMIN_HOST>` in `CSRF_TRUSTED_ORIGINS`, or every admin POST fails the check.
- Hosts outside `ALLOWED_HOSTS` get 400 before authentication on business paths (a credential-less request is 400, not 403). Kubelet HTTP probes send the pod IP as `Host` by default — the template must make probes pass (probe `httpHeaders` Host or the downward-API `POD_IP` added to `ALLOWED_HOSTS`).

## Settings

- pydantic-settings → Django settings; missing required values raise `ImproperlyConfigured` at startup. Secrets come from env (ESO `<pod>-env`) only; non-secret values (`ACCESS_AUD_*`, `ACCESS_EXPECTED_CN`, `AUTH_ACTOR_SUB`, `ADMIN_HOST`, `ALLOWED_HOSTS`, `IDENTITY_M2M_URL`, and `FORCE_SCRIPT_NAME` for `has_admin` pods) from ConfigMap. Mail via `MAILERS` only (no `EMAIL_*`).
- `DATABASE_OWNER_URL` exists only in the migrate Job's env (`<pod>-migrate`); it never appears in runtime env.
- In-cluster service URLs the pod calls (`AUTHENTIK_JWKS_URL`; identity-admin also `AUTHENTIK_API_URL`, `OPENFGA_API_URL`) must not point at the public domain `joshuatech.dev` or its subdomains — startup raises `ImproperlyConfigured` (pods never call public hosts, FR-046). Read settings at call time (`django.conf.settings`), never as import-time constants.
- A startup failure names the offending settings only, never their values: raise `ImproperlyConfigured(...) from None`, because pydantic's `ValidationError` repeats the collected env (secrets included) in `input_value` — `str(exc)` shortens a long representation to its head and tail, which still prints a fragment of the last value — and a chained traceback would print it to the pod log. Also set `hide_input_in_errors=True` on the pydantic-settings model so a stray `str(exc)` carries no values (`errors()` still does, so the names-only rule stands).
- Secret settings (HMAC secrets, API tokens, preshared keys — each pod contract lists its own; identity-admin: `AUTHENTIK_API_TOKEN`, `AUTHENTIK_WEBHOOK_SECRET`, `OPENFGA_PRESHARED_KEY`) must be non-empty — an empty value raises `ImproperlyConfigured` (an empty HMAC key or bearer token is forgeable). The presence-only rule in §Auth covers non-secret values such as `AUTH_ACTOR_SUB` and `ADMIN_HOST`.

## Errors

- Every error response is RFC 9457 `application/problem+json` (`type` = `https://joshuatech.dev/problems/<slug with _ → ->`, `title`, `status`, optional `detail` that never carries tokens, secrets, or credentialed URLs) — build it with `django_common.problem.problem_response(slug, status, *, title=None, detail=None)`. Request validation failures (missing query, wrong type, enum miss, non-JSON body) are 400 `validation_error` — never Ninja's default 422 `{detail}`.
- Django's own error responses are problem+json too: the template urlconf sets `handler400` (disallowed host → 400 `invalid_host`; any other `SuspiciousOperation` or `BadRequest` → 400 `validation_error`), `handler403` (`PermissionDenied` → 403 `forbidden`), `handler404` (no matching URL → 404 `not_found`), and `handler500` (→ 500 `internal_error`, no `detail`) — never Django's default HTML pages. Set the handlers in every urlconf the pod routes to (the admin urlconf included): Django resolves error handlers from the request's urlconf. A CSRF failure is 403 `forbidden` problem+json too: Django routes it to `CSRF_FAILURE_VIEW`, not `handler403`, so the template sets that view (the admin login form).

## Tests (mandatory, constitution II)

- Every pod ships and keeps green the six baseline test areas: health trio (`/healthz`, `/ready` DB-only, `/health` always-200), tenant RLS (A: cross-tenant 0 rows, no-context 0 rows, owner all; B: app role reads all), outbox (usage errors, relay, DLQ, purge), auth middleware (token/Access/denylist/actor matrix, plus host rejection, Django's own 400/403/404/500 problem+json responses in every urlconf (CSRF failure included), startup-settings hygiene, and admin static assets for `has_admin` pods — `contracts/pod-template.md` §기본 테스트 3), logging (fields present, `authorization`/`cookie`/`x-authentik-signature` absent), migrations + OpenAPI snapshot. NEVER delete or skip them.
- DeprecationWarning is promoted to an error only for your own modules — `filterwarnings = ["error::DeprecationWarning:<own module>", …]` in `pyproject.toml`; never a global `-W error` (a dependency's warning must not kill the suite).
- pytest runs with `--tb=short` (`addopts` in `pyproject.toml`): long tracebacks print call arguments with their current values, and psycopg's `Connection.connect` rebinds `conninfo` with the password, so a failed DB connection would print credentials. Use `--tb=long` only locally and never share that output.

## Migrations

- Only the Argo PreSync migrate Job (owner role) runs migrations; the app never migrates. The Job's first step is the idempotent CONNECT-boundary SQL (`REVOKE CONNECT ... FROM PUBLIC; GRANT CONNECT ...`) before `manage.py migrate`.
- Two-phase rule: column drops, adding NOT NULL, and type changes MUST be split expand → contract across two releases.
- RLS policy changes go in their own dedicated migration — never mixed with schema or data changes.
- CI gate: `makemigrations --check` + `django-migration-linter` must pass (linter flags destructive operations).

## Dragonfly

- All self-owned keys use the `<pod>:` prefix — Celery `broker_transport_options.global_keyprefix` and cache `KEY_PREFIX`. Dragonfly user = pod name; denylist keys are read-only via ACL `%R~revoked:*`. `socket_timeout` 0.2 s.

## OpenAPI snapshot refresh

- The snapshot changes only deliberately: after an intentional API change or a django-ninja minor bump, run the suite, review the snapshot diff route-by-route, and commit the updated snapshot in the same commit as the change that caused it. Never regenerate blindly to make the build green.

## Logging

- structlog JSON to stdout with `ts level logger event request_id tenant_id sub_hash trace_id span_id`. The processor strips `authorization`, `cookie`, `x-authentik-signature`, and query strings from logged URLs. Masking recurses into every `collections.abc.Mapping` (Django `request.headers` included), not only `dict`. An upstream `X-Request-ID` is trusted only when it matches `^[A-Za-z0-9._:-]{1,128}$`; otherwise a uuid4 is generated (`DJANGO_STRUCTLOG_TRUST_UPSTREAM_REQUEST_ID = True` in pod settings — the library default drops upstream ids).
- Spans add only `tenant_id` and `sub_hash`, strip query strings from URL attributes, and never capture request headers. Health: `/healthz` touches no dependency, `/ready` is `SELECT 1` only (no django-health-check table — it would break the RLS allowlist), and `/health` runs its dependency checks in parallel so the whole response stays under 3 s (the BFF fetch timeout) even when every dependency is down.
