# Rules for `packages/events/`

Contract of record: `specs/003-platform-foundation/contracts/events.md`. On conflict, the contract prevails; amend it first.

## Envelope (CloudEvents 1.0, JSON, structured mode)

- Every event is a CloudEvents 1.0 JSON envelope with `specversion`, `id`, `source`, `type`, `time`, `subject`, `tenantid`, `datacontenttype: application/json`, `data`.
- `id` = the outbox row id (ULID). Consumers store `(consumer_group, id)` for idempotent processing.
- Kafka headers: `ce_type`, `ce_source`, `ce_id`, `content-type: application/cloudevents+json` (structured mode — the envelope is the message value).
- `tenantid` is a CloudEvents extension attribute (lowercase alphanumeric name). Its value is ALWAYS the tenant UUID — never a slug. User-scoped events carry the user's tenant. An envelope without `tenantid` must never reach Kafka (`OutboxUsageError` upstream guards this).

## Topic conventions

- Names: prod `<pod>.<entity>.<event>`, dev `dev.<pod>.<entity>.<event>`. Pod names are kebab-case; entity and event are singular lowercase. DLQ is prod `<pod>.dlq` · dev `dev.<pod>.dlq` (the relay prefixes the env; `contracts/events.md` §토픽 규약 is the source of truth).
- 3 partitions; partition key = `tenantid` (UUID string), so a tenant's events land in one partition and keep their written order there. The relay publishes in ULID order on a best-effort basis (a failed row is retried after later rows; two relays overlap during a rolling update), so consumers dedupe by `(consumer_group, id)` and tolerate reordering. Retention 7 days — a consumer that falls further behind recovers by re-indexing/re-projecting from the owning pod's DB, never by extending retention.
- Write access: only the owning pod publishes to its `<pod>.` topic prefix. NEVER publish on another pod's behalf.

## Schemas

- Every published topic has a schema under `packages/events/schemas/`; adding a topic without its schema is incomplete work.
- Consumers validate `data` against the `packages/events` schema; validation failure goes to the DLQ, not to a lenient parse.
- A `pattern` must mean the same in ajv (`u` flag) and Python `re.search` (jsonschema): explicit character classes only (no `\d`, `\w`, `\s`), no `.` (Python's `.` also matches CR and U+2028/2029), and the end anchor is `$(?!\n)` (Python's `$` also matches before a trailing newline). Patterns are frozen once on `main`.

## Compatibility rules (CI-enforced)

- Allowed changes: adding an OPTIONAL field; adding an enum value (consumers MUST ignore unknown enum values). Topic `data` schemas and `_envelope.json` therefore never set `additionalProperties: false` — consumers ignore unknown properties; a closed schema would send every event from a newer producer to the consumer's DLQ and would block CloudEvents extension attributes on the envelope.
- Forbidden: removing or renaming a field, changing a field's type (any change to the `type` set, including `string` → `["string", "null"]`), adding OR removing a `required` entry (a field that becomes optional breaks consumers that relied on it), removing an enum value, deleting a schema file. Metadata-only changes (`title`, `description`, `examples`, `x-version`, `$comment`) are not violations.
- A breaking change means a NEW topic (`...v2`) with a dual-publish period on both topics; never mutate the existing schema incompatibly.
- CI runs `packages/events/scripts/check-compat.mjs` (`--base <dir> --head <dir>`; exit 0 clean, 1 violations, 2 usage/IO error), comparing PR schemas field-by-field — nested objects and array `items` included, `_envelope.json` too — against `main`, reporting every violation with file, JSON-pointer path and kind. A violation fails the build. Never weaken or bypass this check to land a schema change.
- CI baseline and checker: a PR compares against the merge commit's first parent (after confirming the second parent is the PR head); a push compares against `before` (all zeros = empty baseline). The gate runs the **baseline commit's** `check-compat.mjs` and falls back to the change's own copy only when the baseline has neither the checker nor any schema (bootstrap), so a PR cannot weaken the checker to land its own schema change; the checker's CLI path therefore imports only Node built-ins (ajv loads lazily inside `validateEvent`). Logic of record: `scripts/ci/events-compat.sh`.
- The gate job `events-compat` runs Node setup, checkout and the gate script, in that order — the gate script is the only step after checkout; PR code (dependency install, vitest and the PR checker it imports) runs in the separate job `events-test`. Never put PR code before the gate on the same runner — it can rewrite the gate script, git objects, attributes or the next step's environment (`GITHUB_PATH`, `GITHUB_ENV`). (Bootstrap is the one exception: the change's checker runs inside the gate step, with an empty baseline to protect.) Node setup precedes checkout because `setup-node` runs `node`/`npm`/`yarn --version` in the workspace after installing, and Yarn 1 first executes any `yarnPath` from `.yarnrc`/`.yarnrc.yml` in that directory or its parents — after checkout, a PR touching no gate file could run code before the gate. The gate's Node version is therefore the literal `node-version` in ci.yml (not `node-version-file`), kept equal to `.node-version` by `schemas.test.mjs` sch-23 in `events-test` (CI) and the harness (local) — if they drift and the checker starts using an API only the newer Node has, the merged checker fails on the gate's older Node and deadlocks the gate. These are line-based drift checks — they catch a value that drifted by mistake, a moved pin or an extra setup-node step; a deliberately obfuscated ci.yml (YAML continuation lines, escapes, aliases, a fake job block) is out of their scope and is left to code-owner review of gate files, because a PR that edits ci.yml can rewrite the gate outright anyway. This protection assumes GitHub-hosted runners (a fresh VM per job, so the workspace is empty before checkout); a self-hosted runner that reuses workspaces voids it. The gate job restores no cache: its `setup-node` has no `cache` input and sets `package-manager-cache: false`, because setup-node otherwise auto-enables an npm cache from the checkout's `package.json` at a path the checkout's `.npmrc` picks, letting an earlier run of the same PR plant files before the gate (kept as defence in depth now that setup-node runs before checkout).
- The gate reads the baseline with `git ls-tree` + `git cat-file blob` (never `git archive`: one merged `export-ignore` line would empty every later baseline). A path component that is not a tree (symlink, file, gitlink) or a failing git command is exit 2, never "absent"; a `.json` entry must be a regular blob named `^[A-Za-z0-9_][A-Za-z0-9._-]*\.json$`. Bootstrap only when the baseline has neither the checker nor any schema — schemas without a checker is exit 2.
- In CI the change side is read the same way from the HEAD commit (= `GITHUB_SHA`), and the checked-out schema files must be byte-identical to those blobs (`git hash-object --no-filters`, same `.json` set) — the checkout applies the PR's `.gitattributes` (`working-tree-encoding`, `ident`, `eol`), so working-tree bytes can differ from what merges. Local runs read the working tree. The change side must also have the shape the next baseline needs, or the gate exits 2 before merge (once merged, every later PR, including the revert, would exit 2): the same path, mode and name rules; the checker path checked like the baseline's whatever the schema count (a path component that is not a directory, or a checker that is not a regular file — symlink, gitlink — is exit 2); and a checker present whenever any schema exists.
- The checker's normal exits (0, 1) print exactly one stderr summary line `check-compat: checked N · added M · violations K`; the gate exits 2 unless there is exactly one such line, K is a decimal of at most 9 digits without a leading zero, K agrees with the exit code, and stdout holds exactly K violation lines. Keep that line's format unchanged (the baseline checker's output is read by the changed script).
- Limit of this trust model: a PR that edits `.github/workflows/ci.yml` or `scripts/ci/events-compat.sh` runs its edited copy (including the bytes its `.gitattributes` makes the checkout write) — review blocks such changes. The gate job reads no other PR content (its Node version is the literal in ci.yml); schemas and checkers come from commit objects. Once merged, a change to a gate file (`ci.yml`, `events-compat.sh`, `check-compat.mjs`) becomes the gate for every later PR — the baseline-checker rule only stops weakening within the same PR — so review must block weakening. A merged checker that is stricter or broken likewise becomes the baseline checker, exits 2 (or reports false violations) on the baseline schemas and blocks every later PR, the revert included. Recover first with a PR that also edits the gate script (that PR runs its own copy — code-owner review, then a PR restoring the script); an operator merge past the required check also skips every other required check in the ruleset, so it is the last resort. Before merge, `events-test` catches it: an out-of-package checker copy compares the real schemas with themselves and with an empty baseline (`schemas.test.mjs` sch-14 — the same condition the gate runs the merged checker under), the summary-line test (sch-21), the CLI path's Node-built-ins-only rule (sch-9) and the gate-Node pin (sch-23). The out-of-package copies run with `NODE_PATH` and `NODE_OPTIONS` removed, and sch-24 first proves ajv does not resolve from the copy's location under that env — pnpm's vitest shim puts `.pnpm/node_modules` (where ajv is hoisted) on `NODE_PATH`, so an inherited environment would let the copy find ajv and miss the gate's no-node_modules condition. All of this holds only while `events-test` actually runs those tests: a change to the test-execution path — the test files, the `test` script in `packages/events/package.json`, a vitest config, the root `pnpm-workspace.yaml`, `package.json`, `pnpm-lock.yaml`, `.npmrc` (pnpm `node-options` and the like) or `.pnpmfile.cjs`, or any other pnpm/vitest setting or hook file `events-test` reads (an earlier PR included; `events-test` runs PR code, so this list is not closed) — can switch the defence off. The `events-test` command is `pnpm --filter @jt/events --fail-if-no-match test`, because a filter that matches nothing otherwise exits 0. CODEOWNERS for `packages/events/`, `scripts/ci/`, `.github/workflows/`, `.gitattributes` at any depth, the root `pnpm-workspace.yaml`, `package.json`, `pnpm-lock.yaml`, `.npmrc` and `.pnpmfile.cjs` (paths that do not exist yet can be listed), and `.github/CODEOWNERS` itself, required code-owner review, and `events-compat` plus `events-test` as required checks on the main ruleset (the deadlock defence relies on `events-test`) are operator decisions.
- Schemas use only the keys the checker compares or carries — structural `type`, `properties`, `required`, `items`, `enum`, `const`, `additionalProperties` (a schema only — `false` anywhere makes the checker exit 2); value constraints `format`, `pattern`, `minLength`, `maxLength`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minItems`, `maxItems`, `uniqueItems`; metadata, where an `x-*` schema key must match `^x-[a-z0-9]+(-[a-z0-9]+)*$` (ajv cannot register other names, so `validateEvent` would throw) — and any other keyword (`$ref`, `allOf`, `prefixItems`, …) makes the checker exit 2. A changed `const`, or a new `enum`/`const` on a previously unrestricted property, counts as `enum-removed`; value constraints are not machine-checked and must not change (a new `…v2` topic instead). Every property states its `type`.
- Adding an enum value ships consumer-first: consumers built with the new schema deploy before the producer emits the value, because an old schema's `enum` rejects it into the DLQ ("ignore unknown enum values" applies to business handling after validation).

## Consumer rules

- Consumer group names: `<pod>-<purpose>` (e.g. `notification-note-published`).
- Commit offsets only AFTER the processing transaction commits.
- 3 processing failures → move the original envelope (+ `error` header) to the DLQ; DLQ reprocessing is a manual command only.
- SP-1 alerting covers outbox pending/oldest-age and broker under-replication only; consumer-group lag metrics arrive in SP-2 — do not add ad-hoc lag alerting here.
